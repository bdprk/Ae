# 失败记录 2026-11-13（M2.2/M2.5/M2.10 阶段，接当日早前记录）

## 7. MIR/CFG 多次部分编辑导致文件混乱

- 时间：2026-11-13 02:00 (Asia/Shanghai)
- 任务：cfg.rs 的 list_ended 标志改造。
- 现象/报错：三个标志位编辑脚本部分断言失败，文件里留下两份注释与矛盾的分支（`terminated` 与 `list_ended` 混用），行为回到旧 bug。
- 已尝试：逐个修补；每次修复又引入新的不一致。
- 原因判断：连续多次「锚点替换 + 部分失败」让文件进入无法推理的中间态；锚点又因破折号（—/--）与换行差异反复错配。
- 教训/下一步：当一个文件连续两次修补失败后，直接整文件重写而不是继续打补丁；Write 工具「File has been modified」失败时用 rm + Write 重来，不要先读再赌缓存状态。

## 8. 结构体声明期嵌套实例化占用了宿主的槽位

- 时间：2026-11-13 02:20 (Asia/Shanghai)
- 任务：ADR-0194 嵌套实例化。
- 现象/报错：`struct Ledger { entries: Pair[i64, f64] }` 之后任何 `l.entries` 都报 "struct 'Pair[i64, f64]' has no field 'entries'"；`structs[0]` 的名字是 Pair 而不是 Ledger。
- 已尝试：先怀疑 field_type 的 token 消耗、再怀疑 struct_literal 的 sid 来源。
- 原因判断：非泛型结构体在解析时先 `let id = self.structs.len()` 并登记 struct_names，**然后**才解析字段；嵌套实例化在解析字段时调 instantiate_struct，把 Pair 的布局推进了 `id` 指向的槽位——Ledger 被挤到下一个 id。修复：先解析全部字段，再保留 id。
- 教训/下一步：任何「先预留 id 再做可能注册新类型的解析」的模式都是别名陷阱；解析与注册的顺序必须在写代码时显式注释约束。

## 9. move walk 把借用当移动，137 文件一次性报 80 个 disagreement

- 时间：2026-11-13 02:40 (Asia/Shanghai)
- 任务：M2.5 L1 CFG move walk。
- 现象/报错：全 suite 137 文件里 80 个报 "parser's move rules and the CFG disagree (v0)"。
- 已尝试：逐个看诊断；加 debug 打印确认状态流。
- 原因判断：For 容器、Match 主语被 `moved.insert`——它们是借用不是移动；Frees 也被当成移动。全部改为 contains 检查（借用）、直接忽略（Frees 不可达读取）。
- 教训/下一步：独立验证器的第一次大扫描就是分类错误的最佳探测器——这正是它存在的意义；先跑全 suite 再修，比逐个构造用例快得多。

## 10. 差分 fuzzer 的除零保护本身除零

- 时间：2026-11-13 03:15 (Asia/Shanghai)
- 任务：M2.10 差分模糊。
- 现象/报错：seed 36 生成的程序在 debug 与 release 一样的位置 `division by zero`——但两边一致地崩，不是 mismatch，而是生成器违反了自己「程序必可运行」的前提。
- 已尝试：检查种子 36 的表达式。
- 原因判断：除法保护 `(b / (b + 1) + 1)` 在 b == -1 时 b+1 == 0。换成 `((b * b) + 1)`：平方加一恒正。
- 教训/下一步：生成器的「不变量」要用可证明的代数性质（平方非负），不要用可能碰巧为零的构造；fuzzer 报告的每个 failure 先分类是 harness bug 还是 compiler bug。

## 11. Windows 上 `build -o` 不加 .exe 后缀

- 时间：2026-11-13 03:10 (Asia/Shanghai)
- 任务：diff_fuzz 运行编译产物。
- 现象/报错：`FileNotFoundError: [WinError 2]`——二进制生成在 `prog_d`（无后缀），fuzzer 找 `prog_d.exe`。
- 已尝试：先怀疑 build 子命令行为。
- 原因判断：`-o` 明确给出路径时 Windows 也不补后缀；且旧种子的无后缀文件会让 rename 冲突。修复：构建后 rename 加 .exe，rename 前 unlink 旧文件。
- 教训/下一步：跨平台的产物命名在 harness 里自己处理，不要依赖 CLI 的默认行为；rename 前清理旧产物。
