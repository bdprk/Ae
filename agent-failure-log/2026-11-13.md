## 1. is_borrowed 助手被自己的正则改写成无限递归

- 时间：2026-11-13 00:20 (Asia/Shanghai)
- 任务：ADR-0184 结构体借用——把所有借用检查点换成 `is_borrowed` 助手。
- 现象/报错：`cargo test` 大面积 `thread '<unknown>' has overflowed its stack`；最小复现 `fn main() { var hit = false; hit = true; }` 也溢出。
- 已尝试：gdb 附加（卡死被终止）；逐级缩小到"赋值语句即溢出"；逐行看 diff。
- 原因判断：Python 批量替换脚本把刚插入的助手函数自身也改写了——`self.borrows.iter().any(|&(bid, _)| bid == id)` 被替换成 `self.is_borrowed(id)`，助手第一行变成自调用，无限递归。
- 教训/下一步：批量替换脚本必须在插入新代码**之后**的文本上运行前检查插入点；对刚插入的代码做模式替换时先把助手定义为不含待替换模式的临时写法，或替换前排除新函数体。自测时先跑一个最小赋值程序再跑全量。

## 2. 函数体二次解析不认识 `&self` 的 `&`

- 时间：2026-11-13 00:45 (Asia/Shanghai)
- 任务：ADR-0184 允许 `&self` 接收者。
- 现象/报错：`expected identifier` 指向 `&`；即便在 `function_rest` 的参数循环里跳过 `&`，仍是同一错误（当时用的是旧二进制）。
- 已尝试：先改第一遍签名收集；再改 `function_rest`；改完忘记重建就测试，浪费一轮。
- 原因判断：编译器是两遍解析（签名收集 + 函数体解析），第二遍 `function_rest` 重新读参数列表，不认识第一遍新接受的 `&`；另外 Windows 上 `cargo build` 后必须确认二进制时间戳再跑 CLI。
- 教训/下一步：改两遍解析器时，凡是"第一遍新接受的语法"都要立刻检查第二遍的对应读取点；每轮修改后固定执行 rebuild + 时间戳确认。

## 3. 探针捕获绑定用了新生 id，与外层 id 对不上

- 时间：2026-11-13 03:30 (Asia/Shanghai)
- 任务：ADR-0188 闭包捕获推断。
- 现象/报错：闭包体引用外层变量报 `unknown variable 'name'`，捕获列表恒为空。
- 已尝试：检查 outer 快照、分类逻辑、两遍探针顺序。
- 原因判断：探针把外层名字绑定到子解析器的新生 var id（`sub.next_var += 1`），而 AST 遍历收集的正是这些新 id，分类却拿它们与外层真实 id 求交集——两个 id 空间永不相交。改为探针阶段沿用原 id、`next_var` 从 max(outer)+1 起，用"探针参数槽位 ↔ 捕获名"按序对应。
- 教训/下一步：跨解析器共享变量时，id 空间必须显式约定（沿用原 id 或建立映射表）；捕获推断这类"先探测再正式解析"的结构，用槽位顺序对应比 id 交集合 robust。

## 4. `||` 被词法器吃成逻辑或

- 时间：2026-11-13 04:10 (Asia/Shanghai)
- 任务：闭包空参数列表。
- 现象/报错：`|| -> i64 { ... }` 报 `expected expression`，单参形式正常。
- 已尝试：在表达式主分支加 `Kind::Pipe`；检查词法器管道字符（已存在）。
- 原因判断：词法器的双字符匹配把 `||` 先匹配成 `Kind::Or`（`a || b` 的逻辑或），闭包语法与之冲突。不改词法器（两处词法器+漂移测试都要动），改在解析器消歧：`Or` 后面跟 `->` 只能是空闭包（`a || -> b` 不是合法表达式）。
- 教训/下一步：给既有语言加标点符号前先查双字符运算符表；能在一处（解析器）用上下文消歧就不要改词法器。

- 已尝试：检查 let 路径、表达式包装层。

## 7. git push 连续 schannel TLS 握手失败

- 时间：2026-11-13 10:41 (Asia/Shanghai)
- 任务：把本地领先 51 个提交的 master 推送到 origin。
- 现象/报错：`fatal: unable to access 'https://github.com/<owner>/ae.git/': schannel: failed to receive handshake, SSL/TLS connection failed`，连续 4 次（含一次 `--dry-run` 成功后的正式推送）。
- 已尝试：`--dry-run` 先验证凭据与连通性（成功），随后正式 push 失败；改为 3 次重试循环（每次间隔 3s），第 3 次成功。
- 原因判断：网络出口到 github.com 的 TLS 握手偶发不稳定（schannel 后端），非凭据问题——dry-run 能通过说明认证正常。
- 教训/下一步：push 前先 `git push --dry-run` 探活；正式 push 用带间隔的重试循环，且以 `git status -sb` 确认 `ahead 0` 才算完成。注意：本机 push 实际可用，原"本机无 GitHub 凭据"的假设已过时。

## 8. 泛型枚举方法测试用例中值接收者（by-value receiver）重复使用导致 move 冲突

- 时间：2026-11-13 16:40 (Asia/Shanghai)
- 任务：ADR-0196 泛型枚举 `impl Opt[T]` 方法与关联函数支持（`tests/run/enum_generic_impls.ae`）。
- 现象/报错：4 个测试套件用例（含 `move_walk_agrees_with_the_parser_on_the_run_suite` 和 `run_snapshots`）失败；`enum_generic_impls.ae` 中对携带 `string` 载荷的 `e = Opt[string]::Some("hi")` 先调用 `e.is_some()` 再调用 `e.unwrap_or("none")` 触发了 `use of moved value 'e'`，且 `declarations.rs` 中残留了 `AE_DEBUG_MOVE` 调试打印。
- 已尝试：检查 `declarations.rs` 泛型枚举方法实例化与 `move_walk` 对值接收者的语义。
- 原因判断：枚举方法接收者 `self` 为按值接收（by-value receiver），当枚举实例化携带拥有所有权的类型（如 `Opt[string]`）时，第一次方法调用 `e.is_some()` 就会将 `e` 移动（move）进方法体内；再次在同一绑定 `e` 上调用方法违反了单次绑定所有权规则。此外前序调试遗留了 `eprintln!("inst debug: ...")`。
- 教训/下一步：编写按值接收（`self`）的泛型枚举/结构体方法测试时，遵循"每个非 Copy 绑定仅调用一次消费型方法"的约束；调试输出在定位完成后应立即清理，避免污染快照输出。
