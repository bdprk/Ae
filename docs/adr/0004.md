# ADR-4: Build Cache Key Based on Generated C

- Background: Phase D requires cache hits to be semantically identical to full builds; the key must cover all inputs that affect the output.
- Decision: Key = SHA-256(generated C text + optimization mode + first line of C compiler `--version` + compiler version + target platform); entries are published via temporary file renaming so interruptions will not leave unusable partial artifacts; cache write failures do not cause build failures; `AE_CACHE` can override the location. (See ADR-27 for subsequent revisions: the key includes the verbatim `AE_CC` string, entries add a manifest digest verification, and the cache is disabled if the compiler cannot be recognized.)
- Rationale: Using generated C as the key is more resilient than using source code (semantically invariant changes still result in cache hits), and correctness is guaranteed without requiring a separate interface digest; compiler upgrades invalidate the cache automatically.
- Consequences: Front-end computation for C generation cannot be skipped (the front end remains O(source code)); interface digests for package-level/function-level incrementality are deferred until multi-file modules are introduced.
