# ADR-21: Monomorphization of Generic Enums by Arguments

- Background: Item 3 of Phase B requires "Generics, constraints, and module visibility; specifying instantiation strategies and code bloat budgets," while Item 4 requires expressive features like `Option`/`Result`. Previous enums were entirely monomorphic: to express "possibly absent", one had to write a separate enum for `Option[string]`, `Option[i64]`, and `Option[vec[string]]` with no way to unify their names. The six preset result types (`ReadResult`/`IntResult`/…) were precisely the product of such hand-written monomorphization—each fallible operation came with a fixed-shape result type, requiring compiler changes for any new shape. Furthermore, `vec[string]` was completely unwriteable as a **type annotation** (only the `&vec[string]` borrow could be written), meaning owned string vectors relied entirely on inference.
- Decision:
  1. Separation of generic **declaration** and layout: `enum Either[T, U] { Left(T), ... }` is recorded in a separate `GenericEnum` table (payloads use `Payload::Concrete(Type)` or `Payload::Param(usize)`), producing no C types; `EnumDef` retains its layout-bearing semantics.
  2. **Monomorphization**: `Type::Enum` can only point to instantiated `EnumDef`s. Upon first encountering `Name[args]`, the compiler looks up the table by `(declaration, argument list)`. If there is no hit, type parameters are replaced with the actual arguments, a new `EnumDef` is generated (with display name `Option[string]`, so diagnostics can directly state the concrete type), and it is appended to `enums`. Consequently, existing code generation, deallocation, forfeiture, struct fields, and `?` checks require zero modifications. Identical argument lists reuse the same `EnumDef`, ensuring `Option[string]` is the same type regardless of where it appears.
  3. `match` patterns use **declaration names**: `EnumDef.pattern` of an instantiated enum remembers the declaration name, allowing `Option::Some(v)` to work for both `Option[string]` and `Option[i64]`, with binding types determined by the matched value.
  4. Type parameters are restricted to a single uppercase letter, up to a maximum of 8; arguments are limited to `i64`/`bool`/`string`/`vec`/`vec[string]` (the same set as payload limitations), making recursive layouts mathematically impossible.
  5. Budget: `MAX_ENUM_TYPES = 256` (including the 6 preset ones). Exceeding this limit triggers an error at the instantiation site, specifying the enum name.
  6. Preset `Option[T] { Some(T), None }`, which, like the six result enums, belongs to the prelude and is public.
  7. Incidentally added type spelling for `vec[string]`: when `named_type` encounters `[` after `vec`, it expects `string` and returns `Type::StrVec`.
- Rationale: Monomorphization was chosen over type erasure (`void*` + function pointers) because the current runtime uses "type-generated deallocation routines"—after erasure, every payload would need to carry its own deallocation function pointer, increasing layout size and allocation overhead, which runs counter to the low-memory goal of §4.5. Moreover, erasure would discard the most valuable static check: the fact that `Option[string]` and `Option[i64]` are distinct types. Enums were chosen as the first step into generics rather than functions because generic functions can only perform "passthrough" operations without generic containers or type parameter constraints, rendering them nearly useless. Conversely, generic enums immediately provide `Option[T]`, and their monomorphization mechanism (declaration table + substitution + reuse + budget) establishes the exact framework that future generic structs and `vec[T]` will use. `Option` is placed in the prelude rather than a standard library file because the concept of "auto-imported libraries" does not yet exist, yet `Option` is a foundational shape that every program may utilize.
- Rejected Alternatives:
  - **Generic functions first**: `fn first<T>(v: vec[T])` requires generic containers, while `fn max<T>(a: T, b: T)` requires constraints (`T: Ord`). Without both, generic functions can only act as no-op pass-throughs, offering little demonstrable value.
  - **Type erasure / boxing**: See above; conflicts with the low-memory goal and destroys type distinction.
  - **Implementing `Option` via sentinel values** (e.g., using an empty string to represent None): This is precisely the source of bugs this feature aims to eliminate.
  - **Inferring type arguments from context** (`let x = Option::Some(1)`): Requires bidirectional type checking (inferring variable types and back-propagating them into construction expressions), whereas the current frontend is strictly top-down and unidirectional. Explicit `Option[i64]::Some(1)` is verbose but readable, requiring no new mechanisms.
  - **Generic structs simultaneously**: Struct field layouts, field borrows, and `FieldStore` deallocation would all need to be duplicated per argument, vastly expanding the scope of changes. Enums are implemented first, deferring `vec[T]` and field generics to a joint design phase.
  - **Allowing `Option[Option[i64]]`**: Payloads cannot be enums (which would introduce layout recursion). This restriction already exists and is not relaxed for generics.
- Consequences and Limitations: No generic functions, no constraints/traits, and no generic structs; generic enum payloads still cannot be structs or enums, meaning `Option[Option[i64]]` and `Option[Point]` cannot be written; `?` does not apply to `Option` (it only recognizes dual-variant result enums `Ok`/`Err`); type arguments must be explicitly spelled out and cannot be inferred from return values or variable types; one layout per argument list, bounded by a 256 limit; `match` patterns cannot be written as `Option[string]::Some` (only declaration names are recognized). Six new end-to-end tests added (instantiation and payloads, layout reuse, 9 classes of rejection paths, budget, cross-file visibility); `examples/maybe.ae` serves as the acceptance example and is included in allocation count validation (`blocks=2`, zero leaks).
