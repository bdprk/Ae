# ADR-19: Resource Model as a Normative Document Rather Than an Implementation Byproduct

- **Background**: The rules for ownership, borrowing, and deallocation were previously scattered across the "Consequences and Limitations" sections of ADR-5/6/8/11/14, as well as within code comments. While these fragments were individually correct, they failed to clarify three things **collectively**: which syntactic positions trigger a move (easy to miss when adding new built-ins), which properties are "coincidentally true for now" (e.g., borrowing cannot escape because it cannot be stored in a variable, rather than due to lifetime analysis), and what must be checked when adding new features. Item 1 of Phase C requires "writing a formal resource model first," precisely because without a normative model, subsequent features like partial moves, loop fixed-points, and cross-thread constraints have no foundation.
- **Decision**: Add `docs/resource-model.md` as a **normative** document. It explicitly details value classifications (scalar/owned/borrowed/array), move positions (6 locations), compile-time and runtime states after a move, borrowing rules and prohibitions, deallocation points (9 locations, including `break`/`continue` and `?` error paths), termination semantics, current concurrency status, **explicitly non-guaranteed properties** (9 items), and an 8-item checklist for adding new features. During the writing process, each point was cross-referenced with the implementation; for example, "the union of move sets from both `if` branches" corresponds to the `after_yes` merge in `if_statement`, and "`?` and `return` deallocate parameters" corresponds to `live_owned()` traversing all scopes.
- **Rationale**: Separating "guaranteed" from "not guaranteed" into two columns is the only reliable way to prevent over-claiming. This also aligns with the Phase A acceptance requirement: "do not claim security properties that are not yet covered." Both the README and this document now only claim three layers—"compile-time checks + runtime sentinels + leak tests"—and do not claim formal verification. The checklist formalizes the "three things that must be handled when adding a new type/statement/built-in," preventing future extensions from relying on memory.
- **Rejected Alternatives**:
  - **Writing the model in code comments**: Comments follow functions; readers cannot see global rules at a glance, nor can they use them for reference during code reviews.
  - **Writing the model after the implementation is complete**: The purpose of the model is to **constrain** the implementation (subsequent Phase C tasks like branch merging and partial moves must follow it); a model written after the fact is merely a post-hoc description.
  - **Describing ideal behavior in the model**: This would turn it into a marketing document, making it impossible for readers to distinguish between what is implemented and what is planned.
- **Consequences and Limitations**: The document must be maintained in sync with the implementation; otherwise, it will lead to discrepancies where "the document claims a guarantee, but the implementation does not provide it." The final item of the checklist makes this a routine action for every extension. The model itself does not add any compile-time capabilities: structs still lack runtime sentinels, partial moves, loop fixed-points, and cross-function lifetimes. These limitations remain in effect, but they are now explicitly documented.
