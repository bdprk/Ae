# ADR-29: `vec[string]` Construction and Subprocess Execution

- Background: Phase E, Item 1 designates "processes" as a fundamental API. The very first thing a script often needs to do is **invoke tools already available on the machine** (`git`, `ffmpeg`, `grep`), whereas ae could previously only read and write files, without the ability to spawn subprocesses. At the same time, passing arguments to a subprocess requires an empty `vec[string]`, which at the time could only be obtained indirectly via `split`/`args`—there was no way to "construct a string vector from scratch."
- Decision:
  1. Added `strvec_new() -> vec[string]`: An empty string vector, paired with `push` to add elements one by one.
  2. `push(v, x)` and `v[i] = x` now also accept `&string` (borrowed): the element is **copied** into the vector, leaving the source string unaffected; owned `string` values are still handled via move semantics.
  3. Added `run_command(program, args) -> CommandResult`, where `args` must be a raw `vec[string]` variable (borrowed, not moved). Predefined enum `CommandResult{Ok(i64 status, string output), Err(string)}` (ID 7).
  4. The subprocess's stdout and stderr are **merged into a single pipe**, preserving the interleaving order of their writes within `output`.
  5. A non-zero exit status is part of **Ok** (`grep` returning 1 with no matches is a normal outcome); only "launch failures" (program not found, permission denied, pipe creation failure) result in `Err`.
  6. POSIX uses `fork` + `execvp` + waiting; Windows uses `CreateProcessW` + anonymous pipes. On POSIX, the argument array is passed verbatim to `execvp` (without any parsing); on Windows, it must be concatenated into a single command line: quotation marks are added only to arguments containing whitespace (adding quotes to arguments that don't need them causes the receiver to treat the quotes as part of the command name), while arguments containing `"` or ending with `\` immediately throw an `Err` rather than guessing at escape rules.
- Rationale: Merging the two streams instead of capturing them separately avoids deadlocks under any real output volume (where one fills up while the parent process is waiting on the other). Avoiding this requires introducing `poll`/`select` or dedicated read threads. Merging eliminates deadlocks while preserving the readability of "error messages appearing where they are supposed to," at the cost of the caller being unable to distinguish which stream a given byte came from. Placing the status inside `Ok` rather than treating non-zero as `Err` stems from the principle that language errors are **recoverable failures** (unable to launch, unable to read), whereas a program returning 1 is a recoverable, normal outcome—treating it as an error would force callers to use `match` for two separate concerns (determining whether it could run versus determining the execution result). Quoting arguments on demand and rejecting problematic quotes avoids rewriting `CreateProcess`'s escape rules: once implemented incorrectly, those rules (backslash counting, quote doubling) would silently alter the arguments received by the subprocess without the error mechanism reporting any issues.
- Incidentally fixed an ownership defect: `push(v, argv[i])` was originally emitted as a "move" (`moving = true`), even though `argv[i]` is a borrowed view. As a result, the view was treated as an owned value and placed into the vector: the source slot was cleared, and the vector stored a `string` "pointing to another buffer." Upon exit, the same chunk of memory was freed twice—on Windows, this manifested as the process terminating with `0xC0000374` (heap corruption), and because stdio buffers were lost, **printing nothing at all**. The parser now records a flag indicating "this element is borrowed," borrows via `ae_str_copy_view`, and prohibits moving it. The newly added end-to-end tests use `args()` + indexed pushes to reproduce the original scenario.
- Excluded Approaches:
  - **`popen`**: Unidirectional, unable to retrieve the exit status, and unable to merge stderr.
  - **`system`**: Inherits the terminal, cannot capture output; scripts cannot make decisions based on its result.
  - **Passing the entire command line as a single string (`run_command("git --version")`)**: Requires shell parsing, reintroducing injection risks and cross-platform discrepancies; an argument array is the only safe form.
  - **Asynchronous/Timeout/Streaming output**: Requires handle types, cancellation semantics, and an event loop; implemented synchronously all-at-once first, to be designed when real demand arises (Phase F will handle concurrency and timeouts).
  - **Injecting stdin**: Requires bidirectional pipes and a "who writes first" protocol; `read_stdin` already covers "reading one's own input," leaving subprocess input for later.
  - **`vec[string]` literals `["a", "b"]`**: `strvec_new` + `push` is sufficient for now; literals would require new expression forms and borrowing rules.
- Consequences and Limitations: No timeout, no stdin, no environment variables or working directory parameters (inherits from the parent process); output resides entirely in memory, making massive outputs (hundreds of MBs) unsuitable. On POSIX, subprocesses terminated by signals report `128 + signal_number` (matching shells); Windows has no concept of signals and instead retrieves the value of `GetExitCodeProcess` (which is an NTSTATUS upon abnormal termination). Windows arguments cannot contain `"` or end with `\`. Neither platform performs shell expansion (wildcards, pipes, and redirection require invoking a shell explicitly, such as using `cmd` as the program name and explicitly passing `/c`). Added `examples/run_tool.ae` and 2 end-to-end tests (one real subprocess, one class of launch failure), validated respectively on Windows and Debian 13 (the POSIX branch uses a `CLOEXEC` error pipe to distinguish between "exec failure" and "the program itself returning 127," preventing both platforms from representing the same outcome with different results).
