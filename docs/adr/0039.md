# ADR-39: Pruning System Headers by Reachability, Without Hand-Written Win32 Declarations

- **Background**: ADR-38 reduced generated C from 109,721 bytes to 20,273 bytes (for `print(1)`), but `#include <windows.h>` falls under "non-function text that must be preserved as-is," which cannot be eliminated by function closure pruning. Consequently, **every** generated program on Windows still parses the entire set of Win32 declarations: a standalone test of a file containing only this header takes about 690 ms, or about 520 ms with `WIN32_LEAN_AND_MEAN`. Empirical measurements show that the C code generated for `float_math.ae` leaves only two `#ifndef _WIN32` lines and an empty Win32 shell after pruning, without calling a single Win32 API, yet still pays this cost. W6 in the design document (§21) proposed "hand-written minimal Win32 declarations," but the runtime actually utilizes `WIN32_FIND_DATAW`, `STARTUPINFOW`, `PROCESS_INFORMATION`, `WIN32_FILE_ATTRIBUTE_DATA`, `FILETIME`, and over twenty APIs (files, directories, clocks, environment variables, working directories, subprocesses). The ABI risks and rewards of precisely replicating these structures are asymmetrical.
- **Key Observation**: `<windows.h>` is written inside an `#ifdef _WIN32` branch, serving solely to provide declarations for runtime functions in the Win32 branch. If closure pruning leaves **not a single function requiring it**, this include line is pure overhead; Linux, meanwhile, does not preprocess this branch at all. A zero-modification probe was conducted: removing this line from the C generated for `float_math.ae` reduced the median of three `gcc -std=c11 -O2` runs from 963.2 ms to 417.7 ms (a saving of 545.5 ms, or a 2.31x speedup), with the outputs of both executables being byte-for-byte identical.
- **Decision**:
  1. **Explicit marking rather than guessing**: Add `/* win32-header */` to the function definition line of the 16 runtime functions that depend on `windows.h` declarations (`ae_widen`, `ae_narrow`, the Win32 branch of `ae_fopen`, `ae_now_ms`, `ae_try_env`, `ae_try_cwd`, `ae_path_exists`, `ae_path_is_dir`, `ae_try_list_dir`, `ae_try_file_info`, `ae_try_rename_path`, `ae_try_remove_file`, `ae_make_one_dir`, `ae_set_cwd`, `ae_try_remove_dir`, and the Win32 branch of `ae_run_command`). The marker is preserved or deleted along with the function unit; it requires no parsing of preprocessing conditionals, nor does it rely on a Win32 API name manifest.
  2. `prune_runtime` checks the runtime section **before** concatenating user suffixes: when not a single marker remains, it replaces `#include <windows.h>` with `/* windows.h omitted */`. User code cannot influence this determination; neither `deps` output nor content-addressed cache keys participate in it.
  3. The decision is based on **capabilities used by the program** rather than the platform: the generated C text is completely identical on both platforms (`print(1)` is 20,352 bytes on both), Linux is unaffected due to preprocessing, and the benefit is realized on Windows.
  4. Added 2 unit tests (pruning behavior: strip header when no markers remain / retain header when markers are present; marker auditing: scanning `runtime.c` and `runtime_ex.c`, ensuring any function unit containing Win32 declarations must carry the marker) and 1 integration test (header decisions for 3 examples, with each generated C file passing `-std=c11 -pedantic-errors -Werror=return-type -fsyntax-only`).
  5. `bench/build_timings.py --header-baseline`: Recreates `<windows.h>` in the exact same generated C file using a **byte-level** replacement, timing it alternately with the stripped-header version in the same script, at the same moment, and under the same toolchain. Cross-session wall-clock figures can fluctuate by over 30% on this machine, making intra-run comparisons the only causal evidence.
- **Excluded Approaches**:
  - **Hand-written minimal Win32 declarations (original W6 route)**: This round introduces no ABI assumptions. W6 remains in §21, requiring structural layout evidence and sanitizer results before implementation can proceed; this ADR merely captures the benefit of "completely avoiding header parsing when Win32 is not needed" in a zero-risk manner.
  - **Automatic scanning of "whether Win32 branch code still exists in the retained text"**: This would incorrectly include `_setmode`/`_O_BINARY` from `ae_try_read_stdin` (which comes from `<io.h>` and does not require `windows.h`), forcing programs that read standard input to still pay the 500 ms cost. It would also require the pruner to understand nested preprocessing conditionals, which is precisely the source of complexity that led to `ae_widen` being mistakenly deleted in ADR-38.
  - **PCH or splitting into another translation unit**: Evaluated and rejected in ADR-38 (69 MB `.gch`; splitting the TU causes a cold build regression of about 68%).
- **Rationale and Safety Boundaries**: Three core metrics benefit simultaneously with no trade-offs—Windows compilation input shrinks, runtime semantics remain unchanged (only a single unreferenced include line is deleted), and disk/cache footprint remains unchanged (no new cache categories introduced). **The consequence of missing a marker is that the generated C lacks declarations and throws a direct compilation error** (an explicit failure; 24 generated C test cases and strict syntax checks will catch it immediately), while **the consequence of an extra marker is merely parsing the header one extra time**; neither silently alters runtime results. The marker audit unit test prevents missing markers when adding new Win32 functions in the future; the Win32 identifier list in this test is used solely for auditing and does not participate in build decisions. An incomplete list merely checks fewer functions and does not alter compiler behavior. The rollback mechanism is to disable this replacement and unconditionally retain the include line; `build`/`run` semantics remain completely unchanged.
- **Consequences and Limitations**: The generated C for `print(1)` goes from 20,273 to 20,352 bytes (the difference is comment text, not code), and the `-O0` executable remains 64,195 bytes on Windows / 17,168 bytes on Linux; there is no new resident memory and no new cache. **Programs that use files, paths, directories, clocks, environment variables, working directories, or subprocesses will still retain `<windows.h>` and pay the parsing cost**—this decision neither "removes the Win32 header dependency" nor implements the minimal declarations of W6. Hand-written minimal declarations, user module/package-level incrementality, parallel scheduling, and interface-summary-driven invalidation remain unimplemented. The absolute execution times of the four scenarios are significantly affected by machine load and are not directly comparable to the single-digit numbers archived in W3.
- **Validation**: Ran the full test suite once each on Windows and Linux, with all 11 unit tests and 136 integration tests passing; all 24 `--leak` test cases PASS on both platforms, with exited allocation block counts equal to the 2-block and 0-block baselines respectively; all 24 `--sanitize` test cases PASS on Linux with 0 reports; all `examples/*.ae` pass `check`; header decisions are consistent across both platforms (`float_math.ae` strips the header, `file_tidy.ae` retains it, and generated C for `print(1)` is identical at 20,352 bytes), and `deps` outputs are consistent after line-ending normalization. As a final safety net against "missing markers," we also ran `gcc -std=c11 -pedantic-errors -Werror=return-type -fsyntax-only` **individually on the generated C for all 31 `examples/*.ae`** across both platforms, and all passed. Header decisions were completely identical on both platforms (11 with headers, 20 stripped), with logs stored in `generated-c-syntax.log` under their respective archive directories. Text heuristics (scanning API names) cannot replace this step: runtime comments mention `_wfopen`, which would be falsely reported as still calling Win32 APIs.
  - Windows (`gcc -std=c11 -O0`, three independent runs, taking the median of 3 internal iterations each): with header 980.9 / 945.6 / 1,296.4 ms, stripped header 252.6 / 301.6 / 319.6 ms, intra-run savings of 644.0–976.8 ms (3.14–4.06x); medians were 980.9 ms with header and 301.6 ms stripped. Medians across the four scenarios (three runs): cold build 435.9, no modification 160.0, modify implementation 510.4, modify interface 482.0 ms. Logs and raw values for the three runs can be found in `bench/results/2026-11-10-windows-winhdr/`.
  - Linux (same parameters): with header 32.0 ms, stripped header 31.4 ms, with the difference falling within measurement noise; four scenarios: 36.2 / 4.6 / 36.5 / 36.1 ms. Logs are in `bench/results/2026-11-10-linux-winhdr/`. This precisely demonstrates that the gains stem from Windows header file parsing rather than changes in generated C file size.
