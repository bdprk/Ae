# ADR-25: Linux Full-Scale Verification and Strict ISO C Fixes

- Background: Previously, `docs/platform-matrix.md` only contained a single Linux record from 2026-11-10. Subsequent capabilities (hash tables, UTF-8 boundaries, allocator interfaces, `pub` visibility, loop movement rules, generic enums, sorting/clocks/environment variables/append writes, `exit`, `read_stdin`/`cwd`) only had native Windows evidence. Re-running `cargo test --locked` on Debian 13 (GCC 14.2.0, rustc 1.99.0, 4 vCPU / 7.8 GB) resulted in **91 out of 117 end-to-end tests failing**, all stuck at the same compilation error:

  ```
  program.c: In function 'ae_now_ms':
  error: implicit declaration of function 'clock_gettime'
  error: 'CLOCK_REALTIME' undeclared
  ```

- Root Cause: Both the tests and `verify_generated_c.py` compile the generated C code using `-std=c11 -pedantic-errors`. The `-std=c11` flag defines `__STRICT_ANSI__`, which causes glibc's `features.h` to disable `_DEFAULT_SOURCE`/`_POSIX_C_SOURCE`. Consequently, `clock_gettime` and `CLOCK_REALTIME` in `<time.h>` (which are POSIX and require `_POSIX_C_SOURCE >= 199309L`) become invisible. Windows uses the `GetSystemTimeAsFileTime` branch, so this issue was never exposed natively. This is a problem that **can only be discovered by running on Linux**—which is precisely the value of this round of cross-platform verification.
- Decision:
  1. The POSIX branch will be updated to use `timespec_get(&ts, TIME_UTC)` (the ISO C11 standard interface), removing the dependency on any feature macros; the millisecond conversion and rounding rules remain unchanged.
  2. We will not adopt the fix of `#define _POSIX_C_SOURCE 200809L` at the top of generated files.
  3. The string escape set will be expanded to include `\r` (previously only `\n \t \\ \"` were allowed).
- Rationale: `timespec_get` is part of C11 and is naturally visible in strict mode. The generated files remain "pure ISO C11," and users do not need to concern themselves with glibc feature macros to compile AE artifacts—this property is one of the promises of ADR-1 (generating C11). Conversely, injecting `_POSIX_C_SOURCE` would pollute the host's compilation unit: if a user `#include`s the generated code into their own project, or switches to musl/BSD, the macro's semantics would become a new platform dependency. The `\r` escape was added because, when handling CRLF text via standard input and `split(text, "\r\n")`, it is impossible to write the literal without it (C's `"\r"` is inherently legal; the frontend was simply rejecting the spelling).
- Excluded Approaches:
  - **`_POSIX_C_SOURCE` macro**: See above; this moves the platform dependency from runtime to the compilation command line.
  - **`gettimeofday`**: Also POSIX; suffers from the same issue.
  - **`time(NULL)` (second-level precision is sufficient)**: The purpose of `now_ms` is to provide millisecond precision; degrading it to seconds would make the name `now_ms` a misnomer.
  - **Adding `-D_POSIX_C_SOURCE` only on Linux**: This would require "different compilation parameters for the same source code on different platforms," which is worse than fixing the runtime.
- Results: After the fix, `cargo test --locked` on Linux passes **all 9 unit tests and 117 end-to-end tests**; all 16 examples in `python3 scripts/verify_generated_c.py --sanitize --leak` pass with **`blocks=0 bytes=0`** (glibc's startup allocation is lower than Windows UCRT, so the baseline is 0, which is stricter than Windows' 2); example output is consistent with Windows after line-ending normalization (previously noted as "byte-for-byte consistent"; this entry corrects that description to "consistent after normalization" as of 2026-11-10). The `\r` escape is covered by `standard_input_arrives_as_bytes_without_newline_translation` (reading back `a\r\nb` results in a length of 4, including the `\r`).
