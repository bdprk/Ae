# ADR-22: Sorting, Clocks, Environment Variables, and Append Writing

- Background: Transforming "file organization/log analysis" from an example into a daily tool lacks four small operations rather than language features: **sorting** (listing top $N$ files by size, sorting by time), **current time** (`try_file_info` provides mtime, and without `now` it is impossible to calculate "how long ago"), **environment variables** (temporary directories, `HOME`, proxy settings; otherwise paths have to be hardcoded), and **append** (writing logs; `write_file` only allows whole-file overwriting, which means rewriting the entire content every time a single line is written). Phase E Item 1 lists these as basic APIs, and the file processing example in Phase B Item 6 happens to require them.
- Decision:
  1. `sort(v)` / `reverse(v)` perform in-place rearrangement. `v` must be a `var` vector: `i64` vectors are sorted numerically, and `vec[string]` vectors are sorted by **byte order** (using the same convention as `keys()` and `try_list_dir`, ensuring sorted output is consistent across both platforms). Empty vectors and single-element vectors are no-ops.
  2. `now_s()` / `now_ms()` return seconds/milliseconds since the Unix epoch (`i64`). `now_s` shares the same unit as the mtime from `try_file_info`, allowing direct subtraction.
  3. `env(name) -> ReadResult`: Returns `Ok(value)` if the variable exists, and `Err("variable not set")` if it does not; **if it exists but is empty**, it returns `Ok("")`. An empty name reports `Err("variable name is empty")`.
  4. `try_append_file(path, text) -> WriteResult`: Opens and writes in append mode, returning the number of bytes written.
- Rationale: In-place sorting rather than returning a new vector is chosen because call sites are almost always "sort this list in place." Returning a new vector would force a full copy and turn the original variable into a "moved" state, which is inconsistent with the "mutable container" paradigm of `push`/`pop`. The C standard library `qsort` is used: it is part of C11, available on both platforms, and the comparison function is a plain function pointer (requiring no closures), while stable sorting yields no observable difference for `i64` and byte-compared strings. `env` reuses `ReadResult` instead of inventing a new `Option`, because "why it cannot be read" is more useful for diagnostics than "whether it exists" (an empty name and non-existence are distinct errors), and `ReadResult` is already in the prelude. Distinguishing between "empty value" and "unset" is a hard requirement: treating `PATH=""` as "no PATH" would cause the program to silently take a completely different branch.
- Excluded Approaches:
  - **`sort_by(key)`**: Requires function values/closures; the current language lacks them, so only fixed comparison rules can be provided.
  - **Returning a new vector `sorted(v)`**: Incurs an extra allocation and moves the original vector, whereas callers typically continue using the same variable after in-place sorting.
  - **`env` returning `Option[string]`**: Discards the error reason; furthermore, `Option` has just been added, and there is no need to fork another set in standard APIs.
  - **`set_env`/`cwd`/process startup**: Modifying the environment affects the semantics of future child processes and should be designed alongside process APIs; `cwd` is coupled with relative path resolution rules and also requires a separate decision (currently it is "relative to the current working directory").
  - **`now` using a monotonic clock**: File mtime is wall-clock time, and comparisons must be from the same source; monotonic clocks are reserved for future timing APIs (such as uses like `AE_TIMINGS`).
- Consequences and Limitations: Only `vec` and `vec[string]` can be sorted; struct/enum vectors do not exist; sorting is unstable; `sort` requires a mutable variable just like `push`, and is disallowed while it is borrowed (e.g., inside the body of `for x in v`); `now_*` will fluctuate with system clock adjustments and is not a monotonic timer; `env` is read-only, non-writing, and non-enumerable; there are no streaming file handles, so `try_append_file` opens and closes the file on every call (when writing many small lines, users should concatenate them themselves for a single write); on Windows, "empty value vs. unset" relies on `SetLastError(ERROR_SUCCESS)` + checking `GetLastError` after reading, which is the most error-prone part of this implementation and has been covered for all three scenarios in tests.
- Incidentally fixed a pre-existing leak: If the **path** argument to `try_write_file` is an owned temporary value (`try_write_file(path_join(dir, name), text)`), the emitter only released the content argument and failed to release the path argument. Previously, no examples invoked it this way, so the allocation count never revealed it; the newly added `examples/dir_report.ae` immediately exposed 3 extra blocks upon execution. After cross-checking all file operation emitters (`try_copy_file`/`try_rename_path`/`try_remove_file`/`try_remove_dir`/`try_create_dir`/`try_file_info`/`try_list_dir`/`try_read_file`), it was confirmed that only this one (along with the newly added append) was missing releases. Both are now uniformly released, and `--leak` has recovered to baseline.
