# ADR-27: Cache Entries with Verification; Disable Caching When Compiler Cannot Be Identified

- **Background**: The key for ADR-4 covers C generation, optimization mode, the first line of the compiler's `--version` output, compiler version, and platform. Entries are published by "copying to a temporary file and renaming." Item 3 of Phase D requires that "caching must be disabled when inputs affecting the result cannot be reliably identified, and potentially stale binaries must not be reused." During review, two non-compliant areas were identified:
  1. Hit determination only checks if "the file exists and its length is greater than 0." In tests, if the executable in the cache is overwritten with `garbage`, the build still succeeds and treats this dead file as a valid artifact—cache corruption silently propagates as "program builds successfully but crashes upon execution."
  2. Compiler identity is derived only from the first line of `--version`, and falls back to the fixed string `"unknown"` if the query fails. Two different compilers (or different installations of the same compiler) share the same key when they cannot be queried, falling into the "unreliably identified" forbidden zone. Furthermore, the key does not include the actual value of `AE_CC`, making it impossible to distinguish between two binaries of the same version.

- **Decision**:
  1. Add a `manifest` file to each entry, containing `<byte_count> <SHA-256>`. Before a hit is confirmed, re-read the executable, re-calculate the digest, and compare it. If they do not match, **delete the entire entry and rebuild it** (treated as a miss; `AE_TIMINGS=1` will print `cache: miss`).
  2. The publication order is fixed: "rename the executable first, then rename the manifest." If a crash occurs in between, the manifest will not match the new file, resulting in a miss upon the next read, preventing the existence of a seemingly valid but corrupted entry.
  3. If the compiler identity query fails (process startup failure, non-zero exit, or empty output), **disable caching for this session**: do not check for hits, do not write entries, and print `cache: disabled (cannot identify the C compiler ...)` when `AE_TIMINGS=1`.
  4. Include the raw string of `AE_CC` in the key, which, combined with the first line of the identity, serves as the criterion for "which compiler this is."

- **Rationale**: A cache is a facility that "trades correctness for time"; its sole obligation is to never return an incorrect result. Checking for file existence and non-zero length only guards against "empty files," whereas truncation (due to full disk), replacement, or manual tampering are realistic scenarios. Comparing SHA-256 alongside file size costs one file read (a few to tens of KB) and the use of the project's existing SHA-256 implementation, which is negligible compared to the hundreds of milliseconds saved on C compilation. Disabling the cache when the compiler cannot be queried is more consistent with the discipline of "do not reuse if inputs cannot be reliably identified" than "making do with a placeholder"—the extra time spent is predictable, whereas an incorrect binary is not.

- **Excluded Approaches**:
  - **Using file modification time or size for verification**: Size can guard against truncation but not against replacement with a file of the same length; timestamps are unreliable after copying, extraction, or filesystem migration.
  - **Including linker/system library versions in the key**: These cannot be reliably enumerated (`ld` version, libc version, SDK paths). Per the discipline in item 3, we should "not claim coverage." The documentation explicitly states: the key covers **C generation, compilation options, compiler identity and path, AE version, and target platform**; changes to libc/SDK require a `cache clear` (or the use of independent cache directories in CI).
  - **Silently rebuilding on hit failure without deleting old entries**: Corrupted entries would fail repeatedly on every build; deleting them ensures a clean state for the next attempt.
  - **Not writing to cache on compilation failure**: This is already the case (publication occurs only after success), so it remains unchanged.

- **Consequences and Limitations**: The first run will result in a total miss and a full rebuild due to the missing manifest (old entries will be deleted); each entry will consume a few dozen extra bytes for the manifest; each hit will incur an additional read of the executable (approx. 60 KB) and one SHA-256 calculation; it still cannot detect "system changes outside of compiler inputs" (libc/SDK/environment variables), and the documentation requires clearing the cache after such changes. Testing has shifted from "corrupted entries treated as hits" to "corrupted entries judged as misses and rebuilt into runnable artifacts," aligning with the semantic promises of ADR-4.
