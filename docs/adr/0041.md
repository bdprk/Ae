# ADR-41: Share Lexical Results by Source File for Generic Declarations, Eliminating O(N²) Frontend Copying

- **Background**: The `bench/constraint_audit_timings.py` comparison from ADR-40 showed that 800 uninstantiated generic declarations with constraints caused `check` to take 0.9–1.4 seconds, and the difference between constrained/unconstrained (Windows 94.2 ms, Linux 119.9 ms) was significantly larger than the audit itself. Investigation revealed the root cause in ADR-31: to allow each instantiation to "re-parse the function body later," `GenericFn` cloned the **entire** token stream and source text into each declaration. If a file contains N generic declarations, the entire token stream (which grows linearly with N) is copied N times, resulting in O(N²) complexity for the frontend. This is an existing design issue, unrelated to ADR-40, but exposed by its timing comparison.
- **Key Observation**: `GenericFn` only needs to "be able to read these tokens later," not "possess an exclusive copy." All declarations in the same file read the same token stream and the same source text, and both are read-only; `start` is merely an index into this stream. Therefore, they can be fully shared.
- **Decision**:
  1. Change `Parser.tokens` from `Vec<Token>` to `Rc<Vec<Token>>`. Each source file is `Rc::new(...)`'d once after `lex`; both `parse_source` and `load_file` are constructed accordingly. All `self.tokens[i]` / `.get()` usages remain unchanged due to `Deref`.
  2. Add `shared_source: Rc<str>` to `Parser` (one `Rc::from(source)` per file); `Parser.source: &'a str` remains unchanged. This keeps 25 diagnostic and position-related code blocks untouched, avoiding the expansion of a performance fix into a lifecycle refactoring.
  3. Change `GenericFn.tokens`/`source` to `Rc<Vec<Token>>`/`Rc<str>`; `collect_functions` now performs only an `Rc::clone` (O(1)). `instantiate_fn` also uses `Rc::clone(&def.tokens)` and `&*def.source` when constructing the sub-parser, making **instantiation zero-copy as well**.
  4. Update `scan_uses` and `audit_generic_fn` to pass `.as_ref()`; the semantics of `start` remain unchanged.
  5. Add 1 unit test (asserting via `Rc::ptr_eq` that all generic declarations in the same file share the same token buffer and source, preventing silent regression to O(N²)) and 1 integration test (80 generic declarations + 80 instantiations, verifying that each `start` still points to its own parameter list and function body).
  6. Add `bench/shared_tokens_timings.py`: Use **two real binaries** (pre-change, exported via `git archive` from the ADR-40 commit, and post-change) to alternately measure `check` on the same source code at the same time, asserting that `emit-c` and diagnostic output at declarations are identical. The script also records consistency after CRLF/LF normalization: runtime source code exported by `git archive` may contain CRLF; only normalized comparison prevents misinterpreting environment differences as semantic changes. This archive cycle has ensured the baseline tree uses the same line endings for `runtime.c`/`runtime_ex.c` as the workspace, so the generated C code is **byte-for-byte identical**.
- **Rejected Alternatives**:
  - **Only change `GenericFn` to `Rc` while keeping `Parser.tokens: Vec`**: Each declaration would still require `Rc::new(self.tokens.clone())`, keeping the number of copies unchanged and retaining the O(N²) behavior.
  - **Global/static token pool or cross-file caching**: This introduces resident memory and lifecycle management issues, and requires handling cross-file loading and name collisions, violating low-resource goals. Per-file `Rc` is sufficient; reference counts automatically drop to zero after file parsing completes.
  - **Change `Parser.source` to `Rc<str>` and rewrite all diagnostic calls**: Source code is already borrowed once per file; the benefit is zero, but it would require modifying 25 locations, creating an asymmetric risk.
  - **Skip parsing of uninstantiated generic declarations**: This would change the timing of errors and `deps` summaries, constituting a semantic change rather than a performance optimization.
- **Rationale and Safety Boundaries**: The token stream is shared as read-only, with no mutable access. `Rc` is used only for the single-threaded frontend and does not enter C generation or the runtime. `start` remains an index into the same stream; measurements confirm that generated C, diagnostic positions, `deps` summaries, and allocation counts remain entirely unchanged. The fallback strategy is to revert `Rc` to an owned clone; semantics remain identical, only restoring O(N²). The `Rc::ptr_eq` unit test serves as a hard constraint against future regressions.
- **Resource Costs (answering §21 acceptance criteria point-by-point)**:
  - **Compilation Speed**: Comparison within the same run (`--runs 7`, median): Windows 200 declarations 132.5 → 29.1 ms (saved 103.4 ms, 4.55x), 800 declarations 1575.9 → 32.8 ms (saved 1543.1 ms, 48.0x); Linux 200 declarations 64.1 → 3.4 ms (saved 60.7 ms, 18.8x), 800 declarations 987.2 → 9.3 ms (saved 978.0 ms, 106.7x). Gains grow super-linearly with the number of declarations, confirming the O(N²) → O(N) profile. The difference in ADR-40's capability audit comparison also dropped from 10.3 / 94.2 ms to 1.2 / 4.5 ms (Windows 200/800), confirming that "previous differences were primarily due to copying rather than auditing." Local load fluctuations are significant; only ratios and magnitudes within the same run are reported, not cross-session subtractions from absolute values archived in W3 / ADR-39 / ADR-40.
  - **Memory**: No longer holds N copies of token streams and source code; allocation frequency and copy volume have decreased significantly; however, **no peak memory sampling was performed**, so no specific figures are claimed.
  - **Generated C / Executable / Cache**: Completely unchanged (both platforms `print(1)` 20,352 bytes; old/new `emit-c` are byte-for-byte identical; `-O0` artifacts Windows 64,195 / Linux 17,168 bytes), with no new cache types or resident processes.
  - **Runtime CPU/Memory**: Zero impact, purely frontend.
  - **Safety Semantics**: No checks disabled; both pre-checks for capability coverage at declaration and full type checking per instantiation are preserved.
- **Boundaries**: We do not claim "all programs compile faster"—gains are concentrated in files with many generic declarations; differences for single-function programs are within measurement noise. We also do not claim specific reductions in peak memory or treat this ratio as a universal speedup factor. User-module-level increments in W3 Phase 2 remain blocked by the empirical conclusions of ADR-38; this ADR does not involve translation unit splitting.
- **Verification**: Full command suites run once on both Windows and Linux, with 15 unit + 139 integration tests passing; all 25 `--leak` cases PASS (Windows 2 blocks, Linux 0 blocks baseline); Linux `--sanitize` 25 cases PASS with 0 reports; all 32 `examples/*.ae` passed `check`; `deps` output is consistent after line-ending normalization (233 bytes); `print(1)` generated C is 20,352 bytes on both platforms, with header decisions consistent with ADR-39. Timings for four scenarios (whole-process ms): Windows cold 352.4 / no-mod 139.3 / mod-impl 457.2 / mod-intf 431.3; Linux 38.2 / 5.4 / 40.0 / 40.2. Logs and comparison JSON (including 7 raw values) are available in `bench/results/2026-11-10-{windows,linux}-w5-front/`.
