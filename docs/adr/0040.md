# ADR-40: Constraints accept capability coverage checks at declaration, but are still not traits

- **Background**: ADR-33 defined constraints as a "whitelist of argument shapes at the call site," explicitly avoiding consistency checks for generic bodies. After practical use, one class of errors remains elusive: in `fn f[T: Copy](a: T, b: T) -> T { return a + b; }`, `Copy` allows `bool`. When calling `f[bool]`, the constraint passes, and only then does the function body report that `'+' requires ...`. More commonly, the function is never called, and the error only appears upon the first instantiation, even though the declaration itself appears self-consistent. §21 W4 requires "making generic declarations checkable themselves," but a full trait/impl system requires method tables, static dispatch, orphan rules, and visibility rules, which carries too high a risk for a single delivery. The current architecture is "re-parsing the function body per instantiation" (ADR-31), with no provable AST for un-substituted generics.
- **Key Observation**: One does not need to prove the generic body to discover that "the constraint is lying." The **intersection** of the constraint whitelist is the set of valid types (types that can satisfy all constraints during instantiation). Every operation the function body imposes on a type parameter has a **supported type set** provided by the actual type-checking rules. If there exists a type in the valid type set that does not support the operation, the declaration is incorrect. This is equivalent to "a certain instantiation will fail" and can be determined at the declaration site without any type inference.
- **Decision**:
  1. Add `Capability` (`Add`/`Arith`/`Modulo`/`Ord`/`Eq`/`Logic`), supporting type sets that mirror the binary operation rules of `expression` (e.g., `+` = i64/f64/string, `- * /` = i64/f64, `%` = i64, order comparison = i64/f64, `== !=` = i64/f64/bool/string, `&& ||` = bool). The capability table is located with `Bound::allows`, and unit tests assert that the whitelists for `Add`/`Ord`/`Eq` are subsets of their corresponding capability support sets, preventing the two sets of rules from drifting when new scalar types are added.
  2. `audit_generic_fn` performs a single-pass token scan on every **constrained** generic declaration within `collect_functions`: it binds parameter variables to type parameter indices and performs conservative taint propagation for `let`/`var` local variables. A capability requirement is recorded only when an operation token is **immediately adjacent** to an identifier bound to a type parameter; call results, subscripts, fields, literals, and indeterminate local variables are skipped. Subsequently, the valid type set is calculated based on the intersection of the constraint whitelist. If any type does not support the required capability, an error is reported at the **type parameter declaration site**, listing the specific type, operation, capability support set, and the current valid type set. Example: `declares T: Copy but its body applies '+' to T; the constraint still admits bool, which does not support it`.
  3. **Reject only, do not permit**: Each instantiation is still fully parsed and type-checked according to ADR-31/33. Constraints do not participate in code generation, do not affect release paths, and do not change the interface summary of `deps`. Pre-checking cannot prove program validity; it can only detect contradictions between constraints and function bodies early.
  4. **Zero false-positive priority**: Unconstrained generics maintain ADR-33 behavior (skip audit). Cases that cannot be reliably classified, such as `&T`, composite types, or variable shadowing, are skipped and left to per-instantiation checks. False negatives are allowed (errors are still reported at instantiation), but false positives are not (declarations where all types are valid cannot be rejected).
  5. **Differential testing**: Instantiate type-by-type after removing constraints to verify that `bool + bool` is still rejected by the actual type checker while `i64`/`f64`/`string` pass. Then, verify that tightening the constraint (`Copy` → `Add`/`Ord`) allows both declaration and execution to pass. Added 3 unit tests, 2 integration tests (including cross-file `pub fn` reporting at the definition file), `examples/generic_constraints.ae`, and 1 test case for generating C allocation counts.
- **Excluded Approaches**:
  - **Full trait/impl static dispatch**: Requires method tables, orphan rules, visibility, and monomorphization dispatch; not introduced in this round. Documentation still states "traits not yet implemented."
  - **Letting pre-checks replace per-instantiation checks / omitting type checks based on constraints**: Constraints are not proofs; allowing unchecked code would cause memory errors or UB, directly violating default safety.
  - **Inferring constraints from function bodies**: Rejected by ADR-33 (equivalent to type inference and breaks interface stability when function bodies change).
  - **"Probe instantiation" for every allowed type at declaration**: Would pollute `generics.fn_done`/`pending`/function IDs and perform N full parses per declaration, causing a significant regression in compile time.
  - **Free-form operand expression analysis**: Requires a generic AST; currently, only a token stream exists. We conservatively look only at adjacent identifiers, deferring complexity until an AST is available.
- **Behavioral Changes and Migration**: This is a **tightening**. Previously, `fn f[T: Copy](a, b) { return a + b; }` would pass declaration and only fail at the `f[bool]` call site; now, it reports an error at declaration, even if called with `i64`. The reason is that the declaration claims to apply to all `Copy` types, which is not actually true. Migration involves narrowing the valid type set to the capability support set (e.g., `T: Add`, or `T: Add + Copy`), or removing the constraint to revert to per-instantiation checking. Existing `examples/*.ae` and all integration tests have been checked; no existing code is affected by this tightening.
- **Resource Costs (answering §21 acceptance questions point-by-point)**:
  - **Generated C / Executable / Cache**: Completely unchanged. `print(1)` remains 20,352 bytes on both platforms; timing scripts assert that `emit-c` output for two source files of identical byte count (one with constraints, one without) is byte-for-byte identical. No new cache types, no resident processes, no runtime allocations.
  - **CPU/Memory usage**: Zero impact; purely front-end.
  - **Compile speed**: Auditing is a single-pass scan of O(function body tokens), traversing using `&Kind` rather than cloning. `bench/constraint_audit_timings.py` uses two source files of **identical byte count**, differing only by `[T: Add]` and comment padding, to measure `check` alternately in the same script at the same time, asserting byte-for-byte identical `emit-c` output. Archived (`--runs 7`, median): Windows 200 declarations 113.4 / 103.1 ms (diff 10.3 ms), 800 declarations 1433.0 / 1338.8 ms (diff 94.2 ms); Linux 200 declarations 67.6 / 62.1 ms (diff 5.5 ms), 800 declarations 1012.6 / 892.6 ms (diff 119.9 ms). Local load fluctuation is significant (Linux 800 declarations reached 2,910 ms once; independent probes show 200-declaration diffs of 5.5–10.3 ms, 800-declaration diffs of 74.8–119.9 ms). **Report magnitude only, not precise ratios**.
  - **Attribution of differences and boundaries**: **This is an upper bound, not pure audit cost**. The constrained version has 2 more tokens per line, and `GenericFn` still saves a full copy of `tokens` and `source` for each declaration per ADR-31. Its O(N²) copying amplifies token count differences. After removing `Kind` clones within the audit, the 200-declaration difference dropped significantly, and the 800-declaration difference remained almost unchanged, indicating that the 800-declaration portion stems primarily from existing copying rather than the scan itself. The number of generic declarations in real programs is far less than 800. **We do not claim "zero compile-time regression"**, only providing the upper bound, attribution, and hard evidence that "generated C is completely unchanged."
  - **Discovered but unfixed existing bottlenecks**: 800 uninstantiated generic declarations cause `check` to reach ~0.9–1.4 seconds, primarily because `GenericFn` clones the entire token stream for each declaration (O(N²)), which is unrelated to this audit. Changing this to share `Rc<Vec<Token>>`/`Rc<str>` and taking copies only during instantiation could directly improve compile speed, a primary metric; this is listed as a future candidate and not mixed into this feature.
- **Failure and Safety Boundaries**: The audit reads the same token stream and modifies no state; scan failures (e.g., failure to find brackets/function bodies, inability to classify variables) are skipped rather than rejected. If the constraint whitelist and capability table drift in the future, unit tests will fail; even if they drift, per-instantiation checking remains the final line of defense. The fallback is to remove the `audit_generic_fn` call in `collect_functions`; `build`/`run` semantics remain identical to ADR-33.
- **Verification**: Full test suite run on both Windows and Linux, with 14 unit + 138 integration tests passing (3 new unit, 2 new integration); all 25 `--leak` cases passed on both platforms, with exit allocation block counts equal to the baseline of 2 and 0 respectively; Linux `--sanitize` 25 cases passed with 0 reports; all 32 `examples/*.ae` passed `check`; `deps` output is consistent after normalizing line endings (233 bytes); `print(1)` generated C is 20,352 bytes on both platforms; decisions for `float_math.ae` (header removed) and `file_tidy.ae` (header kept) are consistent with ADR-39. Four-scenario timing (`bench/build_timings.py --runs 3`): Windows cold 412.6 / no-mod 118.2 / mod-impl 370.1 / mod-intf 391.7 ms; Linux 36.9 / 4.9 / 35.4 / 36.6 ms. These are whole-process durations and are not compared across sessions with historical archives. Logs, timing JSON, and diagnostic samples at the declaration site are available in `bench/results/2026-11-10-{windows,linux}-w4/`.
