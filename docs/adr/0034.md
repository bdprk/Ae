# ADR-34: Propagating `?` via "Two-Variant Shapes", Applying Same Rules to Option and Result Enums

- **Background**: When `?` was introduced in ADR-21, it only accepted `{ Ok(...), Err(string) }` on the grounds that "failure values must be returned to the caller as-is." However, `Option[T] { Some(T), None }` shares the same shape (one success variant, one payload-less failure variant), and `None` can likewise be returned as-is. Previously, `Option` required manual `match` extraction, forcing boilerplate code at every level for functions like "lookup key that might not exist," which created a disjointed experience compared to the Result enum. In practice, this gap became most apparent with types like `Option[string]` and `Option[vec]`.
- **Decision**:
  1. The propagatable shapes are expanded to two categories: `{ Ok(...), Err(string) }` and `{ Some(T), None }`, with fixed variant names and order. Determination is based solely on the **declared shape**, not on whether the enum is a built-in type—user-defined enums with the same shape behave identically to `Option` and do not require registration in a built-in table.
  2. Code generation is unified to branch on the "failure variant tag": when `tag == AE_E{eid}_1`, release all currently live owned variables and `return` the enum value. In the success branch, move the single payload of `variants[0]` into a binding (`let`) or release it according to its type (for bare statements). Struct/enum/`vec`/`vec[string]` payloads follow their respective release routines; there is no assumption that the payload is a `string`.
  3. A `let`-bound success variant must have exactly one payload; otherwise, an error is reported at the declaration site specifying the actual count. Bare statements allow any number of payloads (all are released). The outer function must return the same enum type, propagation is not allowed in `main`, and `?` remains a statement rather than an expression—these rules remain consistent with ADR-21 and have not been relaxed.
- **Rationale**: The difference between `Option` and the Result enum is semantic (presence of error text), not control-flow related. Allowing both to share the same propagation path reduces user boilerplate and avoids creating a separate syntax for `Option`. Using tags instead of variant names for code generation ensures that "custom isomorphic enums" require no special handling and avoids embedding string comparisons in the generated code.
- **Rejected Alternatives**:
  - **Adding `!` or `??` syntax for `Option`**: Using two sets of symbols for the same control flow only increases the learning curve; `?` already accurately expresses "return to caller on failure."
  - **Determining `Option` by type name**: This would turn built-in enums into privileged types, preventing custom isomorphic enums from being reused, and instantiated type names (e.g., `Option[string]`) are unstable.
  - **Allowing `Err` to carry arbitrary payloads**: The failure value of a Result enum must be returned as-is, and `Err(string)` is the established convention. Relaxing this would mix error text with other payloads; this should be designed separately once a formal error type exists.
  - **Automatic `match` conversion for cross-family results in `?`**: This would require mapping rules between error types, which falls under error model expansion rather than the responsibility of a propagation statement.
- **Consequences and Limitations**: `Option`'s `None` and the Result enum's `Err` share the "return on failure" semantics. The compiler does not distinguish between them, so documentation must clarify that `?` does not attach additional error context. A release sequence is generated at every propagation point; the generated C code will grow longer when there are many owned variables within a function (currently linear relative to the number of variables).
