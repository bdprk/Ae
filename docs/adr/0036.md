# ADR-36: `find` returns byte index via Result, avoiding sentinel values

- **Background**: `contains` only answers "whether it exists"; to locate a match, one currently has to `split` and compare segments or manually scan `bytes()`. The workspace contains a reserved name `find` and a draft `Expr::Find` variant, but lacks parsing branches, code generation, and runtime functions, causing `cargo build` to fail due to non-exhaustive matches. This iteration completes it as a full built-in rather than deleting the draft or leaving a non-compiling half-finished feature.
- **Decision**:
  1. `find(text, needle) -> IntResult`: Returns the **byte index** of the first match; returns `Err("substring not found")` if not found; returns `Ok(0)` for an empty `needle`, consistent with `contains` where an empty substring is considered true.
  2. Views carry an explicit length; use `memchr` to locate the first byte, followed by `memcmp` to compare the remainder. The success path is zero-allocation; the failure path allocates only the `Err` payload string, which is reclaimed by the result enum's destructor.
  3. Both parameters accept `string` or views, borrowing rather than moving; the result is a standard enum that must be `let` bound and then `match`ed, as bare expression statements are rejected by existing rules.
  4. `find` is added to `RESERVED` and cannot be redefined.
- **Rationale**: We avoid using `-1` to represent "not found" because the language delegates "recoverable failures" uniformly to the result enum (as seen in `map_get`, `parse_int`, and `json_int`). Sentinel values allow callers to silently ignore failures, whereas `Err` forces handling. Returning **byte** indices rather than code point indices is chosen because `len`, `slice`, and `bytes` all operate on bytes; character indexing would require a code point table or a full scan, introducing allocations for a read-only query—contrary to our core goal of low memory footprint. `memchr` is a platform-optimized implementation of ISO C11, introducing no third-party dependencies and adhering to the constraint of "strict C11, compilable by any compliant compiler" (ADR-25).
- **Excluded Approaches**:
  - **`Option[i64]`**: Semantically valid, but the existing result family already handles "failure with a reason," and `IntResult` is isomorphic to other fallible built-ins, reducing the number of return types users must memorize.
  - **Returning `-1` / `bool`**: The former is a sentinel; the latter discards positional information.
  - **`rfind`, regex, multi-pattern, code point indexing**: These require new semantics and test surfaces; they will be deferred until requested by real-world workflows.
  - **Refactoring `contains` to use the same `memchr` implementation**: `ae_contains` currently uses `strstr`, which stops at the first NUL when encountering embedded NULs; `find` does not. The behaviors differ and must be documented as such, but modifying `contains` constitutes an independent semantic change requiring separate benchmarking and regression testing, and thus is not included in this iteration.
- **Consequences and Limitations**: The worst-case complexity is O(n·m) (`memchr` skips non-matching initial bytes, making common text near-linear). There is no preprocessing like Boyer–Moore, nor are tables allocated. It is less efficient than mature search libraries for long patterns with many repeating initial bytes; the documentation does not claim this to be an optimal implementation. `contains` and `find` may yield different conclusions on strings containing embedded NULs; this is a known and documented discrepancy. Error text is fixed and does not vary with platform `strerror`. Added `examples/find_text.ae`, 1 end-to-end test (covering UTF-8 byte offsets and 4 rejection cases), and 1 C allocation count test (verifying that the `Err` payload is freed). The Linux backfill in the same commit tree (W1, see `bench/results/2026-11-10-linux-borrow-find/`) elevates this ADR to dual-platform verification: ASan/UBSan reports are clean, and the number of allocated blocks exiting the `Err` branch is zero. This iteration also corrects a statement: example outputs for both platforms are consistent only **after line-ending normalization** (Windows stdout text mode outputs CRLF); the platform matrix has been updated accordingly.
