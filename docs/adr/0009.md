# ADR-9: Summary of End-to-End Cost Measurements for the C Backend and Backend Evaluation Trigger Conditions (Does Not Constitute a Backend Decision)

- Background: ADR-1 established the C11 backend as a replaceable bootstrap solution, stipulating that it "re-evaluates when end-to-end data indicates that external compilation/linking is the primary bottleneck and caching is insufficient to meet targets." This session supplements a tier of evidence required for this judgment (2026-11-10, Windows 10 x64/AMD64, MinGW-W64 GCC 16.2.0 UCRT, Go 1.26.0, rustc 1.99.1, Python 3.10.11, D-drive source workspace):
  - Single-program phase timing (`AE_TIMINGS=1`, two runs per mode, completely fresh empty ae cache directory each time): Frontend + C generation takes approx. 0.37–0.50 ms/run; **single external C compilation + linking takes approx. 0.74–0.81 s/run** (two rounds each for development `-O0` and release `-O2`; output is a single gcc invocation, with compilation and linking undivided).
  - `bench/run.py --cold` two rounds (summing programs with identical differential semantics; the specific implementation order of interpolation varies by round, uncommitted raw JSON is in the session temp directory): Cold build medians are approximately ae 0.75 s and 1.09 s, Go 0.52 s and 0.75 s, Rust 0.14 s and 0.25 s; an earlier block-style run from the same session is archived under `bench/results/2026-11-10-windows-local/` (see `bench-cold.json`, etc., whose recording methodology differs from this round). The first cold sample is significantly larger on Go and ae (~8.7 s / 1.7 s), indicating cold-start/external toolchain state noise; inter-round differences are not pooled, and different rounds are not directly compared.
  - Interpreted as an **observation**: On this host/micro-benchmark/toolchain/cold-cache configuration, the external C compilation + linking phase vastly outweighs the frontend + C generation; however, according to ADR-4, when C generation/optimization/compiler flags/versions/platforms remain unchanged, the content-addressed cache directly reuses the executable, skipping the entire external phase on warm execution paths—a massive cold wall-clock time does not equate to a massive time on every build.
  - **Not established**: Linux measurements (no Linux environment in this session), single-stage CPU time (Windows `resource` unavailable, no GNU time or equivalent substitutes used), peak memory, second C toolchain, scaling curves beyond micro-benchmarks, and ad-hoc experiments with differentiated parameters/module-splitting options. These keep the strength of the evidence at the "observation level."

- Decision: **Maintain ADR-1 unchanged**—the C11 backend + user-machine detected C toolchain remains the default backend; frontend/code generation optimizations and caching (ADR-4) remain independent, on-record levers. This item does not pre-approve any specific alternative backend, nor does it trigger a budget; alternative backends, linkers, or allocators are all subject to standalone project decision-making according to Specification §2 and §12 "out-of-control self-development scope" disciplines.

- Rationale: ADR-1 and Specification §5.2 require "end-to-end data" as the basis for switching, whereas the existing data is an observational snapshot from a single host, single micro-benchmark, single toolchain, uncontrolled external cache, and lacking memory and second-platform data; Specification §5.2 also explicitly notes the risk of benchmark misleading (requiring identical functionality, identical inputs, identical security semantics, and identical version criteria, with raw data preserved). Proportions observed in micro-benchmarks must not be extrapolated as constants (frontend magnitude grows with source scale, while external phases grow with translation units and optimization tiers).

- Consequences and Revisit Conditions (do not re-evaluate until met and fully recorded):
  1. Dual-platform (Windows/Linux) remeasurement using a uniform methodology—consistent with current `bench/run.py`-style interpolation repetitions, environmental and cache state declarations, and recorded repetition counts;
  2. Phased wall-clock + CPU + peak memory measurements (compiler's own profiling, such as GNU time or platform equivalents), including real-scale programs (e.g., file-searching utilities);
  3. Warm path quantification: cache hit rates, and the actual occurrence frequency of external phases under invalidation scenarios (source code/public interface/options/compiler changes);
  4. Candidate backends subjected to two comparable experiments ("fast code generation vs. optimized code generation") per Specification §5.2, alongside completed third-party license and self-developed boundary inventories (§2); self-development routes must evaluate workloads against Win x64 + System V ABI, object files, relocation, stack unwinding, debug information, linking, and instruction compatibility—i.e., the ABI and other coverage areas exemplified in Specification §5.2/§12;
  5. Decision and budget recorded as a standalone project (including fallback plan: revert to the ADR-1 default path upon failure).
