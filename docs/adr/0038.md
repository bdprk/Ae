# ADR-38: Compile Speed Reduction via Input Shrinking, Not Larger Caches or More Translation Units

- Background: §21 W3 requires upgrading the "executable content-addressed cache" to package-level incrementality. Before implementation, we broke down the time taken for a single native cold build on Windows (WinLibs GCC 16.2, `fn main() { print(1); }`): the ae frontend takes about 2 ms, and gcc compiles 109,721 bytes of generated C into an executable in about 1,050 ms. The real bottleneck is neither the frontend nor the number of function calls, but rather that **every program has to parse the entire runtime and the complete `<windows.h>`**: running `-fsyntax-only` on a file containing only `<windows.h>` takes 690 ms, whereas a file containing only `<stdio.h>` takes only 66–82 ms. Under this premise, neither "caching more intermediate artifacts" nor "splitting into more translation units" solves the primary contradiction.
- Three approaches tested and rejected (all data from the same machine, same toolchain, and same session):
  1. **Precompiled Headers (PCH)**: After turning the runtime prefix into `rt.h.gch`, compilation dropped from 1,405 ms to 596 ms. However, the `.gch` file was **69,495,776 bytes**, and generating it took an additional 2.1 s. Trading 69 MB of disk space for 0.8 s conflicts with "low disk footprint", and a separate copy is required for every toolchain/optimization level combination $\rightarrow$ Rejected. This lingering `.gch` was previously picked up automatically by gcc, polluting the measurements for separate compilation (see below); once discovered, it was deleted and measurements were re-run.
  2. **Separate Compilation of the Runtime Package + Caching `runtime.o`, with User Code as a Separate TU**: The true data after clearing the lingering PCH is: single TU 1,060 ms, `runtime -c` 915 ms, single invocation of `program.c + runtime.o` 870 ms, separate `-c` plus linking 769 + 138 ms. In other words, cache hits are only about 18% faster, while a cold build becomes 915 + 870 $\approx$ 1,785 ms (a regression of about 68%). Furthermore, this introduces 68 KB of extra object files, two categories of cache entries, consistency risks for declarations/definitions across TUs, and performance risks where small runtime functions cannot be inlined under `-O2`. An implementation was built and fully verified to run, but **rolled back in accordance with the principle of "no inflated performance claims" and is not retained**.
  3. **Handwritten Minimal Win32 Declarations to Replace `<windows.h>`**: Theoretically saves 600 ms, but precisely replicating the ABIs for structures like `WIN32_FIND_DATAW`, `STARTUPINFOW`, and `WIN32_FILE_ATTRIBUTE_DATA` creates an asymmetric risk-to-reward ratio. We instead adopted the zero-risk `WIN32_LEAN_AND_MEAN` (measured reduction from 690 to 520 ms) and left minimal declarations as an independent work item.
- Decision:
  1. **Make the runtime prefix truly program-agnostic**: Moved the layout of user-defined enums from between `runtime.c` and `runtime_ex.c` to *after* `runtime_ex.c`. Since the latter only references 8 enum IDs from the prelude, the prefix becomes byte-for-byte identical across every program (measured at 108,792 bytes, with identical SHA-256 hashes across four different programs).
  2. **Prune Runtime Functions via Reachability Closure**: Cut the runtime prefix into top-level units (`static ... ae_xxx(...) { ... }` function definitions, along with includes, macros, typedefs, static data, and comments that must be preserved as-is). Root set = all `ae_*` symbols in the program suffix + all symbols in non-function text (macro bodies and static initializers invoke functions indirectly) + the documented embedding entry point `ae_set_allocator` + the transitive closure along `ae_*` references within the bodies of retained functions. Unretained functions have no callers within the compilation unit, and deleting them does not alter semantics. **Identically named definitions under conditional compilation must all be preserved and scanned**: the initial version used a `HashMap<name, index>` that kept only the last definition, causing the Windows branch of `ae_fopen` (which relies on `ae_widen`) to scan the Linux branch's function body instead, resulting in compilation failures for 5 file I/O tests. This was fixed by changing it to `HashMap<name, Vec<index>>`.
  3. **`WIN32_LEAN_AND_MEAN`**: Defined before `#include <windows.h>` in `runtime.c` to exclude unused declarations like Winsock, RPC, and GDI.
  4. **Keep Existing Content-Addressed Executable Cache Unchanged**: Unmodified programs still hit the global cache directly; no new cache categories are added, and unbounded caching is avoided.
  5. **Add `ae deps <source.ae>`**: Outputs the module dependency graph, public interface summary hashes for each module, and the program fingerprint. The summary consists exclusively of `pub` function signatures, struct/enum shapes, and generic declarations; function bodies, private items, and comments do not participate. Measured result: "modifying only function bodies" leaves the fingerprint unchanged, while "modifying `pub` signatures" changes the fingerprint. **This serves as the foundation for diagnostics and subsequent package-level incrementality, but does not participate in any caching decisions yet**, because the backend remains a single translation unit per program. Claiming that this "already achieves rebuilding-free implementation changes for unrelated packages" would be false.
- Rationale: Three core metrics improved simultaneously without trade-offs—compilation input shrank (generated C volume, gcc parsing/optimization workload, and compile-time memory all decreased), runtime semantics remained unchanged (all deleted functions had no callers; no checked arithmetic, bounds, or deallocation paths were disabled), and disk footprint decreased (no new cache required; artifacts remain unchanged or smaller). By contrast, the other two routes trade disk space or cold build time for a marginal improvement in hot build speed.
- Consequences and Limitations: Generated C size changed from 109,721 to 20,273 bytes for `print(1)`, and from 115,802 to 35,179 bytes for `float_math.ae`. Using the archived baseline C (`bench/results/2026-11-10-{windows,linux}-w3/timings.json`—the `emit-c` output prior to changes), gcc compilation times measured over 3 median runs went from 1,030 to 690 ms on Windows, and from 121.8 to 30.6 ms on Linux. Native measurements exhibited noticeable jitter across multiple runs (another Windows round showed 1,331 to 705 ms), so we report only the direction and magnitude rather than claiming a precise speedup ratio. Linux does not include `<windows.h>`, so the pruning gains constitute a larger proportion there. `bench/build_timings.py` records overall process elapsed times across four scenarios: cold build, no modification, implementation change, and interface change (Windows: 772 / 99 / 769 / 779 ms; Linux: 37.4 / 5.6 / 34.3 / 37.1 ms). "No modification" includes `cc --version` and copying the executable; it is not the cache lookup itself (which takes about 2 ms). The closure is **conservative**: function names appearing in comments may cause an extra function to be retained, costing a tiny amount of size without affecting correctness. If function pointer tables or runtime symbols generated via macro concatenation are introduced in the future, such symbols must be explicitly added to the root set. `emit-c` output now varies depending on the builtins used by the program; any external tools relying on a "constant generated C byte count" must migrate to semantic or hash-based checks. Path labels in `ae deps` uniformly use `/`, but case-folding is not performed (case-sensitivity differences between Windows and Linux remain a known platform divergence). **User module-level incrementality, parallel scheduling, and interface-driven invalidation are not yet implemented**; W3 is marked as "Phase 1 Complete" rather than fully complete.
- Verification: The full test suite was run once each on Windows and Linux, with all 9 unit tests and 135 integration tests passing (including 2 new `deps` tests); 24 Linux `--sanitize` test cases PASS with no ASan/UBSan reports; all 24 `--leak` test cases PASS on both platforms, with exit allocation block counts equal to 0 and 2 baseline blocks respectively; all `examples/*.ae` pass `check`; the two outputs of `deps` are byte-for-byte identical after line-ending normalization. Logs and 4-scenario timings can be found in `bench/results/2026-11-10-{windows,linux}-w3/`, and the platform matrix has been updated accordingly.
