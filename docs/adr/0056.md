# ADR-56: Reducing the Map Load Factor from 0.75 to 0.5

- Background: Among the four benchmarks, the map benchmark was the only one that consistently lagged behind—AE at 67.96 ms, Go at 66.73 ms, and Rust at 53.32 ms (with peak memory usages of 2.39 / 7.09 / 2.91 MB respectively). While previous rounds achieved a 2.6x speedup by changing `text` from materialized to lazy, `map` had never been profiled, with only `map_inc` added in ADR-46.
- Attribution (measuring before modifying, breaking down a single round using four probes): `arith` (LCG only) AE 3.76 / Rust 3.57 ms; `key` (adding 1M iterations of `"k" + to_string(...)`) 32.55 / 30.82 ms; `hit` (adding another 1M hit lookups) 60.71 / 55.67 ms; `put` (adding another 1M overwrite puts) 58.27 / 53.76 ms. There are three conclusions:
  1. **Arithmetic is not the issue** (on par), while **key construction accounts for half of the real workload** (1M short string allocations + integer formatting; both languages are on par, with Rust only 6% faster)—key construction is already a single allocation (fused in ADR-44/45), meaning there is no free lunch.
  2. **The gap lies in map operations**: 28.2 ns per hit lookup (Rust 25.1 ns), and 24.8 ns per overwrite put (Rust 24.6 ns). Since Rust uses the much more expensive SipHash, the bottleneck is not the hash function, but the **number of probes**: at a 0.75 load factor, 10,000 keys fall into 16,384 slots (effective load of 0.61), requiring an average of 2.5 probes for linear probing; hashbrown uses SIMD group probing with 16 slots per group, eliminating an entire group in a single check.
  3. We incidentally measured an **independent defect**: `map_get` returns `Err(reason_string)` on a cache miss, allocating a string on every miss—1M cache misses on an empty table added 6.9 ms over the `key` baseline (~6.9 ns per miss), whereas Rust's `Option<i64>` only added 0.5 ms. This was not the target of the current round (`Err` carrying an owned string is a language-level design choice), and is noted as a candidate for the next round.
- Decisions:
  1. Changed the growth threshold from `(m->len + 1) * 4 >= cap * 3` to `(m->len + 1) * 2 >= cap`: effective load factor reduced from 0.61 to 0.31, with the average number of probes dropping to about 1.3.
  2. `ae_str_eq` now uses a byte loop for strings of length ≤ 8 instead of calling `memcmp`: map keys are all shaped like `k1234`, and the fixed overhead of `memcmp` exceeds the comparison itself (accounting for 3.2% of pure lookup probes).
- Rejected Approaches:
  - **5/8 load factor**: Yields only a 1.03x speedup (69.31 vs 67.92 ms) while still consuming 2.58 MB. The gain drops off a cliff at 1/2 (1.17x), indicating that what actually drives performance is the **effective load factor** rather than a continuous curve where "smaller factor is always better".
  - **Storing hash tags within slots** (hashbrown's control byte approach): At a 0.5 load factor, the average number of probes is only 1.3, making the comparisons saved by tags very limited, while the additional 8 bytes per slot would further amplify the memory cost just paid above.
  - **Switching to a faster hash**: Rust uses SipHash-1-3 (which is much more expensive than FNV-1a) yet is faster than us, showing that the bottleneck is not the hash function; FNV only performs 5 multiply-adds for 5-byte keys.
  - **Compressing slots to 24 bytes** (moving status bits into an independent byte array): Would reclaim about 0.2 MB of the extra memory paid in this round and might even be faster (contiguous status array, high cache density), but requires rewriting four places: `put`, `find`, `remove`, and `grow`. The effort-to-reward ratio is unfavorable, so this is left for a future round.
  - **Changing the workload to `map_inc`** (single-lookup): Would make AE's numbers look better, but that would be tampering with the test questions—`bench/map.ae` maintains the explicit shape of "lookup once then write once", aligning with Go's `m[k]=m[k]+1`; Rust uses `entry` as its idiomatic form, and the `map_inc` from ADR-46 is already demonstrated in `examples/map_count.ae`.
- Resource Costs (answering the acceptance criteria in §21 one by one):
  - **Runtime CPU** (Linux, 11 alternating runs, ratios calculated pairwise): Map workload improved from 67.92 to 58.08 ms (**1.172x**, all 11 ratios ≥ 1.12); `hit` probe 1.159x, `put` probe 1.178x.
  - **Peak Memory** (VmHWM, max taken across 7 rounds): Increased from 2.44 to **3.43 MB** (+41%). 32-byte slots and a 0.5 load factor mean a slot overhead of about 64 bytes per element: a table of 10,000 keys grows from 512 KB to 1 MB. For comparison, Rust is at 3.11 MB and Go at 7.55 MB—still in the same tier as Rust, and 2.2x lower than Go.
  - **Cross-language** (Linux release suite, 5 interleaved runs): Map workload AE 57.72 ms / 3.14 MB, Go 58.29 / 7.48, Rust 55.37 / 2.98, Python 236.88 / 9.36. **Shifted from "trailing Rust by 27% and tying with Go" to "faster than Go, trailing Rust by 4%"**; the other three benchmarks remain unaffected (`sum` 0.88, `text` 9.37, `textlazy` 3.64).
  - **Generated C**: `ae_str_eq` +4 lines; `print(1)` remains unchanged (the function is not retained by text programs), and programs with string comparisons increase by about 120 bytes.
  - **Allocations**: No new allocations introduced; the exit block counts for the 30 `--leak` test cases remain at 2 blocks on Windows / 0 blocks on Linux—the code path for freeing the old table during slot table resizing was successfully exercised.
- Boundaries (external claims must not exceed):
  - **Gains are workload-dependent**: Tables with dense probes see obvious gains, while small tables with few keys show virtually no difference; the memory cost, however, applies to all tables (32 bytes per slot + 0.5 load factor). We do not claim 1.17x as a universal speedup.
  - `keys` are sorted by byte order, independent of hashes and slot layouts, so **iteration order and observable behavior remain unchanged**; not a single line of the hash function was modified.
  - We do not claim "maps are faster than Rust": even after this round, we are still 4% slower and use 10% more memory.
  - The allocation of the reason string on `map_get` misses **was not modified**, merely measured (~6.9 ns per miss).
- Verification: 35 Windows unit tests + 163 integration tests, 30 `--leak` test cases PASS (baseline 2 blocks), 37 examples passed via `check`; Linux counts match + `--sanitize` 30 test cases with 0 reports + four-benchmark suite. Added integration test `map_grows_reuses_removed_slots_and_keeps_every_survivor`: 5,000 keys undergoing multiple growths, deleting half, and inserting another 5,000 keys from a different family, verifying surviving values, missing keys, and new keys (covering both growth and tombstone reuse paths, which are precisely what the load factor changes affect). Quantitative conclusions rely solely on Linux: native Windows spawns new processes at ~37–40 ms each, making absolute wall-clock values unusable.
