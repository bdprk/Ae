# ADR-28: Cache Size Limit and LRU Eviction

- **Background**: Item 4 of Phase D requires "configurable cache directory, size limit, viewing, and clearing." While directory configuration and viewing/clearing are already implemented (`AE_CACHE`, `cache dir|clear|stats`), entries currently only accumulate: every single-line source code change generates a full executable (approx. 17 KB on Linux, 62 KB on Windows). Over long-term development, this results in thousands of files, contradicting the initial goal of "low disk footprint."
- **Decision**:
  1. Introduce a new environment variable `AE_CACHE_LIMIT` (in bytes). If unset, set to `0`, or unparseable as a number, **no limit** is applied (typos should not trigger entry deletion).
  2. Perform a cleanup after every successful entry publication: calculate the total size of all entries (executables + manifests). If the total exceeds the limit, delete entries starting from the **least recently used** until the total is within the limit.
  3. "Usage" is tracked by an empty file named `used` within each entry: update its modification time upon a cache hit. If the file is missing, fall back to the executable's modification time (for backward compatibility with legacy entries).
  4. Deletion failures do not constitute a build failure; the entry will simply be deferred to the next cleanup cycle.
  5. Add a `limit:` line to `cache stats` (`none` if unset).
- **Rationale**: LRU is chosen over "oldest creation" or "random" eviction because development access patterns are highly skewed—the program currently under development is hit repeatedly, while dozens of experimental programs from yesterday are never touched again. Evicting by access time preserves the compilation time of "hot" entries, which is the primary purpose of a cache. Using a file's modification time as an access clock—rather than writing counters or timestamps inside the file—avoids the need for extra atomicity guarantees (which would be required if writing to the file changed its content and `mtime`), and avoids inconsistent `fs::utime` semantics across platforms. An empty file's `mtime` is maintained by the filesystem, which is simple and sufficient. The limit is disabled by default because "silently deleting user build artifacts" is more surprising than "consuming some disk space"; users must explicitly set a limit if they wish to control it.
- **Rejected Alternatives**:
  - **Default limit (e.g., 512 MB)**: Would delete entries without the user's knowledge, and reasonable values vary by an order of magnitude across different projects; explicit configuration is more honest than guessing.
  - **Eviction by "oldest creation"**: Could delete entries currently in use, potentially removing the very artifact just compiled.
  - **Recording hits in a central index file (JSON/database)**: Requires handling concurrent writes, crash recovery, and format versioning; using a `used` file per entry avoids these issues.
  - **Background cleanup thread/timer**: CLI tools should not be resident; performing cleanup as a side effect of a build is sufficient.
  - **Automatic cleanup during `cache stats`**: Viewing operations should not alter the state.
- **Consequences and Limitations**: The granularity of cleanup is the entire entry (executable + manifest + `used`), so "partial entries" will not occur. During concurrent builds, cleanup processes might delete entries just published by another process that haven't been used yet (the consequence is a re-compilation, not an incorrect artifact). The limit is calculated in **bytes** and does not account for filesystem block sizes or compression. The `used` file consumes one additional inode per entry. The `bytes` statistic excludes the `used` file and directory metadata, representing a lower bound rather than the exact disk usage.
