# ADR-31: Generic Functions Resolve Their Source Code at Call Sites

- Background: Generic structs (ADR-30) proved that monomorphization works for types "with a layout", but what truly needs reuse is **behavior**: functions like `identity`, `swap`, and `wrap` operate identically across any type. The language features neither type inference nor constraints, so "generic functions" must answer three questions: Where do type arguments come from? When is the function body checked? How do cross-file boundaries work?
- Decision:
  1. Type arguments are written at the call site: `identity[i64](41)`. Omitting them triggers an error prompting their supply—without inference, an entire category of "guessing the wrong type" problems is eliminated.
  2. The declaration records only **locations**: parameter names, the token index of `(`, along with the token stream and source code copy of the file. There is neither a function body AST nor a signature. A `Function` is created only upon invocation, and the function body is re-parsed using a substitution table.
  3. The substitution table (`subst: HashMap<String, Type>`) takes effect at the front of `named_type`, ensuring that any type position outside of `Option[T]`, `Pair[T, i64]`, or `vec` automatically parses according to the arguments. Calling another generic (`wrap[T]`) inside a generic body also works out of the box.
  4. Instantiation uses a **sub-parser**: a new `Parser` is created, sharing the same `functions`/`structs`/`enums`/`generics` (via reborrowing like `&mut *self.functions`), while `file`/`source` point to the declaration file. Consequently, the generic body perceives the visibility context of the **declaration file**—it can invoke private functions within the declaration file, whereas importers can only see the `pub` layer. Cross-file instantiation thus requires no additional mechanisms.
  5. There is only a single set of function IDs: `generics.next_fn_id`. Ordinary functions obtain their numbers from it during the signature collection phase, and instantiation obtains them from it as well. Synchronization between `*next_id` and the counter is achieved via `max` folding, preventing overlapping IDs caused by differing collection orders across files.
  6. The instantiation key is "declaration + argument list", with results cached. Keys currently being instantiated are tracked in `fn_in_progress`, triggering an error upon recursion rather than expanding infinitely.
- Rationale: Storing the function body as **text + position** rather than an unsubstituted AST is the simplest and safest choice here—substitution occurs during the parsing phase, meaning the code generation phase never sees `T`, obviating the need for "generic IR", "type erasure", or "runtime type descriptors". The trade-off is that error messages point to the generic body (rather than the call site), which is an inevitable consequence of per-instantiation checking and more honest than "checking as generic first": a language without constraints cannot prove the legality of `x + 1` at the generic level.
- Rejected Alternatives:
  - **Type inference**: Requires unification algorithms and error recovery. "Guessing when omitted" also makes `identity(5)` and `identity("a")` produce two layouts while looking identical.
  - **Traits/Constraints**: Syntax like `T: Add` requires static dispatch and orphan rules; introducing constraints in the absence of these merely defers checks to runtime.
  - **Preserving unsubstituted ASTs and monomorphizing before code generation**: This would require the entire front-end to maintain an intermediate representation for "type variables", with the sole benefit of bringing error messages closer to the call site.
  - **`&T` parameters**: Borrow parameters currently support only three concrete forms (`&string`/`&vec`/arrays); generic borrows require turning `parameter_type` into a "replaceable borrow", which belongs to the next cycle.
- Consequences and Limitations: Error locations point to the declaration site; `main` cannot be generic; `&T` parameters are not supported; identical argument lists share a single C function (preventing bloat across multiple instantiations); each instantiation is a full parse, making programs with heavy instantiation slower (imperceptible at the current scale, but a fast path of "checking as generic first" will be added in the future). Added `examples/generic_fn.ae`, 1 end-to-end test (covering 6 syntactic constructs that must be rejected), and included the example in the allocation counting test suite for C code generation verification (validating that the path "return a, release b" has no leaks or double-frees).
