# ADR-59: `build` Defaults to Optimized Builds, `--debug` Falls Back to Fast Builds, and Optimization Flags Moved Before the `--` Separator

- Background: The entry point for optimization modes has always been `--release` at the end of the line, with `-O0` as the default. As a result, the two most common commands are counterintuitive: `build` produces artifacts intended for user delivery/distribution, yet it defaults to unoptimized builds; `run` is part of the development loop, yet running it faster every time requires manually appending a flag. In daily usage, "forgetting to add `--release` and shipping `-O0` artifacts" is far more common than "forgetting to request a fast build"—defaults pointing in the wrong direction are much costlier than having no default at all.
- Decision:
  1. **Defaults are determined by the command's role**: `build` delivers artifacts → defaults to `-O2`; `run` is the development loop → defaults to `-O0`. `--debug` is the fast exit for `build`, while `--release` is the optimized exit for `run`; both flags are accepted by both commands (`build --release` explicitly specifies the default, ensuring existing scripts remain unaffected).
  2. **Flag parsing moved before the `--` separator**: Previously, the parser first determined the form based on a fixed length without `--`, and then checked for flags, meaning mixed arrangements like `run file --release -- args` would be rejected. Now, program arguments after `--` are extracted first, followed by identifying flags from the end of the remaining arguments, allowing both ordering styles; unknown flags continue to be rejected (covered by newly added tests).
  3. **Both modes remain the same program, generating the same C code, using the same checking suite**: The only difference is the `-O` level used during C compilation. The cache key already incorporates the optimization mode, so entries for both tiers coexist without overwriting each other.
- Rejected Alternatives:
  - **`build` also defaults to `-O0`, relying on documentation**: A default pointing in the wrong direction is precisely the problem this change aims to fix.
  - **Introducing a third mode name** (e.g., `--ship`): Existing `--release`/`--debug` already cover this; an additional name introduces an extra set of semantics to explain.
  - **Making `run` default to `-O2` as well**: Every modification in the development loop would incur the optimization cost of C compilation (measured at +41–191 ms), conflicting with the use case of "editing a line and instantly viewing the result."
- Resource Costs (`bench/build_levels_timings.py`, 5 rounds of Windows building + 9 rounds of running alternating, fresh cache, archived at `bench/results/2026-11-11-windows-buildlevels/`):
  - **Execution**: `-O2` is 1.294× (textlazy) to 1.664× (map) faster than `-O0`; sum is 1.634×, text is 1.499×.
  - **Building**: End-to-end fresh-cache build takes +40.8 to +191.3 ms longer (14–27 KB generated C, MinGW GCC 16.2.0).
  - **Binary Size**: On the local machine, `-O2` artifacts are actually smaller by 662–1,431 bytes. This trend is recorded factually without generalizing it into a universal conclusion.
  - **Correctness**: Stdout is byte-for-byte identical across both tiers (asserted by script); `--leak` 31 test cases baseline remains unchanged.
- Boundaries (External statements must not exceed):
  - Speedups and build costs are figures obtained from **co-alternating runs, end-to-end including process startup**: Linux serves as the quantitative benchmark (1.34×–4.05×, +12.8–87.4 ms), while Windows is provided for directional reference (1.29×–1.66×, +41–191 ms, where process startup overhead renders absolute values unusable); archives for both platforms can be re-run independently.
  - The observation that `-O2` artifacts are slightly smaller is specific to local MinGW and does not claim that "optimized builds are always smaller."
  - Flags must be at the end of the line: `build file.ae --debug -o out` (with flags sandwiched in the middle) will still be rejected. This is a preservation of the original strict ordering rather than a new restriction, but it must be clearly communicated.
  - No claims are made that "-O2 and `-O0` semantics are completely identical for any arbitrary program": assertions cover the test suite and benchmark workloads; language rules inherently mandate that "development and release behavior must be consistent" (checked arithmetic is not disabled by optimization), a guarantee maintained by the existing test matrix rather than proven anew by this ADR.
- Process Discoveries: Code comments from the previous session cited "1.30x–4.70x, gcc +12–89 ms" from untraceable sources; actual measurements in this round show 1.29×–1.66× and end-to-end +41–191 ms, and the comments have been updated to reflect measured values. The lesson remains unchanged: **numbers in comments must point to re-runnable archives**, otherwise it is preferable to state only the directional trend.
