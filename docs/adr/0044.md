# ADR-44: Literal Concatenation Fusion — Keeping Program Text Out of the Allocator

- **Background**: Hotspot analysis of map workloads (`bench/results/2026-11-11-windows-map-hotspots/`) attributed 76% of execution time to string construction rather than map operations. Code review further confirmed that `Expr::StrLit` emits `ae_str_from` on every evaluation—meaning each literal triggers a heap allocation per evaluation, followed immediately by `ae_str_cat` which releases that buffer—a pure allocator round-trip.
- **Decision**:
  1. The emitter will emit new runtime helpers `ae_str_cat_lit_left` and `ae_str_cat_lit_right` for the patterns `"literal" + expression` and `expression + "literal"` respectively. Literals are treated as C strings and `memcpy`'d directly into the result buffer, while the non-literal side is consumed (released) as usual. The literal side incurs zero allocations and zero releases.
  2. Since literals are pure expressions, skipping their evaluation does not alter semantics. The non-literal concatenation path (`ae_str_cat`) remains unchanged.
  3. Runtime helpers are placed alongside `ae_str_cat`, including the same overflow checks and `ae_fail` failure paths. They are automatically stripped by runtime closure pruning (ADR-38) when unused.
- **Rejected Alternatives**:
  - **Adding SSO or a "static" flag to `ae_string`**: Modifying the struct layout affects every move/release/borrow path and the C ABI; it is not worth the cost for a single hotspot. The principle of single-verifiable-change requires validating gains with smaller modifications first.
  - **Caching released literals**: The release path cannot distinguish between "strings originating from literals" and ordinary strings; caching and then releasing would result in a use-after-free.
  - **`realloc`-style in-place concatenation**: This would change the operand contract of `ae_str_cat` (requiring a growable left operand), and is inapplicable here since the left operand in this workload is a literal (not a heap pointer).
- **Resource Costs (Addressing acceptance criteria in §21)**:
  - **Cold/Incremental/Unmodified Builds**: Additive changes (two runtime helpers + one emission branch); not timed separately, recorded as "unmeasured."
  - **Runtime CPU/Memory**: Same-run comparison (old binary = stash changes and rebuild, 9 interleaved runs, output byte-for-byte consistency assertion): map variant 199.3 → 177.1 ms (11.1% faster), pure string bucket 151.0 → 119.6 ms (20.8% faster). Each "literal + string" operation saves 1 allocation, 1 release, and 1 `memcpy`. See `bench/results/2026-11-11-windows-litcat/same-run-comparison.json` for raw values.
  - **Artifact/Cache Size**: Runtime closure pruning handles unused helpers; no new cache types introduced.
  - **Safety Semantics**: No checks disabled; `--leak` exit blocks on Windows remain at 2 (UCRT baseline) and 0 on Linux (glibc baseline); sanitizers report no issues.
- **Scope**: Only fuses concatenations where "one side is a literal." Heap allocations in `to_string` (H1) and map double-hashing (H4) remain untouched; these are candidates for the next batch. Same-run comparison on Linux was not performed (insufficient certificate window); performance evidence is based on Windows benchmarks, and absolute times are not compared across platforms.
- **Verification**: 31 unit + 148 integration tests passed on Windows, `--leak` 25-case baseline 2 blocks; 31 + 148 tests passed on Linux (same worktree), `--leak` 0 blocks, `--sanitize` reports clean. See `bench/results/2026-11-11-linux-litcat/`. **Dual-platform verification.**
