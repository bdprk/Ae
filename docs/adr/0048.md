# ADR-48: Editor Diagnostics — Structured Output for `check --json`

- **Background**: The final item for W5 is editor diagnostics. `ae check` currently outputs a single line of human-readable `file:line:column: message`; editors must parse this text to extract location information, which is error-prone due to colons appearing in both the message text and Windows drive letters. Furthermore, checks triggered upon saving in an editor should not depend on a full project build—they should not require a C compiler, linking, or caching, provided the frontend semantic checks pass or fail.
- **Decision**:
  1. `ae check --json <file>` (also accepts `check <file> --json`): stdout will contain **exactly** one JSON array. If there are no diagnostics, it outputs `[]` and exits with 0; if there are diagnostics, it outputs an object and exits with 1. **The shape of the array is the contract, not its length**—the frontend is currently fail-fast, so it contains at most one element; future error recovery implementations will only add elements without changing the shape.
  2. Object fields are fixed as `file`, `line`, `column`, and `message`. `file` may be `null` (for in-memory source or non-localized messages), and `line`/`column` are numbers or `null`. If a location cannot be determined, the entire message is placed in `message`, and **no guesses are made regarding the position**.
  3. The location source is the existing `error(file, source, offset, message)` rendering result, split by the last `": "`. Two specific cases are handled: Windows drive letters (where `D` + `\path` is split into two segments by the colon, then rejoined) and cases without a filename (`line:column: message`). If parsing fails, it defaults to "null location + full message"—it is better to provide less information than an incorrect location.
  4. JSON escaping is implemented manually (`"`, `\`, `\n`, `\r`, `\t`, and other control characters output as `\u00XX`): The project maintains zero dependencies and will not introduce a serialization library for a single output feature.
  5. Diagnostics are written only to stdout; timing lines from `AE_TIMINGS=1` still go to stderr. No files are written, no source code is modified, and no C compiler is invoked—`check_path` is simply `load_program`, a pure frontend operation.
  6. The human-readable behavior and exit codes of the default `check` remain completely unchanged; `--json` is simply an alternative rendering of the same check, not a new check.
- **Excluded Approaches**:
  - **Introducing a serde/JSON library**: Violates zero-dependency and binary size goals; manual escaping takes only thirty lines.
  - **Mixing human-readable text and JSON on stdout**: Editors must parse the entire stream; any extra output would break the contract.
  - **LSP server/resident process**: Violates low-resource goals (memory residency, lifecycle management); we provide a stable command that can be invoked on-demand by editors, and will evaluate resident forms separately if there is a genuine need for editor integration.
  - **Reporting multiple errors at once**: The frontend is designed as fail-fast; recovery requires synchronizing all diagnostic paths. Establishing the array contract now allows for incremental updates later without blocking editor integration.
  - **Outputting end columns/fix suggestions**: The frontend only records the starting offset; range information requires token-level refactoring, which is out of scope for this iteration.
- **Resource Costs (Addressing §21 acceptance criteria)**:
  - **CPU/Memory/Disk usage**: One frontend check plus one serialization (tens of bytes to a few KB), no caching, no resident processes, no temporary files; process startup cost is identical to `check`.
  - **Compilation speed**: The main compiler pipeline is unchanged; `--json` only affects the CLI rendering branch.
  - **Artifacts/Caching**: No artifacts are produced, and no new cache types are added.
  - **Security semantics**: No checks are disabled; `check_path` uses the same `load_program` as `check`.
- **Boundaries (Must not be exceeded in external communication)**:
  - Not an LSP, no incremental support, no error recovery (array currently has at most 1 element), only starting positions provided.
  - `message` is display text for humans and is not guaranteed to be verbatim-stable; editors should treat `file`/`line`/`column` as the contract and should not branch based on message text.
  - Do not claim that "checks do not require a build" as a universal fact—it holds true for `check`/`check --json` (pure frontend), but not for `run`/`build`.
- **Verification**: The full suite of commands was run on both platforms, with 34 unit tests and 155 integration tests passing (added 3 JSON escaping unit tests and 1 integration test: two parameter orders, successful `[]`, failure object, Windows backslash escaping). Windows `--leak` 27 cases PASS, 2 baseline blocks; Linux `--leak` 27 cases PASS (0 baseline blocks), `--sanitize` 27 cases PASS with 0 reports. All 34 `examples/*.ae` passed `check` on both platforms; `print(1)` generated C code of 24,034 bytes on both platforms. The five inputs for `check --json` (normal, unknown name, missing file, backslash path, reversed parameter order) and the single-line output of the default `check` are archived in `bench/results/2026-11-11-{windows,linux}-checkjson/json-diagnostics.txt`; see individual `PLATFORM.txt` files for platform details.
- **Issues Discovered and Fixed during Verification**: The integration test initially asserted **unconditionally** that the path contained backslash escaping, which inevitably failed on Linux (where the path separator is `/`; the first Linux run resulted in 154/155). This was corrected to use `#[cfg(windows)]` for asserting escaping and `#[cfg(unix)]` for asserting absolute paths starting with `"file":"/`. Both platforms passed upon re-running. The lesson is similar to the fuzzing lesson from ADR-47: **when assertions contain platform-specific shapes, they must be separated using `cfg`**; one cannot treat Windows shapes as universal facts.
