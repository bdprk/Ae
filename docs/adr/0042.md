# ADR-42: `fmt` only rearranges whitespace; idempotency is guaranteed by construction, full validation not required

- **Background**: W5 (§21) requires `fmt` to be idempotent, preserve semantics, retain comments and string contents, and avoid overwriting user files upon failure. The compiler's lexer discards comments and parses numbers into values, so `fmt` cannot directly reuse the compiler's token stream. Furthermore, the threshold for "validity" determines whether module files (which lack their own `main`) can be formatted.
- **Decision**:
  1. `fmt` is an independent module, `src/fmt.rs`, featuring its own lexer that shares the same boundaries as the compiler's lexer (retaining comments, raw literal text, and the gap/whitespace before each token along with its line number). Unit tests assert that the sequence of token classes for both lexers is identical across all 35 sample sources (a hard constraint to prevent drift).
  2. **Only whitespace is rearranged**: Line structure is preserved line-by-line (no line breaking or merging); spacing between adjacent tokens is determined by "token class pairs"; indentation is determined solely by brace depth. Neither relies on original whitespace; **idempotency is guaranteed by construction**.
  3. Comments, strings (including escapes), and literal spellings are re-emitted exactly as they appear in the source bytes (`1e3`, `007`, and CRLF remain untouched). Trailing comments retain the author's alignment gaps (similar to preserved empty lines); a single space is added to "stuck" `;//` sequences; exactly one newline is kept at the end of the file; no spaces are inserted into empty blocks `{}`.
  4. **Validity threshold = lexable by the compiler's lexer (`check_lexable`)**; full validation is not required. Module files cannot be checked as complete programs. Files with semantic errors that are still lexable can be safely formatted, as whitespace rearrangement does not alter their token or line structure. If a file is not lexable, the process exits with an error, and the file remains untouched.
  5. **Write safety**: All processing is performed in memory. If there are no changes, no write occurs. Writes are performed via a temporary file in the same directory followed by a rename; any failure ensures the original file is never touched.
- **Lessons learned**: Three rule bugs were identified and fixed before commit via `diff` against sample corpora: `var v =[10, 20, 30]` (the "no space before `[`" rule incorrectly affected array literals; narrowed to index/generic arguments following an expression-ending token), `=> { }` (spaces were inserted into empty blocks), and `if ! seed(` (`!` was not identified as a prefix after `if`; changed so `!` is always a prefix). Lesson: **Idempotency assertions hold true even for incorrect rules**; spacing rules must be verified line-by-line against the entire corpus via `diff`.
- **Precise definition of semantic invariance**: We do **not** claim that `emit-c` is byte-for-byte identical. Runtime checks embed source line numbers into the generated C code, and rearranging whitespace shifts these line numbers (though line numbers themselves remain unchanged). Acceptance criteria: token sequence and line numbers remain unchanged + `emit-c` is identical line-by-line after normalizing (ignoring numeric characters) + program execution output remains identical.
- **Excluded approaches**:
  - **Reusing the compiler lexer and modifying `Token`**: Adding comment capture and raw text support to the hot path carries disproportionate risk; equivalence is guaranteed by tests, so sharing the implementation is unnecessary.
  - **AST-level pretty-printer**: Comments would need to be re-attached to nodes; the first version would either lose comments or require complex attachment rules. Token-level rearrangement naturally preserves everything.
  - **Requiring `check` to pass before formatting**: Module files can never pass independently (no `main`), which directly falsifies this requirement for real-world corpora. Semantic validity is not a prerequisite for whitespace rearrangement.
  - **Rearranging line structure / aligning trailing comments / collapsing empty lines**: These are valuable style decisions, but each requires its own rules and acceptance criteria; v1 remains conservative and does not implement them.
- **Resource costs (answering §21 acceptance questions)**:
  - **Cold/incremental/no-op build time**: `frontend` only adds the `check_lexable` gate and `lex_kind_names` for testing; the main flow remains unchanged. Build time was not separately measured for this round (changes are additive and do not touch existing paths), recorded as "not measured."
  - **CPU/Memory usage**: Zero impact; `fmt` does not enter the compilation product path.
  - **Artifact/cache size**: No change; no new cache types or resident processes.
  - **Security semantics**: No checks were disabled; `fmt` does not judge semantics; `check` remains the sole semantic gate.
  - **`fmt` performance**: ~300 ms for 35 files × 2 passes (including process startup, ≈4 ms/pass).
- **Boundaries**: v1 does not rearrange line structure, align trailing comments, collapse consecutive empty lines, or perform directory recursion/configuration file parsing. These are explicit trade-offs, not features of an incomplete formatter. We do not claim that "semantically incorrect files are fixed by `fmt`"—`fmt` only touches whitespace.
