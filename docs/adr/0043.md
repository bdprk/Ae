# ADR-43: Testing via Text-Synthesized `main`, Zero Front-End Semantic Changes

- Background: W5 requires the `test` subcommand to have "explicit failure output and exit codes." The language lacks an attribute/annotation mechanism to mark tests; furthermore, the front-end enforces "exactly one main," and test files without a `main` cannot enter the regular pipeline. We must either add a "test mode" to the front-end or handle it at the driver layer.
- Decision:
  1. Convention `fn test_<name>() -> i64`: Returns `0` = pass, non-zero = fail and uses that value as the exit code; `assert`, checked arithmetic, and other failures retain the existing panic path (stderr line/column + exit 1). Signatures starting with `test_` but violating the expected signature (taking parameters, return type other than `i64`, generics) are treated as explicit errors rather than being silently skipped—mispelled signatures must be reported rather than letting tests quietly fall out of the suite.
  2. Zero front-end semantic changes: Use the compiler lexer for token-level scanning to discover test functions (in declaration order), textually append a synthesized `main` to a **copy of the source file in the same directory** (thus keeping relative `use` paths unchanged), and subsequently route everything through the existing check, monomorphization, C generation, content-addressed caching, and execution pipeline. The copy is deleted in `Drop`, and all failure paths clean it up.
  3. Print `RUN <name>` per test, `PASS <name>` on success, `FAIL <name>` on failure, exiting with the test's return value; print `ok: N passed` if all pass. **Stop on failure** (subsequent tests are not executed) is the v1 behavior, which differs from `go test`'s continuation model and is documented as such.
  4. Rejected suite categories: Files that define a `main` (that is a program, use `ae run`), files without any test functions, and tests with invalid signatures.
- Excluded Approaches:
  - **Front-end "Test Mode"**: Would require relaxing the uniqueness of `main`, modifying function collection and diagnostic paths, and touching the entry points of safety checks; the only benefit would be saving a single textual synthesis.
  - **AST-Level `main` Synthesis**: Requires manually constructing statements, variable IDs, and scopes, leading to tight coupling with parser internals; textual synthesis lets the parser perform all checks itself.
  - **Introducing Attribute Syntax (e.g., `#[test]`)**: The language does not yet have an annotation mechanism, and introducing syntax solely for a subcommand is a major decision independent of this work item.
  - **Return Value Ignored (passing as long as no panic occurs)**: `fn test_a() -> i64 { return 1; }` passing silently is a footgun; non-zero equals failure makes exit codes programmable.
- Resource Costs (answering each of §21's acceptance questions):
  - **Cold/Incremental/Unmodified Build Time**: Changes are additive (new `harness.rs` module, one branch in `main.rs`, `lex`/`Kind`/`Token` visibility relaxed to `pub(crate)`), not timed separately, recorded truthfully as "not measured."
  - **Runtime CPU/Memory**: Artifact paths remain unchanged; the test program is just an ordinary program.
  - **Artifact/Cache Size**: Synthesized sources go through the existing content-addressed cache, with keys incorporating the synthesized text hash; no new cache categories are introduced.
  - **Safety Semantics**: No checks are disabled; the synthesized `main` undergoes complete checking and move/borrow rules alongside user code.
- Boundaries: v1 only collects tests from the entry file (`test_*` in module files are not collected; modules remain pure modules); no filtering, no parallelism, no `--list`, no `--release`; test signature is fixed to `() -> i64`. We do not claim the "test framework is complete" — this is a minimal driver where assertions remain limited to `assert` and result values.
