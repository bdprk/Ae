# ADR-46: `map_inc` Consolidates Counting into a Single Lookup, Defaulting Missing Keys to Zero

- **Background**: H4 of hotspot decomposition—the histogram-shaped `map_get` + match + index-store pattern hashes the same key twice, requires an extra key copy upon a hit, and constructs an error string on the miss path. Counting is the most common real-world use case for maps. All three reference languages provide a single-call idiom (Go `m[k] += d`, Rust `entry(k).or_insert(0) += d`, Python `d[k] = d.get(k, 0) + d`), yet ae previously required users to write it out in three steps.
- **Specification (defined prior to implementation)**:
  1. `map_inc(m, key, delta) -> i64`: Adds `delta` to the count of `key` and returns the **new value**; if the key does not exist, it is treated as starting from 0 (returns `delta` and performs an insertion).
  2. Missing keys **do not return an Err**—this difference from `map_get` is part of the semantics: increment is a read-modify-write compound operation, where absence implies zero. The rule that `map_get` treats "missing as a value, not a sentinel" remains unchanged.
  3. `m` is restricted to map variables or their fields (follows the same "place" rules as `map_get`/`map_put`; moved maps are rejected); `key` must be a string/string view; `delta` must be an i64; the returned new value is an expression and cannot be discarded as a bare call statement (existing language rule: statements that are only calls must be bound or propagated).
  4. Implementation: Single-hash lookup + in-place addition; **zero-copy** for hits, allocation only on the first occurrence.
- **Excluded Approaches**: Returning `IntResult` (turns "absence is zero" back into a two-step process requiring a match, defeating the purpose); `map_update(m, key, fn)` (the language lacks closures); modifying `map_get` semantics (violates existing rules).
- **Resource Costs (answering the acceptance criteria in §21 point-by-point)**:
  - **Cold/Incremental Build**: Addition (new Expr variant, one built-in branch, one runtime function), not timed separately, recorded as "unmeasured."
  - **Runtime CPU/Memory**: Comparison of identical binary API shapes (`bench/map.ae` vs `bench/map-inc.ae`, checksum loops are verbatim identical, output is byte-for-byte consistent, interleaved 9 times): 221.9 → 196.9 ms (**-11.2%**). Machine temperature differs from earlier archives, so only relative values are used; see `bench/results/2026-11-11-windows-map-inc/` for JSON.
  - **Artifact/Cache Size**: `ae_map_inc` is retained only if referenced (ADR-38 pruning); `examples/map_count.ae` added to the generated C test suite (25 → 26).
  - **Safety Semantics**: The "place" moved-check is derived from the same source as `map_get`; `--leak` 26-case Windows baseline remains at 2 blocks.
- **Boundaries**: `map_inc` only covers count increments for i64 values (the only value type currently supported by maps); negative `delta` is valid (can be used for decrementing, and decrementing into negative values is also valid); the four-language twin `bench/map.ae` **remains unchanged**—twins must correspond point-by-point, and the gains from `map_inc` are carried by a dedicated `map-inc.ae` comparison, with the two archives stated separately.
- **Verification**: 31 unit tests + 151 integration tests (3 new `map_inc` integration tests added) passed on Windows; `--leak` 26-case (including `map_count.ae`) baseline at 2 blocks; Linux background forensics: 31 + 151 all passed, 52 cases PASS (including `map_count`), `--leak` 0 blocks, no sanitizer reports; see `bench/results/2026-11-11-linux-map-inc/`. **Dual-platform verification.**
