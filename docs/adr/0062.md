# ADR-62: Add Name Filtering to `ae test` (`test <file.ae> [filter]`)

- Background: The test runner delivered in ADR-43 was "full-scale, sequential, fail-fast". The explicit remaining item after W5 was "filtering/parallelism". In daily usage, re-running the entire suite after modifying a single module incurs a real waiting cost. We are delivering **filtering** first (one-time selection, zero frontend changes), while parallelism will be designed separately.
- Decisions:
  1. **Filtering is a substring of the test name** (following the `cargo test` convention), passed as a positional argument: `ae test file.ae trim`. We do not use regular expressions—substring matching covers 90% of use cases, whereas regex introduces escaping and cross-shell quoting issues.
  2. **Empty matches are errors**: `no test functions match filter 'x'`, with a non-zero exit code. A misspelled filter must not look like all-green—this shares the same origin as the "no false claims" discipline: a tool that passes silently is lying.
  3. **Discovery precedes filtering**: `discover` still performs a full scan and signature validation. Malformed `test_*` functions (parameters, return types, generics) are rejected prior to filtering—filtering must not hide bad tests.
  4. **Explicit error for non-UTF-8 filters**: Test names are UTF-8; non-UTF-8 arguments cannot possibly match, and running everything silently would mask encoding accidents from the caller.
  5. Zero frontend semantic changes: Filtering acts solely on the harness test manifest; the synthesized main only contains the selected tests, and `ok: N passed` counts the filtered set. The check/cache/execution pipeline remains completely untouched.
- Excluded Approaches:
  - **`--filter=NAME` long option**: Positional arguments are muscle memory for cargo/pytest users. Long options are reserved for when multiple parameters are genuinely needed in the future (in this round, the trailing parameter is the filter, making it unambiguous).
  - **Regex/glob**: See Decision 1. Glob's `*` must be escaped in shells, and cross-platform shell differences mean "the same filter command" would be written differently across platforms.
  - **Parallel execution**: Fail-fast sequential output is v1 behavior. Parallelism requires prior design for output aggregation, failure semantics, and resource limits, and will be tracked as a separate work item.
- Resource Cost (Archived in `bench/results/2026-11-12-windows-testfilter/`):
  - **Validation**: 36 unit tests (+1 harness filtering test) + 174 integration tests (test_runner extended by 3 sections) all passed; `--leak` 33-testcase baseline unchanged; 43 fmt files; 41 programs `check`ed.
  - **Compiler**: main.rs branch +2 parameters, harness `prepare` augmented with filter parameter; C code generation is completely unchanged for any program (filtering does not touch code generation).
- Boundaries (External statements must not exceed):
  - Do not claim that "test parallelism / `--list` / coverage" are available: this round only introduces substring filtering.
  - Filtering does not change "fail-fast": the second failure within the selected set still halts execution before running the third.
  - The N in `ok: N passed` is the **filtered** count; do not claim it as the total suite size.
- Validation: Windows 36 unit + 174 integration tests, `--leak` 33 test cases PASS (baseline 2 blocks), fmt acceptance 43 files, 41 programs `check`ed; archived in `bench/results/2026-11-12-windows-testfilter/`.
