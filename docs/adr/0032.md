# ADR-32: `set_cwd` is an Explicit Process-Level Side Effect, `set_env` is Not

- Background: `cwd()` (ADR-24) is read-only for the working directory. File management tools and scripts frequently need to "enter the target directory and then operate," and `run_command` (ADR-29) also inherits the parent process's working directory. Therefore, lacking a write API forces every path to be manually concatenated into an absolute path.
- Decision:
  1. Add `set_cwd(path) -> StatusResult`: returns an `Err` and leaves the directory unchanged on failure, or returns an `Ok` without a payload on success; conforming to the same shape as other filesystem write operations.
  2. Do not implement `set_env`. The reason is a hard constraint rather than laziness: `setenv` is a POSIX interface. Under `-std=c11 -pedantic-errors` (which defines `__STRICT_ANSI__`), glibc does not declare it; testing with `gcc -std=c11 -pedantic-errors` results in an `implicit declaration of function 'setenv'` error. Meanwhile, ADR-25 has already determined not to inject feature test macros like `_POSIX_C_SOURCE`, specifically to ensure that the generated C code can compile on any strict C11 compiler. `chdir`, `mkdir`, and `opendir` are unaffected, which is why only `set_env` is locked out.
- Rationale: The working directory is **a single** process-level state with clear semantics that can be saved and restored (`cwd()` + `set_cwd`), and its only failure mode is "unable to enter." Environment variables, on the other hand, consist of an arbitrary number of names; modifying one affects all subsequent child processes, and there is no natural way to "restore the original state" (the original value might not have existed), making it difficult to express "the environment has changed after this block of code" at the type level. Excluding it is more honest than providing a half-baked, globally mutable environment.
- Rejected Alternatives:
  - **Injecting `_POSIX_C_SOURCE` for `setenv`**: A single line of macro could solve it, but it would invalidate the already-verified property of "strict ISO C," the cost of which far outweighs a single built-in function.
  - **Scoped interfaces like `with_cwd(path, fn)`**: The language does not yet have closures or higher-order functions, making this inexpressible.
  - **Adding a working directory parameter solely to `run_command`**: That only bypasses the problem—file operations still require a relative path baseline. The two can coexist, but the latter does not solve the core requirement.
- Consequences and Limitations: `set_cwd` is a global side effect not visible in the function signature, so documentation must explicitly warn callers at the call site; on POSIX, after `chdir` into a deleted directory, `cwd()` will return an `Err` (true behavior, not masked); lacking `set_env`, changing a child process's environment can only be done via the `env` utility; added 1 end-to-end test (entering a subdirectory, writing via relative path, returning to the original directory, and handling non-existent targets), verified on two platforms.
