# ADR-20: Prohibit Moving Owned Values Out of Outer Scopes Within Loop Bodies (Alternative to Loop Fixed-Point)

- Background: A move occurs only at a specific syntactic position, but **loop bodies are executed repeatedly**. Previously, `while`/`for` loops neither merged move sets nor checked if a move would be read in the next iteration after parsing the loop body. Consequently, such programs would compile successfully and only fail at runtime during the second iteration via a sentinel, with diagnostics pointing to `print(len(t))` rather than the actual error location:

  ```
  var s = "x";
  var i = 0;
  while i < 2 { let t = s; print(len(t)); i = i + 1; }
  ```
  The reported error is `use of moved string` (at line 5, `len(t)`), forcing the author to manually deduce that "s is already an empty handle in the second iteration." Item 2 of Phase C requires the implementation of a "loop fixed-point."
- Decision:
  1. For the three types of loops (`while`, `for i in a..b`, `for x in v`), call `close_loop_moves` after parsing the loop body: calculate the **difference** between the "move set before the loop" and the "move set at the end of the loop body." If any variable **declared outside the loop** appears in this difference, report `cannot move 'x' inside a loop body: the next iteration would read it after the move (re-initialize it before the body ends)`, with the error location pointing to the loop keyword.
  2. Reassigning to the variable before the end of the loop body is permitted: reassignment releases the old value before moving in the new one, which is equivalent to re-initialization, ensuring the next iteration reads a valid value.
  3. Owned values declared within the loop body are unaffected: their moves disappear at the end of each iteration block.
  4. The move set is restored to its "pre-loop" state after the loop finishes—since loop bodies cannot move out outer values, there is no need to merge any parts.
- Rationale: A true fixed-point requires running the "body analysis" until it reaches a fixed point (the Rust approach: allowing moves as long as re-initialization is completed before every usage point). The current architecture is single-pass, emitting statements while parsing; the cost of reaching a fixed point far outweighs the benefits. "Prohibiting moving out outer values" is a **decidable local rule**: it eliminates the entire class of "reading a moved value in the second iteration" errors at once, leaves the rest of the language unaffected, and requires only twenty lines of implementation. The cost is rejecting some technically safe patterns (e.g., moving at the end of a loop body when the value is not used thereafter), which aligns with the "safety over convenience" priority.
- Rejected Approaches:
  - **Conservative union of `if` expressions only** (merging the move set at the end of the loop body into the outer scope): This only solves "usage after the loop," not "reading in the second iteration," which is the actual point of failure.
  - **Running to a fixed point**: This requires separating statement parsing from move analysis (building a CFG before analysis), which belongs to the "CFG + Data-flow analysis" planned for after Phase C. This rule can be relaxed once that infrastructure is in place.
  - **Relying on runtime sentinels as a fallback**: Sentinels can only report "used a moved value" and cannot identify which move caused it, leading to poor diagnostic quality; furthermore, structs and enums lack sentinels entirely.
  - **Allowing moves but inserting runtime resets** (automatically clearing and treating as "uninitialized" after a move): The language lacks an "uninitialized" state; any read would degrade into a runtime error, effectively pushing compile-time issues onto the user.
- Consequences and Limitations: Legitimate cases of "moving out within a loop body but not using it thereafter" are rejected. The move of `v` in `for x in v` already had a separate diagnostic (`cannot move the vector being iterated`); now both checks coexist, with the former being more precise. Incidentally, this corrects a documentation error: `current-language.md` previously stated that `push`/`pop`/index writes remain legal within loop bodies, but the actual implementation (since ADR-12) rejects this because the loop body borrows the container. This has now been updated to reflect the actual behavior.
