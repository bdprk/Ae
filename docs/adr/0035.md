# ADR-35: `&T` Resolves to Existing Borrows During Instantiation, Allowing Direct Forwarding of Borrow Parameters

- **Background**: ADR-31 deferred `&T` parameters to a later phase. Generic functions receiving by value move their arguments: `fn size_of[T](x: T)` consumes a string or vector upon the first call, whereas "measuring length" should not consume the value. Additionally, a discrepancy between documentation and implementation was discovered: `current-language.md` states `&vec` is "re-borrowable," but `fn outer(v: &vec) -> i64 { return inner(&v); }` is rejected in practice (`argument must be vec, found &vec`). `call_arguments` only accepts bare owned vectors, and `Argument::Borrow(var, true)` consistently generates `&v{id}`; for parameters that are already `const ae_vec *`, this results in a double pointer.
- **Decision**:
  1. `parameter_type()` now checks the substitution table after encountering `&`. When a generic is instantiated, `T` is bound to a concrete type; thus, `&T` becomes a spelling for one of the three existing borrows: `string → StrView`, `vec → VecRef`, and `vec[string] → StrVecRef`. For `i64`, `bool`, structs, enums, maps, and arrays, the compiler reports `has no read-only borrow` at the **instantiation site**, pointing to the `&`.
  2. In non-generic contexts, `&Ident` (excluding `string`/`vec`) no longer triggers an `expected '['` error, but instead reports `unsupported borrow type` and lists valid alternatives.
  3. `call_arguments` now allows the argument variable itself to be a corresponding borrow parameter; the boolean in `Argument::Borrow` is explicitly defined as "whether to take the address": for owned vectors, it takes the address, while for borrowed vectors, it passes the pointer directly. Type-mismatched forwarding (e.g., passing `&vec[string]` to `&vec`) remains rejected, and read-only rules (no `push`/write) remain unchanged.
  4. Constraints do not check for borrow capability. `T: Add` allows `i64`, but `&i64` is rejected during instantiation per point 1; constraints remain "call-site argument shape checks" as defined in ADR-33, and their scope is not expanded.
- **Rationale**: Monomorphization (ADR-31) replaces `T` with a concrete type at **parse time**; therefore, `&T` requires no generic IR, lifetime annotations, runtime type descriptors, or new deallocation rules—not a single line of code generation needs to change. The re-borrow fix simply avoids generating an extra `&`, fulfilling the promise in the documentation and enabling composite calls within generic bodies. Limiting borrowable types to the three existing ones is intentional, as the language currently only supports these three read-only borrows; creating "borrow-like" constructs for other types would violate the principle of "not misrepresenting safety properties."
- **Rejected Alternatives**:
  - **`&T` as a return type or struct/enum field**: This requires cross-function lifetime and aliasing rules, which cannot be solved by simply changing the spelling of `Type`.
  - **Unified call-site syntax** (forcing all `&T` to either always use `&x` or never use it): `string` views are passed by value, while `vec` borrows explicitly use `&`—these are existing rules. Instantiating another `&T` template within a generic body cannot satisfy both simultaneously, and changing the syntax would break all existing programs.
  - **Adding `&Struct` borrows to structs/enums**: This requires new field access and deallocation boundaries, which should be designed separately.
  - **Allowing `&T` to cover `map`**: `map_*` operations use `MapPlace` (variables or fields), not parameter borrowing; mixing them would create two conflicting sets of ownership rules.
  - **Checking `&T` at declaration**: Consistent with the principle that "function bodies are only parsed upon instantiation," uncalled generic declarations are not checked; this is an existing trade-off, and we will not break it for a single syntax case.
- **Consequences and Limitations**: When the same generic template is instantiated with different `T`s, the argument shape at the call site changes (e.g., `size_of[string](text)` vs. `size_of[vec](&numbers)`), which must be clearly documented. Consequently, "forwarding an `&T` parameter to another `&T` template within a generic body" is currently only reliable for `string` shapes; other shapes must be written according to their concrete types at the call site.
