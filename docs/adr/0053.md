# ADR-53: Streaming Token Cursor `tokenize`—Zero-Allocation Lazy Splitting per Token

- Background: The `text` workload is the weakest of the four benchmarks—9.94 ms for AE on Linux versus 4.57 ms for Rust. Code reading and empirical profiling attribute this to the fact that `split` must **materialize** approximately 450,000 tokens (ADR-49 reduced the allocation count to 2, but each token still requires writing a pointer and copying bytes), whereas Rust's `split(' ')` is a lazy iterator: it **does not store them at all**. Go's `strings.Split` materializes a pointer array without copying bytes, which makes it slightly slower than us. ADR-49 explicitly excluded "zero-copy tokens" at the time on the grounds that it required lifetime analysis and still entailed a 16-byte/element view array. The true gap lies not in "copying versus not copying", but in "whether it is materialized".
- Key Observation: `for x in ...` only needs one token at a time. That being the case, the container form is wrong—what is needed is a **cursor**: remembering the base string view, the delimiter, and the current position, with each `next` returning a view. Zero allocation, zero copy, and requiring no new lifetime mechanisms: borrow tracking (already in use by ADR-52) is sufficient to ensure that the base string is neither moved nor modified during the cursor's lifetime.
- Decision:
  1. Introduce `tokenize(text, sep) -> token cursor`. The base must be a **storage**: a raw string variable or a string field of a struct variable (following the same rule as `slice_view`), borrowing the **entire variable**; temporary values are rejected (they would be freed before the first iteration). Boundary rules are identical to `split`: trailing empty segments, empty segments from consecutive delimiters, a single empty token for empty input, and non-overlapping matches for multi-byte delimiters.
  2. The cursor is a **value type consumed exclusively by `for`**: `for token in cursor` desugars to `ae_tokens_reset(&c); while (ae_tokens_next(&c, &v)) { ... }`, with the loop variable being a read-only view. It needs to be bound to a raw variable first (following the same style as `for x in vec`), and every `for` loop restarts from the first token, allowing the same binding to be iterated multiple times.
  3. No `len`: counting requires consuming the entire stream, which is precisely what a cursor aims to avoid; use `split` when counting is needed, and error messages should state this directly. The cursor cannot be `print`ed, cannot enter containers/structs, and cannot be used as a return value or argument—type mismatch will reject each case (no syntax can express this type, so struct fields and parameters can never contain a cursor).
  4. **The delimiter is copied into the cursor** (inline 16 bytes): arguments are typically temporary values and are freed at the end of the statement; if only a pointer were stored, the cursor would immediately dangle. Once copied, temporary values can be safely freed, and the cursor holds no ownership whatsoever. Both empty delimiters and delimiters exceeding 16 bytes trigger runtime errors at the call site.
