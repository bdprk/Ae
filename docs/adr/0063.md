# ADR-63: General-Purpose Borrow Checker Design Draft (Phase C Core, Status: Designed, Not Implemented)

- **Background**: Current borrowing is "block-scoped read-only + variable-id granularity + non-escaping" (`resource-model.md` §4). While safe, it is limited in expressiveness: field-level granularity does not exist (a known limitation of ADR-52), borrows cannot be returned or stored, and the survival granularity of generic borrows within loops is the entire block. §21 lists "General-Purpose Borrow Checker Design" as a top priority; this delivery focuses on **design**, not implementation.
- **Deliverables**: `docs/borrow-checker-design.md` — Target model (Loan/Place/Origin, Shared-first then Mut, ordered constraints replacing lifetime annotations, "ambiguous source means rejection" trade-off), expressiveness tiers L0–L5 (independent acceptance for each level: NLL → field granularity → escaping → element borrowing → mutable borrowing), release interaction (no release while borrow is active, no reference counting, borrow safety fully shifted to compile-time), **10 categories of adversarial test case matrices** (write tests before implementation), and progression order with acceptance thresholds (relaxations must include differential baselines).
- **Key Design Decisions**:
  1. **Ambiguous source means rejection**: Functions like `fn longer(a: &string, b: &string) -> &string` that require "choosing one source" are rejected outright (users should return owned values) rather than introducing lifetime annotations—the goal is for users to never need annotations; this is an explicit trade-off, not an oversight.
  2. **Borrow safety fully shifted to compile-time**: The host of an escaping borrow must be proven to have no active loans at compile-time; no runtime sentinels are added. Moved sentinels remain on the ownership path unchanged.
  3. **Reject if loop fixed-point does not converge** (with upper bounds and identification of the specific offending borrow), rather than "guessing the shortest one."
  4. Each level of relaxation must explicitly name which items from the existing rejection set are now permitted, accompanied by a safety argument—"the implementation has become more permissive" is not, in itself, a justification for release.
- **Boundaries (External communication must not exceed these)**:
  - **Do not claim the borrow checker has been upgraded**: The current implementation is consistent with L0 as described in this document; L1–L5 are entirely unimplemented; this document is a design draft.
  - Do not promise "never needing lifetime annotations": While this is the design goal, if the implementation of L3 proves that annotations are necessary, a separate ADR will be established for discussion rather than adding them silently.
  - No timeline provided; one ADR per level + differential baseline + dual-platform support.
- **Verification**: Pure design delivery, no runnable evidence; acceptance is via document review—checked for consistency against `resource-model.md` §4 (current state), ADR-35/52/61 (existing capabilities), and §20.4 item 1 (relaxation discipline); a pointer has been established in `resource-model.md` §10. The implementation phase will proceed according to §6, with each level accepted individually.
