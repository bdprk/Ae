# ADR-24: Standard Input and Working Directory

- Background: `grep_cli.ae` needs to support `grep pattern -` (reading from a pipe). Tools like `pipe_stats.ae` that "calculate statistics on the output of the previous command" are a staple of Unix pipelines. Without `cwd()`, programs can only print relative paths, resulting in unusable fragments like `./a.txt`. Both features belong to the first layer of Phase E ("Process and I/O") and neither requires new types.
- Decision:
  1. `read_stdin() -> ReadResult`: Reads the **entire** standard input and returns a raw byte string. Returns `Err(reason)` on read failure, and `Ok("")` if the input is empty.
  2. On Windows, `stdin` is set to binary mode (`_setmode(_fileno(stdin), _O_BINARY)`) beforehand, so `\r\n` is **preserved as-is** without CRLF translation.
  3. The buffer expands exponentially (starting at 4 KiB). It returns `Err` on `ferror`. No UTF-8 validation is performed during reading, consistent with `read_file` (the language treats byte strings as `string`, with character boundaries checked only at `slice` or `utf8_*` operations).
  4. `cwd() -> ReadResult`: Returns the absolute path of the current working directory. Path separators are normalized to `/` (consistent with `path_join` and `path_parent`). On Windows, `\` characters are replaced with `/` character by character.
- Rationale: `read_stdin` returns `ReadResult` rather than a "raw string" because the other end of a pipe might fail (`EPIPE`, device errors). Silently returning an empty string would cause programs to mistake a "read failure" for "no input"—which violates the core principle that "I/O must not silently discard errors." Binary mode is a hard requirement: `println`-style CRLF translation would make `len(input)` smaller on Windows than on Linux, causing the same statistical code to produce different numbers across platforms—a discrepancy that is extremely difficult to debug after the fact. Normalizing `cwd` to `/` ensures that path concatenation results are readable on both platforms and can be passed directly to the `try_*` series (which already accept `/`).
- Excluded Approaches:
  - **Line-by-line reading (`read_line`)**: Requires streaming handles or an iterator protocol. The current `read_stdin` (reading all at once) already covers pipe statistics and `grep`. Line-by-line reading would introduce issues regarding "when to close" and "who owns the buffer."
  - **`read_stdin` returning `string` and terminating on failure**: Conflicts with the existing design of `read_file` (which is recoverable).
  - **`cwd` returning `string` instead of a result**: `getcwd` can fail (e.g., directory deleted, permission changes). Returning a raw string would force the creation of a dummy value upon failure.
  - **`cwd` preserving Windows backslashes**: Conflicts with the `/` convention used by `path_*` functions, and backslashes require escaping within strings.
  - **Changing the working directory (`set_cwd`)**: Like `set_env`, this pertains to process state and requires a separate design (handling relative path resolution, concurrency semantics); it is out of scope for now.
- Consequences and Limitations: `read_stdin` loads the entire input into memory, making it unsuitable for massive inputs (GB scale). There is no support for timeouts or partial reads. It cannot distinguish whether the input is a terminal or a pipe, other than via `args()` (an `is_tty` check could be added in the future). `cwd` does not resolve symbolic links (it returns the path from `getcwd`, which may contain links). On Windows, the result of `cwd()` does not normalize the case of the drive letter. Adds 3 end-to-end tests (binary byte count and `\r` preservation, empty input, and `cwd` availability) and `examples/pipe_stats.ae`; `grep_cli.ae` now supports reading standard input via `-`.
