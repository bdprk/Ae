# ADR-18: Explicit Exporting with `pub` for Cross-File Visibility

- **Background**: Previously, when a file was imported via `use`, **all** of its top-level functions, structs, and enums became immediately visible to the importer—there was no concept of "internal module implementation." This quickly became a burden in practice: if a `lib.ae` wanted to refactor the name or signature of an internal helper function, one had to first verify that no other file called it. Furthermore, the transitive nature of `use` (if A imports B, and B imports C, then A can also see C) made such verification nearly impossible. Item 3 of Phase B requires "module visibility."
- **Decision**:
  1. Top-level items are **private** by default: only `pub fn`, `pub struct`, and `pub enum` are visible across files. `pub` is strictly a top-level declaration prefix and cannot be used for local items, parameters, or fields.
  2. Files can always access their own private items; the six built-in result enums are held by a `PRELUDE` marker and are public to all files.
  3. Three points of check: function calls, struct literals/construction, and enum literals; type annotations (e.g., `fn f(x: Hidden)`) are also checked during type parsing. Diagnostics point to the **usage site** and suggest: "mark it 'pub' to export it," including the file path.
  4. An additional check at the definition site: if the parameters or return type of a `pub` function are private types within the same file, the compiler reports `public function 'x' exposes private struct 'Y'`. This prevents the inevitably failing combination of "exporting a function while hiding its parameter types" from being caught at the definition site, rather than reporting a seemingly unrelated "unknown type" error at the call site.
  5. Implementation: The shared function table values are changed from a triple to `Signature { id, params, ret, file, public }`. `StructDef` and `EnumDef` are updated to include `file` and `public` fields. The visibility check is a single condition: `public || file == self || file == PRELUDE`.
- **Rationale**: Default-private is the only automated way to "localize changes." Default-public would require every author to remember to add `private`, and forgetting to do so would result in a loss of protection that goes unnoticed. Visibility is attached to the **declaration** rather than the `use` statement (e.g., `use "lib.ae" as m; m::helper()`) because there is currently no namespace syntax. Adding path qualifiers would complicate name resolution, method calls, and C symbol generation, whereas a top-level `pub` simply adds a boolean flag to the existing name table. Checking for private type leakage at the definition site is an instance of the principle that "errors should be reported as close to the cause as possible" (the same principle applied to `?` in ADR-14).
- **Rejected Alternatives**:
  - **Visibility declared by the importer** (`use "lib.ae" priv;`): Visibility belongs to the imported entity; writing it at the import site would cause the same module to behave differently in different files.
  - **Private namespaces isolated by file (symbol mangling)**: This is the complete solution for "every module having its own `helper`," but it requires adding file prefixes to C symbols and resolution contexts to call sites. This belongs to future packaging/interface summary work (Phase D). This ADR focuses on "can it be called," not "can duplicate names coexist."
  - **Granular visibility like `pub(crate)`/`pub(super)`**: There is no concept of a package currently; the only boundary is the file.
  - **Field-level visibility**: Struct fields are indivisible in the language (fields can only be borrowed as a whole); type-level visibility already covers the actual risks.
- **Consequences and Limitations**: Duplicate names across files still trigger errors—two modules cannot each have a private `helper` with the same name. This is the most significant rough edge of this ADR; consequently, `examples/modules/` uses prefixed names (e.g., `count_words`, `line`, `summary`) to avoid conflicts. `pub` adds one reserved keyword (40 total). Visibility only affects name resolution and does not affect generated code: private functions still have unique C symbols, so the ABI and cache keys remain unchanged. Diagnostic text is asserted by content in tests.
