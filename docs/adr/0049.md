# ADR-49: `split`/`lines` Single-Block Arena — Reducing Allocations to Constant Time per Token Count

- **Background**: Variance analysis of the text workload (50,000 lines, 2.59 MB, ~450k tokens) shows that `split` itself accounts for 27.3 ms (61% of the 44.8 ms total), while token traversal is nearly free (-0.4 ms, within noise). Code attribution: `ae_split` calls `ae_str_from_len` once per token (one `malloc` + `memcpy` + NUL write), and the pointer array expands `log2(N)` times due to 2x growth. This is isomorphic to the lesson learned from the map workload—**the bottleneck is string construction, not container operations**.
- **Key Observation**: Elements of `vec[string]` are **read-only borrows** (the language model prevents moving elements out of the vector), so no user code needs to free individual element bytes. The elements of the entire vector can share a single byte region, with the vector assuming unified responsibility for deallocation.
- **Decision**:
  1. Add `char *arena; int64_t arena_len;` to `ae_strvec`. `arena == NULL` indicates per-element ownership (vectors constructed via `push`, `args`, or `keys` remain unchanged); outputs from `split`/`lines` point to the arena.
  2. Add `ae_strvec_borrowed(v, s)`: Use `uintptr_t` to compare whether an element pointer falls within `[arena, arena + arena_len)` (cross-object pointer comparison is undefined in ISO C, but integer comparison is safe). `pop`, `release`, and `clear_slot` only zero out the slot for elements within the arena and do not `free`; the arena is released along with the vector.
  3. Refactor `split`/`lines` into two passes: The first pass counts tokens and bytes; the second pass performs a single allocation for the **exact capacity** of the pointer array and a single byte arena, copying tokens one by one while preserving NUL termination (so `ptr` can still be passed directly to C string APIs).
  4. Scanning path: Single-byte delimiters (the most common cases: `" "` and `"\n"`) use `memchr`, leveraging libc's SIMD; multi-byte delimiters retain bitwise `memcmp`. The original SWAR loop in `lines` is replaced entirely by two-pass `memchr` scanning (this macro is used only in this location).
  5. The emission of `Statement::StrVecStore` in the frontend is changed from direct `ae_str_release(&v.data[i])` to `ae_strvec_clear_slot(&v, i, line, col)`; otherwise, the path that overwrites elements would pass internal arena pointers to `free`.
- **Excluded Approaches**:
  - **Zero-copy tokens (elements pointing to input buffer)**: Requires lifetime/borrow analysis (the existing borrow model only covers three types of views), and the `text` might be released before `tokens`, leading to dangling pointers. The language remains copy-semantic.
  - **Adding an `owned` flag to `ae_string`**: The struct would grow from 16 to 24 bytes, impacting memory footprint and generated code for all strings; vector-level arena range checking is equally correct and avoids modifying this struct, which is passed by value everywhere.
  - **Global arena / Replacing the allocator**: The scope of changes would cover all allocation paths, with asymmetric risk-to-reward.
  - **Exact capacity only (without arena)**: This would only save the `log2(N)` pointer array expansions, which empirical testing shows is far less significant than the per-token `malloc` overhead.
- **Resource Costs (answering §21 acceptance criteria)**:
  - **CPU Runtime**: Windows same-run control (two real binaries, 7 alternations, median): `full` 44.78 → 24.37 ms (1.84x, saving 20.4 ms), `count` 44.83 → 23.62 ms, `read` (read-only file) 16.73 → 16.61 ms (difference within noise, indicating gains come from `split` rather than I/O); `split` cost derived from the same run ( `count - read`) dropped from 28.10 ms to 7.01 ms. Both optimizations had same-run controls: an intermediate build showed **arena-only** reduced `split` cost from 27.3 to 15.0 ms, and adding `memchr` scanning achieved the final 7.01 ms. Linux: `full` 25.08 → 10.22 ms (2.45x), `split` cost 22.28 → 8.86 ms.
  - **Memory**: Number of allocations per `split`/`lines` vector reduced from `N + O(log N)` to 2; pointer array allocated at exact token count (previously power-of-two, up to 2x). **Peak memory sampling was not performed**; no specific peak figures are claimed. The arena retains bytes of popped elements until the vector is released (the cost of block-based release).
  - **Compilation Speed**: Runtime text increased by ~70 lines; one new emission replacement in the frontend; no separate timing performed.
  - **Artifact/Cache Size**: Generated C for `print(1)` increased from 24,034 to 25,134 bytes (+1,100, new arena code and comments), but **executable size remains unchanged** (Windows `-O0` 66,849 / `-O2` 66,893 bytes) — unreferenced runtime units are still stripped by ADR-38 closure pruning; programs actually using `split` (e.g., `split_arena.ae`) increased from 72,960 to 75,301 bytes (+2,341, +3.2%), the honest cost of using the fused path. Cache keys cover generated C, so the first build after upgrade will trigger a full rebuild.
  - **Safety Semantics**: No checks disabled; elements remain read-only borrows and cannot be moved; behavior and return types of `pop`/`store`/`push` remain unchanged.
- **Boundaries (must not be exceeded in external communication)**:
  - Not zero-copy: Each token still copies bytes and includes a NUL terminator;
  - Covers `split` and `lines` only; `push`/`args`/`keys` remain per-element owned;
  - Do not claim "all string processing is faster," nor treat the 1.84x/2.45x text workload speedup as a universal acceleration ratio;
  - Do not treat Windows figures as cross-platform conclusions until Linux same-run controls are verified (this round has added Linux records).
- **Verification**: Full command suite run on both platforms, 34 units + 156 integration tests passed (added 1 arena boundary integration test: non-overlapping scanning for multi-byte delimiters, empty fields, empty input, `lines` CRLF and trailing newline, and `pop`/`store`/`push` combinations); `--leak` 28 cases (added `examples/split_arena.ae`, Windows 2 blocks / Linux 0 blocks baseline), Linux `--sanitize` 28 cases 0 reports; 35 `examples/*.ae` passed `check`; generated C for `split_arena.ae` passed `-std=c11 -pedantic-errors -Werror=return-type -fsyntax-only`; `print(1)` generated C identical on both platforms (25,134 bytes, byte-for-byte match). Linux same-run control: `full` 25.08 → 10.22 ms (2.45x), `count` 23.68 → 10.32 ms, `read` 1.40 → 1.46 ms (within noise), `split` cost 8.86 ms — gain direction and magnitude consistent with Windows, though absolute values are not comparable between platforms; another Linux run of the same implementation yielded 2.31x, indicating this ratio is only an order of magnitude. Logs, control JSON (including 7 raw values), and generated C are in `bench/results/2026-11-11-{windows,linux}-split-arena/`.
- **Real Defects Caught During Verification**: `lines("")` returned a vector constructed with **exact capacity** (0); `push` would then trigger `cap * 2`, attempting to allocate 0 bytes and write to `data[0]`, causing an out-of-bounds write. Fixed by adding a lower bound to expansion (`cap < 4 ? 4 : cap * 2`) and incorporating this shape into `examples/split_arena.ae` (thus also into `--leak` and Linux sanitizer cases) and integration tests. Exact capacity made the "zero capacity" state reachable for the first time; such edge cases only surface after writing tests.
- **Process Lessons**: When establishing baseline binaries, I previously copied the **current workspace's** `runtime.c`/`runtime_ex.c` into the old tree (to avoid `git archive` CRLF issues), which turned the control into "new vs. new." Changed to use `git show HEAD:src/runtime.c` and normalized line endings, and asserted that the old tree contains no new symbols (`grep arena` = 0) before proceeding. **Baseline binaries must be verified to be actual baselines.**
