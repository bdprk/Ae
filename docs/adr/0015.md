# ADR-15: `map[string, i64]` Hash Table

- Background: Phase B of the roadmap requires the language to support "counting/attribution tables keyed by arbitrary strings." Previous primitive alternatives had fatal flaws: `vec[string]` lookups are O(n), causing word frequency statistics (`examples/word_count.ae`) to degrade to quadratic complexity with tens of thousands of words; struct fields are fixed sets and cannot express dynamic keys like "count once per day"; using "sorted pair vectors + binary search" requires manual implementation and maintenance of this invariant at every call site. The file organization workflow in ADR-12/13 has also created a natural requirement for "bucketing by extension/size."
- Decision:
  1. Introduce `Type::Map`, with the only instantiation being `map[string, i64]`; type spelling and built-in names (`map_new`/`map_get`/`map_has`/`map_remove`/`keys`) are added to the reserved word list (37 items).
  2. `m[key] = n;` is a statement (`Statement::MapPut`): the key is copied by the runtime, and the value is an `i64`. Mutability is bound to the container—writing is prohibited after `let m = map_new()`, consistent with `vec`.
  3. Queries return a **result value** rather than a "sentinel 0": `map_get(m, k) -> IntResult` returns `Err("key not found")` when missing. `keys(m)` returns a sorted **copy**, and `len(m)` returns the number of entries.
  4. The receiver can be a raw map variable or its struct field (`MapPlace::{Var, Field}`), but not an arbitrary expression: "temporary maps" like `map_get(build(), k)` are meaningless (the table would be freed immediately), and restricting this at the syntax level is clearer than runtime checks.
  5. The runtime is implemented using open addressing with linear probing: FNV-1a hashing, three-state `EMPTY/FULL/DELETED`, using tombstones upon deletion to maintain probe chain integrity, and doubling capacity with tombstone clearing at a 3/4 load factor. Expansion buffers use `malloc + memset` rather than `calloc`—`--wrap` only wraps `malloc/free/realloc`; if `calloc` is used and then returned via the wrapped `free`, it is counted as an "unknown block" and corrupts heap consistency (this is a real failure encountered during implementation, recorded here to prevent recurrence).
- Rationale: `map_get` returns `IntResult` instead of `i64` because 0 is a valid count; "missing" and "count of 0" must be distinguishable—this is the most common source of errors in C-style map APIs, and the language already has a ready-made result enum (ADR-11), making its reuse zero-cost. `keys()` copies and sorts to ensure that "iterating over a map" produces **identical output order** on both platforms: hash order varies with implementation and insertion history, and exposing it directly would pollute all output and tests. Only `string → i64` instantiation is provided because there are no generics (a post-Phase B item); putting `vec`/`string` values into the table would immediately introduce the complexity of "who frees the payload in the slot," whereas `i64` values make the table a pure POD container, where freeing only requires traversing the keys.
- Excluded Approaches:
  - **`map_get` returning `i64`, with 0 for missing**: Cannot distinguish from a real 0; word frequency statistics would conflate "not present" with "appeared 0 times."
  - **Iterators/`for k, v in m`**: Requires a new borrowing iterator protocol and static checks to "forbid modification during iteration"; taking a snapshot via `keys()` is the only safe form under current move semantics that requires no new rules.
  - **Instantiations other than `map[string, i64]` (e.g., `map[string, string]`)**: Without generics, this would require manual templates and would immediately necessitate "freeing values owned within slots"; deferred until after generics.
  - **Chaining**: Each slot would require an extra pointer and allocation, resulting in poor cache locality, which contradicts the low memory footprint goal of §4.5; the cost of tombstones for linear probing is acceptable.
  - **Rehash in place**: Implementation is complex and involves intermediate inconsistent states; doubling + rebuilding two arrays is simpler and remains amortized O(1).
- Consequences and Limitations: Only `string → i64` is supported; maps cannot be traversed directly (use `keys()`, at the cost of an O(n log n) copy); deletions leave tombstones, so the bucket array will not shrink during long-term "insert-delete" cycles (tombstones are cleared during expansion); `keys()` sorting is byte-wise rather than locale-aware. Maps are owned values, with move semantics consistent with `string`/`vec`; the runtime uses a null pointer sentinel for `slots`; maps within struct fields are freed along with the struct. New end-to-end tests cover insertion/overwriting/deletion/missing queries/key order/struct fields/misuse rejection; `examples/word_count.ae` serves as the acceptance example, with allocation counts consistent with the baseline (`blocks=2`).
