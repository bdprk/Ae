# ADR-54: Convert command-line arguments to UTF-8 on Windows in `args()`

- **Background**: While writing the benchmarking script for ADR-53, passing absolute paths of temporary directories (e.g., `D:/用户/...` in addition to `C:/Users/trevv/AppData/Local/Temp/...`) to the program under test resulted in a `cannot read file` error. Further investigation narrowed it down: **any path on Windows containing non-ASCII characters** fails to open, including relative paths; however, Chinese literals in the source code work perfectly. Since the developer's own home directory is `D:/用户/...`, this is not an edge case—the most basic usage, such as `ae prog.ae -- <path>`, is broken in Chinese-language directories.
- **Root Cause**: The Windows CRT passes command-line arguments to `main` according to the **ANSI code page (CP_ACP)**. Consequently, "Chinese directories" enter the program as GBK bytes (measured `len(args()[1])` = 8). Everything else in the language is UTF-8: the runtime treats the path as UTF-8 and calls `MultiByteToWideChar(CP_UTF8, …)` before passing it to `_wfopen`. The GBK bytes are decoded into incorrect characters, causing `_wfopen` to attempt to open a non-existent path.
- **Decision**: In `ae_args()`, convert each argument from **CP_ACP → UTF-16 → UTF-8** (using `MultiByteToWideChar` + `WideCharToMultiByte`). In case of failure (theoretically only possible due to out-of-memory), fall back to the original bytes to ensure the arguments remain usable. After the fix, the same argument is 12 bytes (UTF-8), and both path reading and writing succeed.
- **Excluded Approaches**:
  - **Using `__wgetmainargs` to retrieve the raw UTF-16 command line saved by the CRT**: This is the ideal solution (it retrieves the full command line regardless of the code page and avoids dependency on `<windows.h>`), but it triggers a **segmentation fault** on this MinGW-w64 + UCRT toolchain—UCRT only maintains that data within its own startup path. Documented here to prevent others from attempting this path again.
  - **Parsing `GetCommandLineW` manually**: Windows' quoting/escaping rules are highly nuanced; re-implementing them carries more risk than reward.
  - **Writing a custom UTF-16 → UTF-8 encoder to avoid `<windows.h>`**: The ACP → UTF-16 step still requires Win32 APIs, making it unavoidable.
- **Resource Costs**:
  - **Runtime**: Each argument incurs one short-lived temporary buffer (tens of bytes, freed immediately after conversion); no new resident memory or new allocation types.
  - **Compilation Speed**: Programs calling `args()` on Windows will retain `<windows.h>` (required for the Win32 conversion). Measured on a probe program that only reads arguments, the generated C code size increased from the 15.5 KB level to 16,317 bytes, with an additional header parsing overhead (approx. 30 ms). **Programs that do not use `args()` are unaffected**: `print(1)` remains 11,299 bytes and still includes `/* windows.h omitted */`; `float_math.ae` also strips the header (after ADR-55 goes live, `print(1)` will be 15,243 bytes, with header pruning behavior unchanged). This cost is accepted because, without it, programs cannot open their own arguments.
  - **Security Semantics**: No checks were disabled; the conversion only changes the byte representation and does not alter any visible behavior (ASCII arguments remain byte-for-byte identical).
- **Boundaries (Must not be exceeded in external communication)**:
  - When the command line enters `main`, it is **already** ANSI bytes. Characters not representable in the code page (e.g., certain emojis) are already lost at the CRT stage; this fix cannot recover them. True UTF-16 requires using the CRT's own startup path, which is unavailable on the current toolchain.
  - Only `args()` is modified. `env()` already uses `GetEnvironmentVariableW` followed by a conversion to UTF-8; source code literal paths have always been UTF-8; `run_command` child process arguments use `CreateProcessW` and remain unaffected.
  - Do not claim "all encoding issues are solved": console output encoding, the path of `AE_CC` itself, etc., remain separate topics.
- **Verification**: 35 Windows unit tests + 161 integration tests (added `program_arguments_arrive_as_utf8_on_every_platform`: passing an absolute path containing Chinese as an argument, `write_file` + `read_file` succeeds; and asserting `len(arg)` is 12 instead of 8). **The test fails as expected after rolling back the fix** (verified via `git stash`). The `--leak` baseline for 30 test cases remains unchanged (2 blocks on Windows), and all 37 examples pass `check`. The same number of tests pass on Linux (POSIX `argv` is UTF-8 by default; the test case there verifies that "new code does not break existing behavior"). Logs are available in `bench/results/2026-11-11-{windows,linux}-argv-utf8/`.
