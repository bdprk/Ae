# ADR-45: Stack-Based Number Formatting Buffer for `to_string`, Enabling Zero Heap Allocation in Literal Concatenation

- Background: After ADR-44 eliminated allocations for literals, H1 in hot-spot breakdown became the primary remaining bottleneck: `"k" + to_string(n)` still requires a heap allocation for the number string, followed immediately by a deallocation during concatenation. Since a number string is a temporary value that does not outlive the current expression, allocating memory for it violates the intuition of "no memory ownership if the temporary is short-lived."
- Decision:
  1. Add a new runtime function `ae_int_to_buf`: formats an i64 into a ≥24-byte stack buffer provided by the caller using **the exact same `snprintf` format string** as `ae_to_string`, and returns its length. This provides a single source of truth for formatting logic while bypassing heap round-trips.
  2. Extend the code generator to go one layer deeper within the two literal concatenation branches of ADR-44: when the other side is a `to_string(i64 expression)`, emit `ae_str_cat_lit_buf`/`ae_str_cat_buf_lit` instead (literal + stack-allocated number → result buffer, requiring exactly one allocation for the entire operation). Internal expressions continue to be evaluated in their existing order.
  3. All other usages of `to_string` (standalone bindings, container keys, etc.) remain unchanged and continue to return owned strings.
- Alternatives Considered and Rejected:
  - **Make `ae_to_string` return a stack buffer**: The return type is an owned `string`; changing this contract would alter the ownership semantics.
  - **Add Small String Optimization (SSO) inline buffers to `ae_string`**: Modifying the struct layout impacts all deallocations, moves, and the C ABI; this was rejected for the same reasons as in ADR-44.
  - **New built-ins like `map_inc`** (H4, dual-hashing + key copying): This is a genuine language API evolution that requires a separate specification and acceptance process, and should not be shoehorned into this change.
- Resource Costs (addressing each acceptance question in §21):
  - **Cold/Incremental/Unmodified Builds**: Additive changes, not timed individually; recorded as "not measured."
  - **Runtime CPU/Memory**: Same-run comparison (old = e77eec6, new = e77eec6 + this change; interleaved 9 times, outputs byte-for-byte identical): map variant 176.8 → 152.5 ms (13.7% faster), pure string bucket 132.0 → 88.1 ms (33.3% faster). Cumulative changes since initial baseline: map variant 199.3 → 152.5 (-23.4%), string bucket 151.0 → 88.1 (-41.7%). The new map run exhibited two hot-noise outliers (230/210 ms); raw values are fully preserved, and medians are reported. See `bench/results/2026-11-11-windows-intbuf/same-run-comparison.json`.
  - **Artifact/Cache Size**: Unused helpers are pruned by the runtime closure process. Note that mentioning function names in comments retains an extra function (a conservative behavior already documented in ADR-38; since this round generates C code, it includes an uncalled `ae_to_string` definition, resulting only in a size penalty).
  - **Safety Semantics**: No checks disabled; `--leak` exit block count on Windows remains 2.
- Scope/Boundaries: Covers strictly the "literal + `to_string(i64)`" shape; adding two `to_string`s together, or a variable + `to_string`, still falls back to ADR-44/original paths. Linux correctness verification runs in the background (certificate windows shortened multiple times; evidence collected via `nohup` + later retrieval). If incomplete by the time of submission, this ADR will record "Windows verified, Linux pending backfill."
- Verification: Windows 31 unit tests + 148 integration tests all passed; `--leak` 25-test baseline 2 blocks; emission assertions (generated C contains `ae_str_cat_lit_buf`, with no `= ae_to_string(` calls). Linux (`nohup` background evidence collection) 31 + 148 all passed, 50 test cases PASS, `--leak` 0 blocks, sanitizer reports clean, see `bench/results/2026-11-11-linux-intbuf/`. **Dual-platform verified.**
