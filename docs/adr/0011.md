# ADR-11: Recoverable Errors Expressed via Predefined Result Enums; `+` Copies Borrowed Strings

- Background: Section §4.5 of the proposal requires that "recoverable errors use result values and must be handled or explicitly propagated; I/O interfaces must not silently drop errors," whereas previously a `read_file` failure could only terminate the process. Following the implementation of enums (ADR-10), result types can be defined within the language, but generics are not yet available, making it impossible to write a generic `Result<T, E>`.
- Decision:
  1. The compiler predefines three result enums for every program, which users can reference without importing: `ReadResult{Ok(string), Err(string)}`, `WriteResult{Ok(i64), Err(string)}`, and `IntResult{Ok(i64), Err(string)}`. The variant order is fixed (`Ok = 0`, `Err = 1`) and cannot be redefined.
  2. Added fallible builtins `try_read_file(path) -> ReadResult`, `try_write_file(path, content) -> WriteResult`, and `parse_int(text) -> IntResult`; failure reason strings come from `strerror` or builtin messages ("not a base-10 integer", "integer out of i64 range"). `parse_int` is strict: it permits an optional sign, allows only ASCII digits, must consume the entire string, and checks bounds against `INT64_MAX`/`INT64_MAX+1` for positive and negative numbers respectively, never performing silent truncation or wrapping.
  3. Added `to_string(i64) -> string`, which forms a round-trip with `parse_int`.
  4. `+` accepts owned `string`, `string view`, struct string fields, and `vec[string]` elements: **owned operands transfer their buffers (`ae_str_cat` frees both), while borrowed operands are copied before concatenation**, leaving the original borrows unaffected and still usable.
- Rationale: `str_cat` frees both operands, so passing a borrow directly into it results in a double-free—a real bug discovered during testing this cycle (`print("file " + parts[0])` triggered heap corruption `c0000374`). Treating it uniformly as "transfer if owned, copy if borrowed" is less error-prone than manual `slice` calls at every call site, and makes common scripting patterns like `"prefix: " + args()[1]` valid code. Since views can be concatenated, `slice(x, 0, len(x))` is now reserved solely for cases where a copy is explicitly required.
- Alternatives Considered and Rejected:
  - **Changing `read_file` to return a result value**: This would break existing programs and benchmarks; preserving the "fail-and-terminate" semantics of `read_file`/`write_file` while introducing dedicated `try_*` functions clearly distinguishes between recoverable and unrecoverable errors, aligning with §4.5's division of labor ("panics are for unrecoverable errors").
  - **Global `last_error()` + returning an empty string**: Empty files and failures would become indistinguishable, and this introduces implicit global state.
  - **Implementing generic `Result<T, E>` in the compiler**: Generics have not been designed yet; we use three concrete enums as a temporary measure, which will be migrated to generic types in the stdlib module once generics are implemented (this record documents this pre-migration intermediate state).
  - **`+` returning a view for views**: Views require lifecycles, and the result of `a + b` typically needs to outlive both operands, which cannot be made safe.
- Consequences and Limitations: The three predefined enums permanently occupy enum IDs 0–2, and their C layout and drop functions are always generated (resulting in a negligible size overhead when unused); the predefined type names and `try_*`/`parse_int`/`to_string` become reserved names and cannot be redefined by users; since the subject of a `match` expression must be a bare variable, result values must be bound with `let` first; error message texts vary with the platform's `strerror` localization, and programs should not rely on their exact content.
