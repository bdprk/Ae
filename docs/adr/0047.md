# ADR-47: trait/impl Static Dispatch — Resolved at Instantiation, No Method Tables

- **Background**: The remainder of W4. The call-site shape checking from ADR-33 and the declaration-site capability auditing from ADR-40 only cover four built-in constraints (`Add`/`Eq`/`Ord`/`Copy`). User-defined capabilities (e.g., "calculable area") cannot be expressed, and generic bodies cannot invoke functions that vary based on type parameters.
- **Design** (Fixed prior to implementation, each point has a mechanistic basis):
  1. **Syntax**: `trait Name { fn method(first: T, ...) -> R; }` declares a capability (no method bodies, no default implementations); `impl Name for Type { fn method(...) -> R { body } }` provides a concrete implementation. The type parameter for a trait is fixed as `T` (implicit); the **first parameter of the method must be `T` by value**, while other parameters and return values can be `T` or concrete types.
  2. **Static Dispatch = Resolution at Instantiation**: Generic bodies are re-parsed at each instantiation with `subst` per ADR-31. When a non-ordinary function call is encountered, `resolve_trait_call` searches for the mangled signature `Trait#method#TypeName` (using `trait` + `method` + substituted parameter type; `#` is non-lexical, preventing collisions with user identifiers). A hit results in emitting the ID of the `impl` function (`ae_fn_{id}`) as an ordinary call. **There are no method tables, no function pointers, and no runtime dispatch**—the dispatch result is simply a direct call.
  3. **Instantiation-site Checking**: `instantiate_fn` checks the `impl` registry for every trait binding. If missing, it reports `no impl of trait 'X' for 'Y'; required by 'Z'`, reporting the error at the same point as type checking for each instantiation.
  4. **Coherence (v1 shape)**: `impl` blocks can only be written in the **file where the trait is defined or the file where the type is defined**; third-party files are rejected. The `(trait, type)` pair must be unique per program. Budget: 64 traits / 256 `impl`s per program.
  5. **Visibility**: `pub trait` allows cross-file references (following the same rules as functions). An `impl` is registered once the file containing it is loaded via `use` (loading is a side effect of registration; no items need to be explicitly called from it).
- **Excluded Approaches**:
  - **Rust-style method syntax and `self`**: The language lacks method-call syntax; introducing it for traits is a major, independent decision.
  - **Generic `impl` (`impl Area for Pair[K,V]`) and `&T` trait parameters**: The landing shape for `&T` only supports three types of borrowing (ADR-35); borrowing semantics for trait signatures require independent design. v1 rejects all such cases with explicit errors.
  - **Default method bodies**: `impl` must provide all methods; default bodies introduce override-order issues, and we will not introduce them without evidence of necessity.
  - **Dynamic dispatch / trait objects**: Contrary to the runtime goals of "no GC, deterministic release, direct calls"; will never be the default.
  - **Declaration-site pre-checking of trait calls** (ADR-40 style): Capability auditing scans for operator capabilities; reporting missing trait calls at the instantiation site is sufficiently early and provides more accurate information (via `required by`). Declaration-site scanning is deferred until there is evidence of actual false negatives.
- **Resource Costs** (Addressing §21 acceptance criteria):
  - **Cold/Incremental/No-change builds**: Additive (new keywords, trait/impl pipeline passes, one parsing branch); not timed separately, marked as "untested."
  - **Runtime CPU/Memory**: Zero added overhead—dispatch is a direct call. Differential testing asserts that calls via traits produce the same output as handwritten functions (`traits.ae` line 3).
  - **Artifact/Cache size**: `impl` functions are treated as ordinary functions during C generation. Unreferenced trait/impl functions are handled by ADR-38 closure pruning. `examples/traits.ae` added to the C generation test suite (26 → 27).
  - **Safety semantics**: No checks disabled; move/release semantics remain unchanged during instantiation (Rect is moved into the `impl` method by value; `traits.ae` leak baseline remains unchanged at 2 blocks).
- **Boundaries** (External statements must not exceed these):
  - Trait methods **cannot be called directly outside of generic bodies** (use ordinary functions for `impl` behavior outside of generics);
  - Trait signatures do not support `&T` or generic `impl`s; no default methods; no dynamic dispatch; no method-call syntax;
  - Missing trait calls are reported at the instantiation site, not pre-checked at the declaration site;
  - Diamond imports are already rejected by the module system's circularity rules; therefore, placing `impl` in the same file as the trait or type is the only currently composable cross-file layout—the "impl in the same file as the type" pattern is valid, while "independent `impl` module + main directly linking to trait file" is not;
  - We do not claim a complete Rust-style trait system (associated types, `where` clauses, conditional implementations, etc., are not designed).
- **Verification**: 31 Windows units + 154 integration tests passed (3 new trait integration tests: dispatch/eight categories of rejection/cross-file coherence); `--leak` 27 cases (including `traits.ae`) baseline 2 blocks; fmt acceptance 37 files 0 changes (trait/impl syntax is idempotent); fuzz testing caught and fixed a deep underflow in the pre-scan for malformed input (`saturating_sub`; lesson: scanning must tolerate arbitrary input before validation).
