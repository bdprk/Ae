# ADR-50: Runtime Comments Trimmed with Functions; Names in Comments No Longer Treated as Dependency Roots

- Background: The archiving of ADR-49 showed that the generated C code for `print(1)` grew from 20,352 to 25,134 bytes, despite the new code itself being only a few dozen lines. Investigation revealed two intersecting issues: `runtime_units` left `//` comments **above** functions in "non-function text," and this text was preserved indefinitely; more critically, `ae_symbols` scanned all `ae_*` names within the **retained text** to compute the dependency closure—consequently, function names mentioned in comments were treated as dependency roots, pulling entire functions into every generated program. The more runtime comments existed, the more severe the over-retention became.
- Key Observation: Comments are not dependencies, nor should they consume bytes in the generated C code. By associating comments with the function units they explain, both the false roots and the excess binary size vanish.
- Decision:
  1. Add a `lead` buffer to `runtime_units`: Consecutive `//` comments and blank lines in non-function regions are first recorded in `lead`, and merged into a function unit when a function definition is encountered; when a genuine non-function code line (`#include`, `typedef`, macro) is encountered, `lead` is flushed back to `pending`.
  2. Multi-line `/* */` comments remain in `pending` across the board: File headers and section banners do not disappear with the first pruned function; `/* win32-header */` markers naturally reside within function definition lines, so their semantics are unaffected.
  3. Do not modify the scanning rules of `ae_symbols`: It still inspects comments within retained units (conservatively retaining at most a little extra), but pruned functions disappear along with their comments, eliminating the false roots accordingly.
- Rejected Alternatives: Globally stripping comments before compilation (would lose markers and readability); performing dependency analysis based on comment content (comments should never be dependencies); trimming only `//` lines while retaining blank lines (blank lines also consume bytes and are thus attributed alongside).
- Resource Costs (answering each acceptance question in §21):
  - **Generated C**: `print(1)` dropped from 25,134 to 11,105 bytes (−55.8%). String programs still retain the required `ae_str_from`/`ae_str_eq`, and output remains unchanged—pruning follows reachability, not size.
  - **C Compilation Time**: For the generated C of the same `print(1)`, `gcc -std=c11 -O0 -c` dropped from 164.35 to 143.18 ms (−12.9%, median of 7 alternating runs).
  - **End-to-End Cold Build**: `ae build examples/hello.ae --release` with a fresh cache each time, dropped from 420.59 to 378.95 ms (−41.6 ms, −9.9%, 7 alternating runs).
  - **Artifacts/Cache**: Executable size remains unchanged (what was trimmed was dead code that the linker would discard anyway); cache keys cover the generated C, so the first build after upgrading will rebuild everything once.
  - **Safety Semantics**: No checks were disabled.
- Boundaries (external statements must not exceed): Do not claim "compilers are universally 10% faster"—this is a **constant gain per program** (compiling roughly 14 KB less text); the larger the program, the smaller the percentage. Do not claim peak memory changes (not sampled). Comments on retained functions will still appear in the generated C.
- Verification: 35 unit tests + 157 integration tests (including 1 new unit test for comment attribution: `//` comments merged into functions, comments preceding non-function code remain in persistent text, `/* */` not merged), 28 `--leak` test cases, Linux `--sanitize`, 35 examples; `bench/prune_timings.py --old-exe <pre-ADR-50> --runs 7` can be rerun. Logs and control JSONs are located at `bench/results/2026-11-11-{windows,linux}-prune-comments/`.
