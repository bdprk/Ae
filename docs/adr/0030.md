# ADR-30: Monomorphization for Generic Structs Using the Same Approach as Generic Enums

- **Background**: Generic enums (ADR-21) address the scenario where "a value could be either A or B," but **paired/grouped** data relationships still rely on parallel variables or vectors. Structures like `Pair[K, V]` or `Map.Entry` are unavoidable in a systems language, yet `struct P[T]` previously triggered a "not supported" error during parsing. Furthermore, generic structs are the first step toward `Result[T, E]` and generic functions: we must first prove that monomorphization works for types with defined layouts and release logic before applying it to code blocks.
- **Decision**:
  1. `struct Name[T, U] { ... }` follows the same type parameter rules as generic enums (single uppercase letters, max 8, no duplicates) and the same "declaration produces no layout" principle: only **instantiations** like `Name[string, i64]` generate a `typedef`.
  2. The instantiation key is "declaration + argument list," consistent with the `struct_done` cache in `instantiate_struct`: the same argument list reuses the same `StructDef` (and thus the same `ae_tN` and release/forfeit logic). Consequently, values with the same arguments are mutually assignable and share the same parameter type.
  3. Type arguments are parsed using `named_type()`, which is broader than the `type_argument()` (flat types) used for generic enums: structs, enums, and already-instantiated generics can serve as arguments. The rationale is that struct fields can naturally contain structs and enums, so relaxing this does not introduce new layout shapes. Enum payloads remain restricted to flat types because the payload structure of an enum must be `free`-able based on the variant.
  4. Field types are represented as `Payload` (`Concrete`/`Param`) during the declaration phase and replaced by arguments during instantiation, using the same mechanism as enum variant payloads. `Param` will not leak into code generation.
  5. Budget: `MAX_STRUCT_TYPES = 256` (including ordinary structs), counted separately from the 256 limit for enums. Exceeding this limit triggers an error at the instantiation site.
- **Rationale**: We avoid introducing "runtime code for generic structs"—after monomorphization, they are simply ordinary structs. Release, field borrowing, and move checks all reuse existing implementations, requiring no new runtime facilities and ensuring no exceptions to the safety rule that "struct fields cannot be moved out." Allowing structs/enums as arguments is necessary because restricting argument types saves little implementation effort while rendering natural expressions like `Pair[i64, Tag]` impossible to write.
- **Defect Fix**: Fixed a bug where `skip_struct_def` only skipped `struct Name` before encountering `{`. Upon hitting `[T]`, it misinterpreted `[` as the opening brace and skipped to the end of the file, silently swallowing `fn main` and resulting in a "found 0 main function" error. It now calls `skip_type_params()` first, matching `skip_enum_def`. This defect was exposed by minimal test cases during generic implementation, highlighting that both skip functions must be isomorphic.
- **Excluded Approaches**:
  - **Allowing struct fields to be vectors of `T` (`vec[T]`)**: The element type of a `vec` is fixed at compile time (e.g., `i64` or `string`). Implementing generic containers requires element type descriptors, which is a separate task.
  - **Traits/Constraints (`T: Printable`)**: Without traits and static dispatch, constraints would be empty promises. We will first stabilize monomorphization, then design constraints as "shape checks for arguments."
  - **Type inference for omitted arguments**: The language currently lacks type inference. Omitting arguments would require `Pair { left: "a", right: 1 }` to infer arguments from field expressions, which requires a different mechanism.
- **Consequences and Limitations**: Instantiation occurs only at the **usage site**, so error locations point to the usage rather than the declaration. In error messages, struct types are still displayed as `struct #N` rather than `Pair[string, i64]` (`Type::Struct` only carries an ID, unlike `Type::Enum` which carries a name; this can be aligned later). Borrowing parameters like `&Pair[string, i64]` is not yet supported (`&` only accepts `string`/`vec`/arrays); large structs must be passed by value. Generic functions are not yet implemented. Added `examples/pairs.ae`, one end-to-end test (including 8 cases that must be rejected), and added `pairs.ae` to the allocation counting cases for C generation verification.
