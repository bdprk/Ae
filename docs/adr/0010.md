# ADR-10: Enums via "Tag + Per-Variant Payload Struct" Union, Mandatory Exhaustive `match`

- Background: Phase B of the proposal stage requires the introduction of enums and pattern matching. Furthermore, §4.5 requires recoverable errors to be expressed via result values, whereas the current `read_file` failure can only terminate the process. Without enums, it is impossible to define `Result`/`Option`-style recoverable errors within the language.
- Decision:
  1. `enum Name { Variant, Variant(i64), Variant(string, bool) }`: Variants can carry 0–16 positional payloads. In the initial version, payload types are restricted to `i64`/`bool`/`string`. Construction is written as `Name::Variant(...)`.
  2. The layout is a C-style `enum tag` + `union`, where **the members of the union are the individual payload struct of each variant** (e.g., `struct { int64_t p0; int64_t p1; }`), accessed via the path `v.u.v1.p0`.
  3. `match bare_enum_variable { ... }` is a statement; every variant must appear exactly once (exhaustiveness). Wildcards and nested patterns are not provided.
  4. Enums are owned values: assignment/passing/returning moves them. Scope exit, early return, and jump paths drop payloads according to the variant; `release` is idempotent, and `forfeit` clears without dropping.
  5. `string` payloads are bound as **read-only views** (`string view`) within match arms. No payload can be moved out of an enum; bound variables are non-owned and do not participate in dropping.
  6. The compiler treats `match` as "all variants return" to satisfy return value checks.
- Rationale: The payload struct union avoids the field aliasing issues of C unions; the bare variable subject enables the borrow tracker to guarantee that "the subject cannot be moved/assigned during matching," eliminating the need for lifetime analysis of cross-statement temporary values. Exhaustiveness checking ensures that `match` has no missing paths and requires no runtime traps.
- Rejected Alternatives:
  - **Placing variant fields directly in the union**: C unions only have one active member at a time, so `{ .f1_0 = 4, .f1_1 = 5 }` would overwrite each other. Practical tests showed `Rect(4,5)` resulted in `5x5`, hence the switch to per-variant structs.
  - **Generating `match` using C `switch`**: `break` statements inside arm bodies would be swallowed by `switch`, breaking the semantics of "break exits the innermost loop." Instead, an `if/else` chain is used, with comparison counts handled by the compiler.
  - **Allowing `vec`/struct payloads**: These types lack a bindable borrowing representation (unlike `string` which has `string view`), and moving them out would violate the consistency rule of "do not disassemble owned values." This will be relaxed later once view types are expanded.
  - **`match` as an expression**: This requires expression-level type unification and temporary value lifetime rules; the statement form is implemented first.
- Consequences and Limitations: The `match` subject must be a bare enum variable (function return values must first be bound to a variable); `enum`s, like `struct`s, only support forward declaration and usage within the same file; enum values have no runtime null sentinel, and post-move usage relies on compile-time move sets (consistent with structs); payloads cannot nest enums, so recursive layouts do not exist.
