# ADR-37: Define `f64` Semantics Before Implementation, Text Form Unified by Runtime

- Background: §4.2 has always stated "floating-point numbers will first be specified according to IEEE 754 and target platform behavior, and added later," yet numeric and statistical scripts require decimals. The goal of W2 is to hardcode the rules before touching the frontend, avoiding treating the differences between UCRT and glibc as language semantics. Practical measurements confirmed two real differences: `printf("%.17g")` outputs `-nan(ind)` on UCRT versus `-nan` on glibc. While exponent bit-widths and finite values happen to align on existing toolchains, one cannot assume they will remain identical forever.
- Decision:
  1. `f64` is IEEE 754 binary64, mapping to `double` on the C side. No implicit `i64`/`f64` conversions are performed; mixed arithmetic and mixed comparisons are rejected at type-checking with a prompt to use `to_f64`/`to_i64`. Literals must include a decimal point or an exponent (`1.5`, `1e3`); `1..2` remains a range, and `1.field` remains a field access. Non-finite literals and literals that are "non-zero yet underflow to 0" trigger lexical errors rather than silently substituting the user's value.
  2. `+ - * /` are only permitted between two `f64` operands, generating standard C operators without enabling fast-math. `-O0` and `-O2` must yield identical results. `%` is explicitly rejected (remainders are only defined for `i64`). Division goes through `ae_f64_div`: `x / 0.0` reports failure (non-zero exit) just like integer division, rather than silently producing `inf`. Overflow results in `inf`, and underflow results in subnormal numbers or `0`, handled according to IEEE and documented explicitly.
  3. All six comparisons are supported with IEEE semantics: any comparison with NaN is false, except `!=` which is true. `Eq`/`Ord` constraints thus include `f64` in their allowed sets, but documentation must warn about NaN behavior; the constraints do not constitute a "total order" guarantee.
  4. Textual representations are unified by the runtime function `ae_f64_text`: `nan`, `inf`, and `-inf` use fixed spellings. Finite values take the "shortest significant digit sequence that roundtrips," choosing the shorter between fixed-point and scientific notation (choosing fixed-point on ties), with the exponent standardized to `e±min_digits`. Results without a decimal point or exponent have `.0` appended to ensure `1.0` is never parsed as an `i64`. `print` and `to_string` share this single path. Cross-platform output is thus guaranteed by construction rather than relying on two CRTs happening to match.
  5. Conversions are explicit and checked: `to_f64(i64) -> f64` succeeds only when `|n| ≤ 2^53`; larger integers lose precision and cause an immediate runtime failure rather than rounding. `to_i64(f64) -> IntResult` sequentially checks for finiteness, the `i64` range, and whether the value is an exact integer, with failure reasons being `f64 value is not finite`, `... outside the i64 range`, and `... is not an exact integer`, respectively.
  6. `f64` can be used as function parameters/return values, struct fields, enum payloads, and generic type arguments (`Option[f64]` is available). `vec` still only holds `i64`, `map` values still only hold `i64`, and `&f64` is rejected by ADR-35's rule of "only three kinds of read-only borrows."
- Rationale: Separating "which behaviors are mandated by the language versus which are provided by the host" is a prerequisite for whether this project can claim to be cross-platform. Placing the textual representation in the runtime instead of generating it in code has three benefits: a single fix applies to the entire program; platform discrepancies of `%g` are not hardcoded into every call site; and allocation counting still covers `to_string`. Division adheres to the same "zero is an error" rule as integers, preventing `1/0` from exiting while `1.0/0.0` silently becomes `inf` within the same language. Conversions only accept exact values because "quietly altering the user's value" is precisely the scenario that conservative rules in §4.1 require rejecting.
- Excluded Approaches:
  - **Implicit numeric conversions** (e.g., automatically promoting `1 + 2.0`): Hides precision loss within expressions and makes type errors harder to locate; better to require explicit `to_f64`.
  - **Direct `printf("%.17g")`**: UCRT and glibc spell NaN differently, and historical exponent bit-widths have varied; embedding this in the language equates CRT behavior with the specification.
  - **Always outputting 17 significant digits**: `0.1` would become `0.10000000000000001`, leading to poor readability. Searching for the shortest roundtripping length costs at most 18 `snprintf`+`strtod` calls per value, restricted strictly to the printing path.
  - **`x / 0.0` returning `inf`**: Conflicts with integer division rules and obscures whether a value has been checked. Programs requiring infinite values can construct them explicitly and bear the semantic responsibility.
  - **`to_f64` rounding integers exceeding 2^53**: Silently discards precision, violating the principle of "reject unless proven safe."
  - **Adding math functions like `sqrt`/`sin`/`log` in this round**: Requires libm, linking parameters, and evidence of cross-platform trailing-digit discrepancies, which constitutes independent work. It is better to defer them than to implement and retract them.
  - **`vec[f64]` and `map[string, f64]`**: Each requires new container layouts, bounds, and deallocation paths, which are left for the next round. This round leaves no half-implemented containers.
- Consequences and Limitations: Text is in a **canonical form** rather than the shortest decimal representation: `1.0/3.0` outputs `0.3333333333333333` (16 digits are sufficient to roundtrip), and certain values output in scientific notation (`1e+16`, `1e-4`), which is a direct result of "choosing the shorter form." The documentation provides rules and examples. The sign and payload of NaNs are discarded, uniformly outputting `nan`. `f64` fields add 8 bytes per field to struct/enum layouts, and the generated C code size grows linearly with the number of fields. There is no math library, no decimal fractional type, and no `f32`. Added `examples/float_math.ae`, 4 integration tests (canonical text, struct/enum/generics, 10 must-be-rejected patterns, 2 runtime guards), and 1 generated C allocation-counting test. Full verification run on both platforms: all 9 unit tests and 133 integration tests passed. Linux `--sanitize` produced 0 reports across 24 cases; `--leak` exited with 0 allocated blocks for 24 cases (Windows equaled the 2-block baseline). `float_math.ae` outputs matched byte-for-byte after normalizing line endings, because text is generated by the runtime rather than the CRT's `%g`. Measured resource cost: generating C text adds 6,773 bytes compared to an empty program (109,721 → 116,494), primarily due to the formatter source code. The release artifact of an empty program remains 61,309 bytes on Windows / 16,176 bytes on Linux; unreferenced formatters are optimized away, making this a "pay-for-what-you-use" cost. The release artifact of `float_math.ae` is 70,467 bytes on Windows / 21,576 bytes on Linux. Since it is not the exact same program as `find_text.ae` (66,904 bytes), the difference serves only as a scale reference rather than an exact incremental cost.
