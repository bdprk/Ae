# ADR-70：以过渡编译器库建立 workspace 边界

- 状态：已实现（Windows 验证；Linux 待验证）
- 日期：2026-11-12
- 关联里程碑：M0.3

## 背景

ADR-69 将单体前端拆为模块，但编译器与命令行驱动仍在同一 crate。计划要求逐步引入 workspace 和职责明确的编译器 crate；现有解析、语义检查和 C 输出仍紧密耦合，直接按最终架构切分会同时改变大量内部接口。

## 决定

建立 Cargo workspace，将现有前端、格式化器、测试辅助、哈希及 C 运行时代码整体迁入 `ae-compiler` 库；根包暂时作为命令行驱动。除驱动所需接口的可见性外，本次不改变编译行为。CI 显式测试整个 workspace。

该库是过渡边界，不替代计划中的 `ae-span`、`ae-syntax`、HIR、MIR 和后端 crate；M0.3 的最终拆分及跨平台验收仍未完成。后续按可验证的内部接口逐步迁移，避免将现有 AST 直出 C 误认为目标架构。

## 验证

- Windows：`cargo test --workspace` 通过，含 36 个单元测试、179 个集成测试和 2 个快照测试。
- Windows：`python scripts/verify_generated_c.py --leak` 通过 34 个生成 C 样例；各样例的存活分配数与空程序基线一致。
- 同机对 `examples/**/*.ae` 的 44 个输入，在迁移前后分别运行 `emit-c`，比较退出码、标准输出与标准错误的 SHA-256；全部一致。其中 42 个作为入口成功，另外 2 个模块文件作为入口被拒绝，两次结果一致。
- Linux 与完整 M0.3 验收仍待执行。

## 后果

驱动与编译器现有功能之间有明确的 crate 边界；解析和语义检查仍未分离，运行时也暂存于编译器库。引入更细的 crate 时继续要求现有测试与生成 C 的等价验证。
