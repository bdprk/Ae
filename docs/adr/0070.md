# ADR-70: Establishing Workspace Boundaries via a Transitional Compiler Library

- Status: Implemented (Verified on Windows; Pending verification on Linux)
- Date: 2026-11-12
- Related Milestone: M0.3

## Background

ADR-69 split the monolithic frontend into modules, but the compiler and CLI driver still reside in the same crate. The plan requires the gradual introduction of a workspace and compiler crates with well-defined responsibilities. Since the existing parsing, semantic analysis, and C output remain tightly coupled, directly splitting them according to the final architecture would simultaneously alter a large number of internal interfaces.

## Decision

We establish a Cargo workspace, migrating the existing frontend, formatter, test helpers, hashing, and C runtime code entirely into the `ae-compiler` library crate, with the root package temporarily serving as the CLI driver. Aside from exposing the interfaces required by the driver, this change does not alter compilation behavior. CI explicitly tests the entire workspace.

This library serves as a transitional boundary and does not replace the planned `ae-span`, `ae-syntax`, HIR, MIR, and backend crates; the final splitting and cross-platform acceptance for M0.3 are not yet complete. Subsequent migrations will proceed incrementally based on verifiable internal interfaces, avoiding any misconception that the current direct AST-to-C emission represents the target architecture.

## Verification

- Windows: `cargo test --workspace` passes, including 36 unit tests, 179 integration tests, and 2 snapshot tests.
- Windows: `python scripts/verify_generated_c.py --leak` passes 34 generated C test cases; the number of live allocations for each test case matches the empty program baseline.
- On the same machine, for 44 inputs under `examples/**/*.ae`, `emit-c` was run both before and after the migration, and the exit codes, standard output, and standard error were compared via SHA-256; all are identical. Among them, 42 succeed as entry points, while the other 2 module files are rejected as entry points, with identical results in both runs.
- Linux and full M0.3 acceptance remain to be executed.

## Consequences

A clear crate boundary now exists between the driver and the existing compiler functionality; parsing and semantic analysis remain unseparated, and the runtime also temporarily resides in the compiler library. The introduction of finer-grained crates will continue to require verification of equivalence for existing tests and generated C.
