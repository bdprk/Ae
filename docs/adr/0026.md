# ADR-26: JSON Path Query (Read-Only)

- **Background**: The acceptance criteria for Phase B, Item 6, require that "common text/JSON workflows must be runnable," and Phase E, Item 1, lists JSON/CSV as a foundational API. Without this, reading an API response or configuration file relies on manual `split` + `contains` logic, which becomes unreliable when nested objects, escaped quotes, or arrays are involved—precisely the scenarios where "what a scripting language should do" is most relevant.
- **Decision**:
  1. Implement **read-only path queries** only, with five built-ins: `json_get(text, path) -> ReadResult`, `json_int(text, path) -> IntResult`, `json_bool(text, path) -> BoolResult`, `json_len(text, path) -> IntResult`, and `json_has(text, path) -> bool`.
  2. Path syntax: `key`, `key.sub`, `key[2].sub`, `[0].key`; an empty path represents the entire document. Keys are compared by **decoded** bytes (e.g., `\uXXXX` in object keys are decoded before comparison).
  3. `json_get`: String values are fully decoded (including `\uXXXX` and surrogate pairs, outputting UTF-8); numbers, `true`/`false`/`null` return the **raw text**; arrays and objects return the **raw fragment** (which can be saved or parsed further).
  4. `json_int` only accepts integers without decimal points or exponents; overflow of `i64` results in an error. `json_bool` only accepts `true`/`false`. `json_len` only accepts arrays and objects.
  5. Add a new preset enum `BoolResult{Ok(bool), Err(string)}` (ID 6)—using `IntResult` with 0/1 would conflate "false" with "missing."
  6. Each call re-scans the document; maximum nesting depth is 64; paths are validated separately before document traversal, and invalid paths trigger a path error.
- **Rationale**: We avoid introducing a JSON value type because it would force ownership, recursive layout, access syntax, and error propagation into the type system all at once, conflicting with the existing model of "low memory, deterministic deallocation, and compile-time rejection of moves." Path queries keep complexity in the runtime, and return values remain existing result enums handled via `match`, requiring no changes to the language syntax itself. We split into three return types rather than "fetching as a string and converting" because **"field missing" and "field type mismatch" must be distinguishable**—the same reason ADR-22 rejected returning `Option` for `env`. Surrogate pairs must be decoded; otherwise, Chinese characters and emojis in JSON would appear as literal `\ud83d\ude00` in AE, whereas the raw field value is what any real-world API would provide.
- **Rejected Alternatives**:
  - **`json` type + `doc["key"]` indexing**: As noted above, this would require new types, new ownership rules, and new error semantics.
  - **Parsing into a document handle (parse once, query many)**: This would require a "handle type + deallocation point"; however, the cost of re-scanning configuration-level input is in the microsecond range (16 fields × 10 KB), making it not worth adding an owned resource type.
  - **`json_get` returning strings uniformly, with the caller using `parse_int`**: This loses the "field type error" diagnostic, and `parse_int` cannot distinguish between `"12"` and `12`.
  - **Implementing JSON writing/serialization**: Constructors, escaping, and key ordering require design; `join` and string concatenation can already generate simple JSON, so we will defer this until structured output requirements are clear.
  - **Strict JSON validation** (number syntax, rejecting duplicate keys, rejecting trailing commas): The reader is implemented with a "find and return" loose approach; strictness is guaranteed by `json_int`/`json_bool` during conversion. The documentation will state this to prevent users from assuming `json_get` is a validator.
- **Consequences and Limitations**: No writing, no floating-point support (`json_int` rejects `1.5`), and no traversal callbacks—iterating over an array requires a `json_len` + `[i]` loop (feasible but inelegant). Key names containing `.` or `[` cannot be expressed. Duplicate keys return the first occurrence. UTF-8 BOMs are not skipped. The entire document is not validated; syntax errors are only detected along the traversed path. The document must reside entirely in memory (`read_file`/`read_stdin`). Add 2 end-to-end tests (normal paths and 10 types of errors) and `examples/json_report.ae`, and include this example in allocation count verification (`blocks=2`, no leaks).
