# ADR-52: Read-only views can follow struct string fields (borrowing the entire variable)

- **Background**: Previously, `slice_view` only accepted bare string variables. Struct string fields are the most common form (e.g., record names, paths, tags), yet they currently require copying into a local variable first—which incurs an extra allocation and defeats the purpose of a "zero-copy view."
- **Key Observation**: A view points to the bytes of a field's buffer. As long as the **entire variable** is not moved, not reassigned as a whole, and the field itself is not written to while the view is alive, these bytes remain valid. Therefore, field-level borrowing is unnecessary; borrowing by variable is both sufficient and conservative.
- **Decision**:
  1. The base of `slice_view(expr, start, end)` now accepts two forms: bare string variables or `variable.field` (the field type must be `string`, and the base must be the **variable** itself, not a nested expression).
  2. Both cases register the **variable ID** in the existing `borrows` (adhering to scope depth semantics): moves, whole-variable assignments, and writes to any field of that variable are rejected based on this ID.
  3. Add the missing check for field assignment paths: `s.f = value;` previously did not check `borrows`. This is a tightening of constraints; since field views did not exist previously, no previously valid programs will be rejected.
  4. The generated C uses `AE_VIEW(v{id}.{field})`, which is identical to bare variables: zero-copy, zero runtime overhead, and no new allocations.
- **Rejected Alternatives**:
  - **Field-level borrowing**: This would require tracking `(var, field)` pairs and covering all write paths. The benefit would only be that "other fields of the same struct remain writable." Whole-variable borrowing covers the vast majority of use cases and is less error-prone.
  - **Nested fields `a.b.c`**: This would require a borrowing chain; it will be deferred until there is a genuine requirement.
  - **Fields on array/vector elements** (`v[0].name`): The base is not a variable, and the borrow target is ambiguous; this remains rejected.
- **Resource Costs**: Zero change to generated C and runtime (only an additional field name in `AE_VIEW(...)`); one additional shape check at compile time; no new allocations, cache types, or toggle switches.
- **Boundaries (must not be exceeded in external communication)**:
  - Views remain read-only and still cannot be used as return values, struct fields, or enum payloads.
  - The borrowing granularity is the **entire variable**; writing to other fields of the same struct will also be rejected—this is conservative behavior that must be explicitly stated and not misrepresented as field-level borrowing.
  - Do not claim that the "borrow checker has been generalized": field views simply extend existing borrowing rules to a new base shape.
- **Verification**: 35 unit tests + 158 integration tests (added 1 integration test: positive case for field views, plus five types of rejections: field writes / whole-variable assignment / moves / nested fields / non-string fields), 29 `--leak` tests (added `examples/field_view.ae`, Windows 2 blocks / Linux 0 blocks), Linux `--sanitize` 29 test cases, 36 examples; the generated C for `field_view.ae` contains `AE_VIEW(v0.name)` and passes strict C11 syntax checks.
