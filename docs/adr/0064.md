# ADR-64：`min`/`max` 数学内建——运行时实现，NaN 忽略 + ±0 全序平局

- 背景：ADR-60 的边界明确「无 `min`/`max`」。它们是统计代码的高频原语（峰值、夹取），但语义有三个坑：NaN 怎么处理、±0.0 平局返回谁、要不要支持整数。本轮只做 f64，把三个坑都写成显式规则。
- 决策：
  1. **运行时实现，不调 libm**：`ae_f64_min`/`ae_f64_max`（runtime_ex.c，随可达闭包裁剪）。理由不是性能，是**跨平台确定性**：libm 的 `fmin`/`fmax` 对 `±0.0` 平局是「未指定返回哪个」，UCRT 与 glibc 可以不同——而 `-0.0` 的文本形式是可观察输出（ADR-37 规范文本），直接调 libm 会让 `min(-0.0, 0.0)` 的打印文本依赖平台。运行时写死规则后，输出两平台逐字节一致成为可测性质。
  2. **NaN 忽略**（IEEE 754-2008 minNum/maxNum 口径，与 C `fmin`/`fmax` 同）：一边 NaN 返回另一边，两边 NaN 返回 NaN。与比较运算符的 IEEE 语义（与 NaN 比较为假）自洽：`a < b ? a : b` 在 NaN 下的行为不可用，必须显式处理。
  3. **±0.0 平局按 totalOrder**（−0.0 < +0.0）：`min(-0.0, 0.0)` 恒为 `-0.0`、`max` 恒为 `0.0`，与参数顺序无关——集成测试按两个顺序都断言。
  4. **只做 f64**：整数 min/max 手写 if-else 即可且无 NaN 陷阱，加内建只增加保留名面积；f64 的值在于 NaN/±0 的正确处理。
  5. 前端复用 ADR-60 的 MATH_FNS 通道（元数 2、直接调用 C 符号），名字进保留名单。
- 已排除的做法：
  - **直接映射 `fmin`/`fmax`**：±0 平局未指定 + `fmin` 在某些 libm 还有额外的信号语义；「打印文本跨平台一致」是语言已承诺的性质，不能靠未指定行为。
  - **比较运算符实现**（`a < b ? a : b`）：NaN 下 `a < b` 为假会返回 b——`min(NaN, 5)` 变成 5 但 `min(5, NaN)` 变成 NaN，结果依赖参数顺序，违背「与顺序无关」。
  - **整数版本**：见决策 4。
- 资源成本（归档 `bench/results/2026-11-12-windows-minmax/`）：
  - `print(1)` 保持 13,909 字节（未引用即裁剪）；math_basics.ae 扩展 5 行输出后 27,406 字节；`--leak` 33 用例基线不变。
  - 验证：36 单元 + 176 集成（新增 2 个）、fmt 43 文件、41 程序 `check`。
- 边界（对外表述不得越过）：
  - 不宣称「所有平台的 libm fmin 都不可用」：未指定 ≠ 一定不同；我们的理由是**确定性可测**，不是断言 libm 有 bug。
  - min/max 不接受整数、不做隐式转换（`min(1, 2)` 报错，测试覆盖）。
  - NaN 忽略语义与某些语言的 `min`（NaN 传播）不同——这是选择，写进规范，不是「标准答案」。
- 过程发现：批量插入含 `\r\n` 转义的测试代码再次走了 heredoc→python 路线（2026-11-11 教训的第二次违反），转义层级错位让测试文件编译失败；已把该教训升格为硬规则写入失败日志：**含转义序列的编辑一律 Write/Edit 工具**。
