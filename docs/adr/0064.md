# ADR-64: `min`/`max` Math Builtins — Runtime Implementation, NaN Ignored + ±0 Total Order Tie-Breaking

- Background: The boundary of ADR-60 explicitly stated "no `min`/`max`". They are high-frequency primitives in statistical code (peaks, clamping), but their semantics come with three pitfalls: how to handle NaNs, which operand to return on a `±0.0` tie, and whether to support integers. This round implements `f64` only, codifying all three pitfalls into explicit rules.
- Decision:
  1. **Runtime implementation, bypassing `libm`**: `ae_f64_min`/`ae_f64_max` (`runtime_ex.c`, subject to reachable closure pruning). The rationale is not performance, but **cross-platform determinism**: `libm`'s `fmin`/`fmax` leaves the return value for `±0.0` ties "unspecified", meaning UCRT and glibc may differ—yet the textual representation of `-0.0` is an observable output (per ADR-37 specification text), so directly calling `libm` would cause the printed text of `min(-0.0, 0.0)` to depend on the platform. By hardcoding the rules in the runtime, byte-for-byte consistency of output across both platforms becomes a testable property.
  2. **NaN ignored** (IEEE 754-2008 `minNum`/`maxNum` convention, matching C `fmin`/`fmax`): If one side is NaN, return the other; if both sides are NaN, return NaN. This is consistent with the IEEE semantics of comparison operators (comparisons involving NaN evaluate to false): `a < b ? a : b` behaves incorrectly under NaN and must be handled explicitly.
  3. **`±0.0` ties follow `totalOrder`** (−0.0 < +0.0): `min(-0.0, 0.0)` is always `-0.0`, and `max` is always `0.0`, independent of argument order—integration tests assert both orders.
  4. **`f64` only**: Integer `min`/`max` can be written manually with `if-else` and have no NaN pitfalls; adding them as builtins only increases the reserved name space. The value of `f64` builtins lies in the correct handling of NaN/±0.
  5. The frontend reuses the `MATH_FNS` channel from ADR-60 (arity 2, direct call to C symbols), and the names are added to the reserved list.
- Excluded Alternatives:
  - **Direct mapping to `fmin`/`fmax`**: ±0 ties are unspecified + `fmin` in certain `libm` implementations carries additional signaling semantics; "cross-platform consistency of printed text" is a property already promised by the language and cannot rely on unspecified behavior.
  - **Implementation via comparison operators** (`a < b ? a : b`): Under NaN, `a < b` evaluates to false, returning `b`—meaning `min(NaN, 5)` becomes `5` while `min(5, NaN)` becomes `NaN`. The result depends on argument order, violating order independence.
  - **Integer versions**: See Decision 4.

- Boundaries (external statements must not exceed):
  - Do not claim that "the `libm` `fmin` on all platforms is unusable": unspecified ≠ necessarily different; our rationale is **determinism and testability**, not asserting that `libm` has bugs.
  - `min`/`max` do not accept integers and do not perform implicit conversions (`min(1, 2)` produces an error, covered by tests).
  - The NaN-ignoring semantics differ from the `min` implementations of certain languages (where NaN propagates)—this is a design choice written into the specification, not an "absolute standard answer".
