# ADR-17: UTF-8 Character Boundaries and Character-Based Slicing

- Background: `len` and `slice` have always operated on bytes, which aligns with the principle that "strings are sequences of UTF-8 bytes" and remains $O(1)$. However, this is a trap for text processing: `slice("中文", 0, 1)` produces an isolated `0xE4` byte, and printing it results in invalid UTF-8—displaying garbage in the terminal. If written back to a file or used as a JSON field, the error propagates indefinitely. Previously, there was neither a character-safe slicing method nor any detection mechanism. Phase B, item 5 of the roadmap requires "testing Unicode and iteration boundaries."
- Decision:
  1. `slice`/`slice_view` halts and reports `string index splits a UTF-8 character` when an **index falls in the middle of a character**. This check only needs to inspect a single byte (continuation bytes in UTF-8 always start with `10xxxxxx`), making it $O(1)$. Additionally, `start`/`end` positions that fall exactly at the end (`== len`) are considered valid boundaries.
  2. Added `utf8_len(s) -> i64` (number of characters, i.e., the count of non-continuation bytes) and `utf8_prefix(s, n) -> string` (returns an owned copy of the first $n$ characters; if $n$ exceeds the character count, the entire string is copied; a negative $n$ reports an error).
  3. No entry point for "validating the entire string
