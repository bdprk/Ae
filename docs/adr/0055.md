# ADR-55: `print` writes to Windows console using UTF-16

- **Background**: While writing the verification program for ADR-54, printing Chinese characters to `cmd` resulted in `涓枃娴嬭瘯` on the screen. The program was consistently writing correct UTF-8 bytes (verified via `od` on a pipe as `e4 b8 ad ...`), but the **reader** was at fault: the console decodes received bytes based on its own output code page. On Chinese Windows, this is 936 (GBK), so 6 UTF-8 bytes were decoded into 6 unrelated characters. This is not a Windows-specific topic—POSIX terminals are UTF-8 by convention—so the defect exists on only one platform but affects **every** Chinese output on that platform.
- **Key Observation**: The console screen buffer stores UTF-16, and `ReadConsoleOutputCharacterW` reads back exactly what the user sees. Using this for forensic evidence was decisive: the same bytes written narrowly to the console resulted in `U+6D93 U+E15F U+6783 U+5A34 U+5B2D U+762F`, while `WriteConsoleW` with the same text yielded `U+4E2D U+6587 U+6D4B U+8BD5`. Therefore, the fix is not to "change the encoding," but to **provide the console with the format it expects**: the console receives UTF-16, while pipes and files continue to receive raw bytes.
- **Decision**:
  1. The four forms of `print` (integer, boolean, f64, string/view/literal) all pass through a single sink: `ae_emit(ptr, len, newline)`. The sink determines at runtime whether `stdout` is a console (success of `GetStdHandle` + `GetConsoleMode` counts as true): if it is a console, it decodes UTF-8 to UTF-16 and passes it to `WriteConsoleW`; otherwise, it uses `fwrite` for raw bytes. The result of this check is cached in a static variable within the function, so redirected execution incurs only two system calls.
  2. **Merge newline and value into a single write**: `WriteConsoleW` takes approximately 9.5 µs per call; two calls would double this. Measured over 20,000 lines: 832.0 ms merged, 1120 ms split. Before the change (`fwrite` + `fputc`, console line-buffered), it was 860.3 ms—the merged approach not only avoids regression but is slightly faster.
  3. **Chunked conversion, no allocation**: 1 KiB input chunk → 1024 UTF-16 units, 2 KiB on the stack. Chunk boundaries never fall in the middle of a character (fallback to the last leading byte), so 1022 ASCII characters + one 3-byte character (straddling the 1023-byte boundary) are restored character-by-character on the console; 3000 Chinese characters (multiple chunks) are also restored character-by-character. Illegal bytes are converted to `U+FFFD` by `MultiByteToWideChar` (the console is a display device, not a validator).
  4. **Do not introduce `<windows.h>`**: `print` is used by almost every program; the header file takes ~520 ms to parse (measured in ADR-39), and forcing every program to pay this cost is unacceptable. The four entry points (`GetStdHandle`, `GetConsoleMode`, `WriteConsoleW`, `MultiByteToWideChar`) are manually declared **within the function bodies that use them**, with types matching the header files exactly. This does not conflict with header files retained by the program due to `args()` (generated C passes strict C11 checks). Declaring them inside function bodies has a beneficial side effect: top-level text belongs to "functionless units" and is always retained during pruning, whereas declarations inside functions disappear with the function—programs that do not use `print` pay zero bytes.
  5. **Audit test synchronization extension**: `WIN32_DECLS` now includes these three names; every function using Win32 declarations must carry `/* win32-header */` (retaining the header) or the new `/* win32-declared */` (self-declared); reverse checking ensures every `extern` declaration in `runtime.c` is on the audit list (strip indentation during scanning, otherwise in-function declarations will be missed), and requires exactly four self-declared entry points and at least three functions with the new tag.
- **Excluded Approaches**:
  - **`SetConsoleOutputCP(65001)` at startup**: Only a dozen lines and near-zero size, but it modifies **shared** console state: if the program is killed (Ctrl-C, crash), it cannot restore the state, leaving the parent shell's prompt garbled. Rust uses `WriteConsoleW` rather than changing the code page for this exact reason.
  - **Buffering wide characters until exit**: The console is fastest when written to immediately, but the screen would remain blank during long-running programs after printing "Loading...". A buffer size threshold cannot solve this semantic issue, and the language currently **lacks `stdin`**, so there is no "print prompt then wait" use case to justify it.
  - **Writing each value twice (text + newline)**: 1120 ms for 20,000 lines; a measured regression, replaced by merged writes.
  - **Routing `ae_fail` through the sink**: Runtime error messages are fixed ASCII (failures with user data return `Err`, which the program `print`s itself); routing them would force **programs that do not print** to carry an extra 4.4 KB. Verified that `runtime_ex.c` contains no `ae_fail` calls with dynamic messages.
  - **Hand-written UTF-8 → UTF-16 decoder**: ~45 lines, twice as expensive as a `MultiByteToWideChar` declaration, and handling of illegal sequences must match the system to avoid discrepancies.
  - **Centralized top-level Win32 declarations**: Top-level text is always retained; programs that do not print would pay ~1 KB (measured 514 bytes for comments plus declaration difference). By moving declarations into function bodies, programs that do not print only pay an extra 525 bytes (the remainder is still block comments, see lesson #2 below).
- **Resource Costs (answering §21 acceptance questions point-by-point)**:
  - **Generated C**: `print(1)` 11,341 → 15,243 bytes (+3,902, +34%); `print("hi")` 11,330 → 15,384; programs that do not print 11,286 → 11,811 (+525); `args` + `print` 15,178 → 20,742 (the two costs can overlap, still sharing one header file). Literals appear only once (length uses `strlen`, not `sizeof` to avoid duplication).
  - **Build time**: 9 iterations, 74.6 → 75.7 ms (+1.1 ms, within noise; an earlier iteration measured +4 ms). No new header file parsing; the increase is only ~4 KB of C text.
  - **Console throughput**: 20,000 lines of Chinese, 9 iterations, 860.3 → 832.0 ms (no regression; one `WriteConsoleW` per line).
  - **Redirected throughput** (pipe path, `fwrite` only, no conversion): 20,000 lines 17.6 → 18.2 ms (+0.6 ms, one extra function call and console check per print, ~30 ns).
  - **Runtime memory**: 2 KiB stack frame for conversion, no new allocations; `--leak` 30 test cases exit block count remains Windows 2 blocks / Linux 0 blocks.
  - **Pipes**: Bytes remain completely unchanged (output comparison for 162 integration tests and 30 generated C test cases all passed, including raw bytes before `\r\n` normalization).
  - **Security semantics**: No checks disabled; illegal UTF-8 displays as `U+FFFD` on the console and passes through unchanged in pipes (verified both paths for the same program).
- **Boundaries (must not be exceeded in external communication)**:
  - **The console determines what it can display**: Non-BMP characters (emojis) become `U+FFFD` on this `conhost`, and this is **independent of the code page**—the same under both 936 and 65001 settings, verified via a probe calling `WriteConsoleW` directly, indicating it is not a runtime conversion issue. We do not claim "emojis are supported," nor do we infer behavior under Windows Terminal.
  - Only `stdout` is handled. `stderr` remains `fprintf` because runtime messages are ASCII (see excluded items above). Console output remains **unbuffered**: one system call per line; no additional calls are added when redirecting output to a file/pipe.
  - Window titles, clipboard, and `run_command` subprocess output are out of scope; `run_command` subprocess arguments already use `CreateProcessW` as per ADR-54.
  - We do not change the console code page or any other global console state: the parent shell's environment remains identical after the program exits.
- **Two Process Lessons (both incorporated into the workflow)**:
  1. **Replacing entire blocks by "start/end anchors" can consume other functions in the interval**: This time, `ae_exit` was replaced (it happened to fall between two anchors), causing 7 integration tests to fail with "implicit declaration of `ae_exit`". In the future, `grep -c` key symbols before and after block replacement, or use `git diff --stat` to verify the number of deleted lines.
  2. **Comments without function names are treated as pruning roots**: The function name `ae_emit` was written in a block comment, so the symbol scanner treated the sink and the entire Win32 path as a "root" to be retained, causing programs that do not print to carry an extra 4.4 KB. The lesson from ADR-50 (comments attached to the functions they explain) has a second facet here: **function names in comments have semantics**.
- **Verification**: 35 Windows units + 162 integration (added `print_keeps_every_shape_in_order_with_non_ascii_text`: byte-by-byte output of four forms plus Chinese literals, `\n` escape not truncated), 30 `--leak` test cases PASS (baseline 2 blocks), 37 examples passed via `check`, generated C for both `print(1)` and `args`+`print` programs passed strict C11 syntax checks; Linux same count + `--sanitize` 30 test cases 0 reports. Console forensics used a custom launcher that sets `SetConsoleOutputCP(936)`, passes the `CONOUT$` handle to the tested program, and reads back the screen buffer using `ReadConsoleOutputCharacterW`; results for the four groups (read-back before/after fix, cross-chunk boundaries, 3000 characters, illegal bytes) are in `bench/results/2026-11-11-windows-console-utf8/console.txt`, with raw throughput and size values in the same directory.
