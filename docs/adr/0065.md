# ADR-65: `map[string, f64]` — Second Map Shape and Preset Enum `FloatResult`

- **Background**: Following the implementation of `vec[f64]` (ADR-61), the final missing container in the f64 data analysis stack is the hash map (for sensor latest-value tables, feature weight tables, etc.). The shape of a map is inherently more complex than that of a vector: `map_get` returns an `IntResult` (with a reason string for missing keys), and the f64 version requires its own result shape—this is the core design decision of this cycle.
- **Decision**:
  1. **Preset Enum `FloatResult{Ok(f64), Err(string)}`**: Symmetrical to `IntResult`. For missing keys, it returns the shared read-only `"key not found"` (ADR-58 constant, zero-allocation on miss), ensuring consistent error-handling semantics across both families. The alternative `Option[f64]` (which lacks a text message) was rejected—the error-text philosophy (§4.5 "I/O interfaces must not silently discard errors") is already established for the map family, and inconsistent reading shapes for the two map types would force callers to adopt two different coding styles.
  2. **Appended to the end of the prelude**: The IDs of the existing 8 enums remain unchanged (payload IDs are positional; reordering would rewrite all existing generated C code). The runtime references them via `ae_e8`/`AE_FLOAT_*` macros, and the prelude order assertion ensures the first 6 remain fixed, with the new one added at the 9th position.
  3. **`MapPlace` carries `MapKind`**: The six map built-ins (get/has/remove/inc/keys/index-write) share a single `place` structure, dispatching C symbols based on `f64_value()`—this halves the required changes compared to adding fields to each of the six `Expr`/`Statement` variants, with the kind inferred from the variable type at the parsing point.
  4. **Runtime family is isomorphic to the i64 map**: 24-byte slots (16 for key + 8 for double), parallel status bytes, and half-load expansion (inheriting conclusions from ADR-56/57 directly). Hash and slot calculations **reuse** the i64 version functions (depending only on the key, independent of the value type), avoiding duplication.
  5. **`map_get` missing semantics and index-read non-existence**: `m[key]` as an expression does not compile (this rule was reaffirmed in the examples during this cycle)—reading must follow the `Result` shape; "missing" and "value" must not be conflated.
- **Rejected Approaches**:
  - **`Option[f64]` as `map_get` return**: See Decision 1; error shapes for both map families must be consistent.
  - **Generic maps** (`map[K, V]`): Same as ADR-61, generic containers are a separate decision.
  - **Duplicating hash/slot calculations for `mapf`**: The key-side logic is independent of the value type; duplication would only cause the tuning conclusions of ADR-56/57 to drift out of sync.
  - **On-demand layout (only emitting layouts for referenced prelude enums)**: While this could reclaim the +911 bytes of the resident prefix, it violates the "prefix is byte-for-byte identical" invariant established in W3. This warrants a separate item (recorded as a candidate) and is not included in this cycle.
- **Resource Costs (Archived in `bench/results/2026-11-12-windows-mapf/`)**:
  - **Generated C**: `print(1)` 13,909 → 14,820 (+911 = layout of the 9th prelude enum and release/forfeit into the resident prefix; `mapf` functions are pruned if unreferenced, 0 retained in `print(1)`). No impact on binary size (unreferenced enums do not generate code). This is the fixed cost of "adding a prelude enum," recorded as is.
  - **Runtime**: 24 bytes per slot, same as i64 map; `--leak` 34 test cases (new `sensor_stats`) baseline unchanged—expansion, tombstones, and field deallocation occur exactly once.
  - **Verification**: 36 unit + 179 integration (3 new), 44 `fmt` files, 42 program `check`s.
- **Boundaries (External statements must not exceed these)**:
  - Do not claim "generic maps": These are two hand-written families; `map[string, f64]` does not imply a third or fourth value type—genericization or on-demand layout should be evaluated before adding more.
  - Do not claim "+911 bytes is negligible": It is a resident text cost for all programs; on-demand layout is a clear follow-up candidate, recorded for the record.
  - Enum `==` still does not exist: `map_get` results must be `match`ed (test cases cover this rejection).
  - Keys remain `string` only; `int` keys are not in this cycle.
- **Process Discoveries**:
  1. **Map index-read non-existence** (intentional design) reaffirmed—the initial version of the example hit this immediately; switched to `map_get` + `match`.
  2. **Outer type check for field map assignment missed**: (`fty == Type::Map` did not include `MapF`)—the variable branch was updated, but the field branch was not. Similar to the lesson from ADR-61 regarding `by_ref`, "the second occurrence of the same rule" must be grepped across all occurrences.
  3. After the third error in heredoc→python escaping, all scripts in this cycle were converted to `Write` disk-dump scripts + raw strings, preventing further issues—the hard rule is now in effect.
