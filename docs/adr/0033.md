# ADR-33: Constraints Are Argument-Shape Checks at Call Sites, Not Proofs for Generic Bodies

- Background: ADR-31 implemented generic functions as "write arguments at the call site, re-parse the function body for each instantiation," and explicitly excluded traits/constraints on the grounds that "without traits and static dispatch, constraints can only be empty promises." However, actual usage exposed two problems: when `fn add[T](a: T, b: T) -> T { return a + b; }` is called with `add[bool]`, the error originates from inside the generic body as `'+' requires ...`, placing the error message far away from the user's code; furthermore, the signature completely fails to indicate that this function only applies to types that can be added.
- Decision:
  1. Type parameters of generic **functions** may carry constraints: `[T: Add]`, `[T: Add + Eq]`, `[T: Copy, U: Ord]`. Constraint names are fixed to the four: `Add`, `Eq`, `Ord`, `Copy`. Unknown or duplicate constraints result in an error at the declaration site; writing constraints on generic structs and generic enums immediately reports `constraints are only supported on generic functions` (since their declarations have no function bodies, constraints have no inspectable targets).
  2. Each constraint is a **whitelist of argument types**, corresponding one-to-one with the operations actually available in the current language: `Add` = `i64`/`string` (`+`); `Eq` = `i64`/`bool`/`string` (`==`, `!=`); `Ord` = `i64` (`<`, etc.); `Copy` = `i64`/`bool` (no deallocation needed, repeatable reads). The whitelist is not an "abstraction of operators," but rather a "mirror of existing type-checking rules," so it never lies.
  3. Checks occur at the beginning of `instantiate_fn`, prior to parsing the function body. The error location points to the call site, with a message formatted as: `type argument 'bool' for 'add' does not satisfy 'Add'; that constraint allows i64, string`. Because declarations preserve constraints, constraints on `pub fn` across files remain effective at the importer's call site.
  4. **No** consistency checks between generic bodies and constraints are performed, nor is static dispatch: function bodies are still fully parsed and fully type-checked within each instantiation according to ADR-31. Constraints can only reject early, not permit.
  5. As a minor fix, `bool == bool` / `bool != bool` are now supported: previously, `Eq` claimed to allow `bool`, while the front-end only permitted integer comparisons and string equality, resulting in a contradiction between the two rules. Now, `(Bool, Bool)` is permitted only for `==`/`!=`, while `<` and others remain rejected; the C backend directly emits `==` for boolean values without requiring new runtime code. In unit tests, the test case that previously "rejected `true == false`" is modified to "reject `true < false`", and boolean equality is added to the accepted list.
- Rationale: Defining constraints as "argument-shape checks" rather than "capability contracts for generic bodies" is the only definition compatible with per-instantiation checking. To implement genuine trait contracts, one first needs an unreplaced generic AST and a set of rules for "checking operations on type variables"; only then can it be proven that the generic body used only the declared capabilities. In the current architecture, any claim that "constraints guarantee the legality of the function body" is false, and incorporating it into the language would only mislead users. Although shape checks are weak, they effectively move error messages from "inside someone else's function body" to "the call site written by the user," which is a perceptible improvement for users, and the implementation only adds a loop at the instantiation entry point.
- Excluded Approaches:
  - **User-defined traits / `impl`**: Requires vtables, static dispatch, orphan rules, and visibility rules, which belong to the next phase; opening up constraint names before then would only let each user invent their own uncheckable convention.
  - **Inferring constraints from function bodies** (inferring that `T` needs `Add` if not specified): Equivalent to introducing type inference, and the inferred results would change as the function body is modified, undermining interface stability.
  - **Letting constraints affect code generation** (e.g., omitting deallocations based on `Copy`): Current deallocations are determined by concrete types and duplicate the constraints; any inconsistency between the two sets of rules leads to memory errors. Constraints do not participate in code generation, only in checking.
  - **Adding constraints to generic structs/enums**: Field declarations do not use operations, leaving constraints with nowhere to apply; this can be revisited when `where` clauses or associated types are introduced.
- Consequences and Limitations: Constraints mean "reporting errors earlier," not "checking fewer times"; the same generic body will still be parsed separately for different arguments. The allowed lists are hardcoded; when the language introduces new operations or types, they must be updated in sync, otherwise constraints will fall out of sync with type checking (currently covered by end-to-end tests for both positive and negative cases of all four constraints). Adds `examples/constraints.ae`, 1 end-to-end test (including 9 patterns that must be rejected), and 1 C allocation-counting test case, with full verification run on both platforms.
