# ADR-14: Propagating Recoverable Errors with `?`

- Background: Section §4.5 of the specification requires that "recoverable errors must be handled or explicitly propagated." After ADR-11/13 turned failures into result enum values, every fallible call required writing 6 lines of `match`. A function that "reads three files" became almost entirely error branches, where error handling overwhelmed the main business logic; `examples/file_tidy.ae` is an extreme example of this pattern. At the same time, the language lacked "expression statements," making it impossible to write even a "call once purely for side effects" without first using `let` to bind an unused variable.
- Decision:
  1. `let x = call()?;` is a **propagation statement**: on `Ok`, it extracts and binds the payload to `x` (requiring `Ok` to have exactly one payload); on `Err`, it first frees all currently alive owned variables in the current function, and then returns the result value itself to the caller.
  2. `call()?;` is a **discard statement**: the `Ok` payload (which may be 0, 1, or more) is freed or ignored, and `Err` is similarly returned directly. This also fills the gap of "expression statements," but **is strictly required to end with `?`** to prevent return values from being silently discarded.
  3. Types that can be propagated must be two-variant enums of the form `{ Ok(...), Err(string) }` (`Ok` first, `Err` second), meaning all six preset result enums are supported, as well as custom enums matching this shape.
  4. Propagation requires the **outer function to return the same enum**; `main` cannot propagate (`main` has no return type, so failures must be matched inside `main`).
  5. `?` is statement-level, not expression-level: `f()? + "x"` is invalid.
- Rationale: Error paths must **free already-bound values**, which requires the "list of currently alive owned variables." Since this information is most complete during the parsing phase (`live_owned()` uses the same mechanism as `return`), implementing `?` as a statement is simpler and less prone to missing frees than making it an expression. The `Err` payload directly reuses and returns the entire enum value without unpacking and repacking, naturally preserving the "error context" from being altered. Requiring the outer function to return the same type is an inevitable consequence of currently lacking generics and `From`-style conversions—rather than implicitly rewriting error types, it is better to make boundary `match` statements explicitly visible.
- Rejected Alternatives:
  - **`?` as an expression**: When `Ok` has zero payloads, the expression has no type (the language lacks unit), and early returns inside expressions require temporary value lifetime rules; we implement the statement form first.
  - **Automatic error type conversion** (`From<E>` style): Without traits/generics, any "automation" would have to be hardcoded enum mapping, which would obscure real errors.
  - **Automatically printing errors and exiting when `?` is used in `main`**: This secretly downgrades "recoverable" into "fatal," contradicting §4.5.
  - **Allowing bare call statements without `?`**: This would make "forgetting to handle errors" the default behavior, which is precisely what this entry aims to eliminate.
- Consequences and Limitations: A function can only propagate a single result family (`ReadResult` and `StatusResult` cannot mix `?` within the same function), and crossing family boundaries requires writing a `match` conversion—manifesting in actual code as "thin adapter layers," which is currently the most obvious rough edge and should be eliminated once generic `Result<T, E>` lands. When `Ok` has multiple payloads (such as `FileResult`), binding is not allowed, and one must use a discard statement or `match`. The return path of `?` frees according to the live set at parse time, which does not overlap with moved variables (slots already consumed by calls are skipped during emission).
- Incidental Fix: While implementing this feature, allocation counting revealed two existing leaks—owned temporary arguments of `read_file`/`write_file`/`bytes` were not freed (already fixed in ADR-13), and **owned temporary arguments for read-only borrowed parameters (`&string`)** were not freed (`f("a" + b)` leaked a buffer), which is fixed alongside this entry.
