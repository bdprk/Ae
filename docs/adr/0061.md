# ADR-61: `vec[f64]` — Owned Vector Container for `f64` Elements

- **Background**: Following the implementation of `f64` (ADR-37) and math built-ins (ADR-60), the most significant bottleneck in the data analysis domain (§14.1) is that **containers cannot hold `f64`**. Calculating statistical mean and variance currently requires manually calling `to_f64` on samples one by one before summing them; real-world numerical workflows (feature vectors, time series) are impossible to implement without arrays. This iteration addresses the container layer with the same restraint as ADR-60: we only implement vectors; `map[string, f64]` is out of scope for this round.
- **Decision**:
  1. **Third container family, isomorphic to `vec`**: `Type::VecF`/`Type::VecFRef` are introduced into the type system. The runtime functions `ae_f64vec_*` (new/push/pop/len/get/release/forfeit) are isomorphic to `ae_vec_*`—`double` data, 8 bytes/element, **no state bits, no borrowing flags** (elements are pure values, lacking the borrowed view mechanism used by strings). `ae_f64vec_get` reuses `ae_vec_index` for bounds checking, avoiding duplication of check logic.
  2. **Literal inference by element**: `vec[1, 2]` → `vec`, `vec[1.0, 2.0]` → `vec[f64]`. Mixed types trigger an immediate error (the prohibition of implicit conversion applies to literals as well). The empty literal `vec[]` remains `vec` (i64); empty `vec[f64]` uses the new built-in `f64vec_new()`—aligning with the precedent of `strvec_new` (types with literals do not require a `new` function, but accumulation loops require an empty starting point).
  3. **Explicit rejection of `sort`/`reverse` for `vec[f64]`**: NaN lacks a total ordering; neither i64 numerical comparators nor string byte-order comparators can be applied to `f64` without introducing platform-dependent ordering. Rejection is more honest than providing a "seemingly functional" platform-dependent sort.
  4. **Borrowing and moving follow `vec`**: `&vec[f64]` is a read-only borrow, can be used as a parameter, and can serve as a `&T` generic argument. `for-in` iterates by value (`x` is a copy of `f64`), and the container is borrowed during the loop. Struct fields and enum payloads can use `vec[f64]` and are released exactly once along with the owning value.
  5. **Fixing a vulnerability shared by both families**: The documentation (§Control Flow) has always claimed that "moves or in-place modifications (push/pop/index assignment) within a loop are rejected at compile time," but index assignment did not actually check the borrow table—`for x in v { v[0] = …; }` was permitted for i64 `vec` as well. This round unifies the borrow check to ensure the implementation matches the documentation.
- **Excluded Approaches**:
  - **Making `vec` generic** (`vec[T]` full type instantiation): The current manual implementation of the three containers is intentional—generic containers require a proper generic strategy and a code bloat budget (§Phase B, Item 3), which cannot be addressed as a side task in this round.
  - **`sort` using a "NaN-last" convention**: Any convention is a platform-dependent semantic decision; we reject it for now and will design it according to specifications only when there is a genuine requirement.
  - **`f64` element borrowing (`&f64`)**: The read-only borrow whitelist remains limited to the four containers: string, vec, vec[string], and vec[f64]; there is no use case supporting scalar borrowing.
  - **`map[string, f64]`**: `map_get` returns `IntResult`; an `f64` version requires a decision on the `FloatResult` or `Option[f64]` shape (distinguishing `nan` from "not found"). This requires independent design and is not included in this round.
- **Resource Costs (Archived in `bench/results/2026-11-12-windows-vecoff64/`)**:
  - **Generated C**: `print(1)` 13,822 → 13,909 (+87: `ae_f64vec` typedef and `ae_vec` typedef are both resident—struct layout references them; `f64vec` **functions** are pruned based on reachable closures, with unused ones removed entirely. The first version placed 240 characters of comments next to the typedef in the resident prefix; per ADR-50 discipline, these were moved into the function bodies).
  - **Runtime**: 8 bytes/element slot; all 33 `--leak` test cases (including the new `float_stats`) equal the UCRT baseline of 2 blocks—field/payload release paths execute exactly once.
  - **Verification**: 35 unit + 174 integration tests (4 new: access/iteration, move/borrow early return, 11 classes of rejection, field/payload release); `fmt` verification on 43 files is idempotent; 41 programs pass `check`; `float_stats.ae` (statistics + `sqrt` linkage) outputs are all exactly representable values.
- **Boundaries (External communication must not exceed these)**:
  - Do not claim "generic containers": `vec[f64]` is a manually written third family; generic implementation is an independent decision.
  - Do not claim that maps can hold `f64`: `map[string, i64]` remains the only map shape.
  - One old test **changes semantics**: `vec[1.0]` changes from a rejected item to a valid literal (language growth); the test is updated to assert that mixed literals are still rejected—language changes must be recorded alongside test semantic changes, rather than simply "deleting a test case."
  - Index assignment during loop borrowing changing from "permitted" to "rejected" is a tightening (implementation catching up to existing documentation claims). Theoretically, this might reject programs that previously ran; no such code exists in the current corpus. If encountered in the future, the migration path is to move the write operation outside the loop.
- **Process Discoveries**:
  1. **What `Option` unwrapping contains**: Literal inference initially used `element_ty.unwrap_or(Type::Vec)`, but `element_ty: Option<Type>` contains the **element type**—consequently, `vec[3]` was inferred as `i64`, causing 15 existing tests to fail immediately. Before unwrapping, one must ask "what is actually stored in the Option."
  2. **Second missed update for the `by_ref` flag**: The `first_ty == Type::VecRef` check during `for-in` element construction did not include `VecFRef`, causing value-form C to be generated for borrowed parameters, which `gcc` caught as "v0 is a pointer." Every boolean flag for new types must be checked against "what other types share this path."
