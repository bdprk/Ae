# ADR-23: `exit(status_code)` Termination Statement

- Background: Command-line programs require exit statuses—`grep` returns 1 for no match and 2 for usage errors; pipelines and CI systems rely on them to determine results. Previously, the only way to alter the exit status was to cause a runtime failure (out-of-bounds, assertion), which represents "errors" rather than "normal non-zero conclusions"; `main` always returned `0`. `examples/grep_cli.ae` could only print numbers, making it impossible for scripts to use them in conditional checks.
- Decision:
  1. Add the statement `exit(code);`: `code` must be of type `i64`, and the runtime truncates it to an `int` before calling `exit()`.
  2. Prior to termination, `fflush(stdout)` is executed first, followed by **freeing all live owned variables**, and finally termination.
  3. `exit` counts as "path terminated": functions that end solely via `exit` and never return a value do not require a `return` statement (`returns()` treats `Exit` as termination); it can also be used inside `main`.
- Rationale: Placing resource deallocation before `exit` serves two purposes: first, it ensures allocation count validation (`--leak`) remains meaningful for programs that use `exit`; second, it establishes a deterministic order of "print—free—exit", making it easier to reason about buffer states. Flushing first is necessary because `print` goes through stdio buffering, and calling `exit()` directly might drop the last line when output is redirected to a pipe. Truncating the status code to `int` and documenting it is due to POSIX only retaining the lower 8 bits; pretending to support a 64-bit status code at the language level would cause the program's behavior on Linux to diverge from what is expected when reading the code.
- Rejected Alternatives:
  - **Standard library function like `std::process::exit(code)`**: There is currently no standard library namespace. Statement syntax is the most direct approach and avoids conflicts between "functions that do not return" and the type system (a function returning `i64` cannot appear in an expression position while failing to return a value).
  - **Allowing `main` to return a value as the exit code**: `main` currently lacks a return type; introducing a return type would impact all existing programs and the special handling of `main` (which currently cannot `return` and cannot take arguments), with the sole benefit of saving a single statement.
  - **Exiting directly without freeing in `exit`**: This would simplify implementation, but would make the observable behavior of "orderly exit" inconsistent with "error exit", and allocation count verification would not cover programs using `exit`.
  - **Allowing string/enum status codes in `exit`**: Exit statuses are integers; disallowing other types eliminates an entire layer of conversion rules.
- Consequences and Limitations: Statements within the same block after `exit` are unreachable but must still be syntactically correct (there is no reachability analysis or "unused variable" warning); the range of the status code is not checked, and negative values as well as values greater than 255 will be truncated; there is no `atexit`/cleanup hooks; child processes and signals are not covered (belonging to process APIs). `examples/grep_cli.ae` has been updated to use three states (0/1/2), and 3 new end-to-end tests have been added (status code and flushing, `exit`-only functions, and status code type rejection).
