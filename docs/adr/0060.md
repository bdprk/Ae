# ADR-60: Math Built-ins v1 — 11 Thin Wrappers, IEEE Semantics, `-lm` for Linux Linkage

- **Background**: When `f64` was implemented (ADR-37), it was explicitly decided to leave the "math library" as a separate specification. While data analysis workflows (§14.1) can function without `sqrt` for mean and variance, statistics, geometry, and any serious numerical workflows cannot function without it in the long term. This iteration provides the minimum viable set, with a deliberately narrow scope: each function maps 1:1 to a C library symbol, without introducing any new types, containers, or operators.
- **Decisions**:
  1. **Function Set**: Unary `sqrt`, `abs` (maps to C's `fabs`, not the integer `abs` from `<stdlib.h>`), `floor`, `ceil`, `round`, `exp`, `log` (natural logarithm), `sin`, `cos`; binary `pow(base, exponent)`, `atan2(y, x)` (parameter order matches C). All parameters and return values are `f64`. `min`/`max`/`hypot`/remaining trigonometric functions will be added when there are concrete use cases, avoiding the "copy the entire libm at once" trap.
  2. **Semantics are IEEE/C library semantics, not language-level checks**: Domain errors return values according to IEEE (e.g., `sqrt(-1.0)` → `nan`, `log(0.0)` → `-inf`, `pow(0.0, negative)` → `+inf`), and the program continues execution. This differs from `/` (which reports failure on division by zero) **intentionally**: the check contract for `/` belongs to the language itself (following the same rules as integer division), whereas math functions expose the established domain error representations of IEEE doubles directly to numerical code—terminating on `NaN` would make standard numerical patterns like "probe the domain before calculating" impossible. This asymmetry is documented in the language specification rather than left for the reader to guess.
  3. **Names are reserved**: These names cannot be used for functions, structs, enums, variables, parameters, loop variables, or pattern bindings. This prevents naming collisions between user functions and libm symbols in generated C code and ensures that "these names have only one semantic meaning."
  4. **No implicit conversions, fixed arity**: `sqrt(4)` is a compilation error (`sqrt expects an f64 argument; convert integers explicitly with to_f64`); passing too many or too few arguments results in `takes 2 argument(s)` / `expects 2 f64 argument(s)` respectively. This is consistent with the prohibition of implicit conversions in ADR-37.
  5. **Generated C calls libm symbols directly**: `<math.h>` is already present in every program (required by the float formatter), so no runtime functions are added, and it does not enter the pruning root. The Linux link line now includes `-lm` (a shell script stub since glibc 2.35, but required for older glibc versions); Windows remains unchanged. This is a **linkage command change**, bumping `Cargo.toml` to 0.1.1. Since the cache key includes the compiler version, all old entries are invalidated, leaving no possibility for "old link line artifacts to be reused."
  6. **`round` is C's `round` (rounds 0.5 away from zero)**: `round(2.5)` → `3.0`, `round(-2.5)` → `-3.0`; it is not banker's rounding. The specification document explicitly notes this difference, as both rounding methods have their proponents.
- **Rejected Approaches**:
  - **`Result` wrapping (e.g., `sqrt -> FloatResult`)**: Turning domain errors into values that must be handled would make numerical code unwriteable. IEEE `NaN` is already an accepted representation of domain errors in this language (comparison semantics and `to_string` formatting are already defined).
  - **Language-level `**` operator / overloading `abs` for integers**: Both new operators and overloading fall outside the scope of "thin wrappers." Integer absolute values will be given their own names when there are concrete use cases.
  - **Constant folding**: `sqrt(4.0)` calls libm even at `-O0`. GCC itself performs folding at `-O2`; the compiler does not perform a second pass, keeping the frontend minimal.
  - **Detecting math function usage to decide on `-lm`**: The cost of `-lm` on Linux is zero after merging libm; conditional toggling only adds a branch that needs testing.
- **Resource Costs (Archived in `bench/results/2026-11-11-windows-math/`)**:
  - **Generated C**: `print(1)` remains 13,822 bytes. `MATH_FNS` is a compiler-side constant table and does not enter generated C; programs not using math incur zero cost.
  - **Runtime**: Math built-ins do not allocate memory. All 32 `--leak` test cases (including `math_basics`) match the baseline (2 blocks on Windows).
  - **Verification**: 35 unit tests + 170 integration tests passed. 3 new tests cover exact values, `NaN` domain errors, tolerance-based comparisons, and all rejection paths. 42 files passed `fmt` acceptance; 40 programs passed `check`.
- **Boundaries (Must not be exceeded in external communication)**:
  - **No claims of cross-platform bit-for-bit identical transcendental function output**: `sin(1.0)` and similar may differ by 1 ulp across different libm implementations. The specification provides "consistent exact values and `NaN` spelling, with transcendental values compared using tolerances" (examples and tests are written according to this). The precision of `pow(2,10)=1024.0` is a practical property of libm, not a standard guarantee—confirmed by backfilling on Linux.
  - **No claims of a complete math library**: There is no `f32`, decimal, `min`/`max`, `vec[f64]`/`map[string, f64]`, `&f64` borrowing, complex numbers, or matrices; this is just the 11 functions for v1.
  - `-lm` only appears in the Linux link line; it must not be described as a change for "all platforms."
  - IEEE domain error behavior depends on a correctly implemented libm: bugs in CRT or glibc will directly become the behavior of AE programs; this is noted as a known dependency on external implementations.
- **Process Discoveries**:
  1. **`fmt` acceptance failure caused by stale binaries**: `unknown function 'abs'` originated from an old `ae.exe` in `target/release` (built before the math library). After rebuilding, all 42 files passed. "Verify that release and source are in sync before running acceptance" is worth adding to process memory.
  2. **Hardcoded version tests**: `cache_and_version_commands_work` asserted `ae 0.1.0`, which was broken immediately by the version bump. It has been changed to follow `CARGO_PKG_VERSION`, so future version bumps will not break tests.
  3. **Emission style taken from existing code**: The new emission branch initially included inline `/* line:column */` comments, which were removed after checking existing generated C (which has zero inline block comments)—maintaining consistent style is better than providing extra information.
- **Verification**: Windows 35 unit + 170 integration, 32 `--leak` cases PASS (baseline 2 blocks), 42 files `fmt` accepted, 40 programs `check` passed; archived in `bench/results/2026-11-11-windows-math/`. Linux backfill (same source tree a15e17d, `bench/results/2026-11-11-linux-math/`): 35 unit + 170 integration tests passed, 32 `--leak` cases baseline 0 blocks, 32 `--sanitize` cases 0 reports, 42 files `fmt` accepted, **`math_basics` output is bit-for-bit identical to Windows** (including `pow(2,10)=1024.0` exact value—"libm practical property" confirmed on local machine), generated C byte count identical to Windows. Status: **Dual-platform verified** (2026-11-11).
