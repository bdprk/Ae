# ADR-51: Invoking C Compilers via Relative Filenames Within Temporary Directories

- **Background**: `ae build` fails when executed in a directory with absolute paths containing non-ASCII (e.g., Chinese) characters: `ld.exe: cannot open output file D:/<garbled>/.../.ae-<pid>-0/program.exe: No such file or directory`. The path shown in the error message is corrupted into mojibake. Since `gcc` does not run at all on cache hits, this issue only surfaces on the initial build (or upon cache misses)—which is why it went unnoticed for so long, as daily iterations almost always hit the cache.
- **Root Cause**: `build` creates the temporary directory **within the output file's parent directory**, and then passes the absolute paths of `program.c` and `program.exe` into the `gcc` command line. The MinGW toolchain converts the command line according to the system ANSI code page, replacing characters that cannot be represented in that code page, causing the linker to attempt opening a non-existent path.
- **Decision**: `Command::new(&cc).current_dir(dir).arg("program.c").arg("-o").arg("program.exe")`—set the compiler's working directory to the temporary directory, ensuring that only ASCII relative names appear in the command line. The artifact paths are still managed on the Rust side, and subsequent copying and execution remain unaffected (since Rust internally uses UTF-16).
- **Alternative Approaches Ruled Out**: Moving all temporary directories to the system temporary directory (causes cross-volume copies, and `%TEMP%` itself may also contain non-ASCII characters); 8.3 short name conversion (depends on volume settings and is unstable); direct invocation via `CreateProcessW` (`gcc` itself still uses an ANSI entry point, so the issue does not lie at the invocation layer).
- **Resource Cost**: Zero additional cost (a single `current_dir` call), with no new allocations or caching.
- **Scope**: This fixes **compiler invocations**. The source paths and final artifact copying for `check`/`emit-c`/`run` are already handled natively by Rust and remain unaffected. If the path to the compiler executable specified by `AE_CC` contains non-ASCII characters, it may still fail—this is recorded as a known limitation, and we do not claim that "all non-ASCII path issues are resolved."
- **Verification**: Added an integration test `build_accepts_non_ascii_absolute_output_paths` (creates a "Chinese directory" under a temporary directory, outputs `程序(.exe)`, and points `AE_CACHE` to an empty directory to force `gcc` to actually execute); **the test fails when the fix is rolled back** (verified via `git stash`), and passes on both platforms after applying the fix. The same test passes on Linux (Linux does not perform this encoding conversion, serving as evidence of no regression).
