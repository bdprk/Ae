# ADR-16: Allocator Interface and Allocation Failure Semantics

- **Background**: Section §4.5 requires defining "destruction and allocation failure behavior," and Phase B, Item 5 requires an "allocator interface." Previously, every buffer in the runtime directly used `malloc`/`realloc`/`free`, with failure handling scattered across a dozen locations, each inconsistently deciding whether to "return NULL to let the upper layer report an I/O error" or "directly `exit`." There was no centralized way to replace the allocation backend, and tests could not reliably trigger allocation failure paths (as truly exhausting memory would crash the host machine).
- **Decision**:
  1. All runtime buffers are acquired and released via `ae_allocator` (three function pointers: `alloc`, `resize`, and `release`), with the default implementation being `malloc`/`realloc`/`free`. There are three entry points: `ae_alloc(size, line, column)` (terminates on failure), `ae_alloc_try(size)` (returns NULL on failure, for paths that report failure via return values), and `ae_alloc_resize(block, size, line, column)`. `ae_set_allocator` is provided for the host to replace the backend (for future embed APIs and tracing allocators).
  2. Allocation failure is **terminal**: `ae_fail("out of memory", line, column)` prints the location and exits with status 1. The language lacks `catch`/stack unwinding; it cannot continue execution in a state where a value is only partially constructed, nor can it guarantee that already-constructed functions are released in order. Explicit termination is safer than allowing the program to continue with NULL buffers.
  3. A few paths retain **recoverable** semantics: `try_read_file`, `try_list_dir`, and `try_create_dir` return `Err("out of memory")` upon buffer allocation failure, as their return values are already result enums, providing the caller a place to handle the error.
  4. The diagnostic switch `AE_ALLOC_LIMIT=N` limits the **cumulative** allocated bytes (not live bytes); exceeding this triggers allocation failure handling. This is a switch for tests to deterministically trigger OOM paths, not a memory quota. The cumulative approach requires no size headers for each buffer, incurring zero additional memory overhead, at the cost of counting "reallocations after release." Invalid values (non-numeric, trailing characters) are ignored, and the program runs as usual.
- **Rationale**: Consolidating allocation into a single interface is a prerequisite for "low memory footprint and auditability." Future requirements like arena allocation, statistics, or tracing will only require changing the implementation, not a dozen call sites. Cumulative byte count is sufficient for diagnostics—tests care about "whether the Nth allocation fails," not the precise number of live bytes. Terminal OOM is consistent with the current state of the language (where `ae_fail` is already the unified exit point for out-of-bounds, overflow, and division-by-zero errors). Recoverable OOM is provided only where return values already exist.
- **Rejected Alternatives**:
  - **Making all allocation failures result values**: This would force `ae_str_cat` (the `+` operator) to potentially fail, effectively requiring every expression to be capable of returning an error, which the current language lacks the expressive power to support.
  - **`abort()` on OOM**: `exit(1)` allows the shell and CI to see a standard failure status rather than a signal, and avoids generating core dump noise.
  - **Live byte quota**: This would require adding size headers (8 bytes per allocation) or side-table tracking (hash maps), which conflicts with the "zero-overhead diagnostic" goal and would distort block count statistics for `--wrap` allocation counters.
  - **Implementing `AE_ALLOC_LIMIT` as something other than an environment variable (e.g., compile-time constant)**: Tests need to toggle between success and failure using the same executable, which compile-time constants cannot achieve.
- **Consequences and Limitations**: `ae_set_allocator` is not yet exposed to AE code (no FFI) and can only be called by the C-side host. `AE_ALLOC_LIMIT` uses a cumulative metric, so "large programs + large limits" cannot precisely simulate "imminent memory exhaustion." OOM termination does not guarantee that already-allocated buffers are freed (the process exits, and the OS reclaims memory), which is consistent with §4.5 ("abnormal termination does not guarantee cleanup"). Paths using `ae_alloc_try` must clean up held resources themselves upon failure (e.g., `try_read_file` uses a `failure` flag to unify cleanup).
