# AE 设计决策记录（ADR）

每条记录：背景 → 决策 → 理由 → 后果与 revisit 条件。新决策追加在末尾。

## ADR-1：C 后端作为可替换的启动方案

- 背景：自研机器码后端需覆盖两平台 ABI、对象文件、重定位与调试信息，成本高。
- 决策：第一代编译器生成 C11 并调用受支持的 C 工具链（Windows GCC/MinGW，Linux GCC/Clang）；生成 C 是内部接口，可整体替换。
- 理由：最快获得双平台原生程序与正确性基线；把工程量集中在语言语义与检查器上。
- 后果：构建时间受外部 C 编译器限制；生成 C 必须避免未定义行为（用受检运行时函数承载语义）。当端到端数据表明 C 编译是主要瓶颈且缓存不足以达标时，重新评估后端（见路线阶段 D）。

## ADR-2：整数默认受检，无静默环绕

- 背景：整数语义必须先于实现明确（方案 §4.2）。
- 决策：`+ - * / %` 与一元 `-` 在任何构建模式下遇溢出/除零即报告位置并终止；不提供默认环绕，显式环绕操作留待后续以命名函数引入。
- 理由：安全与正确性优先级最高；开发/发布行为一致使基准数据有效。
- 后果：热循环有检查开销；未来可加"已证明可消除"的优化，但语义不变。

## ADR-3：string 是第一个拥有型类型；移动语义先行

- 背景：需要确定性的资源管理且无 GC；借用检查器需要先在单一类型上验证规则。
- 决策：`string` 拥有堆缓冲；初始化/传参/赋值/返回移动；`+` 消耗两操作数；`print`/`len` 借用。移动后使用编译期拒绝（分支合并保守并集），移动置 NULL + 读取前空检查作运行时兜底；释放幂等，覆盖块退出、提前返回、break/continue、return 全部路径。
- 理由：在受限语法上先跑通所有权机制的端到端正确性，再泛化到结构体/容器；运行时兜底保证"分析器有 bug 也不是内存错误"。
- 后果：循环体内部"先使用后移动"只能由运行时检查捕获（编译期保守并集已覆盖循环后使用）；高频字符串操作有拷贝开销。若运行时检查成为热点，需在证明安全的前提下按位置消除检查。

## ADR-4：构建缓存键建立在生成的 C 之上

- 背景：阶段 D 要求缓存命中与全量构建语义一致，键必须覆盖所有影响结果的输入。
- 决策：键 = SHA-256(生成的 C 文本 + 优化模式 + C 编译器 --version 首行 + 编译器版本 + 目标平台)；条目以临时文件重命名发布，中断不会留下可误用的半成品；缓存写入失败不导致构建失败；AE_CACHE 可覆盖位置。
- 理由：以生成的 C 为键比以源码为键更稳（语义不变的改动仍命中），且无需单独的接口摘要即可保证正确性；编译器升级自动失效。
- 后果：前端复用生成 C 的计算无法跳过（前端仍是 O(源码)）；包级/函数级增量的接口摘要留待多文件模块引入时设计。

## ADR-5：for 范围循环的界只求值一次，计数器不可变

- 背景：`for i in a..b` 的语义必须无歧义（方案 §4.2 求值顺序）。
- 决策：界自左向右求值一次并存放于隐藏变量；`i` 是循环作用域内不可变 `i64`；隐藏自增是受检算术；`continue` 跳转到自增（生成标签），`while` 的 `continue` 保持 C 语义。
- 理由：与常见语言一致、可预测；复用受检算术避免溢出静默回绕。
- 后果：循环中修改界不影响迭代次数（需动态界时用 while）；标签使生成的 C 略难读，属可接受成本。

## ADR-6：内置函数占据保留名

- 背景：`len` 等内置语义必须全局一致，不允许局部遮蔽造成混淆。
- 决策：`len` 为内置，用户不能用 `fn len` 重定义；数组长度是编译期常量，字符串长度是运行时字节计数（UTF-8）。
- 理由：字符串按字节计数的规则简单、可预测，字符级索引延后到字符串 API 设计时统一决策。
- 后果：字符/字素级 `len` 需要新名字或显式 API；内置清单增长时需文档与测试同步。

## ADR-7：编译器工作线程使用大栈

- 背景：递归下降解析与深层 AST 释放依赖递归；Windows 主线程默认栈偏小。
- 决策：编译入口把工作放入 256MB 栈的专用线程；语法层仍显式限制嵌套（表达式 128、块 64、循环 64）。
- 理由：栈溢出是崩溃而非诊断；双重防护让"合法但深"的输入得到明确错误而不是崩溃。
- 后果：内存上限提高；限制数值是早期资源约束，将来按需调整并更新文档。

## ADR-8：字符串现为 NUL 结尾的 C 串；长度携带型表示是既定演进方向

- 背景：C 后端下最简单的字符串表示是 `char *`。实测（工作负载 B，20k 行/1.4 MB）：`slice` 每次调用需 `strlen` 定位，按行切片使 grep 从 5.81 ms 恶化到 202 ms（40×），暴露表示法成本。
- 决策：当前版本保留 `char *` 表示；`len`/`slice`/`bytes` 为 O(n)。文件搜索基准保持朴素字节扫描（对 vec 的 O(1) 索引），不使用按行 slice。`contains` 走平台 `strstr`。演进方向（后续单独立项）：字符串改为携带长度的内部表示或借用视图（方案 §4.2），使 `len`/`slice` O(1)，再重测工作负载 B。
- 演进（2026-11-10，已落地）：字符串改为长度携带型 `ae_string {ptr, len}`——`len`/`slice` O(1)，连接不再扫描，`write_file` 二进制安全，`bytes()` 按长度遍历。全部 70 项测试语义不变。
- 剩余差距（工作负载 B 实测）：slice 版 grep 7.58 ms > 朴素版 5.81 ms > Gojo 4.41 ms——每行 `slice` 仍分配一次（2 万次 malloc）。下一步：借用视图（`&str` 式零拷贝切片，方案 §4.2"区分拥有数据的字符串和借用视图"），使切片不分配；那是独立的设计窗口。
- 后果：`len`/`slice` 时间复杂度达标；按行切片的分配成本仍高，基准继续用朴素字节扫描并如实披露。NUL 截断语义仅影响 `contains`（`strstr` 语义），`len`/`bytes` 已按长度精确。
- 视图演进（2026-11-10，已落地）：`ae_strview {ptr, len}` 借用视图 + `slice_view` 零拷贝切片 + 借用跟踪器（基变量在视图存活期不可移动/重赋值，容器借用期不可修改）+ `for x in vec[string]` 视图迭代。视图版 grep 7.34 ms——切片分配已消除，剩余瓶颈转为逐字节边界检查循环（140 万次受检访问），属标准库成熟度（memchr 类行扫描）而非表示法问题。
