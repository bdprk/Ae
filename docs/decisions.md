# AE 设计决策记录（ADR）

每条记录：背景 → 决策 → 理由 → 后果与 revisit 条件。新决策追加在末尾。

## ADR-1：C 后端作为可替换的启动方案

- 背景：自研机器码后端需覆盖两平台 ABI、对象文件、重定位与调试信息，成本高。
- 决策：第一代编译器生成 C11 并调用受支持的 C 工具链（Windows GCC/MinGW，Linux GCC/Clang）；生成 C 是内部接口，可整体替换。
- 理由：最快获得双平台原生程序与正确性基线；把工程量集中在语言语义与检查器上。
- 后果：构建时间受外部 C 编译器限制；生成 C 必须避免未定义行为（用受检运行时函数承载语义）。当端到端数据表明 C 编译是主要瓶颈且缓存不足以达标时，重新评估后端（见路线阶段 D）。

## ADR-2：整数默认受检，无静默环绕

- 背景：整数语义必须先于实现明确（方案 §4.2）。
- 决策：`+ - * / %` 与一元 `-` 在任何构建模式下遇溢出/除零即报告位置并终止；不提供默认环绕，显式环绕操作留待后续以命名函数引入。
- 理由：安全与正确性优先级最高；开发/发布行为一致使基准数据有效。
- 后果：热循环有检查开销；未来可加"已证明可消除"的优化，但语义不变。

## ADR-3：string 是第一个拥有型类型；移动语义先行

- 背景：需要确定性的资源管理且无 GC；借用检查器需要先在单一类型上验证规则。
- 决策：`string` 拥有堆缓冲；初始化/传参/赋值/返回移动；`+` 消耗两操作数；`print`/`len` 借用。移动后使用编译期拒绝（分支合并保守并集），移动置 NULL + 读取前空检查作运行时兜底；释放幂等，覆盖块退出、提前返回、break/continue、return 全部路径。
- 理由：在受限语法上先跑通所有权机制的端到端正确性，再泛化到结构体/容器；运行时兜底保证"分析器有 bug 也不是内存错误"。
- 后果：循环体内部"先使用后移动"只能由运行时检查捕获（编译期保守并集已覆盖循环后使用）；高频字符串操作有拷贝开销。若运行时检查成为热点，需在证明安全的前提下按位置消除检查。

## ADR-4：构建缓存键建立在生成的 C 之上

- 背景：阶段 D 要求缓存命中与全量构建语义一致，键必须覆盖所有影响结果的输入。
- 决策：键 = SHA-256(生成的 C 文本 + 优化模式 + C 编译器 --version 首行 + 编译器版本 + 目标平台)；条目以临时文件重命名发布，中断不会留下可误用的半成品；缓存写入失败不导致构建失败；AE_CACHE 可覆盖位置。（后续修订见 ADR-27：键加入 `AE_CC` 原样字符串，条目增加 manifest 摘要校验，编译器无法识别时禁用缓存。）
- 理由：以生成的 C 为键比以源码为键更稳（语义不变的改动仍命中），且无需单独的接口摘要即可保证正确性；编译器升级自动失效。
- 后果：前端复用生成 C 的计算无法跳过（前端仍是 O(源码)）；包级/函数级增量的接口摘要留待多文件模块引入时设计。

## ADR-5：for 范围循环的界只求值一次，计数器不可变

- 背景：`for i in a..b` 的语义必须无歧义（方案 §4.2 求值顺序）。
- 决策：界自左向右求值一次并存放于隐藏变量；`i` 是循环作用域内不可变 `i64`；隐藏自增是受检算术；`continue` 跳转到自增（生成标签），`while` 的 `continue` 保持 C 语义。
- 理由：与常见语言一致、可预测；复用受检算术避免溢出静默回绕。
- 后果：循环中修改界不影响迭代次数（需动态界时用 while）；标签使生成的 C 略难读，属可接受成本。

## ADR-6：内置函数占据保留名

- 背景：`len` 等内置语义必须全局一致，不允许局部遮蔽造成混淆。
- 决策：`len` 为内置，用户不能用 `fn len` 重定义；数组长度是编译期常量，字符串长度是运行时字节计数（UTF-8）。
- 理由：字符串按字节计数的规则简单、可预测，字符级索引延后到字符串 API 设计时统一决策。
- 后果：字符/字素级 `len` 需要新名字或显式 API；内置清单增长时需文档与测试同步。

## ADR-7：编译器工作线程使用大栈

- 背景：递归下降解析与深层 AST 释放依赖递归；Windows 主线程默认栈偏小。
- 决策：编译入口把工作放入 256MB 栈的专用线程；语法层仍显式限制嵌套（表达式 128、块 64、循环 64）。
- 理由：栈溢出是崩溃而非诊断；双重防护让"合法但深"的输入得到明确错误而不是崩溃。
- 后果：内存上限提高；限制数值是早期资源约束，将来按需调整并更新文档。

## ADR-8：字符串现为 NUL 结尾的 C 串；长度携带型表示是既定演进方向

- 背景：C 后端下最简单的字符串表示是 `char *`。实测（工作负载 B，20k 行/1.4 MB）：`slice` 每次调用需 `strlen` 定位，按行切片使 grep 从 5.81 ms 恶化到 202 ms（40×），暴露表示法成本。
- 决策：当前版本保留 `char *` 表示；`len`/`slice`/`bytes` 为 O(n)。文件搜索基准保持朴素字节扫描（对 vec 的 O(1) 索引），不使用按行 slice。`contains` 走平台 `strstr`。演进方向（后续单独立项）：字符串改为携带长度的内部表示或借用视图（方案 §4.2），使 `len`/`slice` O(1)，再重测工作负载 B。
- 演进（2026-11-10，已落地）：字符串改为长度携带型 `ae_string {ptr, len}`——`len`/`slice` O(1)，连接不再扫描，`write_file` 二进制安全，`bytes()` 按长度遍历。全部 70 项测试语义不变。
- 剩余差距（工作负载 B 实测）：slice 版 grep 7.58 ms > 朴素版 5.81 ms > Gojo 4.41 ms——每行 `slice` 仍分配一次（2 万次 malloc）。下一步：借用视图（`&str` 式零拷贝切片，方案 §4.2"区分拥有数据的字符串和借用视图"），使切片不分配；那是独立的设计窗口。
- 后果：`len`/`slice` 时间复杂度达标；按行切片的分配成本仍高，基准继续用朴素字节扫描并如实披露。NUL 截断语义仅影响 `contains`（`strstr` 语义），`len`/`bytes` 已按长度精确。
- 视图演进（2026-11-10，已落地）：`ae_strview {ptr, len}` 借用视图 + `slice_view` 零拷贝切片 + 借用跟踪器（基变量在视图存活期不可移动/重赋值，容器借用期不可修改）+ `for x in vec[string]` 视图迭代。视图版 grep 7.34 ms——切片分配已消除，剩余瓶颈转为逐字节边界检查循环（140 万次受检访问），属标准库成熟度（memchr 类行扫描）而非表示法问题。
- 融合路径（2026-11-10，已落地）：`count_lines_with(text, pattern)` 单遍零分配（memchr 找行 + 首字节 memchr 跳过行内搜索）。工作负载 B 融合版 2.14 ms，快于 Gojo 组合式 4.72 ms（2.2 倍）与全部参照；组合式 lines()+视图+contains 仍为 6.37 ms 供对比。标准库以融合原语服务热路径，组合式原语服务可读性。

## ADR-9：C 后端端到端代价的实测小结与后端评估触发条件（不构成后端决策）

- 背景：ADR-1 将 C11 后端作为可替换的启动方案，约定"当端到端数据表明外部编译/链接是主要瓶颈且缓存不足以达标时重新评估"。本会话补齐了这条判断所需的一档证据（2026-11-10，Windows 10 x64/AMD64，MinGW-W64 GCC 16.2.0 UCRT、Go 1.26.0、rustc 1.99.1、Python 3.10.11，D 盘源码工作区）：
  - 单程序相位计时（`AE_TIMINGS=1`，每模式两次、每次全新空 AE 缓存目录）：前端+生成 C 约 0.37–0.50 ms/次；**单次外部 C 编译+链接约 0.74–0.81 s/次**（开发 `-O0` 与 release `-O2` 各两轮；输出为单次 gcc 调用，编译+链接未拆分）。
  - `bench/run.py --cold` 两轮（差分语义相同的求和程序；插值顺序的具体实现因轮次而异，未入库的原始 JSON 在会话临时目录）：冷构建中位数约 ae 0.75 s 与 1.09 s、Go 0.52 s 与 0.75 s、Rust 0.14 s 与 0.25 s；同会话另有早一轮块式运行归档于 `bench/results/2026-11-10-windows-local/`（见 `bench-cold.json` 等，其记录 methodology 与本轮不同）。首个冷样本在 Go 与 AE 上明显偏大（约 8.7 s / 1.7 s），指示冷启动/外部工具链状态噪声；轮间差异不池化、不同轮不直接比较。
  - 解读为**观察**：在该主机/该微基准/该工具链/冷缓存配置下，外部 C 编译+链接阶段远大于前端+生成 C；但按 ADR-4，生成 C/优化/编译器标识/版本/平台未变时内容寻址缓存直接重用可执行文件，暖执行路径整段外部阶段被跳过——庞大冷墙钟不等于每次构建都庞大。
  - **未建立**：Linux 实测（本会话无 Linux 环境）、单阶段 CPU 时间（Windows `resource` 不可用，未用 GNU time 等替代）、峰值内存、第二 C 工具链、超出微基准的规模曲线、差异化参数/分模块等选项的顺手实验。以上使证据强度停留在"观察级"。

- 决策：**维持 ADR-1 不变**——C11 后端 + 用户机已检测 C 工具链仍为默认后端；前端/代码生成优化与缓存（ADR-4）仍是独立、已在案的杠杆。本条不预批任何具体替代后端，也不触发预算；后端/链接器/分配器类替代均按方案 §2 与 §12"自研范围失控"纪律作单独立项决策。

- 理由：ADR-1 与方案 §5.2 要求"端到端数据"作为切换依据，而现有数据是单主机、单微基准、单工具链、外部缓存未控、不含内存与第二平台的观察级快照；方案 §12 亦明示基准误导风险（须同功能/同输入/同安全语义/同版本口径，保留原始数据）。微基准上的比例不得外推为常数（前端量级随源码规模增长，外部阶段随翻译单元与优化档位增长）。

- 后果与 revisit 条件（满足且记录完整前不重新评估）：
  1. 双平台（Windows/Linux）同方法论补测——现行 `bench/run.py` 式插值重复、环境与缓存状态声明、重复次数记录；
  2. 分阶段壁钟+CPU+峰值内存（编译器自身档案，如 GNU time 或平台等价物），含真实规模程序（如文件搜索类）；
  3. 暖路径量化：缓存命中率，及失效场景（源码/公共接口/选项/编译器变更）下外部阶段的实际发生频率；
  4. 候选后端按方案 §5.2 做"快速代码生成 vs 优化代码生成"两个可比较实验，并完成第三方许可与全自研边界清单（§2）；自研路线需按 Win x64 + System V ABI、对象文件、重定位、栈展开、调试信息、链接、指令兼容评估工作量——即方案 §5.2/§12 挙例的 ABI 等覆盖面；
  5. 决策与预算单独立项记录（含回退方案：失败则回守 ADR-1 默认路径）。

## ADR-10：枚举用「标签 + 每变体独立负载结构体」的联合，match 强制穷尽

- 背景：方案阶段 B 要求引入枚举与模式匹配；同时 §4.5 要求可恢复错误用结果值表达，而当前 `read_file` 失败只能终止进程。没有枚举就无法在语言内定义 `Result`/`Option` 式的可恢复错误。
- 决策：
  1. `enum Name { Variant, Variant(i64), Variant(string, bool) }`：变体可带 0–16 个位置负载，负载类型在首版限定为 `i64`/`bool`/`string`。构造写作 `Name::Variant(...)`。
  2. 布局为 C 的 `enum tag` + `union`，**联合的成员是每个变体各自的负载结构体**（`struct { int64_t p0; int64_t p1; }`），访问路径 `v.u.v1.p0`。
  3. `match 裸枚举变量 { ... }` 是语句；每个变体必须恰好出现一次（穷尽性），不提供通配符与嵌套模式。
  4. 枚举是拥有型值：赋值/传参/返回移动它，作用域退出、提前返回与跳转路径按变体释放负载；`release` 幂等，`forfeit` 只清空不释放。
  5. `string` 负载在分支里绑定为**只读视图**（`string view`），任何负载都不能被移出枚举；绑定变量不是拥有型，不参与释放。
  6. 编译期把 `match` 视为「全部变体都返回」才能满足返回值检查。
- 理由：负载结构体联合避免了 C 联合的字段别名问题；裸变量主题使借用跟踪器能保证「匹配期间主题不可移动/不可赋值」，无需跨语句临时值的生命周期分析；穷尽性检查让 `match` 没有漏网路径，也不需要运行时 trap。
- 已排除的做法：
  - **联合直接放各变体的字段**：C 的联合同一时刻只有一个成员有效，`{ .f1_0 = 4, .f1_1 = 5 }` 会互相覆盖。实测 `Rect(4,5)` 得到 `5x5`，故改为变体结构体。
  - **用 C `switch` 生成 match**：分支体里的 `break` 会被 `switch` 吞掉，破坏「break 退出最内层循环」的语义；改为 if/else 链，比较次数由编译器处理。
  - **允许 `vec`/结构体负载**：这些类型没有可绑定的借用表示（string 有 `string view`），移出又违反「不拆解拥有值」的一致规则；等视图类型扩展后再放开。
  - **`match` 作为表达式**：需要表达式级类型统一与临时值生命周期规则，先做语句形式。
- 后果与限制：`match` 主题必须是裸枚举变量（函数返回值需先绑定变量）；`enum` 与 `struct` 一样只支持同文件内先声明后使用；枚举值没有运行时空哨兵，移动后使用依赖编译期移动集合（与结构体一致）；负载不能嵌套枚举，因此不存在递归布局。

## ADR-11：可恢复错误用预置结果枚举表达；`+` 对借用字符串做复制

- 背景：方案 §4.5 要求「可恢复错误使用结果值且必须处理或显式传播；I/O 接口不能静默丢弃错误」，而此前 `read_file` 失败只能终止进程。枚举（ADR-10）落地后可以在语言内定义结果类型，但还没有泛型，无法写一个 `Result<T, E>`。
- 决策：
  1. 编译器为每个程序预置三个结果枚举，用户无需导入即可命名：`ReadResult{Ok(string), Err(string)}`、`WriteResult{Ok(i64), Err(string)}`、`IntResult{Ok(i64), Err(string)}`。变体顺序固定（Ok = 0，Err = 1）且不可重定义。
  2. 新增可失败内建 `try_read_file(path) -> ReadResult`、`try_write_file(path, content) -> WriteResult`、`parse_int(text) -> IntResult`；失败原因字符串来自 `strerror` 或内建文案（"not a base-10 integer"、"integer out of i64 range"）。`parse_int` 严格：可选正负号、只允许 ASCII 数字、整串必须消费完、正负分别按 `INT64_MAX`/`INT64_MAX+1` 界检查，绝不静默截断或回绕。
  3. 新增 `to_string(i64) -> string`，与 `parse_int` 构成往返。
  4. `+` 接受拥有型 `string`、`string view`、结构体字符串字段、`vec[string]` 元素：**拥有型操作数移交缓冲（`ae_str_cat` 释放两者），借来的操作数先复制再拼接**，借用本身不受影响、仍然可用。
- 理由：`str_cat` 会释放两个操作数，把借用直接交进去就是双重释放——这是本轮实测到的真实缺陷（`print("file " + parts[0])` 触发了堆损坏 c0000374）。按「拥有则移交、借用则复制」统一处理，比在每处调用点手工 `slice` 更不容易出错，也让 `"prefix: " + args()[1]` 这类最常见的脚本写法成为合法代码。视图可拼接后，`slice(x, 0, len(x))` 只用于确实需要副本的场合。
- 已排除的做法：
  - **`read_file` 改成返回结果值**：会破坏既有程序与基准；保留 `read_file`/`write_file` 的「失败即终止」语义，另设 `try_*` 明确区分可恢复与不可恢复，符合 §4.5「panic 用于不可恢复」的分工。
  - **全局 `last_error()` + 返回空串**：空文件与失败不可区分，且引入隐式全局状态。
  - **在编译器里写泛型 `Result<T, E>`**：泛型尚未设计，先用三个具体枚举，等泛型落地后迁移为 stdlib 模块中的泛型类型（本条记录即为迁移前的临时形态）。
  - **`+` 对视图返回视图**：视图形需要生命周期，且 `a` + `b` 的结果通常要脱离两个操作数存活，做不到安全。
- 后果与限制：三个预置枚举恒占用枚举编号 0–2，且其 C 布局与释放函数总会生成（未使用时体积开销极小）；预置类型名与 `try_*`/`parse_int`/`to_string` 成为保留名，用户不能重定义；`match` 主题是裸变量，所以结果值必须先 `let` 绑定；错误信息文本随平台 `strerror` 语言变化，程序不应依赖其精确内容。

## ADR-12：只读借用参数（`&string`、`&vec[string]`）与目录遍历

- 背景：方案 §19.3 把「跨平台批量文件整理、目录遍历」列为首批验收任务，而语言此前只能读写单个文件，且函数参数一律按值移动——递归遍历需要反复使用同一个路径/模式字符串，按值传参在循环里立刻被移动集合拒绝。
- 决策：
  1. 新增参数类型 `&string`，绑定为 `string view`：调用点把实参表达式包成 `AE_VIEW(...)`，不移动、不复制；实参可为拥有型字符串、字面量、视图或 `vec[string]` 元素。函数体内它是一个普通视图（`len`/`contains`/`slice`/`==`/`print`/`+` 可用），不能返回、不能转交按值接收的参数。
  2. 新增参数类型 `&vec[string]`（`Type::StrVecRef`），与既有 `&vec` 同构：只读、可 `len`、可 `v[i]` 取元素视图、可 `for x in v` 迭代、可继续以 `&vec[string]` 转发；不可 push/pop/写/移动。
  3. 借用值没有独立存储：`let q = borrowed_param;` 被拒绝（此前对 `&vec` 也存在这个漏洞，会生成非法 C），借用只能作为参数或模式绑定存在。
  4. 枚举负载放开到 `vec` 与 `vec[string]`，在 `match` 分支里分别绑定为 `&vec` 与 `&vec[string]`，负载同样不能被移出。
  5. 新增文件系统内建：`try_list_dir(path) -> DirResult{Ok(vec[string]), Err(string)}`（只返回条目名，不含 `.`/`..`，按字节序排序以保证两平台一致）、`path_exists(path) -> bool`、`path_is_dir(path) -> bool`。Windows 用 `FindFirstFileW`/`GetFileAttributesW`（UTF-8 路径转 UTF-16），POSIX 用 `opendir`/`stat`。
- 理由：递归/重复调用需要「借用而非移动」的参数，手写 `slice(x, 0, len(x))` 制造副本既慢又容易被遗忘；视图已经是语言内成熟表示（ADR-8），把它开放为参数类型是零新增运行时成本的做法。`try_list_dir` 复用 ADR-11 的结果值模式，目录不存在是可恢复错误而不是进程终止——文件整理脚本必须能跳过无权限目录继续工作。
- 已排除的做法：
  - **`fn f(s: string)` 自动借用**：会让「按值即移动」的规则变得依赖调用点形状，破坏现有移动语义的可预测性；显式 `&string` 更清楚。
  - **`list_dir(path) -> vec[string]`（失败即终止）**：遍历必然遇到无权限/竞态删除的目录，终止不可接受。
  - **返回完整路径而非条目名**：拼接策略（分隔符、相对/绝对）属于调用方，运行时不应预设。
- 后果与限制：`&string` 是「调用期间有效」的浅借用，没有跨函数生命周期检查，因此不能返回、不能存进变量；`&vec[string]` 同理。目录遍历不返回文件元数据（大小、时间），不递归，不区分符号链接；排序是字节序（非本地化排序），仅为可复现。`vec[string]` 负载使 `DirResult` 的 C 布局包含 `ae_strvec`，其释放由枚举释放例程接管。

## ADR-13：路径代数与文件元数据/整理操作内建

- 背景：ADR-12 之后可以递归遍历目录，但方案 §19.3 的文件整理验收任务还需要三件缺失的能力：一是拼接路径（此前只能 `dir + "/" + name`，容易产生 `dir//name` 或不含分隔符的错误路径）；二是读取文件大小/时间（否则无法「按大小/时间归类」）；三是搬移、复制、删除与建目录（否则只能读不能整理）。ADR-12 明确把「不返回文件元数据」列为限制，本条正是对该限制的收口。
- 决策：
  1. 新增纯字符串路径函数 `path_join(dir, name)`、`path_name(path)`、`path_parent(path)`。不规范化、不访问文件系统；输出统一 `/`；`path_join` 遇到绝对 `name` 时整个替换 `dir`；`path_parent` 对无分隔符路径返回空串。
  2. 新增预置枚举 `FileResult{Ok(i64 size, i64 modified, bool is_dir), Err(string)}`（编号 4）与 `StatusResult{Ok, Err(string)}`（编号 5）。二者与 ADR-11 的四个结果枚举同批预置、同顺序校验，迁移计划相同（泛型 `Result<T, E>` 落地后整体搬到 stdlib）。
  3. 新增 `try_file_info(path) -> FileResult`：`modified` 统一为「自 Unix 纪元起的秒数」，Windows 侧把 FILETIME 的 100ns 计数换算成同一口径（`/10000000 - 11644473600`），因此两平台数值可直接比较。
  4. 新增 `try_copy_file`、`try_rename_path`、`try_remove_file`、`try_create_dir`、`try_remove_dir`，全部返回 `StatusResult`。`try_create_dir` 具备 `mkdir -p` 语义；`try_remove_dir` 只删空目录。
- 理由：路径拼接的错误率极高（分隔符、绝对路径、空参数），把它做成内建比在每个示例里手写拼接更可靠；元数据以秒为单位而不是纳秒，是因为 i64 纳秒只能表示到 2262 年且各平台结构体字段宽度不同，秒级整数在两侧都无歧义。写操作返回 `StatusResult` 而不是复用 `WriteResult`，是因为「删除/改名/建目录」没有天然的返回值，用 `Ok` 空负载如实表达，避免编造一个无意义的计数。
- 已排除的做法：
  - **`try_remove_file` 在 POSIX 上直接 `remove()`**：它会删掉空目录，导致同一个程序在两平台行为不同；改为先判定 `is_dir` 并报错，宁可少一个便利也不产生平台分歧。
  - **递归删除 `try_remove_all(path)`**：一旦参数算错就不可恢复，且当前语言没有「确认」这类交互能力。整理脚本应自己列出条目逐个删除（示例 `examples/file_tidy.ae` 即如此）。
  - **`path_parent` 对相对路径返回 `.`**：会让 `path_join(".", "a")` 产生 `./a`，把「有没有父目录」这个信息藏起来；返回空串让调用方显式选择默认值。
  - **路径规范化（解析 `..`、折叠 `//`、大小写统一）**：符号链接与 Windows 大小写不敏感使规范化结果依赖真实文件系统，属于 I/O 语义而非字符串语义，留给后续显式的 `try_canonicalize`。
  - **`try_create_dir` 目录已存在时报错**：调用方通常只想「确保存在」，报错会强迫每个调用点写重试分支。
- 后果与限制：六个结果枚举恒占用编号 0–5；新增 9 个保留名。复制不保留权限/时间戳，改名跨卷在 Windows 上依赖 `MOVEFILE_COPY_ALLOWED`（POSIX `rename` 跨卷会失败并如实返回 `Err`）；不提供递归删除、不提供目录大小汇总；元数据不含权限位与访问时间；`path_*` 不处理 `~` 展开与环境变量替换。同时修正一个既有缺陷：`read_file`/`write_file`/`bytes` 的拥有型临时实参此前未释放（`write_file("a" + b, ...)` 会泄漏路径缓冲），现在与其它内建一致，在调用后释放临时值。

## ADR-14：用 `?` 传播可恢复错误

- 背景：方案 §4.5 要求「可恢复错误必须处理或显式传播」。ADR-11/13 把失败做成结果枚举值后，每个可失败调用都要写 6 行 `match`，一个「读三个文件」的函数几乎全是错误分支，错误处理淹没了主线逻辑；`examples/file_tidy.ae` 就是这种形态的极端例子。同时语言没有「表达式语句」，连「只为副作用调用一次」都写不出来（必须先 `let` 绑定一个没人用的变量）。
- 决策：
  1. `let x = call()?;` 是**传播语句**：`Ok` 时把负载移出并绑定到 `x`（要求 `Ok` 恰好一个负载）；`Err` 时先释放当前函数里所有仍存活的拥有型变量，再把该结果值本身返回给调用者。
  2. `call()?;` 是**丢弃语句**：`Ok` 负载（可能是 0 个、1 个或多个）被释放或忽略，`Err` 同样直接返回。它同时补上了「表达式语句」这一空缺，但**只允许以 `?` 结尾**，避免把返回值无声丢掉。
  3. 能传播的类型必须是形如 `{ Ok(...), Err(string) }` 的两个变体枚举（`Ok` 在前、`Err` 在后），因此六个预置结果枚举都可用；自定义枚举照此形状也可用。
  4. 传播要求**外层函数返回同一个枚举**；`main` 不能传播（`main` 没有返回类型，失败必须在 `main` 里 `match` 掉）。
  5. `?` 是语句级的，不是表达式级：`f()? + "x"` 不合法。
- 理由：错误路径必须**释放已经绑定的值**，这需要「当前存活的拥有变量列表」，而该信息在解析期最完整（`live_owned()` 与 `return` 用的是同一份机制），所以把 `?` 做成语句比做成表达式更省事、更不容易漏释放。`Err` 载荷直接复用整个枚举值返回，不拆包再打包，天然保持「错误上下文」不被改写。要求外层函数返回同一类型，是当前没有泛型、也没有 `From` 式转换的必然结果——与其偷偷改写错误类型，不如让边界处的 `match` 显式可见。
- 已排除的做法：
  - **`?` 作为表达式**：`Ok` 零负载时表达式没有类型（语言没有 unit），且表达式内部提前返回需要临时值生命周期规则；先做语句形式。
  - **自动转换错误类型**（`From<E>` 风格）：没有 trait/泛型，任何「自动」都只能是硬编码的枚举映射，会掩盖真实错误。
  - **`?` 在 `main` 里自动打印错误并退出**：把「可恢复」偷偷降级成「终止」，与 §4.5 相反。
  - **允许裸调用语句而无 `?`**：会让「忘记处理错误」变成默认行为，正是本条要消除的。
- 后果与限制：一个函数只能传播一个结果族（`ReadResult` 与 `StatusResult` 不能在同一函数里混用 `?`），跨族边界必须写 `match` 转换——这在实际代码里表现为「薄薄的适配层」，是当前最明显的粗糙处，泛型 `Result<T, E>` 落地后应消除。`Ok` 有多个负载（如 `FileResult`）时不能绑定，只能用丢弃语句或 `match`。`?` 的返回路径按解析期的存活集合释放，与被移动的变量互不重叠（发射时跳过调用已经消费的槽位）。
- 顺带修正：实现本条时用分配计数发现两处既有泄漏——`read_file`/`write_file`/`bytes` 的拥有型临时实参未释放（ADR-13 已修），以及**只读借用参数（`&string`）的拥有型临时实参**未释放（`f("a" + b)` 泄漏一份缓冲），后者在本条一并修复。

## ADR-15：`map[string, i64]` 哈希表

- 背景：方案阶段 B 要求语言具备「以任意字符串为键的计数/归属表」。此前的初级替代品都有硬伤：`vec[string]` 查找是 O(n)，词频统计（`examples/word_count.ae`）在万级词量下退化为平方；结构体字段是固定集合，无法表达「每天各算一次」这类动态键；用「排序后的成对向量 + 二分」需要每个调用点手写并维护这一不变量。ADR-12/13 的文件整理流程也已经出现「按扩展名/大小分桶」的天然需求。
- 决策：
  1. 引入 `Type::Map`，唯一实例化是 `map[string, i64]`；类型拼写与内建名（`map_new`/`map_get`/`map_has`/`map_remove`/`keys`）进入保留字表（37 项）。
  2. `m[key] = n;` 是语句（`Statement::MapPut`）：键由运行时代为复制，值为 `i64`。可变性绑定在容器上——`let m = map_new()` 之后不能写入，与 `vec` 一致。
  3. 查询返回**结果值**而不是「哨兵 0」：`map_get(m, k) -> IntResult` 缺失时为 `Err("key not found")`。`keys(m)` 返回排好序的**副本**，`len(m)` 返回条目数。
  4. 接收者可以是裸映射变量或其结构体字段（`MapPlace::{Var, Field}`），但不可以是任意表达式：`map_get(build(), k)` 这类「临时映射」没有意义（表会立刻被释放），限制在语法层面比在运行时检查更清楚。
  5. 运行时实现为开放寻址 + 线性探测：FNV-1a 哈希、`EMPTY/FULL/DELETED` 三态、删除留墓碑以保持探测链完整、负载因子 3/4 时翻倍扩容并清墓碑。扩容缓冲用 `malloc + memset` 而非 `calloc`——`--wrap` 只包装 `malloc/free/realloc`，`calloc` 分配再用包装的 `free` 归还会被计成「未知块」并破坏堆一致性（这一条是实现期踩到的真实故障，记录于此以免重犯）。
- 理由：`map_get` 返回 `IntResult` 而不是 `i64`，是因为 0 是合法计数值，「缺失」与「计数为 0」必须可区分——这正是 C 风格映射 API 最常见的错误来源，而语言已经有现成的结果枚举（ADR-11），复用它零成本。`keys()` 复制并排序，是为了让「遍历映射」这件事在两平台产生**同一顺序的输出**：哈希顺序随实现与插入历史变化，直接暴露会污染所有输出与测试。只有 `string → i64` 一种实例化，是因为当前没有泛型（阶段 B 后续项），把 `vec`/`string` 值放进表会立刻引出「槽位里的 payload 由谁释放」的复杂度，而 `i64` 值让表成为纯 POD 容器，释放只需遍历键。
- 已排除的做法：
  - **`map_get` 返回 `i64`，缺失给 0**：无法与真实 0 区分，词频统计会把「没出现」和「出现 0 次」混为一谈。
  - **迭代器/`for k, v in m`**：需要新的借用型迭代器协议与「迭代期间禁止修改」的静态检查；`keys()` 先取快照是当前移动语义下唯一无需新增规则的安全形态。
  - **`map[string, i64]` 之外的实例化（`map[string, string]` 等）**：没有泛型时只能靠手工模板，且立即需要「槽位内拥有值的释放」；留到泛型之后。
  - **链地址法**：每个槽位要额外指针与分配，缓存局部性差，与 §4.5 的低内存占用目标相反；线性探测的高负载因子需要墓碑，这个代价可以接受。
  - **扩容时原地（rehash in place）**：实现复杂且有中间不一致态，翻倍 + 重建两张数组更简单，仍摊还 O(1)。
- 后果与限制：只有 `string → i64`；不能直接遍历映射（用 `keys()`，代价是一次 O(n log n) 复制）；删除留墓碑，长期「插入—删除」循环下桶数组不会收缩（墓碑会在扩容时清除）；`keys()` 排序是字节序而非本地化排序。映射是拥有型值，移动语义与 `string`/`vec` 一致，运行时有 `slots` 空指针哨兵；结构体字段中的映射随结构体一起释放。新增端到端测试覆盖插入/覆盖/删除/缺失查询/键序/结构体字段/误用拒绝，`examples/word_count.ae` 作为验收示例，分配计数与基线一致（`blocks=2`）。

## ADR-16：分配器接口与分配失败语义

- 背景：方案 §4.5 要求明确「析构及分配失败行为」，阶段 B 第 5 项要求「分配器接口」。此前运行时的每个缓冲区都直接 `malloc`/`realloc`/`free`，失败处理散落在十几处，各自决定「返回 NULL 让上层报 I/O 错误」还是「直接 `exit`」，没有任何地方能整体替换分配后端；测试也无法可靠地走到分配失败路径（真正耗尽内存会拖垮机器）。
- 决策：
  1. 运行时所有缓冲区经由 `ae_allocator`（三个函数指针 `alloc`/`resize`/`release`）获取与归还，默认实现即 `malloc`/`realloc`/`free`。三个入口：`ae_alloc(size, line, column)`（失败终止）、`ae_alloc_try(size)`（失败返回 NULL，供「用返回值报告失败」的路径使用）、`ae_alloc_resize(block, size, line, column)`。`ae_set_allocator` 供宿主替换后端（未来 embed API 与追踪分配器）。
  2. 分配失败是**终止性**的：`ae_fail("out of memory", line, column)` 打印位置并以 1 退出。语言没有 `catch`/析构栈展开，无法在「值只构造了一半」的状态下继续执行，也无法保证已构造函数按顺序释放；明确终止比让程序带着 NULL 缓冲继续跑更安全。
  3. 少数路径保留**可恢复**语义：`try_read_file`/`try_list_dir`/`try_create_dir` 里为缓冲分配失败返回 `Err("out of memory")`，因为它们的返回值本来就是结果枚举，调用方有地方处理它。
  4. 诊断开关 `AE_ALLOC_LIMIT=N` 限制**累计**分配字节数（不是存活字节数），超出后按分配失败处理。它是让测试确定性地走 OOM 路径的开关，不是内存配额：累计口径不需要为每个缓冲记录大小头，零额外内存开销，代价是「释放后再分配」也会计入。非法值（非数字、带尾随字符）被忽略，程序照常运行。
- 理由：把分配收敛到一个接口，是「低内存占用、可审计」的前提：将来要接区域分配、统计、追踪，只需换实现而不用改十几处调用点。累计字节数作为诊断足够——测试关心的是「第 N 次分配会不会失败」，而不是精确的存活字节。终止式 OOM 与语言现状一致（`ae_fail` 已是越界、溢出、除零的统一出口），可恢复 OOM 只在**本来就返回值**的地方提供。
- 已排除的做法：
  - **所有分配失败都变成结果值**：这会让 `ae_str_cat`（`+` 运算符）也能失败，等于要求每个表达式都能返回错误，当前语言没有这个表达力。
  - **OOM 时 `abort()`**：`exit(1)` 让 shell 与 CI 看到普通失败状态而不是信号，且不产生核心转储噪声。
  - **存活字节口径的配额**：需要为每次分配加大小头（8 字节/次）或旁路记录（哈希表），与「零开销诊断」目标冲突，且会让 `--wrap` 分配计数器的块数统计失真。
  - **把 `AE_ALLOC_LIMIT` 做成环境变量白名单之外的东西（如编译期常量）**：测试需要在同一份可执行文件上切换成功/失败，编译期常量做不到。
- 后果与限制：`ae_set_allocator` 尚未对 AE 代码暴露（没有 FFI），只能由 C 侧宿主调用；`AE_ALLOC_LIMIT` 是累计口径，因此「大程序 + 大限额」不能精确模拟「内存即将耗尽」；OOM 终止时不保证已分配缓冲被释放（进程退出，操作系统回收），这与 §4.5「异常终止不保证清理」一致；`ae_alloc_try` 的路径必须在失败时自行清理已持有的资源（`try_read_file` 用 `failure` 标志统一收口）。

## ADR-17：UTF-8 字符边界与按字符截断

- 背景：`len`/`slice` 一直按字节工作，这与「字符串是 UTF-8 字节序列」一致且 O(1)，但对文本处理是陷阱：`slice("中文", 0, 1)` 会产出一个孤立的 `0xE4` 字节，再 `print` 出去就是非法 UTF-8——终端显示乱码，若把它写回文件或作为 JSON 字段，错误会一路传播。此前既没有字符安全的截断方式，也没有任何检测。方案阶段 B 第 5 项要求「测试 Unicode 与迭代边界」。
- 决策：
  1. `slice`/`slice_view` 在**索引落在字符中间**时终止并报 `string index splits a UTF-8 character`。判定只看一个字节（UTF-8 的后续字节恒为 `10xxxxxx`），因此是 O(1)，且 `start`/`end` 恰好在末尾（`== len`）视为合法边界。
  2. 新增 `utf8_len(s) -> i64`（字符数，即非后续字节的个数）与 `utf8_prefix(s, n) -> string`（前 n 个字符的拥有副本；n 超过字符数则复制全部；n 为负报错）。
  3. 不引入「校验整个字符串」的入口：非法字节序列（来自二进制文件、argv）允许存在并可被 `bytes`/`slice` 原样处理，本规则只保证**不新引入**断裂的序列。
- 理由：一条 O(1) 的边界检查就能把「静默产生非法 UTF-8」这个最常见的文本处理缺陷变成显式错误，代价可以忽略。`utf8_prefix` 而不是 `utf8_offset` + `slice` 两段式，是因为实际需求几乎总是「截到 N 个字符」，一次调用就能表达，且内部只会产出合法边界；`utf8_len` 与 `len` 并存，让「按字节」与「按字符」的差别在调用点就可见，而不是藏在一个 `len` 的模式参数里。
- 已排除的做法：
  - **`len` 直接返回字符数**：会让字符串与字节缓冲（`bytes`、文件大小、`read` 返回值）的计数口径不一致，且每次 `len` 从 O(1) 变成 O(n)。
  - **`slice` 自动吸附到最近的字符边界**：静默改动调用者的索引，`slice(s, 0, 1)` 会得到 3 个字节，越界行为被掩盖。
  - **引入 `char`/grapheme 类型与迭代器**：需要新的类型系统支持（阶段 C 之后），当前用两个函数即可覆盖计数与截断。
  - **加载时校验并拒绝非法 UTF-8**：读文件、读 argv 都是字节流，拒绝会让处理二进制/半结构化数据的程序无法运行；且使每次 I/O 多一次 O(n) 扫描。
- 后果与限制：字符按 Unicode 码点计，不处理组合字符与字素簇（`e` + 组合重音算 2 个字符，emoji 的 ZWJ 序列算多个）；不提供按字符索引取第 i 个字符（用 `utf8_prefix` 截前缀或先转 `bytes`）；`split`/`contains`/`lines`/`path_*` 仍按字节匹配分隔符（分隔符是 ASCII 时行为不受影响）；错误消息列入运行时常见诊断，测试按消息文本断言。

## ADR-18：跨文件可见性用 `pub` 显式导出

- 背景：`use` 引入一个文件后，该文件的**全部**顶层函数、结构体、枚举立即对导入者可见——没有「模块内部实现」这个概念。这在实际使用中很快成为负担：一个 `lib.ae` 想重构内部辅助函数的名字或签名，就必须先确认没有别的文件调用过它；而 `use` 的传递性（A 导入 B、B 导入 C，则 A 也能看到 C）让这种确认几乎不可能。阶段 B 第 3 项要求「模块可见性」。
- 决策：
  1. 顶层项默认**私有**：`pub fn`/`pub struct`/`pub enum` 才跨文件可见。`pub` 只是顶层声明前缀，不能用于局部项、参数或字段。
  2. 文件总能访问自己的私有项；预置的六个结果枚举由 `PRELUDE` 标记持有，对所有文件公开。
  3. 三处检查：函数调用、结构体字面量/构造、枚举字面量；以及类型标注（`fn f(x: Hidden)`）在解析类型时检查。诊断指向**使用处**并给出文件路径与「mark it 'pub' to export it」。
  4. 额外一条定义处检查：`pub` 函数的参数或返回类型若是本文件的私有类型，直接报 `public function 'x' exposes private struct 'Y'`。这让「导出函数但藏起它的参数类型」这个必然失败的组合在定义处结束，而不是在调用处报一个看似无关的「unknown type」。
  5. 实现上把共享函数表的值从三元组换成 `Signature { id, params, ret, file, public }`，`StructDef`/`EnumDef` 增加 `file`/`public` 字段；判定只有一句：`public || file == 自己 || file == PRELUDE`。
- 理由：默认私有是「让改动局部化」的唯一自动化手段，默认公开则需要每个作者记得加 `private`，而忘记写的结果只是少了一层保护、不会被发现。把可见性挂在**声明**上而不是挂在 `use` 上（如 `use "lib.ae" as m; m::helper()`），是因为当前没有命名空间语法，加路径限定词会牵动名字解析、方法调用与 C 符号生成；而顶层 `pub` 只是给已有名字表加一个布尔位。定义处检查私有类型泄漏，是「错误要在离原因最近的地方报」的实例（ADR-14 的 `?` 也是同一原则）。
- 已排除的做法：
  - **按导入方声明可见性**（`use "lib.ae" priv;`）：可见性属于被导入者，写在导入处会让同一模块在不同文件里行为不同。
  - **按文件隔离的私有命名空间（符号名 mangle）**：这才是「每个模块都能有自己的 `helper`」的完整解法，但需要给 C 符号加文件前缀、给调用点加解析上下文，属于后续打包/接口摘要工作（阶段 D），本条先解决「能不能调用」，不解决「重名能不能共存」。
  - **`pub(crate)`/`pub(super)` 之类的分级**：当前没有包的概念，唯一的边界是文件。
  - **字段级可见性**：结构体字段在语言里本来就不可拆分（字段只能整体借用），类型级可见性已经覆盖了实际风险。
- 后果与限制：跨文件重名仍然一律报错——两个模块不能各自拥有同名的私有 `helper`，这是本条最大的粗糙处；`examples/modules/` 因此用带域前缀的名字（`count_words`、`line`、`summary`）避开冲突。`pub` 增加一个保留名（40 项）。可见性只影响名字解析，不影响生成代码：私有函数仍有唯一的 C 符号，因此 ABI 与缓存键都不变。诊断文本被测试按内容断言。

## ADR-19：资源模型作为规范文档而非实现副产品

- 背景：所有权、借用与释放的规则此前只散落在 ADR-5/6/8/11/14 的「后果与限制」里，以及代码注释中。这些片段各自正确，但**合起来**说不清三件事：到底哪些语法位置会移动（新增内建时容易漏）、哪些性质只是「目前碰巧成立」（例如借用不能逃逸是因为不能存进变量，而不是因为生命周期分析）、以及新增特性时要检查什么。阶段 C 第 1 项要求「先写正式资源模型」，理由正是：没有规范的模型，后续的部分移动、循环固定点、跨线程约束都无处安放。
- 决策：新增 `docs/resource-model.md` 作为**规范性**文档，逐条写清值分类（标量/拥有型/借用/数组）、移动位置（6 处）、移动后的编译期与运行时状态、借用规则与禁止项、释放点（9 处，含 `break`/`continue` 与 `?` 错误路径）、终止语义、并发现状、**明确不保证的性质**（9 条），以及新增特性时的 8 项检查清单。写作过程中逐条对照实现核对，例如「`if` 两个分支的移动集合取并集」对应 `if_statement` 里的 `after_yes` 合并，「`?` 与 `return` 释放参数」对应 `live_owned()` 遍历全部作用域。
- 理由：把「已保证」与「未保证」分成两栏，是防止过度声称的唯一可靠办法。这也符合阶段 A 验收要求的「尚未覆盖的安全性质不对外宣称」：README 与本文现在都只声明「编译期检查 + 运行时哨兵 + 泄漏测试」三层，不声明形式化保证。检查清单把「新增类型/语句/内建时必须同时处理的三件事」固定下来，避免下一次扩展再靠记忆。
- 已排除的做法：
  - **把模型写在代码注释里**：注释跟着函数走，读者无法一次看到全局规则，也无法在评审时对照。
  - **等实现完整后再写模型**：模型的作用是**约束**实现（阶段 C 后续的分支合并、部分移动都要照它做），补写的模型只是事后描述。
  - **在模型里描述理想行为**：那会变成营销文档，读者无法区分已实现与计划。
- 后果与限制：文档需要与实现同步维护，否则会产生「文档说保证、实现没做到」的失真——检查清单的最后一项把这条变成每次扩展的例行动作。模型本身不增加任何编译期能力：结构体无运行时哨兵、无部分移动、无循环固定点、无跨函数生命周期，这些限制照旧，只是现在被明确记录。

## ADR-20：循环体禁止移出外层拥有值（代替循环固定点）

- 背景：一次移动只发生在语法位置，但**循环体会重复执行**。此前 `while`/`for` 在解析完循环体后既不合并移动集合，也不检查移动是否会在下一轮被读到，于是这段程序能通过编译、直到第二轮的运行时哨兵才失败，且诊断指向 `print(len(t))` 而不是真正的错误位置：

  ```
  var s = "x";
  var i = 0;
  while i < 2 { let t = s; print(len(t)); i = i + 1; }
  ```
  报告的是 `use of moved string`（第 5 行 `len(t)`），作者要自己倒推「s 在第二轮已经是空句柄」。阶段 C 第 2 项要求实现「循环固定点」。
- 决策：
  1. 三种循环（`while`、`for i in a..b`、`for x in v`）在解析完循环体后调用 `close_loop_moves`：取「循环前移动集合」与「循环体结束时移动集合」的**差**，若其中出现**在循环外声明**的变量，报 `cannot move 'x' inside a loop body: the next iteration would read it after the move (re-initialize it before the body ends)`，位置指向循环关键字。
  2. 在循环体结束前重新赋值给该变量则不算：重新赋值先释放旧值再移入新值，等价于重新初始化，下一轮读到的是有效值。
  3. 循环体内声明的拥有值不受影响：它们的移动随每轮块结束而消失。
  4. 移动集合在循环结束后恢复为「循环前」的状态——循环体既然不能移出外层值，就没有需要合并的部分。
- 理由：真正的固定点需要把「体分析」跑到不动点（Rust 的做法：只要在每个使用点之前已完成重新初始化，就允许移动）。当前架构是单遍解析、边解析边发射语句，跑到不动点的代价远大于收益。而「禁止移出外层值」是一条**可判定的局部规则**：它把「第二轮读到已移动值」整类错误一次性排除，语言其余部分不受影响，实现只有二十行。代价是拒绝了一些实际安全的写法（例如在循环体末尾移动、且之后不再使用），这与「安全优先于便利」的排序一致。
- 已排除的做法：
  - **只合并 `if` 式的保守并集**（把循环体结束时的移动集合并入外层）：只能解决「循环之后再用」，解决不了「第二轮读到」，而后者才是真实故障。
  - **跑到不动点**：需要把语句解析与移动分析分离（先建 CFG 再分析），属于阶段 C 后续的「控制流图 + 数据流分析」，等那套基础设施到位后可以放宽这条规则。
  - **依赖运行时哨兵兜底**：哨兵只能报「用了已移动的值」，无法指出是哪个移动造成，诊断质量差；而且结构体与枚举根本没有哨兵。
  - **允许移动但插入运行时重置**（移动后自动清空并视为「未初始化」）：语言没有「未初始化」状态，任何读都会退化为运行时错误，等同把编译期问题推给用户。
- 后果与限制：合法的「循环体内移出、但之后不再使用」被拒绝；`for x in v` 里对 `v` 的移动此前已有单独诊断（`cannot move the vector being iterated`），现在两层检查同时存在，前者更精确。顺带修正了一处文档错误：`current-language.md` 曾写「循环体内 `push`/`pop`/索引写保持合法」，实际实现（自 ADR-12 起）因循环体借用容器而拒绝，现已改为如实描述。

## ADR-21：泛型枚举按实参单态化

- 背景：阶段 B 第 3 项要求「泛型、约束与模块可见性；规范实例化策略和代码膨胀预算」，而第 4 项要求 `Option`/`Result` 这类表达方式。此前的枚举全是单态的：想表达「可能没有」就得为 `Option[string]`、`Option[i64]`、`Option[vec[string]]` 各写一个枚举，名字还没法统一；六个预置结果枚举（`ReadResult`/`IntResult`/…）正是这种手写单态化的产物——每个可失败操作配一个固定形状的结果类型，新形状就得改编译器。同时 `vec[string]` 作为**类型标注**根本写不出来（只有 `&vec[string]` 借用能写），拥有型字符串向量只能靠推断。
- 决策：
  1. 泛型**声明**与布局分离：`enum Either[T, U] { Left(T), ... }` 记入独立的 `GenericEnum` 表（负载里用 `Payload::Concrete(Type)` 或 `Payload::Param(usize)` 表示），不产生任何 C 类型；`EnumDef` 保持「有布局」的语义不变。
  2. **单态化**：`Type::Enum` 只能指向已实例化的 `EnumDef`。首次见到 `Name[args]` 时按 `(声明, 实参列表)` 查表，未命中则把参数替换成实参、生成一个新的 `EnumDef`（显示名 `Option[string]`，以便诊断直接说出具体类型）并追加到 `enums`，因此既有的发射、释放、forfeit、结构体字段、`?` 检查全部无需改动。同一实参列表复用同一 `EnumDef`，所以 `Option[string]` 在任何位置都是同一类型。
  3. `match` 的模式用**声明名**：实例化枚举的 `EnumDef.pattern` 记住声明名，`Option::Some(v)` 同时适用于 `Option[string]` 与 `Option[i64]`，绑定类型由被匹配值决定。
  4. 类型参数只能是单个大写字母、最多 8 个；实参限 `i64`/`bool`/`string`/`vec`/`vec[string]`（与负载限制同一集合），所以永远不可能构造出递归布局。
  5. 预算：`MAX_ENUM_TYPES = 256`（含预置 6 个），超出时在触发实例化的位置报错并指出枚举名。
  6. 预置 `Option[T] { Some(T), None }`，与六个结果枚举一样属于 prelude 且公开。
  7. 顺带补上 `vec[string]` 的类型拼写：`named_type` 在 `vec` 后遇到 `[` 时要求 `string`，返回 `Type::StrVec`。
- 理由：单态化而不是类型擦除（`void*` + 函数指针），是因为当前运行时是「按类型生成的释放例程」——擦除后每个负载都要带自己的释放函数指针，布局变大、分配变多，与 §4.5 的低内存目标相反；而且擦除会丢掉「`Option[string]` 与 `Option[i64]` 是不同类型」这个最有价值的静态检查。选枚举作为泛型的第一步而不是函数，是因为泛型函数在没有泛型容器、也没有对类型参数的运算约束时只能做「原样传递」，几乎没有用处；而泛型枚举立刻给出 `Option[T]`，并且它的单态化机制（声明表 + 替换 + 复用 + 预算）正是将来泛型结构体/`vec[T]` 要用的同一套。把 `Option` 放进 prelude 而不是标准库文件，是因为当前还没有「自动导入的库」这个概念，而 `Option` 是每个程序都可能用到的基础形状。
- 已排除的做法：
  - **泛型函数先行**：`fn first<T>(v: vec[T])` 需要泛型容器，`fn max<T>(a: T, b: T)` 需要约束（`T: Ord`）；两者都没有时泛型函数只能做无操作的传递，测不出价值。
  - **类型擦除 / 装箱**：见上，与低内存目标冲突，且丢掉类型区分。
  - **`Option` 用哨兵值实现**（如空串表示 None）：这正是本条要消灭的错误来源。
  - **从上下文推断类型实参**（`let x = Option::Some(1)`）：需要双向类型检查（推断变量类型再回填到构造表达式），当前前端是自顶向下单向的；显式 `Option[i64]::Some(1)` 啰嗦但可读，且不需要新机制。
  - **泛型结构体一起做**：结构体的字段布局、字段借用、`FieldStore` 释放都要按实参复制一份，改动面比枚举大得多；先做枚举，等 `vec[T]`/字段泛型一起设计。
  - **允许 `Option[Option[i64]]`**：负载不能是枚举（会引入布局递归），这条限制本来就有，泛型不放开。
- 后果与限制：没有泛型函数、没有约束/trait、没有泛型结构体；泛型枚举的负载仍不能是结构体或枚举，因此 `Option[Option[i64]]`、`Option[Point]` 写不出来；`?` 不适用于 `Option`（它只认 `Ok`/`Err` 双变体结果枚举）；类型实参必须显式拼写，不能从返回值或变量类型推断；每个实参列表一份布局，配合 256 上限；`match` 的模式不能写 `Option[string]::Some`（只认声明名）。新增 6 个端到端测试（实例化与负载、布局复用、9 类拒绝路径、预算、跨文件可见性），`examples/maybe.ae` 作为验收示例并纳入分配计数校验（`blocks=2`，无泄漏）。

## ADR-22：排序、时钟、环境变量与追加写入

- 背景：把「文件整理/日志分析」从示例变成日常工具，缺的不是语言特性而是四个小操作：**排序**（按大小列出前 N 个文件、按时间排序）、**当前时间**（`try_file_info` 给出 mtime，没有 `now` 就无法算「多久以前」）、**环境变量**（临时目录、`HOME`、代理设置，否则路径只能硬编码）、**追加**（写日志；`write_file` 只能整体覆盖，等于每写一行就要读全量再重写）。阶段 E 第 1 项把这些列为基础 API，而阶段 B 第 6 项的文件处理样例正好需要它们。
- 决策：
  1. `sort(v)` / `reverse(v)` 就地重排，`v` 必须是 `var` 向量：`i64` 向量按数值，`vec[string]` 按**字节序**（与 `keys()`、`try_list_dir` 同一口径，因此排序后的输出在两平台一致）。空向量与单元素向量是空操作。
  2. `now_s()` / `now_ms()` 返回 Unix 纪元以来的秒/毫秒（`i64`）。`now_s` 与 `try_file_info` 的 mtime 同单位，可直接相减。
  3. `env(name) -> ReadResult`：变量存在则 `Ok(值)`，不存在则 `Err("variable not set")`；**存在但为空**返回 `Ok("")`。空名字报 `Err("variable name is empty")`。
  4. `try_append_file(path, text) -> WriteResult`：以追加模式打开并写入，返回写入字节数。
- 理由：就地排序而不是返回新向量，是因为调用点几乎总是「把这个列表排一下」，返回新向量会强制一次完整复制并且让原变量变成「已移动」，与 `push`/`pop` 的「可变容器」形态不一致。用 C 标准库的 `qsort`：它是 C11 的一部分、两平台都有、比较函数是普通函数指针（不需要闭包），而稳定排序对 `i64` 和按字节比较的字符串没有可观察差别。`env` 复用 `ReadResult` 而不是新造 `Option`，因为「为什么读不到」在诊断上比「有没有」更有用（空名字与不存在是不同错误），而且 `ReadResult` 已经在 prelude 里。区分「空值」与「未设置」是硬要求：把 `PATH=""` 当成「没有 PATH」会让程序悄悄走一条完全不同的分支。
- 已排除的做法：
  - **`sort_by(key)`**：需要函数值/闭包；当前语言没有，所以只能提供固定比较规则。
  - **返回新向量 `sorted(v)`**：多一次分配、原向量被移动，调用方通常在原地排序后继续用同一个变量。
  - **`env` 返回 `Option[string]`**：丢掉错误原因；且 `Option` 刚加入，没有必要在标准 API 里再分叉一套。
  - **`set_env`/`cwd`/进程启动**：写环境会影响将来子进程的语义，应当与进程 API 一起设计；`cwd` 与相对路径解析规则耦合，也需要单独决定（现在是「相对当前工作目录」）。
  - **`now` 用单调时钟**：文件 mtime 是墙钟，比较必须同源；单调时钟留给将来的计时 API（`AE_TIMINGS` 那类用途）。
- 后果与限制：只有 `vec` 与 `vec[string]` 能排序，结构体/枚举向量不存在；排序不稳定；`sort` 与 `push` 一样要求可变变量、且在其被借用期间（例如 `for x in v` 体内）被拒绝；`now_*` 会随系统时钟回拨，不是单调计时；`env` 只读、不写、不枚举；没有流式文件句柄，`try_append_file` 每次调用都会开合文件（写大量小行时应自行拼接后一次写入）；Windows 上「空值 vs 未设置」依赖 `SetLastError(ERROR_SUCCESS)` + 读取后检查 `GetLastError`，这一段是本条实现中最容易出错的地方，已在测试中覆盖三种情形。
- 顺带修复一处既有泄漏：`try_write_file` 的**路径**实参若是拥有型临时值（`try_write_file(path_join(dir, name), text)`），发射器只释放了内容实参、没有释放路径实参。此前没有示例这样调用，所以分配计数一直没发现；新增的 `examples/dir_report.ae` 一跑就多出 3 个块。逐个核对了全部文件操作发射器（`try_copy_file`/`try_rename_path`/`try_remove_file`/`try_remove_dir`/`try_create_dir`/`try_file_info`/`try_list_dir`/`try_read_file`）后确认只有这一处（以及新增的 append）遗漏，现已统一释放，`--leak` 恢复基线。

## ADR-23：`exit(状态码)` 终止语句

- 背景：命令行程序需要退出状态——`grep` 无匹配返回 1、用法错误返回 2，管道与 CI 都靠它判断结果。此前唯一能改变退出状态的办法是让运行时自己失败（越界、断言），而那是「出错」而非「正常的非零结论」；`main` 固定返回 0。`examples/grep_cli.ae` 只能打印数字，脚本无法用它做条件判断。
- 决策：
  1. 新增语句 `exit(code);`：`code` 必须是 `i64`，运行时按 `int` 截断后调用 `exit()`。
  2. 终止前先 `fflush(stdout)`，再**释放全部存活拥有型变量**，最后终止。
  3. `exit` 计入「路径已终止」：只经 `exit` 结束、从不返回值的函数不需要 `return`（`returns()` 把 `Exit` 视为终止）；`main` 里同样可用。
- 理由：把释放放在 `exit` 之前，一是让分配计数校验（`--leak`）在有 `exit` 的程序上仍然有意义，二是让「打印—释放—退出」的顺序确定，方便判断缓冲区状态；先 flush 是因为 `print` 走的是 stdio 缓冲，直接 `exit()` 在输出被重定向到管道时可能丢掉最后一行。状态码按 `int` 截断并在文档里说明，是因为 POSIX 只保留低 8 位，如果在语言层假装支持 64 位状态码，程序在 Linux 上的行为会与阅读代码时的预期不符。
- 已排除的做法：
  - **`std::process::exit(code)` 式的标准库函数**：当前没有标准库命名空间，语句形式最直接，也避免「函数调用不返回」与类型系统的冲突（一个返回 `i64` 的函数不能出现在表达式位置却不返回值）。
  - **让 `main` 返回值作为退出码**：`main` 目前没有返回类型；改成有返回类型会牵动所有既有程序与 `main` 的特殊处理（它不能 `return`、不能有参数），收益只是省一个语句。
  - **`exit` 不释放直接退出**：实现更简单，但会让「有序退出」与「出错退出」的可见行为不一致，且分配计数校验无法覆盖带 `exit` 的程序。
  - **`exit` 允许字符串/枚举状态**：退出状态是整数，不接受其他类型可以省掉一层「怎么转换」的规则。
- 后果与限制：`exit` 之后同块内的语句虽不可达但仍需语法正确（没有可达性分析，也没有「未使用变量」告警）；不检查状态码范围，负数与大于 255 的值会被截断；没有 `atexit`/清理钩子；子进程与信号不在此列（属于进程 API）。`examples/grep_cli.ae` 改为使用 0/1/2 三种状态，新增 3 个端到端测试（状态码与刷新、只 `exit` 的函数、状态码类型拒绝）。

## ADR-24：标准输入与工作目录

- 背景：`grep_cli.ae` 想支持 `grep pattern -`（从管道读），`pipe_stats.ae` 这种「统计上一个命令输出」的工具是 Unix 管道的日常形态；而没有 `cwd()`，程序只能打印相对路径，输出「./a.txt」这类无法直接使用的碎片。两者都属于阶段 E「进程与 I/O」的第一层，且都不需要新类型。
- 决策：
  1. `read_stdin() -> ReadResult`：读**全部**标准输入并返回原始字节串；读失败返回 `Err(原因)`，读到空输入返回 `Ok("")`。
  2. Windows 上先把 `stdin` 切成二进制模式（`_setmode(_fileno(stdin), _O_BINARY)`），因此 `\r\n` **原样保留**，不做 CRLF 翻译。
  3. 缓冲区按倍增扩容（起始 4 KiB），`ferror` 时返回 `Err`；读取过程中不做 UTF-8 校验，与 `read_file` 同一口径（语言把字节串当 `string` 用，字符边界只在 `slice`/`utf8_*` 处检查）。
  4. `cwd() -> ReadResult`：返回当前工作目录的绝对路径，分隔符统一为 `/`（与 `path_join`/`path_parent` 一致），Windows 下把 `\` 逐字符换成 `/`。
- 理由：标准输入返回 `ReadResult` 而不是「直接给字符串」，是因为管道另一端可能出错（`EPIPE`、设备错误），静默返回空串会让程序把「读失败」当成「没有输入」——这正是方案里「I/O 不能静默丢错」那条底线。二进制模式是硬要求：`println` 风格的 CRLF 翻译会让 `len(input)` 在 Windows 上比 Linux 少，同一段统计代码两平台给出不同数字，而这种差异极难在事后发现。`cwd` 统一 `/` 让路径拼接的结果在两平台可读且可直接传给 `try_*` 系列（它们本身接受 `/`）。
- 已排除的做法：
  - **逐行读取（`read_line`）**：需要流式句柄或迭代器协议，当前 `read_stdin` 一次读全已经覆盖管道统计与 `grep`；逐行会引入「什么时候关闭」「缓冲区归谁」的问题。
  - **`read_stdin` 返回 `string` 并在失败时终止**：与 `read_file` 的既有设计冲突（那里是可恢复的）。
  - **`cwd` 返回 `string` 而非结果**：`getcwd` 会失败（目录被删除、权限变化），返回裸字符串就必然要在失败时编造一个值。
  - **`cwd` 保留 Windows 反斜杠**：与 `path_*` 的 `/` 约定冲突，且反斜杠在字符串里还要转义。
  - **改变工作目录 `set_cwd`**：与 `set_env` 一起属于进程状态，需要单独设计（相对路径解析、并发语义），本次不做。
- 后果与限制：`read_stdin` 会把整个输入读进内存，超大输入（GB 级）不合适；没有超时与部分读取；不能与 `args()` 之外的方式感知「输入是终端还是管道」（将来可加 `is_tty`）；`cwd` 不做符号链接解析（返回 `getcwd` 的路径，可能含链接）；Windows 上 `cwd()` 的结果不含盘符大小写归一。新增 3 个端到端测试（二进制字节数与 `\r` 保留、空输入、`cwd` 可用性）与 `examples/pipe_stats.ae`；`grep_cli.ae` 支持 `-` 读标准输入。

## ADR-25：Linux 全量验证与严格 ISO C 修正

- 背景：`docs/platform-matrix.md` 此前只有 2026-11-10 的一次 Linux 记录，而其后新增的能力（哈希表、UTF-8 边界、分配器接口、`pub` 可见性、循环移动规则、泛型枚举、排序/时钟/环境变量/追加写入、`exit`、`read_stdin`/`cwd`）全部只有 Windows 本机证据。在 Debian 13（GCC 14.2.0、rustc 1.99.0、4 vCPU / 7.8 GB）上重跑 `cargo test --locked`，**117 个端到端测试里 91 个失败**，全部卡在同一处编译错误：

  ```
  program.c: In function 'ae_now_ms':
  error: implicit declaration of function 'clock_gettime'
  error: 'CLOCK_REALTIME' undeclared
  ```

- 根因：测试与 `verify_generated_c.py` 都用 `-std=c11 -pedantic-errors` 编译生成的 C。`-std=c11` 会定义 `__STRICT_ANSI__`，glibc 的 `features.h` 因此不启用 `_DEFAULT_SOURCE`/`_POSIX_C_SOURCE`，`<time.h>` 里的 `clock_gettime` 与 `CLOCK_REALTIME`（POSIX，需要 `_POSIX_C_SOURCE >= 199309L`）就不可见。Windows 走 `GetSystemTimeAsFileTime` 分支，所以本机从未暴露。这是**只有真正在 Linux 上跑才会发现**的问题——正是本轮跨平台验证的价值。
- 决策：
  1. POSIX 分支改用 `timespec_get(&ts, TIME_UTC)`（ISO C11 标准接口），不再依赖任何特性宏；毫秒换算与取整规则不变。
  2. 不采用「在生成文件顶部 `#define _POSIX_C_SOURCE 200809L`」的修法。
  3. 字符串转义集合增加 `\r`（此前只允许 `\n \t \\ \"`）。
- 理由：`timespec_get` 是 C11 的一部分，在严格模式下天然可见，生成文件继续是「纯 ISO C11」，不需要用户为编译 AE 产物而关心 glibc 特性宏——这条性质本身就是 ADR-1（生成 C11）的承诺之一。相反，注入 `_POSIX_C_SOURCE` 会污染宿主的编译单元：若用户把生成代码 `#include` 进自己的项目，或换用 musl/BSD，宏的语义就成了新的平台依赖。`\r` 之所以补齐，是因为标准输入与 `split(text, "\r\n")` 处理 CRLF 文本时没有它就无法写出字面量（C 的 `"\r"` 本来就合法，只是前端拒绝了这个拼写）。
- 已排除的做法：
  - **`_POSIX_C_SOURCE` 宏**：见上，把平台依赖从运行时搬到了编译命令行。
  - **`gettimeofday`**：同样是 POSIX，问题一样。
  - **`time(NULL)` 秒级足够**：`now_ms` 的存在意义就是毫秒，退化成秒会让 `now_ms` 名不副实。
  - **只在 Linux 上加 `-D_POSIX_C_SOURCE`**：那会让「同一份源码在两平台需要不同编译参数」，比修运行时更糟。
- 结果：修正后 Linux 上 `cargo test --locked` **9 单元 + 117 端到端全部通过**；`python3 scripts/verify_generated_c.py --sanitize --leak` 16 个示例全部 PASS，分配计数 **`blocks=0 bytes=0`**（glibc 的启动分配比 Windows UCRT 少，因此基线为 0，比 Windows 的 2 更严格）；示例输出与 Windows 在行尾归一化后一致（当时记作「逐字节一致」，2026-11-10 核对该表述并修正为归一化后一致）。`\r` 转义由 `standard_input_arrives_as_bytes_without_newline_translation` 覆盖（`a\r\nb` 读回长度 4 且含 `\r`）。

## ADR-26：JSON 路径查询（只读）

- 背景：阶段 B 第 6 项的验收要求「常见文本/JSON 工作流可运行」，阶段 E 第 1 项把 JSON/CSV 列为基础 API。没有它，读一份 API 响应或配置文件只能靠 `split` + `contains` 手写，一旦出现嵌套对象、转义引号或数组就不可靠——而这正是「脚本语言该做的事」里最常出现的一种。
- 决策：
  1. 只做**只读路径查询**，五个内建：`json_get(text, path) -> ReadResult`、`json_int(text, path) -> IntResult`、`json_bool(text, path) -> BoolResult`、`json_len(text, path) -> IntResult`、`json_has(text, path) -> bool`。
  2. 路径语法：`key`、`key.sub`、`key[2].sub`、`[0].key`；空路径表示整个文档。键按**解码后**的字节比较（对象键里的 `\uXXXX` 先还原再比）。
  3. `json_get`：字符串值解码全部转义（含 `\uXXXX` 与代理对，输出 UTF-8）；数字、`true`/`false`/`null` 返回**原文**；数组与对象返回**原始片段**（可直接保存或再解析）。
  4. `json_int` 只接受没有小数点与指数的整数，溢出 i64 报错；`json_bool` 只接受 `true`/`false`；`json_len` 只接受数组与对象。
  5. 新增预置枚举 `BoolResult{Ok(bool), Err(string)}`（编号 6）——用 `IntResult` 加 0/1 会把「假」和「没有」混在一起。
  6. 每次调用重新扫描文档；嵌套深度上限 64；路径先在文档之前单独校验，路径写错就报路径错误。
- 理由：不引入 JSON 值类型，是因为那会把容器的所有权、递归布局、访问语法、错误传播一次性塞进类型系统，与「低内存、确定性释放、编译期拒绝移动」的既有模型正面冲突；路径查询把复杂度留在运行时，返回值仍是既有的结果枚举，用 `match` 处理，语言本身一个语法都不用改。分成三个返回类型而不是「统一取字符串再转换」，是因为**「没有这个字段」和「字段类型不对」必须能区分**——这正是 ADR-22 拒绝让 `env` 返回 `Option` 的同一条理由。代理对要还原，否则中文与 emoji 的 JSON 在 AE 里会变成字面的 `\ud83d\ude00`，而原始字段值是任何真实 API 都会给出的东西。
- 已排除的做法：
  - **`json` 类型 + `doc["key"]` 索引**：见上，需要新类型、新所有权规则、新错误语义。
  - **解析成文档句柄（一次解析、多次查询）**：需要「句柄类型 + 释放点」；而配置级输入重扫的成本是微秒级（16 个字段 × 10 KB），不值得为此增加一种拥有型资源。
  - **`json_get` 统一返回字符串、由调用者 `parse_int`**：丢掉「字段类型错误」的诊断，且 `parse_int` 对 `"12"` 与 `12` 无从区分。
  - **实现 JSON 写入/序列化**：构造器、转义、键序都需要设计；`join` 与字符串拼接已能生成简单 JSON，等结构化输出需求明确再做。
  - **严格 JSON 校验**（数字语法、拒绝重复键、拒绝尾随逗号）：读取器按「找到值就走」的宽松口径实现，严格性由 `json_int`/`json_bool` 在转换时保证；文档写明这一点，避免使用者以为 `json_get` 是验证器。
- 后果与限制：没有写入、没有浮点（`json_int` 拒绝 `1.5`）、没有遍历回调——遍历数组要 `json_len` + `[i]` 循环（可行但不优雅）；键名里含 `.` 或 `[` 无法表达；重复键取第一个；不跳 UTF-8 BOM；不校验整个文档，只在路径经过的地方探测语法错误；文档必须完整驻留内存（`read_file`/`read_stdin`）。新增 2 个端到端测试（正常路径与 10 类错误）与 `examples/json_report.ae`，并把该示例纳入分配计数校验（`blocks=2`，无泄漏）。

## ADR-27：缓存条目带校验，无法识别编译器时不用缓存

- 背景：ADR-4 的键覆盖了生成 C、优化模式、编译器 `--version` 首行、编译器版本与平台，条目以「复制到临时文件 + 重命名」发布。阶段 D 第 3 项要求在「不能可靠识别影响结果的输入时禁用相应缓存，不复用可能过期的二进制」。审查时发现两处不满足：
  1. 命中判定只看「文件存在且长度大于 0」。测试里把缓存中的可执行文件写成 `garbage` 后，构建仍然成功并把这个死文件当成产物——缓存损坏会静默传播成「程序构建成功但一运行就崩」。
  2. 编译器身份只取 `--version` 首行，且查询失败时回落到固定字符串 `"unknown"`。两个不同的编译器（或同一编译器的不同安装）在无法查询时会共用同一个键，恰好落在「不可靠识别」的禁区里；键里也没有 `AE_CC` 的实际取值，同一版本的两个二进制无法区分。
- 决策：
  1. 条目里增加 `manifest` 文件，内容为 `<字节数> <SHA-256>`。命中前重新读取可执行文件、重算摘要并比对，不一致就**整条删除并重建**（视为 miss，`AE_TIMINGS=1` 会打印 `cache: miss`）。
  2. 发布顺序固定为「先重命名可执行文件、再重命名 manifest」：中间崩溃时 manifest 与新文件不匹配，下次读取即为 miss，不会留下看似可用的条目。
  3. 编译器身份查询失败（进程启动失败、非零退出、输出为空）时**禁用本次缓存**：不查命中、也不写入条目，并在 `AE_TIMINGS=1` 下打印 `cache: disabled (cannot identify the C compiler ...)`。
  4. 键中加入 `AE_CC` 的原样字符串，与身份首行一起构成「这是哪个编译器」的判据。
- 理由：缓存是「用正确性换时间」的设施，它的唯一义务是不能返回错误结果。文件存在 + 长度非零只挡住了「空文件」这一种损坏，而截断（磁盘满）、被替换、被人手改都是现实中会发生的形态；SHA-256 与长度一起比对，成本是一次读文件（几到几十 KB）与本项目已有的 SHA-256 实现，相对于省下的数百毫秒 C 编译可以忽略。查询不到编译器时禁缓存，比「用一个占位符凑合」更符合「不能可靠识别就不复用」这条纪律——多花的时间是可预期的，错误的二进制不是。
- 已排除的做法：
  - **用文件修改时间或大小做校验**：大小能挡住截断，挡不住同长度替换；时间戳在复制/解压/文件系统迁移后不可靠。
  - **在键里加入链接器/系统库版本**：无法可靠枚举（`ld` 版本、libc 版本、SDK 路径），按第 3 项纪律应当「不声称覆盖」。文档明确写：键覆盖的是**生成 C、编译选项、编译器身份与路径、AE 版本、目标平台**；更换 libc/SDK 后需要 `cache clear`（或在 CI 里使用独立缓存目录）。
  - **命中失败时静默重建、不删旧条目**：损坏条目会在每次构建时重新失败一次；删掉它让下一次干净。
  - **编译失败时不写缓存**：本来就不写（发布发生在成功之后），保持不变。
- 后果与限制：首次运行会因缺少 manifest 全部 miss 并重建一次（旧条目被删除）；每个条目多一个几十字节的 manifest；每次命中多读一遍可执行文件（约 60 KB）并计算一次 SHA-256；仍不能发现「编译器输入之外的系统变化」（libc/SDK/环境变量），文档要求这类变更后清理缓存。测试从「损坏条目被当成命中」改为「损坏条目被判为 miss 并重建出可运行产物」，与 ADR-4 的语义承诺对齐。

## ADR-28：缓存大小上限与按最近使用清理

- 背景：阶段 D 第 4 项要求「可配置缓存目录、大小限制、查看和清理」。目录与查看/清理已有（`AE_CACHE`、`cache dir|clear|stats`），但条目只增不减：每次改一行源码就多一个完整可执行文件（Linux 约 17 KB，Windows 约 62 KB），长期开发会积累成千上万个，与「低磁盘占用」的初始目标相反。
- 决策：
  1. 新增环境变量 `AE_CACHE_LIMIT`，单位字节。未设置、`0` 或无法解析为数字时**不限制**（拼错不该导致删条目）。
  2. 每次成功发布条目后运行一次清理：统计所有条目（可执行文件 + manifest 的字节数），总量超过上限就从**最久未使用**的开始整条删除，直到回到上限以内。
  3. 「使用」由条目内的空文件 `used` 记录：命中时写一次，清理时读它的修改时间；没有该文件时回退到可执行文件的修改时间（兼容旧条目）。
  4. 删除失败不算构建失败；条目留到下次清理。
  5. `cache stats` 增加 `limit:` 行（`none` 表示未设置）。
- 理由：用 LRU 而不是「最旧创建」或「随机」删除，是因为开发时的访问分布高度倾斜——正在改的那个程序反复命中，几十个昨天的实验程序再也不会碰；按访问时间删能保住热条目的编译时间，正是缓存存在的意义。用文件修改时间当访问时钟，而不是在文件里写计数或时间戳：写入会改变文件内容与 mtime，需要额外的原子性保证，而 `fs::utime` 语义在各平台不一致；一个空文件的 mtime 由文件系统维护，简单且够用。限制默认关闭，是因为「悄悄删用户的编译产物」比「占点磁盘」更让人意外；要控就显式设上限。
- 已排除的做法：
  - **默认上限（例如 512 MB）**：会在用户不知道的情况下删除条目，且不同项目的合理值差一个数量级；显式设置比猜测更诚实。
  - **按「最旧创建」删除**：正在使用的条目可能被删掉，恰好删掉刚编译好的那个。
  - **在命中时记录到中心索引文件（JSON/数据库）**：需要并发写、崩溃恢复与格式版本管理；每个条目一个 `used` 文件没有这些问题。
  - **后台清理线程/定时器**：命令行工具不该常驻；构建后顺手清理一次足够。
  - **在 `cache stats` 里自动清理**：查看操作不应改变状态。
- 后果与限制：清理粒度是整条（可执行文件 + manifest + used），不会出现「半个条目」；并发构建时两个进程的清理可能互相删掉对方刚发布但尚未使用的条目（后果是重新编译一次，不会产生错误产物）；上限按**字节**计，不区分文件系统块大小与压缩；`used` 文件让每个条目多一个 inode；统计 `bytes` 不含 `used` 与目录项本身，是下界而非精确磁盘占用。

## ADR-29：`vec[string]` 构造与子进程执行

- 背景：阶段 E 第 1 项把「进程」列为基础 API。脚本要做的第一件事常常是**调用机器上已有的工具**（`git`、`ffmpeg`、`grep`），而 AE 此前只能读写文件，无法启动子进程。同时，向子进程传参数需要一个空的 `vec[string]`，而当时只能从 `split`/`args` 间接得到——没有「从零开始构造字符串向量」的方式。
- 决策：
  1. 新增 `strvec_new() -> vec[string]`：一个空字符串向量，配合 `push` 逐个添加。
  2. `push(v, x)` 与 `v[i] = x` 现在也接受 `&string`（借用）：元素是**复制**进向量，源字符串不受影响；拥有型 `string` 仍按移动处理。
  3. 新增 `run_command(program, args) -> CommandResult`，`args` 必须是裸 `vec[string]` 变量（借用，不移动）。预置枚举 `CommandResult{Ok(i64 status, string output), Err(string)}`（编号 7）。
  4. 子进程的 stdout 与 stderr **合并到同一个管道**，`output` 里保持两者写入的先后顺序。
  5. 非零退出状态是 **Ok** 的一部分（`grep` 无匹配返回 1 是正常结论）；只有「启动失败」（找不到程序、无权限、管道创建失败）才是 `Err`。
  6. POSIX 用 `fork` + `execvp` + 等待；Windows 用 `CreateProcessW` + 匿名管道。参数数组在 POSIX 上原样传给 `execvp`（不经任何解析），Windows 上必须拼成一条命令行：只给含空白的参数加引号（给不需要引号的参数加引号会让接收方把引号当成命令名的一部分），含 `"` 或以 `\` 结尾的参数直接报 `Err` 而不是猜转义规则。
- 理由：合并两个流而不是分别捕获，是因为「同时读两个管道」在任何真实输出量下都会死锁（一个写满、父进程在等另一个），要避免就得引入 `poll`/`select` 或读线程；合并后既没有死锁，也保住了「错误信息出现在它该出现的位置」这一可读性，代价是调用方无法区分某个字节来自哪个流。把状态放进 `Ok` 而不是「非零即 `Err`」，是因为语言的错误是**可恢复的失败**（启动不了、读不到），而程序返回 1 是可恢复的正常结果——把它当错误会逼调用方用 `match` 做两件事（既判断能不能运行，又判断运行结果）。参数按需加引号、拒绝引号，是为了不重写 `CreateProcess` 的转义规则：那条规则（反斜杠计数、引号加倍）一旦实现错，子进程收到的参数就悄悄变了，而错误值不会报任何错。
- 顺带修复一处所有权缺陷：`push(v, argv[i])` 最初被当作「移动」发射（`moving = true`），而 `argv[i]` 是借用视图。结果是把视图当成拥有值放进向量：源槽位被清空、向量里存了一份「指向别处缓冲区的 string」，退出时同一块内存被释放两次——Windows 上的表现是进程以 `0xC0000374`（堆损坏）结束，并且因为 stdio 缓冲丢失而**什么也不打印**。现在解析期记录「这个元素是借用」的标志，借用走 `ae_str_copy_view` 并禁止移动；新增的端到端测试用 `args()` + 索引 push 复现原来的场景。
- 已排除的做法：
  - **`popen`**：单向、拿不到退出状态，且 stderr 无法合并。
  - **`system`**：继承终端，拿不到输出；脚本无法据其结果做判断。
  - **把整条命令行当一个字符串传（`run_command("git --version")`）**：需要 shell 解析，注入风险与跨平台差异都回来了；参数数组是唯一安全的形态。
  - **异步/超时/流式输出**：需要句柄类型、取消语义与事件循环；先做同步一次性，等真实需求出现再设计（方案阶段 F 会处理并发与超时）。
  - **注入 stdin**：需要双向管道与「谁先写完」的协议；`read_stdin` 已覆盖「读自己的输入」，子进程的输入留给后续。
  - **`vec[string]` 字面量 `["a", "b"]`**：`strvec_new` + `push` 已够用，字面量需要新的表达式形式与借用规则。
- 后果与限制：没有超时、没有 stdin、没有环境变量与工作目录参数（继承父进程）；输出全量驻留内存，超大输出（数百 MB）不适合；POSIX 上被信号终止的子进程报 `128 + 信号号`（与 shell 一致），Windows 没有信号概念，拿到的就是 `GetExitCodeProcess` 的值（异常终止时是 NTSTATUS）；Windows 参数不能含 `"` 或以 `\` 结尾；两个平台都不做 shell 展开（通配符、管道、重定向需要自己调用 shell，例如以 `cmd` 为程序名并显式传 `/c`）。新增 `examples/run_tool.ae` 与 2 个端到端测试（一次真实子进程、一类启动失败），并在 Windows 与 Debian 13 上分别验证（POSIX 分支用 `CLOEXEC` 错误管道区分「exec 失败」与「程序自己返回 127」，否则两平台会用不同的结果表示同一件事）。

## ADR-30：泛型结构体用与泛型枚举相同的单态化

- 背景：泛型枚举（ADR-21）解决的是「一个值可能是 A 也可能是 B」，但数据的**成对/成组**关系仍然只能靠并列变量或平行向量表达。`Pair[K, V]`、`Map.Entry` 这类结构在一门系统语言里无法回避，而当时 `struct P[T]` 会在解析处直接报「不支持」。同时，泛型结构体是通往 `Result[T, E]` 与泛型函数的第一步：先证明单态化在「有布局、有释放」的类型上也成立，再把它用到有函数体的地方。
- 决策：
  1. `struct Name[T, U] { ... }` 与泛型枚举共用类型参数规则（单个大写字母、最多 8 个、不得重复），也共用「声明不产生布局」的原则：只有 `Name[string, i64]` 这样的**实例化**才产生 `typedef`。
  2. 实例化键是「声明 + 实参列表」，与 `instantiate_struct` 的 `struct_done` 缓存一致：同一实参列表复用同一个 `StructDef`（也就复用同一个 `ae_tN` 与 release/forfeit），因此同实参的值可以互相赋值、可以共用同一个参数类型。
  3. 类型实参用 `named_type()` 解析，比泛型枚举的 `type_argument()`（扁平类型）更宽：结构体、枚举、已实例化的泛型都能当实参。理由是结构体字段本来就能容纳结构体与枚举，放宽不会引入新的布局形状；枚举负载仍然限扁平类型，因为枚举的负载结构必须能按变体 `free`。
  4. 字段类型在声明期用 `Payload`（`Concrete`/`Param`）表示，实例化时替换成实参，与枚举变体负载同一套机制，`Param` 不会漏到代码生成。
  5. 预算：`MAX_STRUCT_TYPES = 256`（含普通结构体），与枚举的 256 分开计，超限在实例化处报错。
- 理由：不引入「泛型结构体的运行时代码」——单态化后它就是普通结构体，释放、字段借用、移动检查全部沿用既有实现，因此不需要新的运行时设施，也不会让「结构体字段不能移出」这条安全规则出现例外。允许结构体/枚举做实参，是因为限制实参种类省不下多少实现，却会让 `Pair[i64, Tag]` 这种最自然的写法无法表达。
- 顺带修复一处缺陷：`skip_struct_def` 只跳过 `struct Name` 再接 `{`，遇到 `[T]` 就把 `[` 当成左花括号，然后一路跳到文件末尾，`fn main` 被静默吞掉，报错却是「found 0 main function」。现在与 `skip_enum_def` 一样先调用 `skip_type_params()`；这个缺陷是加泛型时被最小用例暴露的，说明两个跳读函数必须同形。
- 已排除的做法：
  - **让泛型结构体的字段可以是 `T` 的向量（`vec[T]`）**：`vec` 的元素类型是编译期固定的 `i64` 或 `string`，要做通用容器得先有元素类型描述符，属于另一件事。
  - **trait/约束（`T: Printable`）**：没有 trait 与静态分派之前，约束只能是个空承诺；先让单态化跑通，再把约束设计成「对实参形状的检查」。
  - **在类型位置省略实参并做推断**：语言目前没有任何类型推断，省略实参会让 `Pair { left: "a", right: 1 }` 需要从字段表达式反推实参，那是另一套机制。
- 后果与限制：实例化只发生在**使用处**，因此错误位置指向使用处而不是声明处；错误信息里的结构体类型仍显示为 `struct #N` 而不是 `Pair[string, i64]`（`Type::Struct` 只带 id，未像 `Type::Enum` 那样带名字，后续可对齐）；`&Pair[string, i64]` 借用参数暂不支持（`&` 只接受 `string`/`vec`/数组），大结构体只能按值传；泛型函数仍未实现。新增 `examples/pairs.ae`、1 个端到端测试（含 8 个必须被拒绝的写法），并把 `pairs.ae` 加入生成 C 校验的分配计数用例。

## ADR-31：泛型函数在调用点解析自己的源码

- 背景：泛型结构体（ADR-30）证明了单态化在「有布局」的类型上成立，但真正需要复用的是**行为**：`identity`、`swap`、`wrap` 这些函数对任何类型都一样。语言没有类型推断，也没有约束，所以「泛型函数」必须回答三个问题：类型实参从哪来、函数体什么时候检查、跨文件怎么办。
- 决策：
  1. 类型实参写在调用点：`identity[i64](41)`。不写就报错并提示补上——没有推断，就没有「猜错类型」这一整类问题。
  2. 声明时只记录**位置**：参数名、`(` 的 token 下标、该文件的 token 流与源码副本。没有函数体 AST，也没有签名。一次调用才创建一份 `Function`，函数体按替换表重新解析。
  3. 替换表（`subst: HashMap<String, Type>`）在 `named_type` 的最前面生效，因此 `Option[T]`、`Pair[T, i64]`、`vec` 之外的任何类型位置都能自动按实参解析，泛型体里调用另一个泛型（`wrap[T]`）也自然成立。
  4. 实例化用**子解析器**：新建一个 `Parser`，共享同一份 `functions`/`structs`/`enums`/`generics`（reborrow `&mut *self.functions` 这类），`file`/`source` 指向声明文件。于是泛型体看到的是**声明文件**的可见性上下文——它可以调用声明文件里的私有函数，导入者只能看到 `pub` 的那一层。跨文件实例化因此不需要额外的机制。
  5. 函数 id 只有一套：`generics.next_fn_id`。普通函数在签名收集阶段从它取号，实例化也取号，`*next_id` 与它的同步用 `max` 折叠，避免不同文件的收集顺序造成重号。
  6. 实例化键是「声明 + 实参列表」，结果缓存；正在实例化的键放在 `fn_in_progress` 里，闭合时报错而不是无限展开。
- 理由：把函数体当**文本 + 位置**保存，而不是保存一个未替换的 AST，是这里最省事也最安全的选择——替换发生在解析期，因此代码生成阶段永远不会看到 `T`，不需要「泛型 IR」「类型擦除」或「运行时类型描述符」。代价是错误信息指向泛型体（而非调用点），这是逐实例化检查的必然结果，也是它比「先按泛型检查」更诚实的地方：不给约束的语言没法在泛型层面证明 `x + 1` 合法。
- 已排除的做法：
  - **类型推断**：需要统一算法与错误恢复，「不写就猜」还会让 `identity(5)` 与 `identity("a")` 产生两份布局却看起来一样。
  - **trait/约束**：`T: Add` 之类的语法需要静态分派与孤儿规则；在没有它们的阶段引入约束，只是把检查推迟到运行时。
  - **保存未替换的 AST，在代码生成前单态化**：意味着整个前端要为「类型变量」留一层中间表示，收益只是错误信息更靠近调用点。
  - **`&T` 参数**：借用参数目前只有 `&string`/`&vec`/数组三种具体形式，泛型借用要先把 `parameter_type` 变成「可替换的借用」，属于下一轮。
- 后果与限制：错误位置指向声明处；`main` 不能是泛型；`&T` 参数不支持；同一实参列表共享一个 C 函数（所以两份实例化不会各自膨胀）；每个实例化都是一次完整解析，实例化很多的程序会变慢（当前规模无感，未来要加「先按泛型检查」的快速路径）。新增 `examples/generic_fn.ae`、1 个端到端测试（6 个必须被拒绝的写法），并把示例加入生成 C 校验的分配计数用例（验证「返回 a、释放 b」这条路径不漏不重）。

## ADR-32：`set_cwd` 是显式的进程级副作用，`set_env` 不做

- 背景：`cwd()`（ADR-24）只能读工作目录。文件整理工具与脚本经常需要「进入目标目录再操作」，而 `run_command`（ADR-29）也继承父进程的工作目录，所以缺少写入口时只能把每个路径都拼成绝对路径。
- 决策：
  1. 新增 `set_cwd(path) -> StatusResult`：失败返回 `Err` 且目录不变，成功返回不带负载的 `Ok`；与其它文件系统写入操作同一形状。
  2. 不做 `set_env`。理由是硬约束而不是偷懒：`setenv` 是 POSIX 接口，在 `-std=c11 -pedantic-errors`（定义了 `__STRICT_ANSI__`）下 glibc 不声明它，实测 `gcc -std=c11 -pedantic-errors` 报 `implicit declaration of function 'setenv'`；而 ADR-25 已经决定不注入 `_POSIX_C_SOURCE` 之类的特性宏，为的就是生成的那份 C 能在任何严格 C11 编译器上编译。`chdir`/`mkdir`/`opendir` 不受影响，所以只有 `set_env` 被挡在门外。
- 理由：工作目录是**一个**进程级状态，语义清楚、可以保存与恢复（`cwd()` + `set_cwd`），失败模式只有「进不去」。环境变量则是任意多个名字，改一个就影响所有后续子进程，而且没有「恢复原样」的自然写法（原值可能不存在），很难在类型上表达「这段代码之后环境变了」。把它排除在外，比提供一个半吊子的全局可变环境更诚实。
- 已排除的做法：
  - **为 `setenv` 注入 `_POSIX_C_SOURCE`**：一行宏就能解决，但会让「严格 ISO C」这条已验证的性质不再成立，代价远大于一个内建函数。
  - **`with_cwd(path, fn)` 之类的作用域化接口**：语言还没有闭包或高阶函数，无法表达。
  - **只给 `run_command` 增加工作目录参数**：那只是绕开问题——文件操作仍然需要相对路径基准；两者可以并存，但后者不解决核心需求。
- 后果与限制：`set_cwd` 是签名看不出来的全局副作用，文档必须在调用处提醒；POSIX 上被 chdir 到已删除的目录后 `cwd()` 会返回 `Err`（真实行为，不掩盖）；没有 `set_env`，改变子进程环境只能借 `env` 程序；新增 1 个端到端测试（进入子目录、相对路径写入、返回原目录、目标不存在），并在两个平台上验证。

## ADR-33：约束是调用点的实参形状检查，不是泛型体的证明

- 背景：ADR-31 把泛型函数做成「调用点写实参、逐实例化重新解析函数体」，并明确排除了 trait/约束，理由是「没有 trait 与静态分派，约束只能是个空承诺」。但实际使用后暴露出两个问题：`fn add[T](a: T, b: T) -> T { return a + b; }` 用 `add[bool]` 调用时，错误来自泛型体内部的 `'+' requires ...`，用户看到的位置离自己写的代码很远；同时签名完全看不出这个函数只适用于能相加的类型。
- 决策：
  1. 泛型**函数**的类型参数可带约束：`[T: Add]`、`[T: Add + Eq]`、`[T: Copy, U: Ord]`。约束名固定为 `Add`/`Eq`/`Ord`/`Copy` 四个，未知或重复在声明处报错；泛型结构体与泛型枚举写约束直接报 `constraints are only supported on generic functions`（它们的声明没有函数体，约束没有可检查的对象）。
  2. 每个约束是一张**实参类型白名单**，与当前语言里真实可用的运算一一对应：`Add` = `i64`/`string`（`+`）；`Eq` = `i64`/`bool`/`string`（`==`、`!=`）；`Ord` = `i64`（`<` 等）；`Copy` = `i64`/`bool`（无需释放、可重复读）。白名单不是「运算符的抽象」，而是「现有类型检查规则的镜像」，所以它不会撒谎。
  3. 检查发生在 `instantiate_fn` 的开头、解析函数体之前，错误位置是调用点，消息形如 `type argument 'bool' for 'add' does not satisfy 'Add'; that constraint allows i64, string`。声明保存了约束，因此跨文件 `pub fn` 的约束在导入者的调用点同样生效。
  4. **不做**泛型体与约束的一致性检查，也不做静态分派：函数体仍按 ADR-31 在每个实例化里完整解析、完整类型检查。约束只能提前拒绝，不能放行。
  5. 顺带补齐 `bool == bool` / `bool != bool`：原先 `Eq` 声称允许 `bool`，而前端只允许整数比较与字符串相等，两条规则互相矛盾。现在 `(Bool, Bool)` 只对 `==`/`!=` 放行，`<` 等仍被拒绝；C 后端对布尔值直接发射 `==`，不需要新运行时代码。单元测试中原本「拒绝 `true == false`」的用例改为「拒绝 `true < false`」，并在接受列表里加入布尔相等。
- 理由：把约束定义成「实参形状检查」而不是「泛型体的能力契约」，是唯一与逐实例化检查相容的定义。要实现真正的 trait 契约，需要先有一份未替换的泛型 AST 和一套「在类型变量上检查运算」的规则；那时才能证明泛型体只用了声明的能力。在当前架构里，任何声称「约束保证函数体合法」的说法都是假的，写进语言反而会误导。形状检查虽然弱，但确实把错误信息从「别人的函数体内部」搬到了「自己写的调用点」，这是用户能感知的改进，且实现只在实例化入口加一个循环。
- 已排除的做法：
  - **用户自定义 trait / `impl`**：需要方法表、静态分派、孤儿规则与可见性规则，属于下一阶段；在此之前开放约束名只会让每个用户自己发明一套无法检查的约定。
  - **从函数体反推约束**（不写就推断 `T` 需要 `Add`）：等价于引入类型推断，且推断结果会随函数体改动而变，破坏接口稳定性。
  - **让约束影响代码生成**（例如按 `Copy` 省略释放）：当前释放由具体类型决定，与约束重复；两套规则一旦不一致就是内存错误。约束不参与代码生成，只参与检查。
  - **给泛型结构体/枚举也加约束**：字段声明不使用运算，约束无处落脚；等有 `where` 子句或关联类型再说。
- 后果与限制：约束是「早一点报错」，不是「少检查一次」；同一个泛型体用不同实参仍会各解析一遍。允许列表是硬编码的，语言新增运算或类型时必须同步更新，否则约束会与类型检查脱节（当前由端到端测试覆盖四个约束的正反用例）。新增 `examples/constraints.ae`、1 个端到端测试（含 9 个必须被拒绝的写法）、1 个生成 C 分配计数用例，两平台各跑一遍全量验证。

## ADR-34：`?` 按「两变体形状」传播，Option 与结果枚举同规则

- 背景：ADR-21 引入 `?` 时只接受 `{ Ok(...), Err(string) }`，理由是「失败值要能原样交还调用者」。但 `Option[T] { Some(T), None }` 是同一形状（一个成功变体、一个无负载的失败变体），`None` 同样可以原样交还；此前要求 `Option` 必须 `match` 取出，导致「查找可能没有的键」这类函数在每一层都要写一遍样板 `match`，与结果枚举的体验割裂。实际使用中（`Option[string]`、`Option[vec]`）这个缺口最先暴露。
- 决策：
  1. 可传播形状扩为两类：`{ Ok(...), Err(string) }` 与 `{ Some(T), None }`，变体名与顺序固定。判定只看**声明形状**，不看是否预置枚举——用户自定义的同形枚举与 `Option` 行为完全一致，不需要登记到预置表。
  2. 代码生成统一按「失败变体的 tag」分支：`tag == AE_E{eid}_1` 时释放当前所有存活拥有型变量并 `return` 该枚举值；成功分支把 `variants[0]` 的唯一负载移出绑定（`let`）或按类型释放（裸语句）。结构体/枚举/`vec`/`vec[string]` 负载都走各自的释放例程，不假设负载是 `string`。
  3. `let` 绑定的成功变体必须恰好一个负载，否则在声明处报错并指出实际数量；裸语句允许任意负载个数（全部释放）。外层函数必须返回同一枚举类型，`main` 里不能传播，`?` 仍是语句而非表达式——这些规则与 ADR-21 一致，没有放宽。
- 理由：`Option` 与结果枚举的区别在语义（有没有错误文本），不在控制流；让两者共用一条传播路径，既减少用户的样板代码，也避免为 `Option` 再造一套语法。用 tag 而不是变体名生成代码，保证「自定义同形枚举」不需要任何特判，也避免字符串比较进入生成代码。
- 已排除的做法：
  - **为 `Option` 新增 `!` 或 `??` 语法**：同一控制流用两套记号只会增加学习成本；`?` 已经准确表达「失败就交给调用者」。
  - **用类型名判定 `Option`**：会把预置枚举变成特权类型，自定义同形枚举无法复用，且实例化后的类型名（`Option[string]`）不稳定。
  - **允许 `Err` 携带任意负载**：结果枚举的失败值要能原样返回，`Err(string)` 是既有约定；放宽会让错误文本与其它负载混在一起，等有正式错误类型再单独设计。
  - **在 `?` 里自动 `match` 转换跨族结果**：需要错误类型之间的映射规则，属于错误模型扩展，不是传播语句的职责。
- 后果与限制：`Option` 的 `None` 与结果枚举的 `Err` 共用「失败即返回」的语义，编译器不区分二者，文档必须说明「`?` 不附加错误上下文」。每个传播点生成一次释放序列，函数内拥有型变量多时生成的 C 会变长（当前按变量数线性）。新增 `examples/option_propagate.ae`、1 个端到端测试（覆盖 `Option[string]`、`Option[vec]`、自定义同形枚举与 6 个必须被拒绝的形状）、1 个生成 C 分配计数用例；Windows 与 Linux（`instabox-node`）均已全量通过：9 单元 + 127 集成测试、21 个生成 C 用例两种优化模式 PASS、Linux 净化器无报告且 `--leak` 分配计数为 0（Windows 2 块基线），原始输出见 `bench/results/2026-11-10-linux-node-option/`。

## ADR-35：`&T` 在实例化时落到既有借用，借用参数可以直接转发

- 背景：ADR-31 把「`&T` 参数」明确留到下一轮。按值接收的泛型函数会移动实参：`fn size_of[T](x: T)` 调用一次就把字符串或向量交出去了，而「量一下长度」不该消耗值。同时发现文档与实现不一致：`current-language.md` 写 `&vec`「可转借」，但 `fn outer(v: &vec) -> i64 { return inner(&v); }` 实测被拒（`argument must be vec, found &vec`）——`call_arguments` 只接受裸的拥有型向量，而 `Argument::Borrow(var, true)` 一律生成 `&v{id}`；对本身已是 `const ae_vec *` 的参数，那会变成二级指针。
- 决策：
  1. `parameter_type()` 在 `&` 之后先查替换表。泛型实例化时 `T` 已经绑定具体类型，于是 `&T` 就是既有三种借用的一种拼写：`string → StrView`、`vec → VecRef`、`vec[string] → StrVecRef`。`i64`、`bool`、结构体、枚举、映射、数组在**实例化处**报 `has no read-only borrow`，位置指向 `&`。
  2. 非泛型上下文里的 `&Ident`（除 `string`/`vec`）不再掉进 `expected '['`，而是报 `unsupported borrow type` 并列出可用写法。
  3. `call_arguments` 允许实参变量本身就是对应的借用参数；`Argument::Borrow` 的布尔值语义明确为「是否取地址」：拥有型向量取地址，借用型向量直接把指针传下去。类型不匹配的转发（`&vec[string]` 传给 `&vec`）仍被拒绝，只读规则（不能 push/写）不变。
  4. 约束不检查借用能力。`T: Add` 允许 `i64`，但 `&i64` 在实例化时由第 1 条拒绝；约束仍是 ADR-33 定义的「调用点实参形状检查」，不扩大它的职责。
- 理由：单态化（ADR-31）在**解析期**就把 `T` 换成了具体类型，因此 `&T` 不需要泛型 IR、生命周期标注、运行时类型描述符或新的释放规则；代码生成一行都不用改。转借修复只是少生成一个 `&`，却把文档里的承诺变成事实，也让泛型体里组合调用成为可能。把可借用类型限定为三种，是因为语言目前只有这三种只读借用；为其它类型造一个「看起来像借用」的东西会打破「不谎报安全性质」的底线。
- 已排除的做法：
  - **`&T` 作为返回类型或结构体/枚举字段**：需要跨函数生命周期与别名规则，不是把 `Type` 换个拼写就能解决。
  - **统一调用点语法**（让 `&T` 全部写 `&x` 或全部不写）：`string` 视图直接传值、`vec` 借用显式写 `&`，是既有规则；泛型体里再实例化另一个 `&T` 模板时无法同时满足两者，改语法会让所有现成程序失效。
  - **给结构体/枚举加 `&Struct` 借用**：需要新的字段访问与释放边界，单独设计。
  - **让 `&T` 覆盖 `map`**：`map_*` 走 `MapPlace`（变量或字段），不是参数借用，混在一起会产生两套所有权规则。
  - **在声明处检查 `&T`**：与「函数体在实例化时才解析」一致，未被调用的泛型声明不做检查；这是既有代价，不为一处语法破例。
- 后果与限制：同一个泛型模板用不同 `T` 实例化时，调用点的实参形状随 `T` 变化（`size_of[string](text)` 与 `size_of[vec](&numbers)`），文档必须写清楚；因此「泛型体内再把 `&T` 参数转交给另一个 `&T` 模板」目前只对 `string` 形状可靠，其它形状要在调用点按具体类型写。新增 `examples/generic_borrow.ae`、1 个端到端测试（3 种实例化、2 条转发链、8 个必须被拒绝的写法）、1 个生成 C 分配计数用例。Windows 验证见 `bench/results/2026-11-10-windows-borrow-find/`；W1 的 Linux 回填（同提交树 `2e26000`）见 `bench/results/2026-11-10-linux-borrow-find/`，9 单元 + 129 集成、23 个 `--sanitize` 与 23 个 `--leak` 用例全部通过、无净化器报告、退出分配块数为 0，本 ADR 至此为双平台验证。

## ADR-36：`find` 用结果值返回字节下标，不引入哨兵

- 背景：`contains` 只回答「有没有」，要定位一次匹配就只能 `split` 后逐段比较或自己扫 `bytes()`。工作区里留有 `find` 的保留名和 `Expr::Find` 变体草稿，但没有解析分支、代码生成和运行时函数，`cargo build` 会因 match 不穷尽而失败。本轮把它补成完整内建，而不是删掉草稿或留一个编译不过的半成品。
- 决策：
  1. `find(text, needle) -> IntResult`：返回首次匹配的**字节下标**；找不到返回 `Err("substring not found")`；空 `needle` 返回 `Ok(0)`，与 `contains` 的「空子串为真」一致。
  2. 视图带显式长度，用 `memchr` 定位首字节、再 `memcmp` 比较剩余部分。成功路径零分配；失败路径只分配 `Err` 负载那一个字符串，由结果枚举的释放例程回收。
  3. 两个参数都接受 `string` 或视图，借用而不移动；结果是普通枚举，必须 `let` 绑定后 `match`，裸表达式语句由既有规则拒绝。
  4. `find` 进 `RESERVED`，不能重定义。
- 理由：不用 `-1` 表示「没有」，是因为语言把「可恢复的失败」统一交给结果枚举（`map_get`、`parse_int`、`json_int` 都是这个形状）；哨兵会让调用方可以静默忽略失败，而 `Err` 必须被处理。返回**字节**而不是码点下标，是因为 `len`/`slice`/`bytes` 都按字节工作，字符下标需要码点表或每次扫描，会给一个只读查询引入分配——与低内存占用的核心目标相反。`memchr` 是 ISO C11 的平台优化实现，不引入第三方依赖，符合「严格 C11、任一合规编译器可编译」的约束（ADR-25）。
- 已排除的做法：
  - **`Option[i64]`**：语义同样成立，但预置结果族已经承担「带原因的失败」，且 `IntResult` 与其它可失败内建同形，少一种需要用户记住的返回类型。
  - **返回 `-1` / `bool`**：前者是哨兵，后者丢掉位置信息。
  - **`rfind`、正则、多模式、码点下标**：需要新的语义与测试面，等真实工作流提出需求。
  - **顺手把 `contains` 改成同样的 `memchr` 实现**：`ae_contains` 现在用 `strstr`，遇到嵌入 NUL 会在第一个 NUL 处停止；`find` 不会。两者行为不同必须如实标注，但改 `contains` 属于独立语义变更，要有单独的基准与回归，不塞进本轮。
- 后果与限制：最坏情况 O(n·m)（`memchr` 跳过首字节不匹配的位置，常见文本接近线性），没有 Boyer–Moore 之类的预处理，也不分配表；长模式 + 大量重复首字节时不如成熟搜索库，文档不宣称是最优实现。`contains` 与 `find` 在含嵌入 NUL 的字符串上结论可能不同，这是已知且已记录的差异。错误文本固定，不随平台 `strerror` 变化。新增 `examples/find_text.ae`、1 个端到端测试（含 UTF-8 字节偏移与 4 个拒绝用例）、1 个生成 C 分配计数用例（验证 `Err` 负载被释放）。同提交树的 Linux 回填（W1，见 `bench/results/2026-11-10-linux-borrow-find/`）把本 ADR 升为双平台验证：ASan/UBSan 无报告，`Err` 分支的退出分配块数同为 0。本轮还纠正了一处表述：两平台示例输出只在**行尾归一化后**一致（Windows stdout 文本模式输出 CRLF），平台矩阵已据此改写。

## ADR-37：`f64` 先定语义再落实现，文本形式由运行时统一

- 背景：§4.2 一直写着「浮点先按 IEEE 754 和目标平台行为制定规范，再加入」，而数值与统计脚本需要小数；W2 的目标是先写死规则再动前端，避免把 UCRT 与 glibc 的差异当成语言语义。实测确认了两处真实差异：`printf("%.17g")` 对 NaN 分别输出 `-nan(ind)`（UCRT）与 `-nan`（glibc），指数位宽与有限值在现有工具链上恰好一致，但不能据此假设永远一致。
- 决策：
  1. `f64` 是 IEEE 754 binary64，C 侧就是 `double`；不做隐式 `i64`/`f64` 转换，混合算术、混合比较在类型检查处拒绝并提示用 `to_f64`/`to_i64`。字面量必须带小数点或指数（`1.5`、`1e3`），`1..2` 仍是范围、`1.field` 仍是字段访问；非有限字面量与「非零却下溢为 0」的字面量在词法处报错，不静默替换用户写的值。
  2. `+ - * /` 只对两个 `f64` 放行，生成普通 C 运算符，不启用 fast-math，`-O0` 与 `-O2` 必须给出同样结果；`%` 明确拒绝（余数只在 `i64` 上有定义）。除法走 `ae_f64_div`：`x / 0.0` 与整数除法一样报告失败（非零退出），而不是静默产生 `inf`；溢出得到 `inf`、下溢得到次正规数或 `0`，按 IEEE 处理并在文档写明。
  3. 六个比较都支持，语义就是 IEEE：任何与 NaN 的比较为假，`!=` 为真；`Eq`/`Ord` 约束因此把 `f64` 列入允许集合，但文档必须提示 NaN 行为，约束不是「全序」承诺。
  4. 文本形式由运行时 `ae_f64_text` 统一：`nan`、`inf`、`-inf` 用固定拼写；有限值取「能往返的最短有效位数」，在定点与科学计数法之间选更短的一种（同长取定点），指数统一为 `e±最小位数`；没有小数点也没有指数的结果补 `.0`，保证 `1.0` 不会被读成 `i64`。`print`、`to_string` 共用这一条路径。这样跨平台输出由构造保证，而不是依赖两个 CRT 恰好一致。
  5. 转换显式且受检：`to_f64(i64) -> f64` 只在 `|n| ≤ 2^53` 时成功，更大整数会丢精度，运行时直接失败而不是四舍五入；`to_i64(f64) -> IntResult` 依次检查有限性、i64 范围、是否为精确整数，失败原因分别是 `f64 value is not finite`、`... outside the i64 range`、`... is not an exact integer`。
  6. `f64` 可作函数参数/返回值、结构体字段、枚举负载与泛型实参（`Option[f64]` 可用）；`vec` 仍只装 `i64`，`map` 值仍只有 `i64`，`&f64` 被 ADR-35 的「只有三种只读借用」拒绝。
- 理由：把「哪些行为是语言规定的、哪些是宿主给的」分开，是这个项目能不能宣称跨平台的前提。文本形式放进运行时而不是生成代码，有三个好处：一处修改全程序生效；不把 `%g` 的平台差异写进每个调用点；分配计数仍能覆盖 `to_string`。除法与整数保持同一条「零是错误」的规则，避免同一门语言里 `1/0` 退出而 `1.0/0.0` 静默变成 `inf`。转换只接受精确值，是因为「悄悄改掉用户的值」正是 §4.1 要求保守规则拒绝的情况。
- 已排除的做法：
  - **隐式数值转换**（`1 + 2.0` 自动提升）：会让精度丢失藏在表达式里，也让类型错误更难定位；宁可要求显式写 `to_f64`。
  - **直接 `printf("%.17g")`**：UCRT 与 glibc 对 NaN 的拼写不同，指数位宽在历史上也不同；把它写进语言等于把 CRT 行为当规范。
  - **总是输出 17 位有效数字**：0.1 会变成 `0.10000000000000001`，可读性差；先按最短往返位数搜索，代价是每个值最多 18 次 `snprintf`+`strtod`，只在打印路径上。
  - **`x / 0.0` 返回 `inf`**：与整数除法规则冲突，且让「检查过没有」变得不可见；需要无穷值的程序可以显式构造并承担语义。
  - **`to_f64` 对超出 2^53 的整数四舍五入**：静默丢精度，违反「不能证明安全就拒绝」。
  - **本轮加入 `sqrt`/`sin`/`log` 等数学函数**：需要 libm、链接参数与跨平台末位差异的证据，属于独立工作项；先不做，比做了再撤回好。
  - **`vec[f64]` 与 `map[string, f64]`**：各自需要新的容器布局、边界与释放路径，留给下一轮；本轮不留下半实现的容器。
- 后果与限制：文本是**规范形式**而不是最短十进制：`1.0/3.0` 输出 `0.3333333333333333`（16 位即可往返），某些值会输出科学计数法（`1e+16`、`1e-4`），这是「选更短形式」的直接结果，文档给出规则与例子。NaN 的符号与负载不保留，统一写 `nan`。`f64` 字段让结构体/枚举布局每个字段多 8 字节，生成 C 体积随字段数线性增长。没有数学库，没有十进制小数类型，也没有 `f32`。新增 `examples/float_math.ae`、4 个集成测试（规范文本、结构体/枚举/泛型、10 个必须被拒绝的写法、2 个运行时守卫）、1 个生成 C 分配计数用例。两平台各跑一次全量验证：9 单元 + 133 集成测试全通过，Linux `--sanitize` 24 个用例无报告，`--leak` 24 个用例退出分配块数为 0（Windows 等于 2 块基线）；`float_math.ae` 输出按行尾归一化后逐字节一致，因为文本由运行时生成而不是 CRT 的 `%g`。资源成本实测：生成 C 文本比空程序多 6,773 字节（109,721 → 116,494），主要是格式化器源码；空程序的 release 产物仍是 Windows 61,309 / Linux 16,176 字节，未被引用的格式化器会被优化掉，所以这是「用到才付费」的成本。`float_math.ae` 的 release 产物 Windows 70,467 / Linux 21,576 字节；它与 `find_text.ae`（66,904）不是同一程序，差值只作量级参考，不是精确增量。日志见 `bench/results/2026-11-10-{windows,linux}-float/`。

## ADR-38：编译速度先减输入，不靠更大的缓存或更多翻译单元

- 背景：§21 W3 要求把「可执行文件内容寻址缓存」升级为包级增量。动手前先分解 Windows 本机一次冷构建的耗时（WinLibs GCC 16.2，`fn main() { print(1); }`）：AE 前端约 2 ms，gcc 编译 109,721 字节生成 C 约 1,050 ms。真正的瓶颈不是前端、也不是函数调用次数，而是**每个程序都要解析整份运行时与整套 `<windows.h>`**：单独 `-fsyntax-only` 一个只含 `<windows.h>` 的文件就要 690 ms，而一个只含 `<stdio.h>` 的文件只要 66–82 ms。在这个前提下，「缓存更多中间产物」和「拆成更多翻译单元」都不能解决主要矛盾。
- 三条被实测否决的路线（数据都来自同一台机器、同一工具链、同一次会话）：
  1. **预编译头（PCH）**：把运行时前缀做成 `rt.h.gch` 后，编译从 1,405 ms 降到 596 ms，但 `.gch` 文件是 **69,495,776 字节**，生成它还要 2.1 s。用 69 MB 磁盘换 0.8 s 与「低磁盘占用」冲突，且每个工具链/优化级别组合都要一份 → 否决。曾因这个残留的 `.gch` 被 gcc 自动使用，导致后续分离编译的测量被污染（见下条），发现后已删除并重测。
  2. **运行时包单独编译 + 缓存 `runtime.o`，用户代码单独一个 TU**：清除残留 PCH 后的真实数据是单 TU 1,060 ms、`runtime -c` 915 ms、`program.c + runtime.o` 一次调用 870 ms、分开 `-c` 加链接 769+138 ms。也就是说缓存命中后只快约 18%，而首次构建变成 915+870 ≈ 1,785 ms（回归约 68%）；多出 68 KB 对象、两类缓存条目、声明/定义跨 TU 一致性风险，以及 `-O2` 下运行时小函数无法内联的性能风险。实现过一版并完整验证可运行，**按「不虚报性能结论」回退，不保留**。
  3. **手写最小 Win32 声明替代 `<windows.h>`**：理论上可省 600 ms，但要精确复刻 `WIN32_FIND_DATAW`、`STARTUPINFOW`、`WIN32_FILE_ATTRIBUTE_DATA` 等结构体的 ABI，风险与收益不对称；先采用零风险的 `WIN32_LEAN_AND_MEAN`（实测 690 → 520 ms），把最小声明留作独立工作项。
- 决策：
  1. **让运行时前缀真正程序无关**：把用户自定义枚举的布局从 `runtime.c` 与 `runtime_ex.c` 之间移到 `runtime_ex.c` 之后。后者只引用 prelude 的 8 个枚举 id，因此前缀变成对每个程序逐字节相同（实测 108,792 字节，四个不同程序的 SHA-256 一致）。
  2. **按可达闭包裁剪运行时函数**：把前缀切成顶层单元（`static ... ae_xxx(...) { ... }` 函数定义，以及必须原样保留的 include、宏、typedef、静态数据、注释）。根集合 = 程序后缀中的所有 `ae_*` 符号 + 所有非函数文本中的符号（宏体和静态初始化器会间接调用函数）+ `ae_set_allocator` 这个文档化的嵌入入口；再沿保留函数体内的 `ae_*` 引用做传递闭包。未保留的函数在本编译单元内没有调用者，删除它不改变语义。**条件编译下的同名定义必须全部保留并全部扫描**：初版用 `HashMap<name, index>` 只留最后一个定义，Windows 分支的 `ae_fopen` 依赖 `ae_widen` 却扫描到了 Linux 分支的函数体，5 个文件 I/O 测试因此编译失败；改成 `HashMap<name, Vec<index>>` 后修复。
  3. **`WIN32_LEAN_AND_MEAN`**：在 `runtime.c` 的 `#include <windows.h>` 前定义，排除 winsock/RPC/GDI 等从未使用的声明。
  4. **保留现有内容寻址可执行缓存不变**：无修改的程序仍走整体缓存命中，不增加缓存种类，不引入无限缓存。
  5. **新增 `ae deps <source.ae>`**：输出模块依赖图、每个模块的公开接口摘要哈希和程序指纹。摘要只由 `pub` 函数签名、结构体/枚举形状与泛型声明组成，函数体、私有项、注释都不参与；实测「只改函数体」指纹不变、「改 pub 签名」指纹改变。**这是诊断与后续包级增量的地基，目前不参与任何缓存决策**，因为后端仍是每程序一个翻译单元；把它说成「已经做到改实现不重建无关包」是不实的。
- 理由：三项核心指标同时改善且没有交换条件——编译输入变小（生成 C 体积、gcc 解析/优化工作量、编译期内存都下降）、运行语义不变（删除的全是无调用者的函数，未关闭任何受检算术、边界或释放路径）、磁盘占用下降（无需新增缓存，产物不变或更小）。相比之下，另外两条路线都要用磁盘或首次构建时间换一点热构建速度。
- 后果与限制：生成 C 从 109,721 → 20,273 字节（`print(1)`）、115,802 → 35,179 字节（`float_math.ae`）；归档的 `bench/results/2026-11-10-{windows,linux}-w3/timings.json` 用同一份基线 C（`baseline-full-runtime.c`，改动前的 `emit-c` 输出）测得 gcc 编译 Windows 1,030 → 690 ms、Linux 121.8 → 30.6 ms（各为 3 次中位值）。本机多次测量波动明显（另一轮 Windows 为 1,331 → 705 ms），所以只报告方向与量级，不宣称精确加速比；Linux 没有 `<windows.h>`，裁剪收益占比更大。`bench/build_timings.py` 记录冷构建、无修改、改实现、改接口四类场景的整体进程耗时（Windows 772 / 99 / 769 / 779 ms，Linux 37.4 / 5.6 / 34.3 / 37.1 ms）；「无修改」含 `cc --version` 与复制可执行文件，不是缓存查找本身（后者约 2 ms）。闭包是**保守**的：注释里出现的函数名会多保留一个函数，只损失一点体积，不影响正确性；将来若引入函数指针表或宏拼接出的运行时符号，必须把该符号显式加入根集合。`emit-c` 输出现在随程序所用内建变化，任何依赖「生成 C 字节数恒定」的外部工具都要改用语义或哈希判断。`ae deps` 的路径标签统一用 `/`，但不对大小写做折叠（Windows 与 Linux 的大小写敏感性差异仍是已知平台差异）。**用户模块级增量、并行调度与接口驱动的失效判定仍未实现**，W3 记为「阶段 1 完成」而不是完成。
- 验证：Windows 与 Linux 各跑一次全套命令，均为 9 单元 + 135 集成测试通过（新增 2 个 `deps` 测试）；Linux `--sanitize` 24 个用例 PASS 且无 ASan/UBSan 报告，两平台 `--leak` 24 个用例全部 PASS、退出分配块数分别等于 0 与 2 块基线；全部 `examples/*.ae` 通过 `check`；`deps` 的两份输出在行尾归一化后逐字节一致。日志与四类场景计时见 `bench/results/2026-11-10-{windows,linux}-w3/`，平台矩阵同步记录。

## ADR-39：系统头也按可达性裁剪，不手写 Win32 声明

- 背景：ADR-38 把生成 C 从 109,721 字节降到 20,273 字节（`print(1)`），但 `#include <windows.h>` 属于「必须原样保留的非函数文本」，函数闭包裁剪删不到它。于是 Windows 上**每个**生成程序仍要解析整套 Win32 声明：单独测一个只含该头的文件约 690 ms，加 `WIN32_LEAN_AND_MEAN` 后约 520 ms。实测 `float_math.ae` 生成的 C 在裁剪后只剩两处 `#ifndef _WIN32` 和空壳 Win32 分支，一个 Win32 API 都没调用，却仍付这笔成本。方案文档 §21 的 W6 提议「手写最小 Win32 声明」，但该运行时实际用到 `WIN32_FIND_DATAW`、`STARTUPINFOW`、`PROCESS_INFORMATION`、`WIN32_FILE_ATTRIBUTE_DATA`、`FILETIME` 与二十余个 API（文件、目录、时钟、环境变量、工作目录、子进程），精确复刻这些结构的 ABI 风险与收益不对称。
- 关键观察：`<windows.h>` 写在 `#ifdef _WIN32` 分支内，只为 Win32 分支的运行时函数提供声明。若闭包裁剪后**一个需要它的函数都没留下**，这行 include 就是纯开销；而 Linux 本来就不预处理这个分支。先做了零改动探测：把 `float_math.ae` 生成 C 里这一行删掉，`gcc -std=c11 -O2` 三次中位从 963.2 ms 降到 417.7 ms（省 545.5 ms，2.31 倍），两个可执行文件的输出逐字节一致。
- 决策：
  1. **显式标记而不是猜**：给 16 个依赖 windows.h 声明的运行时函数（`ae_widen`、`ae_narrow`、Windows 分支的 `ae_fopen`、`ae_now_ms`、`ae_try_env`、`ae_try_cwd`、`ae_path_exists`、`ae_path_is_dir`、`ae_try_list_dir`、`ae_try_file_info`、`ae_try_rename_path`、`ae_try_remove_file`、`ae_make_one_dir`、`ae_set_cwd`、`ae_try_remove_dir`、Windows 分支的 `ae_run_command`）在函数定义行加 `/* win32-header */`。标记随函数单元一起被保留或删除，不需要解析预处理条件，也不依赖 Win32 API 名清单。
  2. `prune_runtime` 在拼接用户后缀**之前**检查运行时部分：一个标记都不剩时，把 `#include <windows.h>` 换成 `/* windows.h omitted */`。用户代码不能影响这个判断；`deps` 的输出与内容寻址缓存键都不参与。
  3. 判断按**程序用到的能力**而不是按平台：两平台生成的 C 文本完全相同（`print(1)` 均为 20,352 字节），Linux 因预处理而不受影响，收益体现在 Windows。
  4. 新增 2 个单元测试（裁剪行为：无标记删头 / 有标记留头；标记审计：扫描 `runtime.c` 与 `runtime_ex.c`，凡含 Win32 声明的函数单元必须带标记）与 1 个集成测试（3 个 example 的头决策，每份生成 C 都过 `-std=c11 -pedantic-errors -Werror=return-type -fsyntax-only`）。
  5. `bench/build_timings.py --header-baseline`：把同一份生成 C 用**字节级**替换还原 `<windows.h>`，与去头版本在同一脚本、同一时刻、同一工具链下交替计时。跨会话的墙钟数字在这台机器上波动可达 30% 以上，只有同一次运行内的对照是因果证据。
- 已排除的做法：
  - **手写最小 Win32 声明（W6 原路线）**：本轮不引入任何 ABI 假设。W6 仍留在 §21，要求先给出结构布局证据与净化器结果才能进入实现；本 ADR 只把「不需要 Win32 时完全不解析头」这部分收益以零风险方式拿到。
  - **自动扫描「保留文本里是否还有 Win32 分支代码」**：会把 `ae_try_read_stdin` 的 `_setmode`/`_O_BINARY`（来自 `<io.h>`，不需要 windows.h）也算进去，让读标准输入的程序仍付 500 ms；还要求裁剪器理解嵌套预处理条件，正是 ADR-38 里 `ae_widen` 被误删那类复杂度的来源。
  - **PCH 或再拆一个翻译单元**：ADR-38 已实测否决（69 MB `.gch`；分离 TU 冷构建回归约 68%）。
- 理由与安全边界：三项核心指标同时受益且没有交换条件——Windows 编译输入变小、运行语义不变（只删一行不再被引用的 include）、磁盘与缓存占用不变（没有新增缓存种类）。**漏加标记的后果是生成 C 缺少声明、编译期直接报错**（显式失败，24 个生成 C 用例与严格语法检查会立刻抓到），**多加标记的后果只是多解析一次头**；两者都不会静默改变运行结果。标记审计单元测试用于防止将来新增 Win32 函数时漏标；该测试的 Win32 标识符清单只用于审计、不参与构建决策，清单不全只会少检查几个函数，不会改变编译器行为。回退方式是关闭这次替换、无条件保留 include 行，`build`/`run` 语义完全不变。
- 后果与限制：`print(1)` 的生成 C 从 20,273 → 20,352 字节（多出的是注释文字，不是代码），`-O0` 可执行文件仍是 Windows 64,195 / Linux 17,168 字节；无新增常驻内存、无新增缓存。**用到文件、路径、目录、时钟、环境变量、工作目录或子进程的程序仍会保留 `<windows.h>` 并付解析成本**——本决策不是「移除了 Win32 头依赖」，也没有实现 W6 的最小声明。手写最小声明、用户模块级包级增量、并行调度与接口摘要驱动的失效判定仍未实现。四类场景的绝对耗时受本机负载影响明显，不与 W3 归档的单次数字直接比较。
- 验证：Windows 与 Linux 各跑一次全套命令，均为 11 单元 + 136 集成测试通过；两平台 `--leak` 24 个用例全部 PASS、退出分配块数分别等于 2 与 0 块基线，Linux `--sanitize` 24 个用例 PASS 且 0 报告；全部 `examples/*.ae` 通过 `check`；两平台的头决策一致（`float_math.ae` 去头、`file_tidy.ae` 留头，`print(1)` 生成 C 同为 20,352 字节），`deps` 输出按行尾归一化后一致。作为「漏标」的最终安全网，两平台还对**全部 31 个 `examples/*.ae` 的生成 C 逐份**跑了 `gcc -std=c11 -pedantic-errors -Werror=return-type -fsyntax-only`，全部通过；头决策在两平台完全相同（11 个含头、20 个去头），日志为各自归档目录的 `generated-c-syntax.log`。文本启发式（扫描 API 名）不能替代这一步：运行时注释里提到了 `_wfopen`，会被误报成仍在调用 Win32 API。
  - Windows（`gcc -std=c11 -O0`，三次独立运行、每次内部 3 次取中位）：含头 980.9 / 945.6 / 1,296.4 ms，去头 252.6 / 301.6 / 319.6 ms，同次运行内省 644.0–976.8 ms（3.14–4.06 倍）；中位含头 980.9、去头 301.6 ms。四类场景中位（三次运行）：冷构建 435.9、无修改 160.0、改实现 510.4、改接口 482.0 ms。日志与三次原始值见 `bench/results/2026-11-10-windows-winhdr/`。
  - Linux（同参数）：含头 32.0 ms、去头 31.4 ms，差异在测量噪声内；四类场景 36.2 / 4.6 / 36.5 / 36.1 ms。日志见 `bench/results/2026-11-10-linux-winhdr/`。这正好说明收益来自 Windows 的头文件解析，而不是生成 C 的体积变化。

## ADR-40：约束在声明处接受能力覆盖检查，但仍不是 trait

- 背景：ADR-33 把约束定义为「调用点的实参形状白名单」，明确不做泛型体一致性检查。实际使用后仍有一类错误逃不掉：`fn f[T: Copy](a: T, b: T) -> T { return a + b; }` 里 `Copy` 允许 `bool`，调用 `f[bool]` 时约束通过，随后才在函数体里报 `'+' requires ...`；更常见的是函数根本没被调用，错误要等到第一次实例化才出现，而声明本身看上去是自洽的。§21 W4 要求「让泛型声明自身可检查」，但完整 trait/impl 需要方法表、静态分派、孤儿规则与可见性规则，一次交付风险过高；当前架构是「逐实例化重新解析函数体」（ADR-31），没有可证明的未替换泛型 AST。
- 关键观察：不需要证明泛型体，也能发现「约束在撒谎」。约束白名单的**交集**是有效类型集（实例化时能满足全部约束的类型）；函数体对类型参数施加的每个运算，都有真实类型检查规则给出的**支持类型集**。只要有效类型集里存在不支持该运算的类型，声明就是错的——这与「某次实例化会失败」等价，且不需要任何类型推断就能在声明处判出来。
- 决策：
  1. 新增 `Capability`（`Add`/`Arith`/`Modulo`/`Ord`/`Eq`/`Logic`），支持类型集逐条镜像 `expression` 的二元运算规则（`+` = i64/f64/string，`- * /` = i64/f64，`%` = i64，序比较 = i64/f64，`== !=` = i64/f64/bool/string，`&& ||` = bool）。能力表与 `Bound::allows` 放在同一处，并有单元测试断言 `Add`/`Ord`/`Eq` 的白名单是对应能力支持集的子集，防止新增标量类型时两套规则脱节。
  2. `audit_generic_fn` 在 `collect_functions` 里对每个**带约束**的泛型声明做一次单遍 token 扫描：把参数变量绑定到类型参数索引，`let`/`var` 局部变量做保守的 taint 传播；只有当运算 token **紧邻**的标识符确实绑定到某个类型参数时才记录一次能力需求，调用结果、下标、字段、字面量、无法判定的局部变量一律跳过。随后按约束白名单交集计算有效类型集，若有类型不支持所需能力，就在**类型参数声明处**报错，消息列出具体类型、运算、能力支持集与当前有效类型集。例如 `declares T: Copy but its body applies '+' to T; the constraint still admits bool, which does not support it`。
  3. **只拒绝、不放行**：每个实例化仍按 ADR-31/33 完整解析与类型检查；约束不参与代码生成、不影响释放路径、不改变 `deps` 的接口摘要。预检查不能证明程序合法，只能提前发现约束与函数体的矛盾。
  4. **零误报优先**：无约束泛型保持 ADR-33 行为（跳过审计）；`&T`、复合类型、变量遮蔽等无法可靠归类的情形跳过检查，由逐实例化检查兜底。漏报允许（错误仍在实例化时报），误报不允许（不能拒绝本来所有类型都合法的声明）。
  5. 差分测试：把约束去掉后逐类型实例化，验证 `bool + bool` 仍被真实类型检查拒绝而 `i64`/`f64`/`string` 通过；再验证收紧约束（`Copy` → `Add`/`Ord`）后声明与运行都通过。新增 3 个单元测试、2 个集成测试（含跨文件 `pub fn` 在定义文件报错）、`examples/generic_constraints.ae` 与 1 个生成 C 分配计数用例。
- 已排除的做法：
  - **完整 trait/impl 静态分派**：需要方法表、孤儿规则、可见性与单态化分派；本轮不引入，文档仍写「trait 尚未实现」。
  - **让预检查替代逐实例化检查 / 按约束省略类型检查**：约束不是证明，放行未被检查的代码会造成内存错误或 UB，直接违背默认安全。
  - **从函数体反推约束**：ADR-33 已否决（等价于类型推断，且随函数体改动破坏接口稳定性）。
  - **在声明处对每个允许类型做「探针实例化」**：会污染 `generics.fn_done`/`pending`/函数 id，且对每个声明做 N 次完整解析，编译时间显著回归。
  - **自由格式的运算数表达式分析**：需要一份泛型 AST；当前只有 token 流，保守地只看紧邻标识符，把复杂度留到有 AST 时再谈。
- 行为变化与迁移：这是一次**收紧**。以前 `fn f[T: Copy](a, b) { return a + b; }` 能通过声明、只在 `f[bool]` 调用时失败；现在声明处直接报错，即使用 `i64` 调用也不行。理由是该声明声称适用于所有 `Copy` 类型，实际并不成立。迁移方式是把有效类型集收窄到能力支持集（如 `T: Add`，或 `T: Add + Copy`），或去掉约束回到逐实例化检查。已核对现有 `examples/*.ae` 与全部集成测试，没有被这次收紧影响的写法。
- 资源成本（逐条回答 §21 的验收问题）：
  - **生成 C / 可执行文件 / 缓存**：完全不变。`print(1)` 仍为 20,352 字节，两平台相同；计时脚本断言「带约束」与「无约束」两份同字节数源码的 `emit-c` 输出逐字节相同。无新增缓存种类、无常驻进程、无运行时分配。
  - **运行 CPU/内存**：零影响，纯前端。
  - **编译速度**：审计是 O(函数体 token) 的单遍扫描，遍历用 `&Kind` 而非 clone。`bench/constraint_audit_timings.py` 用两份**字节数相同**、仅差 `[T: Add]` 与补齐注释的源码在同一脚本、同一时刻内交替测 `check`，并断言两份 `emit-c` 输出逐字节相同。归档（`--runs 7`，中位值）：Windows 200 个声明 113.4 / 103.1 ms（差 10.3 ms），800 个声明 1433.0 / 1338.8 ms（差 94.2 ms）；Linux 200 个声明 67.6 / 62.1 ms（差 5.5 ms），800 个声明 1012.6 / 892.6 ms（差 119.9 ms）。本机负载波动明显（Linux 800 声明某次达 2,910 ms；多次独立探测的 200 声明差值 5.5–10.3 ms、800 声明 74.8–119.9 ms），**只报量级、不报精确比值**。
  - **差值的归因与边界**：**这是上界，不是纯审计成本**。带约束版本每行多 2 个 token，而 `GenericFn` 仍按 ADR-31 为每个声明保存整份 `tokens` 与 `source` 的副本，其 O(N²) 复制会放大 token 数差异：把审计内部的 `Kind` clone 去掉后，200 声明的差值明显下降、800 声明几乎不变，说明 800 声明那部分主要来自既有复制而非扫描本身。真实程序的泛型声明数远小于 800。**不宣称「零编译时间回归」**，只给出上界、归因与「生成 C 完全不变」的硬证据。
  - **发现但未修复的既有瓶颈**：800 个未实例化泛型声明让 `check` 达到约 0.9–1.4 秒，主因是 `GenericFn` 每个声明 clone 整份 token 流（O(N²)），与本轮审计无关。改为共享 `Rc<Vec<Token>>`/`Rc<str>`、只在实例化时取副本可直接服务编译速度这一首要指标，列为下一候选，本轮不混入同一特性。
- 失败与安全边界：审计读的是同一份 token 流，不修改任何状态；扫描失败（找不到括号/函数体、变量无法归类）一律跳过而不是拒绝。约束白名单与能力表若将来脱节，单元测试会失败；即使脱节，逐实例化检查仍是最终防线。回退方式是删除 `collect_functions` 里的 `audit_generic_fn` 调用，`build`/`run` 语义与 ADR-33 完全一致。
- 验证：Windows 与 Linux 各跑一次全套命令，均为 14 单元 + 138 集成测试通过（新增 3 个单元测试、2 个集成测试）；两平台 `--leak` 25 个用例全部 PASS、退出分配块数分别等于 2 与 0 块基线，Linux `--sanitize` 25 个用例 PASS 且 0 报告；全部 32 个 `examples/*.ae` 通过 `check`；`deps` 输出按行尾归一化后一致（233 字节）；`print(1)` 生成 C 两平台同为 20,352 字节，`float_math.ae` 去头、`file_tidy.ae` 留头的决策与 ADR-39 一致。四类场景计时（`bench/build_timings.py --runs 3`）：Windows 冷 412.6 / 无修改 118.2 / 改实现 370.1 / 改接口 391.7 ms，Linux 36.9 / 4.9 / 35.4 / 36.6 ms；这些是整进程耗时，不与历史归档跨会话比较。日志、计时 JSON 与声明处诊断样例见 `bench/results/2026-11-10-{windows,linux}-w4/`。

## ADR-41：泛型声明按源文件共享词法结果，消除前端 O(N²) 复制

- 背景：ADR-40 的 `bench/constraint_audit_timings.py` 对照显示，800 个未实例化的带约束泛型声明让 `check` 达到 0.9–1.4 秒，且带约束/无约束的差值（Windows 94.2 ms、Linux 119.9 ms）远大于审计本身。追查发现根因在 ADR-31：`GenericFn` 为了让每个实例化能「稍后重新解析函数体」，把**整份** token 流与源码文本各 clone 一份存进声明；文件里有 N 个泛型声明就复制 N 次整份 token 流（其大小又随 N 线性增长），前端因此是 O(N²)。这是既有设计，与 ADR-40 无关，但由它的计时对照暴露出来。
- 关键观察：`GenericFn` 需要的是「稍后仍能读这些 token」，不是「独占一份」。同一个文件的所有声明读的是同一份 token 流和同一段源码，且都是只读；`start` 只是这份流上的索引。因此完全可以共享。
- 决策：
  1. `Parser.tokens` 从 `Vec<Token>` 改为 `Rc<Vec<Token>>`，每个源文件在 `lex` 之后 `Rc::new(...)` 一次；`parse_source` 与 `load_file` 都按此构造。所有 `self.tokens[i]` / `.get()` 用法靠 `Deref` 保持不变。
  2. `Parser` 新增 `shared_source: Rc<str>`（每文件一次 `Rc::from(source)`）；`Parser.source: &'a str` 保持不变，25 处诊断与位置代码不动，避免把一次性能改动扩大成生命周期重构。
  3. `GenericFn.tokens`/`source` 改为 `Rc<Vec<Token>>`/`Rc<str>`；`collect_functions` 里只做 `Rc::clone`（O(1)）。`instantiate_fn` 构造子 Parser 也用 `Rc::clone(&def.tokens)` 与 `&*def.source`，**实例化同样零复制**。
  4. `scan_uses` 与 `audit_generic_fn` 改传 `.as_ref()`；`start` 语义不变。
  5. 新增 1 个单元测试（`Rc::ptr_eq` 断言同文件所有泛型声明共享同一 token buffer 与源码，防止悄悄回退到 O(N²)）与 1 个集成测试（80 个泛型声明 + 80 个实例化，验证每个 `start` 仍指向自己的参数列表与函数体）。
  6. 新增 `bench/shared_tokens_timings.py`：用改动前（`git archive` 导出 ADR-40 提交）与改动后**两个真实二进制**，在同一脚本、同一时刻、同一份源码上交替测 `check`，并断言两者 `emit-c` 一致、声明处诊断一致。脚本同时记录原始与 CRLF/LF 归一化后的一致性：`git archive` 导出的运行时源码可能带 CRLF，只按归一化比较才不会把环境差异误判成语义变化；本轮归档已让基线树使用与工作区相同行尾的 `runtime.c`/`runtime_ex.c`，因此两份生成 C 是**原始逐字节相同**。
- 已排除的做法：
  - **只把 `GenericFn` 改成 Rc、保留 `Parser.tokens: Vec`**：每个声明仍需 `Rc::new(self.tokens.clone())`，复制次数不变，O(N²) 原样保留。
  - **全局/静态 token 池或跨文件缓存**：引入常驻内存与生命周期管理，还要处理跨文件加载与重名，违背低资源目标；按文件 `Rc` 已够用，文件解析结束后引用计数自动归零。
  - **把 `Parser.source` 也改成 `Rc<str>` 并重写所有诊断调用**：源码本来就是每文件一份借用，收益为零，却要改 25 处，风险不对等。
  - **跳过未实例化泛型声明的解析**：会改变错误时机与 `deps` 摘要，属于语义变更，不是性能优化。
- 理由与安全边界：token 流只读共享，没有任何可变访问；`Rc` 只用于单线程前端，不进入生成 C 或运行时。`start` 仍是同一份流上的索引，实测生成 C、诊断位置、`deps` 摘要与分配计数全部不变。回退方式是把 `Rc` 换回 owned clone，语义完全不变，只恢复 O(N²)。`Rc::ptr_eq` 单元测试是防止未来回归的硬约束。
- 资源成本（逐条回答 §21 的验收问题）：
  - **编译速度**：同次运行对照（`--runs 7`，中位值）：Windows 200 个声明 132.5 → 29.1 ms（省 103.4 ms，4.55 倍），800 个声明 1575.9 → 32.8 ms（省 1543.1 ms，48.0 倍）；Linux 200 个声明 64.1 → 3.4 ms（省 60.7 ms，18.8 倍），800 个声明 987.2 → 9.3 ms（省 978.0 ms，106.7 倍）。收益随声明数超线性增长，正是 O(N²) → O(N) 的形状。ADR-40 的能力审计对照差值也随之从 10.3 / 94.2 ms 降到 1.2 / 4.5 ms（Windows 200/800），印证「之前的差值主要来自复制而非审计」。本机负载波动明显，只报同次运行内的比值与量级，不与 W3 / ADR-39 / ADR-40 归档的绝对值跨会话相减。
  - **内存**：不再持有 N 份 token 流与源码副本，分配次数与复制量显著下降；但**没有做峰值内存采样**，不宣称具体数字。
  - **生成 C / 可执行文件 / 缓存**：完全不变（两平台 `print(1)` 20,352 字节；旧/新 `emit-c` 原始逐字节相同；`-O0` 产物 Windows 64,195 / Linux 17,168 字节），无新增缓存种类或常驻进程。
  - **运行 CPU/内存**：零影响，纯前端。
  - **安全语义**：未关闭任何检查；声明处能力覆盖预检查与逐实例化完整类型检查都保留。
- 边界：不宣称「所有程序编译都变快」——收益集中在泛型声明多的文件，单函数程序的差异在测量噪声内；也不宣称峰值内存下降了多少、或把这个比值当成普遍加速比。W3 阶段 2 的用户模块级增量仍被 ADR-38 的实测结论阻塞，本 ADR 不涉及翻译单元切分。
- 验证：Windows 与 Linux 各跑一次全套命令，均为 15 单元 + 139 集成测试通过；两平台 `--leak` 25 个用例全部 PASS（Windows 2 块、Linux 0 块基线），Linux `--sanitize` 25 个用例 PASS 且 0 报告；全部 32 个 `examples/*.ae` 通过 `check`；`deps` 输出按行尾归一化后一致（233 字节）；`print(1)` 生成 C 两平台同为 20,352 字节，头决策与 ADR-39 一致。四类场景计时（整进程 ms）：Windows 冷 352.4 / 无修改 139.3 / 改实现 457.2 / 改接口 431.3，Linux 38.2 / 5.4 / 40.0 / 40.2。日志与对照 JSON（含 7 次原始值）见 `bench/results/2026-11-10-{windows,linux}-w5-front/`。

## ADR-42：fmt 只重排空白，幂等由构造保证，不要求完整检查

- 背景：W5（§21）要求 `fmt` 幂等、不改语义、保留注释与字符串内容、失败不覆盖用户文件。编译器词法器丢弃注释、把数字解析成值，fmt 不能直接复用编译器 token 流；而「有效性门槛」定在哪里，决定模块文件（没有自己的 `main`）能否被格式化。
- 决策：
  1. fmt 是独立模块 `src/fmt.rs`，自带与编译器词法器同边界的词法器（保留注释、raw 字面量文本、每 token 行号与注释前空隙）。单元测试在全部 35 个示例源上断言两个词法器的 token 类序列逐个相同（防漂移硬约束）。
  2. 只重排空白：换行结构逐行保留（不拆行、不并排）；相邻 token 间距由「token 类对」决定；缩进只由花括号深度决定。二者都不依赖原始空白，**幂等由构造成立**。
  3. 注释、字符串（含转义）与字面量拼写按源码字节原样重发（`1e3`、`007`、CRLF 均不动）；行尾注释保留作者的对齐空隙（与保留空行同理），粘死的 `;//` 补一个空格；文件末尾恰为一个换行；空块 `{}` 不插入空格。
  4. 有效性门槛 = 可被编译器词法器切分（`check_lexable`），**不要求完整检查**：模块文件无法独立整程序检查；语义有错的文件 token 可切分，空白重排不改变其 token 与行结构，是安全的。不可词法化 → 报错退出，文件不动。
  5. 写入安全：全部处理在内存完成；内容无变化不写；写入经同目录临时文件后改名，任何失败不触碰原文件。
- 开发中被示例语料逐文件 diff 抓出并在提交前修正的三个规则 bug：`var v =[10, 20, 30]`（「`[` 前不加空格」误伤数组字面量，规则收窄为表达式结尾 token 后的索引/泛型实参）、`=> { }`（空块被插入空格）、`if ! seed(`（`!` 在 `if` 之后未被判定为前缀，改为 `!` 恒为前缀）。教训：**幂等断言对错误规则同样成立**，间距规则必须对全部语料 diff 逐条核对。
- 语义不变的精确表述：**不宣称 emit-c 逐字节相同**——运行时检查在生成 C 里嵌入源码列号，重排空格移动列号（行号不变）。验收性质：token 序列与行号不变 + 格式化前后 emit-c 在「每行忽略数字字符」的归一化下逐行一致 + 程序运行输出一致。
- 已排除的做法：
  - **复用编译器词法器并改造 `Token`**：要给热路径加注释捕获与 raw 文本，风险不成比例；等价性由测试保证，不必共享实现。
  - **AST 级 pretty-printer**：注释要重新挂回节点，首版即丢注释或引入复杂的附着规则；token 级重排天然保留一切。
  - **要求 `check` 通过才格式化**：模块文件永远无法独立通过（无 main），真实语料直接证伪；语义有效性也不是空白重排的前提。
  - **重排行结构 / 对齐尾注释 / 折叠空行**：都是有价值的风格决策，但每个都需要自己的规则与验收，v1 保守不做。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量/无修改构建时间**：`frontend` 只新增 `check_lexable` 门与测试用 `lex_kind_names`，主流程零改动；本轮未单独计时构建（改动为加法，不触碰既有路径），如实记「未测」。
  - **运行 CPU/内存**：零影响，fmt 不进入编译产物路径。
  - **产物/缓存体积**：无变化；无新增缓存种类或常驻进程。
  - **安全语义**：未关闭任何检查；fmt 不判断语义，`check` 仍是唯一语义门槛。
  - **fmt 自身**：35 文件 × 2 次共约 300 ms（含每次进程启动，≈4 ms/次）。
- 边界：v1 不重排行结构、不重对齐尾注释、不折叠连续空行、不做目录递归与配置文件；这些是明确取舍，不是完整格式化器已完成。不宣称「语义错误文件被 fmt 修复」——fmt 只动空白。
- 验证：Windows 27 单元 + 145 集成全通过（新增 12 单元 + 6 集成）；`scripts/fmt_acceptance.py` 对 35 个示例（含 3 个模块，在临时副本上，仓库文件不动）验证 emit-c 数字归一化逐行一致 + 二次 fmt 逐字节幂等，`changed_files = []`（全部示例已在规范风格内，fmt 对现役代码是 no-op）；手工字节级复制对照 diff 零差异。日志与 JSON 见 `bench/results/2026-11-10-windows-fmt/`。**2026-11-11 Linux 回填完成**：提交 `5d153d4` 在 instabox-node（Debian 13 / GCC 14.2.0 / rustc 1.99.0）cargo test 31 + 148 全通过、净化器与 `--leak` 干净、`fmt_acceptance.py` 35 文件 changed=0 且幂等、32 个独立示例 + 模块根 check OK，见 `bench/results/2026-11-11-linux-fmt-test/`；现为**双平台验证**。

## ADR-43：测试走文本合成的 main，前端零语义改动

- 背景：W5 要求 `test` 子命令「失败输出与退出码明确」。语言没有属性/注解机制可标记测试；前端又强制「恰好一个 main」，无 main 的测试文件进不了常规管线。要么给前端加「测试模式」，要么在驱动层想办法。
- 决策：
  1. 约定 `fn test_<名称>() -> i64`：返回 0 = 通过，非零 = 失败并把该值作为退出码；`assert`、受检算术等失败沿用既有 panic 路径（stderr 行列号 + exit 1）。以 `test_` 开头但签名不符（带参、返回类型不是 `i64`、泛型）是显式错误而非静默跳过——拼错的签名必须被报告，而不是让测试悄悄落榜。
  2. 零前端语义改动：用编译器词法器做 token 级扫描发现测试函数（声明序），把一个合成的 `main` 以文本追加到**同目录的源文件副本**（`use` 相对路径因此不变），随后一切走既有 check、单态化、生成 C、内容寻址缓存与运行管线。副本在 `Drop` 中删除，所有失败路径都清理。
  3. 逐测试打印 `RUN <名>`，通过后 `PASS <名>`，失败打印 `FAIL <名>` 并以测试返回值退出；全部通过打印 `ok: N passed`。**失败即停**（后续测试不运行）是 v1 行为，与 go test 的继续执行不同，已写进文档。
  4. 拒绝三类套件：文件定义了 `main`（那是程序，用 `ae run`）、没有任何测试函数、测试签名不符。
- 已排除的做法：
  - **前端「测试模式」**：要放宽 main 唯一性、改函数收集与诊断路径，触及安全检查的入口；收益只是省一次文本合成。
  - **AST 级合成 main**：要手工构造语句、变量 id 与作用域，与解析器内部强耦合；文本合成让解析器自己完成全部检查。
  - **引入属性语法（如 `#[test]`）**：语言还没有注解机制，为一个子命令引入语法是大决策，独立于本工作项。
  - **返回值忽略（只要不 panic 就算过）**：`fn test_a() -> i64 { return 1; }` 静默通过是脚枪；非零即失败让退出码可编程。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量/无修改构建时间**：改动为加法（新模块 `harness.rs`、main.rs 一个分支、`lex`/`Kind`/`Token` 可见性放宽为 `pub(crate)`），未单独计时，如实记「未测」。
  - **运行 CPU/内存**：编译产物路径不变；测试程序就是普通程序。
  - **产物/缓存体积**：合成源走既有内容寻址缓存，键含合成文本哈希，无新缓存种类。
  - **安全语义**：未关闭任何检查；合成 main 与用户代码一起通过完整 check 与移动/借用规则。
- 边界：v1 只收集入口文件的测试（模块文件里的 `test_*` 不收集，模块仍是纯模块）；无过滤、无并行、无 `--list`、无 `--release`；测试签名固定 `() -> i64`。不宣称「测试框架已完成」——这是一个最小驱动，断言仍只有 `assert` 与结果值。
- 验证：Windows 31 单元 + 148 集成全通过（新增 4 单元 + 3 集成）；三路径冒烟（通过 / 返回 3 → exit 3 / panic → exit 1 带位置）与模块协用（`use` 的 `pub fn` 被测试调用）见集成测试与 `bench/results/2026-11-10-windows-test/smoke.log`；`tests_demo/strings_test.ae` 是随仓库的演示套件（3 测试全过，exit 0）。**2026-11-11 Linux 回填完成**：同一提交树在 instabox-node 上 31 单元 + 148 集成全通过，test 三路径（通过 / 返回 3 → exit 3 / panic → exit 1 带位置）与 Windows 逐字一致，见 `bench/results/2026-11-11-linux-fmt-test/`；现为**双平台验证**。

## ADR-44：字面量拼接融合——程序文本不进分配器

- 背景：map 负载热点分解（`bench/results/2026-11-11-windows-map-hotspots/`）把 76% 的运行时间归因到字符串构造而非 map 操作；读码进一步确认 `Expr::StrLit` 每次求值都发射 `ae_str_from`，即每个字面量每次求值做一次堆分配，而紧随其后的 `ae_str_cat` 立即把这个缓冲释放掉——纯粹的分配器往返。
- 决策：
  1. 发射器对 `"字面量" + 表达式` 与 `表达式 + "字面量"` 两个形状分别发射新运行时辅助 `ae_str_cat_lit_left/right`：字面量作为 C 字符串直接 memcpy 进结果缓冲，非字面量侧照常消费（释放），字面量侧零分配零释放。
  2. 字面量是纯表达式，跳过其求值不改语义；非字面量拼接路径（`ae_str_cat`）逐字不变。
  3. 运行时辅助放在 `ae_str_cat` 旁，带同样的溢出检查与 `ae_fail` 失败路径；未使用时被运行时闭包裁剪自动去除（ADR-38）。
- 已排除的做法：
  - **`ae_string` 加 SSO 或「静态」标志**：改结构体布局牵动每一条移动/释放/借用路径与 C ABI，为一个热点不值得；单一可测变更原则要求先拿小改动验证收益。
  - **缓存已释放的字面量**：释放路径无法区分「来自字面量的串」与普通串，缓存命中再释放就是 use-after-free。
  - **realloc 式原位拼接**：改变 `ae_str_cat` 的操作数契约（需要可增长的左操作数），且本负载的左操作数是字面量（非堆指针），不适用。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量/无修改构建**：加法改动（两个运行时辅助 + 一个发射分支），未单独计时，如实记「未测」。
  - **运行 CPU/内存**：同次运行对照（旧二进制 = stash 改动重建，同一脚本交错 9 次，输出逐字节一致断言）：map 变体 199.3 → 177.1 ms（快 11.1%），纯字符串桶 151.0 → 119.6 ms（快 20.8%）；每次「字面量 + 串」少 1 次分配 + 1 次释放 + 1 次 memcpy。原始值见 `bench/results/2026-11-11-windows-litcat/same-run-comparison.json`。
  - **产物/缓存体积**：运行时闭包裁剪处理未用辅助；无新缓存种类。
  - **安全语义**：未关闭任何检查；`--leak` 退出块 Windows 仍为 2（UCRT 基线）、Linux 0（glibc 基线），净化器无报告。
- 边界：只融合「一侧是字面量」的拼接；`to_string` 自身的堆分配（H1）与 map 双哈希（H4）未动，它们是下一批候选；Linux 侧同次运行对照未做（证书窗口不足），性能证据以 Windows 对照为准，绝对时间不跨平台比较。
- 验证：Windows 31 单元 + 148 集成全通过，`--leak` 25 用例基线 2 块；Linux（同一工作树）31 + 148 全通过、`--leak` 0 块、`--sanitize` 无报告，见 `bench/results/2026-11-11-linux-litcat/`。**双平台验证。**

## ADR-45：`to_string` 的数字进栈缓冲，与字面量拼接时零堆分配

- 背景：ADR-44 消掉字面量的分配后，热点分解的 H1 成为主要剩余项：`"k" + to_string(n)` 仍要先为数字串堆分配一次、由拼接释放一次。数字串是活不过当前表达式的临时值，为它分配内存违背「临时不死就不拥有内存」的直觉。
- 决策：
  1. 运行时新增 `ae_int_to_buf`：把 i64 用与 `ae_to_string` **同一个 `snprintf` 格式串**写进调用方提供的 ≥24 字节栈缓冲并返回长度——格式逻辑单源，只去掉堆往返。
  2. 发射器在 ADR-44 的两个字面量拼接分支里再探一层：另一侧是 `to_string(i64 表达式)` 时，改发 `ae_str_cat_lit_buf`/`ae_str_cat_buf_lit`（字面量 + 栈上数字 → 结果缓冲，全程一次分配）。内部表达式按既有顺序求值。
  3. 其余 `to_string` 用法（单独绑定、容器键等）不变，仍返回拥有型字符串。
- 已排除的做法：
  - **让 `ae_to_string` 返回栈缓冲**：返回类型是拥有型 `string`，改契约就是改所有权语义。
  - **给 `ae_string` 加内联小缓冲（SSO）**：结构体布局变化牵动全部释放/移动/C ABI，与 ADR-44 同样被否决。
  - **`map_inc` 类新内建**（H4，双哈希 + 键拷贝）：是真正的语言 API 演进，需要独立规范与验收，不塞进本变更。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量/无修改构建**：加法改动，未单独计时，记「未测」。
  - **运行 CPU/内存**：同次运行对照（old = e77eec6，new = e77eec6 + 本变更；交错 9 次、输出逐字节一致）：map 变体 176.8 → 152.5 ms（快 13.7%），纯字符串桶 132.0 → 88.1 ms（快 33.3%）。自首次基线累计：map 变体 199.3 → 152.5（-23.4%）、字符串桶 151.0 → 88.1（-41.7%）。new 侧 map 出现两次热噪声离群（230/210 ms），原始值全保留、报中位数。见 `bench/results/2026-11-11-windows-intbuf/same-run-comparison.json`。
  - **产物/缓存体积**：运行时闭包裁剪处理未用辅助；注意在注释里写函数名会多保留一个函数（ADR-38 已记录的保守行为，本轮生成 C 因此多含一个未调用的 `ae_to_string` 定义，只损失体积）。
  - **安全语义**：未关闭任何检查；`--leak` 退出块 Windows 仍为 2。
- 边界：只覆盖「字面量 + `to_string(i64)`」形状；两个 `to_string` 相加、变量 + `to_string` 等仍走 ADR-44/原路径；Linux 正确性验证在后台运行（证书窗口多次缩短，取证方式为 nohup + 稍后收取），若未及完成则本 ADR 记「Windows 已验、Linux 待回填」。
- 验证：Windows 31 单元 + 148 集成全通过，`--leak` 25 用例基线 2 块；发射断言（生成 C 含 `ae_str_cat_lit_buf`、无 `= ae_to_string(` 调用）。Linux（nohup 后台取证）31 + 148 全通过、50 用例 PASS、`--leak` 0 块、净化器无报告，见 `bench/results/2026-11-11-linux-intbuf/`。**双平台验证。**

## ADR-46：`map_inc` 把计数收敛为一次查找，缺键从零开始

- 背景：热点分解的 H4——直方图形状的 `map_get` + match + 索引存储对同一个键哈希两次、命中后还要把键再拷贝一次，且 miss 路径会构造错误字符串。计数是映射最常见的真实用途，三种参照语言都有单调用形状（Go `m[k] += d`、Rust `entry(k).or_insert(0) += d`、Python `d[k] = d.get(k, 0) + d`），AE 却要求用户手写三步。
- 规范（先于实现写定）：
  1. `map_inc(m, key, delta) -> i64`：把 `key` 的计数加上 `delta` 并返回**新值**；键不存在时视为从 0 开始（返回 `delta` 并插入）。
  2. 缺键**不返回 Err**——与 `map_get` 的差异是语义的一部分：递增是读改写复合操作，缺席即零。`map_get` 的「缺失是值不是哨兵」规则不变。
  3. `m` 限于 map 变量或其字段（与 `map_get`/`map_put` 同一 place 规则，moved map 拒绝）；`key` 为 string/string view；`delta` 为 i64；返回新值是表达式，不能作为裸调用语句丢弃（语言既有规则：仅调用的语句必须绑定或传播）。
  4. 实现：单次哈希定位 + 原地加；命中的键**零拷贝**，仅首见分配。
- 已排除的做法：返回 `IntResult`（把「缺席即零」重新变成必须 match 的两步，等于没省）；`map_update(m, key, fn)`（语言没有闭包）；修改 `map_get` 语义（破坏既有规则）。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量构建**：加法（新 Expr 变体、一个内建分支、一个运行时函数），未单独计时，记「未测」。
  - **运行 CPU/内存**：同一二进制 API 形状对照（`bench/map.ae` vs `bench/map-inc.ae`，校验和循环逐字相同、输出逐字节一致，交错 9 次）：221.9 → 196.9 ms（**-11.2%**）。机器温度与早前归档不同，只取相对值；JSON 见 `bench/results/2026-11-11-windows-map-inc/`。
  - **产物/缓存体积**：`ae_map_inc` 被引用才保留（ADR-38 裁剪）；`examples/map_count.ae` 进入生成 C 用例集（25 → 26）。
  - **安全语义**：place 的 moved 检查与 `map_get` 同源；`--leak` 26 用例 Windows 基线仍 2 块。
- 边界：`map_inc` 只覆盖 i64 值的计数递增（当前 map 的唯一值类型）；负 delta 合法（可以递减，减到负也合法）；`bench/map.ae` 四语言孪生**不改**——孪生必须逐点对应，map_inc 的收益由专门的 `map-inc.ae` 对照承载，两个归档分开陈述。
- 验证：Windows 31 单元 + 151 集成（新增 3 个 map_inc 集成）全通过；`--leak` 26 用例（含 `map_count.ae`）基线 2 块；Linux 后台取证：31 + 151 全通过、52 用例 PASS（含 map_count）、`--leak` 0 块、净化器无报告，见 `bench/results/2026-11-11-linux-map-inc/`。**双平台验证。**

## ADR-47：trait/impl 静态分派——实例化时解析，无方法表

- 背景：W4 剩余部分。ADR-33 的调用点形状检查与 ADR-40 的声明处能力审计只覆盖四个内建约束（Add/Eq/Ord/Copy），用户自定义能力（如「可求面积」）无法表达，泛型体也无法调用「随类型参数变化」的函数。
- 设计（先于实现定死，每条都有机制依据）：
  1. 语法：`trait Name { fn method(first: T, ...) -> R; }` 声明能力（无方法体、无默认实现）；`impl Name for Type { fn method(...) -> R { body } }` 提供具体实现。trait 的类型参数固定拼写为 `T`（隐式），方法**首参必须是 T 按值**，其余参数与返回值可以是 T 或具体类型。
  2. **静态分派 = 实例化时解析**：泛型体按 ADR-31 在每次实例化时以 `subst` 重解析；遇到非普通函数的调用，`resolve_trait_call` 以「trait + 方法 + 替换后的参数类型」查找混淆签名 `Trait#method#TypeName`（`#` 不可词法化，用户标识符无法碰撞），命中即按普通调用发射 impl 函数的 id（`ae_fn_{id}`）。**没有方法表、没有函数指针、没有运行时分派**——分派结果就是一次直接调用。
  3. 实例化点检查：`instantiate_fn` 对每个 trait 绑定查 impl 注册表，缺失即报 `no impl of trait 'X' for 'Y'; required by 'Z'`，与逐实例化类型检查同点报错。
  4. 一致性（v1 形状）：impl 只能写在 **trait 所在文件或类型所在文件**，第三文件拒绝；(trait, type) 全程序唯一；预算 64 trait / 256 impl 每程序。
  5. 可见性：`pub trait` 跨文件引用（与函数同规则）；impl 所在文件经 `use` 载入即注册（加载是注册的副作用，无需从中调用任何项）。
- 已排除的做法：
  - **Rust 式方法语法与 `self`**：语言没有方法调用形式，为 trait 引入它是独立的大决策。
  - **泛型 impl（`impl Area for Pair[K,V]`）与 `&T` trait 参数**：`&T` 的落地形状只有三种借用（ADR-35），trait 签名的借用语义需要独立设计；v1 全部拒绝并给出明确错误。
  - **默认方法体**：impl 必须提供全部方法；缺省体引入覆盖顺序问题，无证据不引入。
  - **动态分派 / trait 对象**：与「无 GC、确定性释放、直接调用」的运行时目标相反，永不默认。
  - **声明处预检查 trait 调用**（ADR-40 式）：能力审计扫描的是运算符能力，trait 调用的缺失在实例化点报错已足够早且信息更准（带着 `required by`）；声明处扫描留待有真实误报证据再做。
- 资源成本（逐条回答 §21 的验收问题）：
  - **冷/增量/无修改构建**：加法（新关键字、trait/impl 两遍管线、一个解析分支）；未单独计时，记「未测」。
  - **运行 CPU/内存**：零新增开销——分派就是直接调用，差分测试断言经由 trait 的调用与手写函数输出一致（`traits.ae` 第三行）。
  - **产物/缓存体积**：impl 函数按普通函数进生成 C，未引用的 trait/impl 函数被 ADR-38 闭包裁剪处理；`examples/traits.ae` 进入生成 C 用例集（26 → 27）。
  - **安全语义**：未关闭任何检查；移动/释放按实例化照常（Rect 按值移入 impl 方法，`traits.ae` 泄漏用例基线不变，Windows 2 块）。
- 边界（对外表述不得越过）：
  - trait 方法**不能在泛型体外直接调用**（impl 行为在体外以普通函数书写）；
  - trait 签名不支持 `&T` 与泛型 impl；无默认方法；无动态分派；无方法调用语法；
  - trait 调用缺失在实例化点报错，不在声明处预检；
  - 菱形导入是模块系统既有的环形拒绝，因此 impl 与 trait/类型同文件是当前唯一可组合的跨文件布局——「impl 与类型同文件」模式成立，「独立 impl 模块 + main 直连 trait 文件」不成立；
  - 不宣称完整的 Rust 风格 trait 系统（关联类型、where 子句、条件实现等均未设计）。
- 验证：Windows 31 单元 + 154 集成全通过（新增 3 个 trait 集成：分派/八类拒绝/跨文件一致性）；`--leak` 27 用例（含 `traits.ae`）基线 2 块；fmt 验收 37 文件 0 改动（trait/impl 语法幂等）；模糊测试在实现过程中抓到并修复预扫描对畸形输入的深度下溢（`saturating_sub`，教训：扫描先于验证运行时必须容忍任意输入）。Linux 后台取证见 `bench/results/2026-11-11-linux-traits/`。

## ADR-48：编辑器诊断——`check --json` 的结构化输出

- 背景：W5 的最后一项是编辑器诊断。`ae check` 只输出一行人类可读的 `file:line:column: message`；编辑器要拿位置就得自己解析文本，而消息文本里既有冒号、又有 Windows 盘符里的冒号，解析容易出错。另一方面，编辑器保存时触发的检查不应依赖整项目构建成功——不该需要 C 编译器、链接或缓存，只要前端语义检查通过/失败。
- 决策：
  1. `ae check --json <file>`（`check <file> --json` 也接受）：stdout **恰好**一个 JSON 数组；无诊断输出 `[]` 并以 0 退出，有诊断输出一个对象并以 1 退出。**数组的形状是契约，长度不是**——前端目前 fail-fast，所以至多一个元素；将来做错误恢复时只增加元素，不改形状。
  2. 对象字段固定为 `file`、`line`、`column`、`message`。`file` 可为 `null`（内存源码或非位置消息），`line`/`column` 为数字或 `null`；无法定位时把整条消息放进 `message`，**不猜位置**。
  3. 位置来源就是既有的 `error(file, source, offset, message)` 渲染结果，按最后一个 `": "` 切分；特判两种形态：Windows 盘符（`D` + `\path` 被冒号拆成两段，拼回）与无文件名（`line:column: message`）。解析失败一律退化为「null 位置 + 整条消息」，宁可少信息也不给错位置。
  4. 手写 JSON 转义（`"`、`\`、`\n`、`\r`、`\t`、其余控制字符输出 `\u00XX`）：项目零依赖，不为一处输出引入序列化库。
  5. 诊断只写 stdout；`AE_TIMINGS=1` 的耗时行仍走 stderr。不写文件、不改源码、不调用 C 编译器——`check_path` 就是 `load_program`，纯前端。
  6. 默认 `check` 的人类可读行为与退出码完全不变；`--json` 是同一检查的另一种渲染，不是新检查。
- 已排除的做法：
  - **引入 serde/JSON 库**：违背零依赖与体积目标，手写转义只有三十行。
  - **stdout 混排人类文本与 JSON**：编辑器必须整段解析，任何额外输出都会破坏契约。
  - **LSP 服务/常驻进程**：违反低资源目标（常驻内存、生命周期管理）；先给可被编辑器一次性调用的稳定命令，等有真实编辑器集成需求再单独评估常驻形态。
  - **一次报多个错**：前端是 fail-fast 设计，恢复要同步改所有诊断路径；先立数组契约，恢复是纯增量，不阻塞编辑器接入。
  - **输出结束列/修复建议**：前端只记录起始 offset，范围信息需要 token 级改造，超出本轮。
- 资源成本（逐条回答 §21 的验收问题）：
  - **运行 CPU/内存/磁盘**：一次前端检查加一次序列化（几十字节到几 KB），无缓存、无常驻进程、无临时文件；进程启动成本与 `check` 相同。
  - **编译速度**：编译器主流程未改动，`--json` 只影响 CLI 的渲染分支。
  - **产物/缓存**：不产生产物，不新增缓存种类。
  - **安全语义**：未关闭任何检查；`check_path` 与 `check` 走同一个 `load_program`。
- 边界（对外表述不得越过）：
  - 不是 LSP、不做增量、不做错误恢复（数组当前至多 1 个元素）、只有起始位置；
  - `message` 是面向人的展示文本，不保证逐字稳定；编辑器应以 `file`/`line`/`column` 为契约，不要按消息文本分支；
  - 不宣称「检查不需要构建」是普遍事实——它对 `check`/`check --json` 成立（纯前端），对 `run`/`build` 不成立。
- 验证：两平台各跑一次全套命令，均为 34 单元 + 155 集成通过（新增 3 个 JSON 转义单元测试与 1 个集成测试：两种参数顺序、成功 `[]`、失败对象、Windows 反斜杠转义）；Windows `--leak` 27 个用例 PASS、基线 2 块；Linux `--leak` 27 用例 PASS（0 块基线）、`--sanitize` 27 用例 PASS 且 0 报告；两平台全部 34 个 `examples/*.ae` 通过 `check`；`print(1)` 生成 C 两平台同为 24,034 字节。`check --json` 的五种输入（正常、未知名字、缺失文件、反斜杠路径、参数顺序颠倒）与默认 `check` 的单行输出归档在 `bench/results/2026-11-11-{windows,linux}-checkjson/json-diagnostics.txt`，平台说明见各自的 `PLATFORM.txt`。
- 验证中暴露并修复的问题：集成测试最初**无条件**断言路径里包含反斜杠转义，Linux 上必然失败（路径分隔符是 `/`，第一轮 Linux 运行为 154/155）。修正为 `#[cfg(windows)]` 断言转义、`#[cfg(unix)]` 断言 `"file":"/` 的绝对路径，两平台重跑全绿。教训与 ADR-47 的模糊测试教训同类：**断言里含平台形状时必须用 cfg 分开**，不能把 Windows 的形状当通用事实。

## ADR-49：`split`/`lines` 单块 arena——按 token 数的分配降为常数次

- 背景：text 负载（50,000 行、2.59 MB、约 45 万 token）的变体差值法显示，`split` 本身占 27.3 ms（总 44.8 ms 的 61%），而遍历 token 几乎免费（−0.4 ms，噪声内）。读码归因：`ae_split` 对每个 token 调一次 `ae_str_from_len`（一次 `malloc` + `memcpy` + 写 NUL），指针数组还要按 2 倍增长扩容 `log2(N)` 次。这与 map 负载的教训同型——**慢在字符串构造，不在容器操作**。
- 关键观察：`vec[string]` 的元素是**只读借用**（语言层面不能把元素移出向量），所以没有任何用户代码需要单独释放某个元素的字节。整个向量的元素可以共用一块字节区，释放由向量统一负责。
- 决策：
  1. `ae_strvec` 增加 `char *arena; int64_t arena_len;`。`arena == NULL` 表示逐元素自有（`push`、`args`、`keys` 构造的向量不变），`split`/`lines` 的输出指向 arena。
  2. 新增 `ae_strvec_borrowed(v, s)`：用 `uintptr_t` 比较元素指针是否落在 `[arena, arena + arena_len)`（跨对象指针比较在 ISO C 里没有定义序，整数比较是安全的写法）。`pop`、`release`、`clear_slot` 对 arena 内元素只清零槽位、不 `free`；arena 随向量一起释放。
  3. `split`/`lines` 改两遍：第一遍数 token 数与字节数，第二遍一次性分配**精确容量**的指针数组和一块字节 arena，逐 token 拷贝并保留 NUL 结尾（`ptr` 仍可直接交给 C 字符串 API）。
  4. 扫描路径：单字节分隔符（`" "`、`"\n"` 这两个最常见形状）走 `memchr`，由 libc 做 SIMD；多字节分隔符保持逐位 `memcmp`。`lines` 原来的 SWAR 循环整体替换为 `memchr` 两遍扫描（该宏只在这一处使用）。
  5. 前端 `Statement::StrVecStore` 的发射从直接 `ae_str_release(&v.data[i])` 改为 `ae_strvec_clear_slot(&v, i, line, col)`，否则覆盖元素的路径会把 arena 内部指针交给 `free`。
- 已排除的做法：
  - **零拷贝 token（元素指向输入缓冲区）**：需要生命周期/借用分析（现有借用模型只覆盖三种视图），而且 `text` 可能在 `tokens` 之前被释放，直接悬垂。语言仍是拷贝语义。
  - **给 `ae_string` 加 owned 标志**：结构体从 16 字节变 24 字节，影响所有字符串的内存占用与生成代码；向量级 arena 区间判断同样正确，且不动这个到处按值传递的结构。
  - **全局 arena / 替换分配器**：改动面覆盖所有分配路径，风险与收益不对称。
  - **只做精确容量（不做 arena）**：省掉的只是 `log2(N)` 次指针数组扩容，实测远小于逐 token malloc 的部分。
- 资源成本（逐条回答 §21 的验收问题）：
  - **运行 CPU**：Windows 同次运行对照（两个真实二进制、7 次交替、中位）：`full` 44.78 → 24.37 ms（1.84 倍，省 20.4 ms），`count` 44.83 → 23.62 ms，`read`（只读文件）16.73 → 16.61 ms（差在噪声内，说明收益来自 split 而非 I/O）；由同一次运行推导的 `split` 成本（`count − read`）从 28.10 ms 降到 7.01 ms。两处优化各有同次对照：一次中间构建显示**只做 arena** 已把 split 成本从 27.3 降到 15.0 ms，再加入 `memchr` 扫描得到最终的 7.01 ms（中间值来自另一次同次运行，不与归档值相减）。Linux：`full` 25.08 → 10.22 ms（2.45 倍），`split` 成本 22.28 → 8.86 ms。
  - **内存**：每个 split/lines 向量的分配次数由 `N + O(log N)` 降到 2；指针数组按精确 token 数分配（原来是 2 的幂，最多两倍）。**未做峰值内存采样**，不宣称具体峰值数字；arena 会保留被 pop 掉元素的字节直到向量释放（按块释放的代价）。
  - **编译速度**：运行时文本增加约 70 行，前端新增一个发射替换，未单独计时。
  - **产物/缓存体积**：`print(1)` 的生成 C 从 24,034 增至 25,134 字节（+1,100，新增 arena 代码与注释），但**可执行文件大小不变**（Windows `-O0` 66,849 / `-O2` 66,893 字节）——未引用的运行时单元仍被 ADR-38 的闭包裁剪去掉；真正使用 `split` 的程序 `split_arena.ae` 从 72,960 增至 75,301 字节（+2,341，+3.2%），这是使用融合路径的诚实代价。缓存键覆盖生成的 C，因此升级后首次构建会全部重建一次。
  - **安全语义**：未关闭任何检查；元素仍是只读借用、不能移出；pop/store/push 的行为与返回类型不变。
- 边界（对外表述不得越过）：
  - 不是零拷贝：每个 token 仍复制字节并自带 NUL；
  - 只覆盖 `split` 与 `lines`；`push`/`args`/`keys` 仍是逐元素自有；
  - 不宣称「所有字符串处理变快」，也不把 text 负载的 1.84/2.45 倍当普遍加速比；
  - 未测 Linux 同次对照前不把 Windows 数字当跨平台结论（本轮已补 Linux 记录）。
- 验证：两平台各跑一次全套命令，均为 34 单元 + 156 集成通过（新增 1 个 arena 边界集成测试：多字节分隔符的非重叠扫描、空字段、空输入、`lines` 的 CRLF 与尾部换行、以及 pop/store/push 组合）；`--leak` 28 个用例（新增 `examples/split_arena.ae`，Windows 2 块 / Linux 0 块基线），Linux `--sanitize` 28 个用例 0 报告；35 个 `examples/*.ae` 通过 `check`；`split_arena.ae` 的生成 C 通过 `-std=c11 -pedantic-errors -Werror=return-type -fsyntax-only`；`print(1)` 生成 C 两平台一致（25,134 字节，逐字节相同）。Linux 同次对照：`full` 25.08 → 10.22 ms（2.45 倍），`count` 23.68 → 10.32 ms，`read` 1.40 → 1.46 ms（噪声内），split 成本 8.86 ms——收益方向与量级和 Windows 一致，但两平台绝对值不可比；同一实现的另一次 Linux 运行给出 2.31 倍，说明该比值只能当量级。日志、对照 JSON（含 7 次原始值）与生成 C 见 `bench/results/2026-11-11-{windows,linux}-split-arena/`。
- 验证中抓到的真实缺陷：`lines("")` 返回的向量按**精确容量**构造，容量为 0；此时 `push` 走 `cap * 2` 会申请 0 字节再写 `data[0]`，越界写。修复是给扩容加下界（`cap < 4 ? 4 : cap * 2`），并把这个形状写进 `examples/split_arena.ae`（于是也进 `--leak` 与 Linux 净化器用例）与集成测试。精确容量把「容量为 0」这个状态第一次变成可达状态，这类边界只有在写完测试后才暴露。
- 过程教训：建立基线二进制时曾把**工作区当前**的 `runtime.c`/`runtime_ex.c` 复制进旧树（为规避 `git archive` 的 CRLF），那会让对照变成「新 vs 新」。改为用 `git show HEAD:src/runtime.c` 并归一化行尾，并在构建后断言旧树不含新符号（`grep arena` = 0）才继续。**基线二进制必须验证它真的是基线**。

## ADR-50：运行时注释随函数裁剪，注释里的名字不再当作依赖根

- 背景：ADR-49 的归档显示 `print(1)` 的生成 C 从 20,352 涨到 25,134 字节，但新增代码本身只有几十行。追查发现两件事叠在一起：`runtime_units` 把函数**上方**的 `//` 注释留在「非函数文本」里，而这段文本永远保留；更关键的是 `ae_symbols` 会在**保留下来的文本**里扫描所有 `ae_*` 名字来求依赖闭包——于是注释里提到的函数名被当成依赖根，把整个函数拉进每一个生成程序。运行时注释越多，过度保留越严重。
- 关键观察：注释不是依赖，也不该占生成 C 的字节。把注释归到它解释的函数单元，虚假的根与体积一起消失。
- 决策：
  1. `runtime_units` 增加 `lead` 缓冲：非函数区里连续的 `//` 注释与空行先记在 `lead`，遇到函数定义时并入该函数单元；遇到真正的非函数代码行（`#include`、`typedef`、宏）时把 `lead` 冲回 `pending`。
  2. 多行 `/* */` 一律留在 `pending`：文件头与分节横幅不会随第一个被裁掉的函数消失；`/* win32-header */` 标记本来就在函数定义行内，语义不受影响。
  3. 不改 `ae_symbols` 的扫描规则：它仍然会看保留单元里的注释（保守，最多多留一点），但被裁掉的函数连同其注释一起消失，虚假根随之消失。
- 已排除的做法：全局剥掉注释再编译（会丢掉标记与可读性）；按注释内容做依赖分析（注释本就不该是依赖）；只裁 `//` 行而保留空行（空行同样占字节，一并归属）。
- 资源成本（逐条回答 §21 的验收问题）：
  - **生成 C**：`print(1)` 25,134 → 11,105 字节（−55.8%）。字符串程序仍保留所需的 `ae_str_from`/`ae_str_eq`，输出不变——裁剪按可达性走，不是按大小走。
  - **C 编译时间**：同一份 `print(1)` 生成的 C，`gcc -std=c11 -O0 -c` 164.35 → 143.18 ms（−12.9%，7 次交替中位）。
  - **端到端冷构建**：`ae build examples/hello.ae --release`，每次新缓存，420.59 → 378.95 ms（−41.6 ms，−9.9%，7 次交替）。
  - **产物/缓存**：可执行文件大小不变（剪掉的本就是链接器会丢弃的死代码）；缓存键覆盖生成的 C，升级后首次构建全部重建一次。
  - **安全语义**：未关闭任何检查。
- 边界（对外表述不得越过）：不宣称「编译器普遍提速 10%」——这是**每个程序**的常量收益（少编译约 14 KB 文本），程序越大比例越小；不宣称内存峰值变化（未采样）。保留函数的注释仍会出现在生成 C 里。
- 验证：35 单元 + 157 集成（新增 1 个注释归属单元测试：`//` 注释并入函数、非函数代码前的注释留在常驻文本、`/* */` 不并入）、28 个 `--leak` 用例、Linux `--sanitize`、35 个 examples；`bench/prune_timings.py --old-exe <pre-ADR-50> --runs 7` 可复跑。日志与对照 JSON 见 `bench/results/2026-11-11-{windows,linux}-prune-comments/`。

## ADR-51：C 编译器在临时目录内以相对文件名调用

- 背景：在绝对路径含中文的目录里 `ae build` 会失败：`ld.exe: cannot open output file D:/<乱码>/.../.ae-<pid>-0/program.exe: No such file or directory`，错误信息里的路径本身已经是乱码。缓存命中时 gcc 根本不运行，所以只有首次构建（或缓存未命中）才暴露——这也是它长期没被发现的原因：日常迭代几乎总是命中缓存。
- 根因：`build` 把临时目录建在**输出文件所在目录**下，再把 `program.c` 与 `program.exe` 的绝对路径拼进 gcc 命令行。MinGW 工具链把命令行按 ANSI 代码页转换，代码页表示不了的字符被替换，链接器打开的是一个不存在的路径。
- 决策：`Command::new(&cc).current_dir(dir).arg("program.c").arg("-o").arg("program.exe")`——把编译器的工作目录设为临时目录，命令行只出现 ASCII 相对名。产物路径仍由 Rust 侧持有，后续复制与执行不受影响（Rust 内部走 UTF-16）。
- 已排除的做法：把临时目录一律改到系统临时目录（跨卷复制，且 `%TEMP%` 本身也可能含非 ASCII）；8.3 短名转换（依赖卷设置，不稳定）；用 `CreateProcessW` 直连（gcc 自身仍是 ANSI 入口，问题不在调用层）。
- 资源成本：零额外成本（一次 `current_dir`），不新增分配或缓存。
- 边界：修的是**编译器调用**。`check`/`emit-c`/`run` 的源码路径与最终产物复制本来由 Rust 处理，不受影响。`AE_CC` 指向的编译器可执行文件路径若含非 ASCII，仍可能失败——记为已知边界，不宣称「所有非 ASCII 路径问题都解决」。
- 验证：新增集成测试 `build_accepts_non_ascii_absolute_output_paths`（临时目录下建「中文目录」，输出 `程序(.exe)`，并把 `AE_CACHE` 指向空目录强制 gcc 真正运行）；**回滚修复后该测试失败**（`git stash` 验证），修复后两平台通过。Linux 侧同一测试通过（Linux 无此编码转换，作为无回归证据）。

## ADR-52：只读视图可以跟随结构体的字符串字段（借用整个变量）

- 背景：`slice_view` 之前只接受裸字符串变量。结构体的字符串字段是最常见的形态（记录的名字、路径、标签），却只能先拷进局部变量——既多一次分配，也丢掉了「零拷贝视图」的意义。
- 关键观察：视图指向字段缓冲区的字节。只要在视图存活期间**整个变量**不移动、不被整体赋值，且该字段不被写入，这些字节就一直有效。因此不需要字段级借用，按变量借用既充分又保守。
- 决策：
  1. `slice_view(expr, start, end)` 的 base 接受两种形状：裸字符串变量，或 `变量.字段`（字段类型必须是 `string`，且 base 必须是**变量**本身，不能是嵌套表达式）。
  2. 两种情况都在既有的 `borrows` 里登记**变量 id**（沿用 scope 深度语义）：移动、整体赋值、以及该变量任何字段的写入都凭它拒绝。
  3. 补上字段赋值路径原本缺失的检查：`s.f = value;` 以前不查 `borrows`。这是一次收紧；由于此前不存在字段视图，不会有任何原本合法的程序被拒。
  4. 生成 C 用 `AE_VIEW(v{id}.{field})`，与裸变量完全相同：零拷贝、无运行时开销、无新增分配。
- 已排除的做法：
  - **字段级借用**：要记录 `(var, field)` 对并覆盖所有写入路径，收益只是「同一结构体的其它字段仍可写」；整变量借用已覆盖绝大多数用法，且更难出错。
  - **嵌套字段 `a.b.c`**：需要借用链，留到有真实需求时再设计。
  - **数组/向量元素上的字段**（`v[0].name`）：base 不是变量，借用对象不明确，保持拒绝。
- 资源成本：生成 C 与运行时零变化（只是 `AE_VIEW(...)` 里多一个字段名）；编译期多一次形状判断；无新增分配、缓存种类或检查开关。
- 边界（对外表述不得越过）：
  - 视图仍是只读，仍不能作为返回值、结构体字段或枚举负载；
  - 借用粒度是**整个变量**，写同一结构体的其它字段也会被拒绝——这是保守行为，必须写明，不能说成字段级借用；
  - 不宣称「借用检查器已通用化」：字段视图只是把既有借用规则扩到一种新 base 形状。
- 验证：35 单元 + 158 集成（新增 1 个集成测试：字段视图正例，以及字段写入 / 整体赋值 / 移动 / 嵌套字段 / 非字符串字段五类拒绝）、29 个 `--leak`（新增 `examples/field_view.ae`，Windows 2 块 / Linux 0 块）、Linux `--sanitize` 29 用例、36 个 examples；`field_view.ae` 的生成 C 含 `AE_VIEW(v0.name)` 并通过严格 C11 语法检查。日志见 `bench/results/2026-11-11-{windows,linux}-field-view/`。

## ADR-53：流式 token 游标 `tokenize`——按 token 零分配的惰性切分

- 背景：`text` 负载是四项基准里最弱的一项——Linux 上 AE 9.94 ms、Rust 4.57 ms。读码与实测归因：`split` 必须**物化**约 45 万个 token（ADR-49 已把分配次数降到 2 次，但每个 token 仍要写入指针并复制字节），而 Rust 的 `split(' ')` 是惰性迭代器：**根本不存**。Go 的 `strings.Split` 物化指针数组但不复制字节，所以比我们略慢。ADR-49 当时明确把「零拷贝 token」列为排除项，理由是它需要生命周期分析且仍有 16 字节/元素的视图数组。真正的差距不在「拷贝与否」，而在「是否物化」。
- 关键观察：`for x in ...` 一次只需要一个 token。既然如此，容器形态就是错的——需要的是一条**游标**：记住基字符串视图、分隔符、当前位置，每次 `next` 返回一个视图。零分配、零拷贝，且不需要任何新的生命周期机制：借用跟踪器（ADR-52 已经在用）足以保证基字符串在游标存活期内不被移动或改写。
- 决策：
  1. 新增 `tokenize(text, sep) -> token cursor`。基必须是**存储**：裸字符串变量，或结构体变量的字符串字段（与 `slice_view` 同规则），并借用**整个变量**；临时值被拒绝（第一次迭代前就会被释放）。边界规则与 `split` 完全一致：尾部空段、连续分隔符的空段、空输入一个空 token、多字节分隔符非重叠匹配。
  2. 游标是**只被 `for` 消费的值类型**：`for token in cursor` 降级为 `ae_tokens_reset(&c); while (ae_tokens_next(&c, &v)) { ... }`，循环变量是只读视图。需要先绑定成裸变量（与 `for x in vec` 同风格），每次 `for` 都从第一个 token 重新开始，因此同一绑定可重复迭代。
  3. 没有 `len`：计数必须消费整条流，那正是游标要避免的；需要计数时用 `split`，报错信息直接这么说。游标不能 `print`、不能进容器/结构体、不能作返回值或实参——类型不匹配会各自拒绝（没有语法能写出这个类型，所以结构体字段与形参不可能出现游标）。
  4. **分隔符复制进游标**（内联 16 字节）：实参通常是临时值，语句结束时被释放；如果只保存指针，游标立即悬垂。复制后临时值可以安全释放，游标也不持有任何所有权。空分隔符与超过 16 字节的分隔符都在调用点报运行时错误。
  5. 命名用 `tokenize` 而不是 `tokens`：`tokens` 作为局部变量太常见，`bench/text.ae` 自己就写了 `let tokens = split(...)`，把它设为保留名会直接破坏现有程序（本轮确实先撞上再改名）。这条值得记住：**保留名是与用户抢词汇**。
- 已排除的做法：
  - **`split` 直接返回视图向量**：450k × 16 字节的视图数组 ≈ 7.2 MB，比现在的「8 字节指针 + 字节 arena」更占内存，而且仍然物化——两头都不划算。
  - **通用迭代器协议（闭包/`Iterator` trait）**：语言还没有闭包，为一种 shape 引入整套协议是把成本前置；先用一个具体类型覆盖最常见的「按分隔符扫描」，等有第二种真实需求再抽象。
  - **允许临时值作基**：`tokenize("a b", " ")` 读起来自然，但临时字符串在语句末释放，游标随即悬垂；拒绝比隐式延长生命周期安全。
  - **游标持有分隔符指针**：泄漏检查直接抓到（每个 `tokenize(text, " ")` 残留 1 个块）。
  - **保留名 `tokens`**：见上。
- 资源成本（逐条回答 §21 的验收问题）：
  - **运行 CPU**（Linux，空闲，9 次交替中位，同一二进制、同一输入）：`read` 1.69 ms，物化版 9.30 ms，惰性版 3.56 ms → **2.61 倍**；超出 I/O 的 token 化成本 7.61 → 1.87 ms。Windows 同一脚本：`read` 15.09，物化 22.11，惰性 17.97（1.23 倍），token 化 7.02 → 2.88 ms——**Windows 的绝对差值不可用**：这台机器上每次新建进程要付约 37–40 ms（同一台机器上 `sum` 负载跑出 40 ms，Linux 同程序 0.88 ms），所以总量被启动开销主导，只有「减掉共同底噪的 token 化差值」与峰值内存可用。
  - **峰值内存**（单独一趟采样）：Linux 12.52 → 3.90 MB（−69%），Windows 19.55 → 10.98 MB（−44%）。
  - **跨语言**（Linux，`bench/run.py --release`，5 次交错）：新增 `textlazy` 负载两次运行给出 AE 3.67–3.98 ms、Go 3.62–3.63、Rust 3.45–3.71——**三者同档，排序在本机噪声内不可分辨**；峰值内存 AE 最低（3.85–3.90 vs 4.54–4.60 / 4.48–4.49 MB）。同一输入的物化版 `text` 为 AE 9.26–9.48 / Go 11.83–11.86 / Rust 3.66（Rust 那一栏本来就是惰性写法，不可比）。`sum` 上 AE 0.88 / Rust 0.87 / Go 1.54。Windows 的套件 JSON 原样归档但不作跨语言结论：这台机器上进程启动开销（约 37–40 ms）比被测程序的运行时间还长。
  - **生成 C**：`tokens.ae` 两平台同为 23,397 字节；未使用游标的程序只多 169 字节（`#define` + typedef 属常驻文本）。运行时不新增分配。
  - **编译速度**：运行时文本 +60 行、前端 +80 行，未单独计时；冷构建仍由 C 工具链主导（ADR-50 的测量）。
  - **安全语义**：未关闭任何检查；借用规则是现有机制的复用，游标没有任何所有权与释放路径（`owned: false`）。
- 证据链上同时修正的三处缺陷：
  1. `slice_view` 与 `tokenize` 的调用点位置曾被写成 `0, 0`，运行期错误因此报 `ae:0:0`。现在都带上调用点（`3:13`），测试断言了这一点。
  2. 游标第二遍迭代曾直接返回空（只重置了 `pos`，没重置 `done`）；由「同一绑定迭代两遍」的用例抓出，改为 `ae_tokens_reset`。
  3. 讲解用注释写在 `typedef` 之上会被留在**常驻文本**里（ADR-50 的规则只把注释归给函数），`print(1)` 因此多出 906 字节；把注释移到函数正上方后回落到 +169 字节。ADR-50 的教训有第二条：注释要贴着它解释的函数。
- **测量口径修正（重要）**：`bench/run.py` 与 `bench/tokens_timings.py` 原来在计时循环里采样峰值内存，而 Windows 上 `time.sleep(0.001)` 实际睡满 15.6 ms 的时钟中断，于是**每个数字都被拉长十几毫秒，且越快越被拉得越狠**。现在计时与峰值内存分成两趟（同一命令跑两次，计时那趟不碰采样器）。因此本轮归档的墙钟数字与更早的 Windows 归档**不可跨会话比较**；更早的 Windows 数字偏高。Linux 侧采样走 `/proc`，影响≤1 ms，但同样改用两趟口径。
- 边界（对外表述不得越过）：
  - 不是通用迭代器：只有「字符串 + 分隔符」这一种形态，没有 `len`、没有流式过滤/映射，也不能嵌套进容器。
  - 分隔符上限 16 字节；更长的分隔符报错而不是退化为分配。
  - 不宣称「`split` 变快了」——`split` 一行未改；变快的是**用另一种写法**的同一个程序。
  - 不把 2.59 倍当普遍加速比：它来自「不再物化 45 万个 token」，物化本身是使用者的选择；对 token 很少的输入，两种写法几乎无差别。
- 验证：Windows 35 单元 + 160 集成（新增 2 个集成测试：与 `split` 的逐 token 等价、借用/错误七类拒绝、分隔符 16 与 17 字节边界）、`--leak` 30 个用例 PASS（新增 `examples/tokens.ae`，基线 2 块）；37 个 `examples/*.ae` 通过 `check`；`tokens.ae` 的生成 C 通过严格 C11 语法检查。Linux 同数 + `--sanitize` 30 用例。日志与原始值见 `bench/results/2026-11-11-{windows,linux}-tokens/`。
- 过程发现（另立 ADR-54，不在本轮修）：Windows 上**任何含非 ASCII 字符的路径**（含相对路径）都无法读写——源码里的中文字面量可以，命令行传来的不行，因为 `argv` 是 ANSI 代码页而非 UTF-8。这是本轮写计时脚本时把绝对临时路径传进去才暴露的。README 里「Unicode 路径」的表述在本轮已改为如实描述。

## ADR-54：`args()` 在 Windows 上把命令行转成 UTF-8

- 背景：写 ADR-53 的计时脚本时，把临时目录的绝对路径（`C:/Users/trevv/AppData/Local/Temp/...` 之外还有 `D:/用户/...`）传给被测程序，程序报 `cannot read file`。进一步收窄：**Windows 上任何含非 ASCII 字符的路径**都打不开，相对路径也一样；而源码里的中文字面量完全正常。开发者自己的主目录就是 `D:/用户/...`，所以这不是边角情形——`ae prog.ae -- <路径>` 这种最基本的用法在中文目录下是坏的。
- 根因：Windows 的 CRT 按 **ANSI 代码页（CP_ACP）** 把命令行传给 `main`，于是「中文目录」以 GBK 字节进入程序（实测 `len(args()[1])` = 8）。语言里其它一切都是 UTF-8：运行时把路径当 UTF-8 再 `MultiByteToWideChar(CP_UTF8, …)` 交给 `_wfopen`，GBK 字节被解成错误字符，`_wfopen` 打开一个不存在的路径。
- 决策：在 `ae_args()` 里把每个实参 **CP_ACP → UTF-16 → UTF-8** 转换一次（`MultiByteToWideChar` + `WideCharToMultiByte`），失败（理论上只有内存不足）时回退到原始字节，保证参数仍可用。修复后同一个参数是 12 字节（UTF-8），路径读写都成功。
- 已排除的做法：
  - **用 `__wgetmainargs` 取 CRT 保存的原始 UTF-16 命令行**：这是最理想的方案（能拿到代码页之外也完整的命令行、且不依赖 `<windows.h>`），但在这套 MinGW-w64 + UCRT 工具链上**直接段错误**——UCRT 只在它自己的启动路径里维护那份数据。记下来，避免以后有人再照这条路重试。
  - **自己解析 `GetCommandLineW`**：Windows 的引号/转义规则很细，重实现一遍风险高于收益。
  - **手写 UTF-16 → UTF-8 编码器以避开 `<windows.h>`**：ACP → UTF-16 这一步仍然只能用 Win32，绕不开。
- 资源成本：
  - **运行**：每个实参多一次短命的临时缓冲（长度级几十字节，转换后立即释放），无新增常驻内存、无新增分配种类。
  - **编译速度**：调用 `args()` 的程序在 Windows 上会保留 `<windows.h>`（转换用到 Win32），实测只读参数的探测程序生成 C 从 15.5 KB 级涨到 16,317 字节、多付一次头文件解析（约 30 ms）；**不用 `args()` 的程序不受影响**：`print(1)` 仍 11,299 字节且仍带 `/* windows.h omitted */`，`float_math.ae` 同样去头（ADR-55 上线后 `print(1)` 为 15,243 字节，头文件裁剪行为不变）。这笔代价被接受，因为没有它程序打不开自己的实参。
  - **安全语义**：未关闭任何检查；转换只改字节表示，不改任何可见行为（ASCII 参数逐字节相同）。
- 边界（对外表述不得越过）：
  - 命令行进入 `main` 时**已经是** ANSI 字节，代码页表示不了的字符（例如某些 emoji）在 CRT 那一步就已丢失，本修复无法恢复。真 UTF-16 需要走 CRT 自己的启动路径，当前工具链上不可用。
  - 只改 `args()`。`env()` 早就走 `GetEnvironmentVariableW` 再转 UTF-8；源码字面量路径一直是 UTF-8；`run_command` 的子进程参数走 `CreateProcessW`，未受影响。
  - 不宣称「所有编码问题解决」：控制台输出编码、`AE_CC` 自身路径等仍是各自的话题。
- 验证：Windows 35 单元 + 161 集成（新增 `program_arguments_arrive_as_utf8_on_every_platform`：把含中文的绝对路径作为实参传入，`write_file` + `read_file` 走通；并断言 `len(arg)` 为 12 而不是 8）。**回滚修复后该测试确实失败**（`git stash` 验证）。`--leak` 30 个用例基线不变（Windows 2 块），37 个 examples 全部 `check` 通过。Linux 同数通过（POSIX 的 `argv` 本来就是 UTF-8，该用例在那里验证的是「新代码不破坏已有行为」）。日志见 `bench/results/2026-11-11-{windows,linux}-argv-utf8/`。

## ADR-55：`print` 在 Windows 控制台上按 UTF-16 写出

- 背景：写 ADR-54 的验证程序时把中文打印到 cmd 里，屏幕上是 `涓枃娴嬭瘯`。程序写出的字节一直是正确的 UTF-8（管道里 `od` 能看到 `e4 b8 ad ...`），错在**读者**：控制台按自己的输出代码页解码收到的字节，中文 Windows 上是 936（GBK），6 个 UTF-8 字节被解成 6 个无关字符。这不是 Windows 独有的话题——POSIX 终端按约定就是 UTF-8，所以缺陷只在一个平台、但影响这个平台的**每一条**中文输出。
- 关键观察：控制台的屏幕缓冲区存的是 UTF-16，`ReadConsoleOutputCharacterW` 读回来就是用户真正看到的内容。用它取证的对照是决定性的：同一段字节，窄写进控制台得到 `U+6D93 U+E15F U+6783 U+5A34 U+5B2D U+762F`，`WriteConsoleW` 写入同样的文本得到 `U+4E2D U+6587 U+6D4B U+8BD5`。所以修法不是「改编码」，而是**给控制台它要的形态**：控制台走 UTF-16，管道与文件继续收原始字节。
- 决策：
  1. `print` 的四种形态（整数、布尔、f64、字符串/视图/字面量）全部经过同一个汇点 `ae_emit(ptr, len, newline)`。汇点在运行期判断一次 stdout 是不是控制台（`GetStdHandle` + `GetConsoleMode` 成功才算）：是控制台就把 UTF-8 解成 UTF-16 交给 `WriteConsoleW`，否则原样 `fwrite` 字节。判断结果缓存在函数内的静态变量里，重定向的运行只付两次系统调用。
  2. **换行与值合并成一次写入**：`WriteConsoleW` 一次约 9.5 µs，两次就是两倍。2 万行实测：合并后 832.0 ms，拆成两次是 1120 ms，而改动前（`fwrite`+`fputc`，控制台行缓冲）是 860.3 ms——合并后不但没有回归，还略快。
  3. **分块转换，不分配**：1 KiB 输入块 → 1024 个 UTF-16 单元，栈上 2 KiB。块边界绝不落在字符中间（回退到最后一个前导字节），所以 1022 个 ASCII + 一个 3 字节字符（正好跨 1023 字节边界）在控制台上逐字符复原；3000 个汉字（多次分块）也逐字符复原。非法字节由 `MultiByteToWideChar` 变成 U+FFFD（控制台是显示设备，不是校验器）。
  4. **不引入 `<windows.h>`**：`print` 几乎每个程序都用，头文件约 520 ms 解析（ADR-39 的测量），让所有程序付这笔钱不可接受。四个入口（`GetStdHandle`、`GetConsoleMode`、`WriteConsoleW`、`MultiByteToWideChar`）在**用到它们的函数体内**手写声明，类型与头文件完全一致，所以和程序因 `args()` 而保留的头文件并存不冲突（生成 C 通过严格 C11 检查）。声明写在函数体内有一个副作用是**好事**：顶层文本属于「无函数名单元」，裁剪时永远保留，而函数内的声明随函数一起消失——不 print 的程序一个字节都不付。
  5. 审计测试同步扩展：`WIN32_DECLS` 加入这三个名字；每个用到 Win32 声明的函数必须带 `/* win32-header */`（保留头文件）或新的 `/* win32-declared */`（自己声明）；反向检查 runtime.c 里**每个** `extern` 声明都必须在审计名单里（扫描时去缩进，否则函数内声明会被漏掉），并要求自声明入口正好四个、带新标记的函数至少三个。
- 已排除的做法：
  - **启动时 `SetConsoleOutputCP(65001)`**：只有十几行、体积几乎为零，但它在改**共享的**控制台状态：程序被强杀（Ctrl-C、崩溃）时来不及恢复，父 shell 的提示符就变成乱码。Rust 用 `WriteConsoleW` 而不是改代码页，正是这个原因。
  - **把宽字符缓冲到退出再写**：控制台每次都最快，但程序打印「加载中…」后长时间运行时屏幕一片空白。缓冲区大小阈值解决不了这个语义问题，而语言目前**没有 stdin**，也就没有「打印提示再等待」的用例来兜底。
  - **每个值写两次（文本 + 换行）**：2 万行 1120 ms，实测的回归，被合并写入取代。
  - **让 `ae_fail` 也走汇点**：运行时的错误消息是固定 ASCII（带用户数据的失败会返回 `Err`，由程序自己 `print`），接进来只会让**不 print 的程序**多背 4.4 KB。检查过 `runtime_ex.c` 里没有动态消息的 `ae_fail` 调用。
  - **手写 UTF-8 → UTF-16 解码器**：约 45 行，比一个 `MultiByteToWideChar` 声明贵一倍，而且非法序列的处理要与系统一致才不会有偏差。
  - **顶层集中声明 Win32 入口**：顶层文本永远保留，不 print 的程序会白背约 1 KB（实测 514 字节的注释加声明差值）。声明放进函数体内后，不 print 的程序只多 525 字节（剩下的还是块注释，见下面第 2 条教训）。
- 资源成本（逐条回答 §21 的验收问题）：
  - **生成 C**：`print(1)` 11,341 → 15,243 字节（+3,902，+34%）；`print("hi")` 11,330 → 15,384；不打印的程序 11,286 → 11,811（+525）；`args` + `print` 15,178 → 20,742（两笔代价可以叠加，仍共用一份头文件）。字面量只出现一次（长度用 `strlen`，不用 `sizeof` 复制一份）。
  - **构建时间**：9 次交替，74.6 → 75.7 ms（+1.1 ms，噪声内；更早一次交替测到 +4 ms）。没有新增头文件解析，多出来的只是约 4 KB C 文本。
  - **控制台吞吐**：2 万行中文，9 次交替，860.3 → 832.0 ms（无回归；一行一次 `WriteConsoleW`）。
  - **重定向吞吐**（管道路径，只有 `fwrite` 没有转换）：2 万行 17.6 → 18.2 ms（+0.6 ms，每次 print 多一次函数调用与一次控制台判断，约 30 ns）。
  - **运行内存**：转换用 2 KiB 栈帧，不新增任何分配，`--leak` 30 个用例的退出块数仍是 Windows 2 块 / Linux 0 块。
  - **管道**：字节完全不变（既有 162 个集成测试与 30 个生成 C 用例的输出比对全部通过，含 `\r\n` 归一化前的原始字节）。
  - **安全语义**：未关闭任何检查；非法 UTF-8 在控制台上显示为 U+FFFD，在管道里原样通过（同一个程序，两条路都验证过）。
- 边界（对外表述不得越过）：
  - **控制台能显示什么由控制台决定**：非 BMP 字符（emoji）在这个 conhost 上变成 U+FFFD，而且**与代码页无关**——936 与 65001 两种设置下都一样，用一个直接调用 `WriteConsoleW` 的探针验证过，说明不是运行时的转换问题。不宣称「emoji 也能显示」，也不推断 Windows Terminal 下的表现。
  - 只处理 stdout。stderr 仍是 `fprintf`，因为运行时消息是 ASCII（见上面排除项）。控制台输出仍是**不缓冲**的：每行一次系统调用，把输出重定向到文件/管道时不额外增加调用。
  - 窗口标题、剪贴板、`run_command` 子进程的输出不在范围内；`run_command` 的子进程参数在 ADR-54 已走 `CreateProcessW`。
  - 不改控制台代码页，也不改控制台的其它全局状态：程序退出后父 shell 的环境与运行前一致。
- 两条过程教训（都已落到流程里）：
  1. **按「起止锚点」整块替换会吃掉区间里的其它函数**：这次替换掉了 `ae_exit`（它正好落在两个锚点之间），7 个集成测试以「implicit declaration of `ae_exit`」失败。以后整块替换前后都要 `grep -c` 关键符号，或先 `git diff --stat` 核对删除行数。
  2. **无函数名的注释会被当作裁剪根**：块注释里写了 `ae_emit` 这个函数名，符号扫描就把汇点连同整条 Win32 路径当成「根」保留，不 print 的程序也会多背 4.4 KB。ADR-50 的教训（注释贴着它解释的函数）在这里有第二个面：**注释里的函数名是有语义的**。
- 验证：Windows 35 单元 + 162 集成（新增 `print_keeps_every_shape_in_order_with_non_ascii_text`：四种形态加中文字面量的逐字节输出、`\n` 转义不截断）、30 个 `--leak` 用例 PASS（基线 2 块）、37 个 examples 通过 `check`、`print(1)` 与 `args`+`print` 两种程序的生成 C 通过严格 C11 语法检查；Linux 同数 + `--sanitize` 30 用例 0 报告。控制台取证用一个自建控制台（`SetConsoleOutputCP(936)`）、把 `CONOUT$` 句柄交给被测程序、再用 `ReadConsoleOutputCharacterW` 读回屏幕缓冲区的启动器；修复前后的回读、跨块边界、3000 字、非法字节四组结果见 `bench/results/2026-11-11-windows-console-utf8/console.txt`，吞吐与体积原始值同目录。

## ADR-56：map 的装载因子从 0.75 降到 0.5

- 背景：四个负载里 map 是唯一一直落后的一项——Linux 上 AE 67.96 ms、Go 66.73、Rust 53.32（峰值内存 2.39 / 7.09 / 2.91 MB）。前几轮把 text 从物化改成惰性拿到 2.6 倍，map 却从没做过归因，只有 ADR-46 加了 `map_inc`。
- 归因（先量再改，四个探针把一轮拆开）：`arith`（只有 LCG）AE 3.76 / Rust 3.57 ms；`key`（再加 1M 次 `"k" + to_string(...)`）32.55 / 30.82；`hit`（再加 1M 次命中查找）60.71 / 55.67；`put`（再加 1M 次覆盖写）58.27 / 53.76。结论有三条：
  1. **算术不是问题**（同级），**键构造占真负载一半**（1M 次短字符串分配 + 整数格式化，两语言同级，Rust 只快 6%）——键构造已经是单次分配（ADR-44/45 的融合），没有免费午餐。
  2. **差距在 map 操作**：每次命中查找 28.2 ns（Rust 25.1），覆盖写 24.8 ns（Rust 24.6）。Rust 用的是贵得多的 SipHash，所以慢的不是哈希函数，而是**探测次数**：0.75 装载因子下 10000 个键落在 16384 个槽里（有效装载率 0.61），线性探测平均要探 2.5 次；hashbrown 用 16 槽一组的 SIMD 组探测，一次就能排除整组。
  3. 顺带量到一个**独立缺陷**：`map_get` 未命中时返回 `Err(理由字符串)`，每次未命中分配一个字符串——空表上 1M 次未命中的探针比 `key` 基准多 6.9 ms（约 6.9 ns/次），而 Rust 的 `Option<i64>` 只多 0.5 ms。这不是本轮改的对象（`Err` 携带拥有型字符串是语言层决定），记为下一轮候选。
- 决策：
  1. 增长阈值 `(m->len + 1) * 4 >= cap * 3` 改为 `(m->len + 1) * 2 >= cap`：有效装载率 0.61 → 0.31，平均探测次数约 1.3。
  2. `ae_str_eq` 对长度 ≤ 8 的字符串走字节循环而不是 `memcmp` 调用：映射键都是 `k1234` 形状，`memcmp` 的固定开销比比较本身还大（纯查找探针 3.2%）。
- 已排除的做法：
  - **5/8 装载因子**：只给 1.03×（69.31 vs 67.92 ms），却一样要 2.58 MB。收益在 1/2 处是断崖（1.17×），说明起作用的是**有效装载率**而不是「因子越小越好」的连续曲线。
  - **槽内放哈希标签**（hashbrown 的 control byte 思路）：0.5 装载率下平均只有 1.3 次探测，标签能省的比较已经很有限，而每槽多 8 字节会把上面刚付的内存代价再放大。
  - **换更快的哈希**：Rust 用 SipHash-1-3（远比 FNV-1a 贵）却比我们快，说明瓶颈不在哈希；5 字节键上 FNV 只做 5 次乘加。
  - **把槽压到 24 字节**（状态位挪进独立的字节数组）：能把这轮多付的内存拿回约 0.2 MB，可能还更快（状态数组连续、缓存密度高），但要重写 put/find/remove/grow 四处，收益与风险不成比例，留给下一轮。
  - **把负载改成 `map_inc`**（单次查找）：能让 AE 的数字更好看，但那是在改考题——`bench/map.ae` 保持「查一次再写一次」的显式形状，与 Go 的 `m[k]=m[k]+1` 对齐；Rust 用 `entry` 是它的本命写法，ADR-46 的 `map_inc` 已经在 `examples/map_count.ae` 里展示。
- 资源成本（逐条回答 §21 的验收问题）：
  - **运行 CPU**（Linux，11 次交替，比值逐对计算）：map 负载 67.92 → 58.08 ms（**1.172×**，11 个比值全部 ≥1.12）；`hit` 探针 1.159×、`put` 探针 1.178×。
  - **峰值内存**（VmHWM，7 轮取最大）：2.44 → **3.43 MB**（+41%）。槽 32 字节、0.5 装载率意味着每个元素约 64 字节的槽开销：10000 个键的表从 512 KB 变成 1 MB。作为对照 Rust 3.11 MB、Go 7.55 MB——仍在 Rust 同一档，比 Go 低 2.2 倍。
  - **跨语言**（Linux release 套件，5 次交错）：map 负载 AE 57.72 ms / 3.14 MB，Go 58.29 / 7.48，Rust 55.37 / 2.98，Python 236.88 / 9.36。**从「落后 Rust 27%、与 Go 平手」变成「快过 Go、落后 Rust 4%」**；其余三个负载不受影响（sum 0.88、text 9.37、textlazy 3.64）。
  - **生成 C**：`ae_str_eq` +4 行；`print(1)` 不变（该函数不被文本程序保留），带字符串比较的程序多约 120 字节。
  - **分配**：没有新增分配；`--leak` 30 个用例的退出块数仍是 Windows 2 块 / Linux 0 块——槽表扩容时释放旧表这条路径被覆盖到了。
- 边界（对外表述不得越过）：
  - **收益是负载相关的**：探测密集的表收益明显，几个键的小表几乎无差别；内存代价则对所有表都成立（每槽 32 字节 + 0.5 装载率）。不把 1.17× 当普遍加速比。
  - `keys` 按字节序排序，与哈希和槽布局无关，所以**迭代顺序与可观察行为不变**；哈希函数一行未改。
  - 不宣称「map 比 Rust 快」：本轮之后仍然慢 4%，且内存多 10%。
  - `map_get` 未命中时分配理由字符串这件事**没有改**，只是量到了（6.9 ns/次）。
- 验证：Windows 35 单元 + 163 集成、30 个 `--leak` 用例 PASS（基线 2 块）、37 个 examples 通过 `check`；Linux 同数 + `--sanitize` 30 用例 0 报告 + 四负载套件。新增集成测试 `map_grows_reuses_removed_slots_and_keeps_every_survivor`：5000 个键多次增长、删掉一半、再插 5000 个另一族键，核对幸存值、缺失键与新键（覆盖增长与墓碑复用两条路径，这两条正是装载因子改动会动到的地方）。定量结论只用 Linux：Windows 本机每次新建进程约 37–40 ms，墙钟绝对值不可用。归档 `bench/results/2026-11-11-{windows,linux}-map-loadfactor/`（Linux 侧含四个归因探针的 AE/Rust 孪生程序、`pair.py` 与 `measure.py`）。

## ADR-57：map 的状态位搬出槽，槽从 32 字节压到 24 字节

- 背景：ADR-56 用「表翻倍」换来 map 负载 1.17× 的时间，代价写在 ADR 里——每元素约 64 字节的槽开销、负载峰值 2.44 → 3.43 MB，并把「24 字节槽 + 独立状态数组」列为下一步。这一步就是把它做掉。
- 关键观察：槽里真正需要一起读的东西只有键指针、键长、值，共 24 字节；`unsigned char state` 单独占第 25 字节，却因为结构体对齐把整个槽撑到 32 字节。而探测链最频繁的操作恰恰是「看这个位置是不是空的」，不是读键。
- 决策：`ae_map_slot` 只保留 `{ ae_string key; int64_t value; }`，状态改成平行的 `unsigned char *states`（每槽 1 字节，`memset` 成 EMPTY）。映射表结构变成 `{ slots, states, cap, len, used }`，`find/put/inc/remove/grow/release/forfeit` 与 `keys` 全部改走状态数组。
- 为什么可能更快（而不是变慢）：探测链读的是状态字节，32768 个槽的状态数组只有 32 KB，基本常驻 L1/L2；只有状态是 FULL 时才去碰 24 字节的槽。旧的布局每次探测都要把包含键指针和值的 32 字节槽拉进缓存。
- 已排除的做法：
  - **把状态压进 `key.len` 的高位**：能省下 1 字节/槽，但 `len` 是语言可见的（`len(s)`、切片边界都读它），埋一个标志位会让这些地方全部变脆。
  - **槽内放哈希标签**（上一轮已排除）：0.5 装载率下平均只有 1.3 次探测，标签省不下多少；这次改成先读状态字节，效果与标签同级但不多占空间。
- 资源成本（逐条回答 §21 的验收问题）：
  - **峰值内存**（VmHWM，7 轮取最大，同一次会话内交替）：**3.43 → 2.90 MB（−15%）**。表本体从 32768 × 32 = 1,048,576 字节降到 32768 × 25 = 819,200 字节（−22%）；峰值只降 15%，因为键字符串（1M 次分配）占了大头。作为对照 Rust 3.04 MB、Go 7.77 MB——**现在低于 Rust**。
  - **运行 CPU**（Linux，11 次交替配对）：map 负载 59.84 → 59.36 ms（1.012×），`hit` 1.007×，`put` 1.027×。也就是说内存是白拿的，时间没有退。
  - **四负载套件**（5 次交错）：map 59.88 ms / 2.86 MB，Go 69.71 / 7.49，Rust 56.99 / 2.91，Python 245.64 / 9.36。时间仍落后 Rust 约 5%，内存已经反超。
  - **生成 C**：`print(1)` 15,243 → 15,302 字节（+59：结构体多一个指针、注释多一行，均属常驻文本）；map 程序 20,472 字节。没有新增分配。
  - **编译速度**：只改运行时文本，未单独计时；`print(1)` 的 +59 字节对 gcc 无感。
- 边界（对外表述不得越过）：
  - 这是**内部布局**：`keys()` 仍按字节序排序，哈希不变，可观察行为一行未改；不宣称「map 更快」，只宣称「同样的速度、更少的内存」。
  - 内存数字是 VmHWM 峰值，包含键字符串与运行时其余部分，不是「表本体」。
  - 时间上的 1.012× / 1.027× 在噪声边缘（`put` 的比值多数 >1，`map` 负载的比值一半在 1 附近），所以表述为「持平」，不写「更快」。
- 过程提示：改这个结构时漏了 `runtime_ex.c` 里的 `ae_map_keys`（`map()` 的 `keys` 内建实现不在 runtime.c），两处集成测试立刻以「`ae_map_slot` has no member named `state`」失败——编译期抓到，比运行期抓到好。同时补了一个行为用例 `keys_after_removal_skips_tombstones_and_sees_reused_slots`：删除后 `keys()` 只报幸存键、重插的键只出现一次。
- 验证：Windows 35 单元 + 164 集成、30 个 `--leak` 用例 PASS（基线 2 块）、37 个 examples 通过 `check`；Linux 同数 + `--sanitize` 30 用例 0 报告 + 四负载套件。归档 `bench/results/2026-11-11-{windows,linux}-map-states/`。


## ADR-58：map 未命中的理由文本改为只读常量，未命中不再分配

- 背景：ADR-56 归因时量到「`map_get` 未命中返回 `Err(理由字符串)`，每次未命中分配一个字符串」（空表 1M 次未命中比 key 基准多 6.9 ms，约 6.9 ns/次），当时因为「`Err` 携带拥有型字符串是语言层决定」没有动它。ADR-57 之后 map 的时间仍落后 Rust 约 5%、内存已经反超，于是回头处理这条唯一还留在未命中路径上的分配。
- 关键观察：文本是固定常量 `"key not found"`，内容与长度永远不变，唯一阻碍是「拥有型字符串必须在释放时 free」。把它放进只读数据后，释放路径只要**按地址身份**跳过它，其余语义（内容、`len`、`==`、`+` 拼接、拷进 `vec[string]`、随枚举移动、`?` 传播）全部不变——释放是唯一需要认识它的地方。
- 决策：
  1. `runtime.c` 定义 `static const char ae_missing_key_text[] = "key not found";`；`ae_map_get` 未命中时直接用它构造 `ae_string`（仍是拥有型值，内容与长度不变）。
  2. `ae_str_release` 改成 `if (slot->ptr && slot->ptr != ae_missing_key_text) ae_free(slot->ptr);`。相等比较对不相关指针是定义良好的（C11 6.5.9p6），范围比较（`<`/`>`）才是未定义行为，所以用身份判断而不是地址区间。
  3. 释放函数上移到 `ae_string` 定义之后，去掉原来的前置声明；`ae_map_get` 保留 `line`/`column` 形参以维持内建函数签名一致，用 `(void)` 标注不再使用。
  4. 顺带修掉一个体积问题：`ae_string` 的注释里写了 `ae_str_cat` 这个名字，而顶层文本里的标识符会被裁剪器当成根（ADR-50 教训的第二面），于是**每个程序**都保留整条字符串拼接簇；改成「Concatenation」后 `print(1)` 少 1,480 字节。
- 已排除的做法：
  - **地址区间判断**（`ptr >= text && ptr < text + n`）：不同对象之间的指针关系比较是未定义行为，优化器可以合法地折叠它。
  - **全局可变 `ae_immortal` 指针**（`map_get` 写入、`release` 读取）：省不到 100 字节，却引入可变全局状态，将来多线程还要处理可见性；静态常量没有这个问题。
  - **首次未命中分配一份、之后复用**：同一指针会被多个 `Err` 同时拥有，第一个释放就让其余悬垂；加引用计数等于把成本搬回运行时，还会改变泄漏账本。
  - **把 `IntResult::Err` 负载改成视图或错误码**：这是语言语义变更（`map_get` 的公开形状），超出本轮；固定文本 + 身份跳过能拿到同样的收益而不动语言。
  - **常量放顶层 + 三行注释**（第一版实现）：注释落在「无函数名单元」里永远保留，`print(1)` 因此 +484 字节；现在的做法是数组紧贴释放函数、解释性注释放进函数体内，随函数一起裁剪。
- 资源成本（逐条回答 §21 的验收问题）：
  - **运行 CPU**（Linux，21 次交替，比值逐对计算）：未命中探针 43.06 → 24.26 ms，**1.764×**（同会话另两轮 1.775× / 1.789×，逐对比值区间 1.71–1.91）；命中探针 27.11 → 26.93（1.012×），同二进制对照组 1.006× / 1.002×，即命中路径不变。1M 次未命中的分配从 100 万次降到 0；`miss - hit` 的差值口径从 +15.9 ms 变成 −2.7 ms（未命中在空槽结束探测，比命中还便宜）。
  - **峰值内存**：1.36 ↔ 1.43 MB，两轮之间方向相反（另一次采样是 1.54 → 1.35），判为采样噪声，不宣称下降。
  - **可执行文件**：Linux +8 字节；Windows PE 的两个探针 −521 字节（来自注释根修复把拼接簇裁掉，不是这段文本本身）。
  - **生成 C**：miss 22,928 → 23,019、hit 22,926 → 23,017（各 +91）；`print(1)` 15,302 → 13,822（−1,480，注释根修复）。
  - **分配/泄漏**：`--leak` 31 个用例，Windows 2 块 / Linux 0 块基线不变；新用例 `map_missing.ae` 的 1000 次未命中不残留块。
  - **安全语义**：没有关闭任何检查；释放仍幂等，静态文本永远不会被 free。
- 边界（对外表述不得越过）：
  - 不宣称「map 变快」：命中路径 1.012×（对照 1.006×），收益只在**未命中且需要理由**的路径。
  - 不宣称超越 Rust：同一探针 Rust 8.58 ms vs AE 24.26 ms（约 4.9×）。Rust 返回的是 `Option`（无负载），AE 每次调用要构造 24 字节的 `Result` 枚举并走受检算术；这是 builtin 调用形状的问题，不是本轮能解决的，记为下一轮候选。
  - 只有 `map_get` 的固定文本这么做；文件、JSON、进程等错误文本带路径或系统消息，仍是动态分配。
  - 常量对象（14 字节数组 + 声明）在**所有**程序的常驻顶层文本里，约 50 字节；`print(1)` 从 15,302 降到 13,822 是净收益，但不能把它算到「未命中优化」头上。
- 过程发现：
  1. **字面量实参是每次调用都分配的拥有型临时值**：第一版探针把 `"absent"` 写在循环里，1M 次键分配约 18 ms，把待测差异压小了一半；把键提到循环外才看到 1.76×。以后任何「每次调用」的探针，先确认循环里没有别的分配。
  2. **注释里的函数名是裁剪根**（ADR-50、ADR-55 已记过两次）：这次是 `ae_string` 的注释提到 `ae_str_cat`，让 `print(1)` 一直背着约 1.5 KB 的拼接簇。修法不是删注释，而是别在顶层文本里写函数名。
  3. **同二进制对照组不能省**：第一次测到命中路径「慢 4%」，正是同二进制对照组（1.006× / 1.002×）才判定那是布局与噪声，不是新逻辑。
- 验证：Windows 35 单元 + 165 集成、`--leak` 31 用例 PASS（基线 2 块）、38 examples 通过 `check`；Linux 35 + 165、`--leak` 31（基线 0 块）、`--sanitize` 31 用例 0 报告、38 examples 通过；四负载套件同轮跑过（本机有干扰，只作参考）。新增集成测试 `missing_map_key_text_survives_every_owned_string_path` 覆盖读取、左右两侧拼接、移入函数、`vec[string]` 拷贝与 `?` 跨函数传播。归档 `bench/results/2026-11-11-{windows,linux}-map-missing/`。

## ADR-59：`build` 默认优化构建，`--debug` 退回快速构建，优化标志移到 `--` 分隔之前

- 背景：优化模式的入口一直是「行尾 `--release`」，默认 `-O0`。结果是最常用的两条命令都不合直觉：`build` 写的是用户要交付/分发的产物，却默认不优化；`run` 是开发循环，每次想跑快一点都要手加 flag。日常使用里「忘了加 `--release` 就把 `-O0` 的产物发了出去」比「忘了要快速构建」常见得多——错误方向的默认值比没有默认值更贵。
- 决策：
  1. **默认值按命令的角色定**：`build` 交付产物 → 默认 `-O2`；`run` 开发循环 → 默认 `-O0`。`--debug` 是 `build` 的快速出口，`--release` 是 `run` 的优化出口；两个 flag 对两条命令都接受（`build --release` 显式点名默认值，现有脚本不受影响）。
  2. **flag 解析移到 `--` 分隔之前**：原来先按「无 `--` 的固定长度」判形态、再判 flag，`run file --release -- args` 这种混排会被拒。现在先摘出 `--` 之后的程序参数，再从剩余参数的行尾识别 flag，两种顺序都可用；未知 flag 仍被拒绝（新增测试覆盖）。
  3. **两种模式仍是同一程序、同一份生成 C、同一套检查**：差别只在 C 编译的 `-O` 级别，缓存键本来就含优化模式，两档条目并存互不覆盖。
- 已排除的做法：
  - **`build` 也默认 `-O0`、靠文档提醒**：错误方向的默认值，正是本轮要修的问题。
  - **新增第三种模式名**（如 `--ship`）：现有 `--release`/`--debug` 已经覆盖，多一个名字多一份要解释的语义。
  - **让 `run` 也默认 `-O2`**：开发循环的每次改动都要付 C 编译的优化代价（实测 +41–191 ms），与「改一行立刻看结果」的用途冲突。
- 资源成本（`bench/build_levels_timings.py`，Windows 5 轮构建 + 9 轮运行交替，fresh cache，归档 `bench/results/2026-11-11-windows-buildlevels/`）：
  - **运行**：`-O2` 比 `-O0` 快 1.294×（textlazy）至 1.664×（map）；sum 1.634×、text 1.499×。
  - **构建**：端到端 fresh-cache 构建 +40.8 至 +191.3 ms（14–27 KB 生成 C，MinGW GCC 16.2.0）。
  - **体积**：本机 `-O2` 产物反而小 662–1,431 字节，方向如实记录，不作普遍结论。
  - **正确性**：两档 stdout 逐字节一致（脚本断言）；`--leak` 31 用例基线不变。
- 边界（对外表述不得越过）：
  - 加速比与构建代价是**同次交替、端到端含进程启动**的数字：Linux 是定量基准（1.34×–4.05×，+12.8–87.4 ms），Windows 供方向参考（1.29×–1.66×，+41–191 ms，进程启动开销使绝对值不可用）；两平台归档各自可重跑。
  - `-O2` 产物略小是本机 MinGW 的观察，不宣称「优化构建总是更小」。
  - flag 必须在行尾：`build file.ae --debug -o out`（flag 夹在中间）仍会被拒绝，这是原有严格顺序的保留而非新限制，但要如实告知。
  - 不宣称「-O2 与 -O0 语义完全等价对任意程序成立」：断言覆盖的是套件与基准负载；语言规则本来就是「开发与发布行为一致」（受检算术不因优化关闭），这条由既有测试矩阵保证，不由本 ADR 新证。
- 过程发现：上一轮会话的代码注释引用了「1.30x–4.70x、gcc +12–89 ms」，来源不可追溯；本轮同次实测为 1.29×–1.66×、端到端 +41–191 ms，注释已改为实测值。教训照旧：**注释里的数字必须指向可重跑的归档**，否则宁可只写方向。
- 验证：Windows 35 单元 + 167 集成全通过（新增 2 个），`--leak` 31 用例 PASS（基线 2 块），39 个程序通过 `check`（report.ae/words.ae 是库模块，被正确拒绝计入行为）。归档 `bench/results/2026-11-11-windows-buildlevels/`。Linux 回填（同一源码树 3916057，`bench/results/2026-11-11-linux-buildlevels/`）：170 集成全通过，运行加速 **1.34×（text）至 4.05×（sum）**、构建代价 +12.8–87.4 ms——sum 的 4.05× 说明 `-O0` 热循环里受检算术的检查很贵，这正是默认值的数据支撑。状态：**双平台验证**（2026-11-11）。

## ADR-60：数学内建 v1——11 个薄封装，IEEE 语义，Linux 链接行加 `-lm`

- 背景：`f64` 落地（ADR-37）时明确把「数学库」留作独立规范：数据分析领域（§14.1）的均值方差可以没有 `sqrt`，但统计、几何与任何真实数值工作流不能长期没有。本轮补上最小可用集，范围故意压窄：每个函数 1:1 映射到 C 库符号，不引入任何新类型、新容器或运算符。
- 决策：
  1. **函数集**：一元 `sqrt`、`abs`（映射 C 的 `fabs`，不是 `<stdlib.h>` 的整数 `abs`）、`floor`、`ceil`、`round`、`exp`、`log`（自然对数）、`sin`、`cos`；二元 `pow(底, 指数)`、`atan2(y, x)`（参数顺序同 C）。参数与返回值全部 `f64`；`min`/`max`/`hypot`/三角函数的其余部分等有真实用例再加，避免「一次把 libm 全抄一遍」。
  2. **语义是 IEEE/C 库语义，不是语言级检查**：定义域错误按 IEEE 返回（`sqrt(-1.0)`→`nan`、`log(0.0)`→`-inf`、`pow(0.0, 负数)`→`+inf`），程序继续运行。这与 `/`「除零报告失败」的不同是**有意的**：`/` 的检查契约属于语言本身（与整数除法同规则），而数学函数是把 IEEE double 的既定域错误表示原样暴露给数值代码——终止在 NaN 上会让「先探定义域再算」的常规数值写法不可能。这条不对称写进了语言文档而不是留给读者猜。
  3. **名字全部进入保留名单**：不能用作函数、结构体、枚举、变量、参数、循环变量或模式绑定；防止用户函数与 libm 符号在生成 C 里同名冲突，也让「这些名字的语义只有一种」成立。
  4. **不做隐式转换、元数固定**：`sqrt(4)` 是编译错误（`sqrt expects an f64 argument; convert integers explicitly with to_f64`）；多传少传分别报 `takes 2 argument(s)` / `expects 2 f64 argument(s)`。与 ADR-37 的禁隐式转换一致。
  5. **生成 C 直接调用 libm 符号**：`<math.h>` 本就在每个程序里（float 格式化器需要），不加运行时函数、不进裁剪根；Linux 链接行加 `-lm`（glibc 2.35 起是空壳脚本，旧 glibc 必需），Windows 不变。这是**链接命令变化**，把 Cargo.toml 提升到 0.1.1——缓存键含编译器版本，全部旧条目随之失效，不留下「旧链接行产物被复用」的可能。
  6. **`round` 是 C 的 `round`（0.5 远离零）**：`round(2.5)`→`3.0`、`round(-2.5)`→`-3.0`，不是银行家舍入。规范文档明确写出这一差异，因为两种舍入都有人默认。
- 已排除的做法：
  - **`Result` 包装（如 `sqrt -> FloatResult`）**：把域错误变成必须处理的值会让数值代码不可写；IEEE NaN 本身就是这门语言已经接受的域错误表示（比较语义、`to_string` 拼写都定义过了）。
  - **语言级 `**` 运算符 / 重载 `abs` 到整数**：新增运算符与重载都超出「薄封装」范围；整数绝对值等有真实用例时按类型各给名字。
  - **常量折叠**：`sqrt(4.0)` 在 `-O0` 下也调 libm——gcc 自身会在 `-O2` 折叠，编译器不做第二遍，保持前端最小。
  - **探测数学函数是否被使用再决定 `-lm`**：Linux 的 `-lm` 在合并 libm 后成本为零，按需开关只增加一个要测试的分支。
- 资源成本（归档 `bench/results/2026-11-11-windows-math/`）：
  - **生成 C**：`print(1)` 保持 13,822 字节——`MATH_FNS` 是编译器端常量表，不进生成 C，不用数学的程序零成本。
  - **运行时**：数学内建不分配内存——`--leak` 32 个用例（含 math_basics）全部等于基线（Windows 2 块）。
  - **验证**：35 单元 + 170 集成全通过；新增 3 个测试覆盖精确值、NaN 域错误、容差判定与全部拒绝路径；fmt 验收 42 个文件幂等；40 个程序通过 `check`。
- 边界（对外表述不得越过）：
  - **不宣称跨平台逐字节一致的超越函数文本**：`sin(1.0)` 等不同 libm 可差 1 ulp；规范提供的是「精确值与 `nan` 拼写一致、超越值用容差比较」（示例与测试都按这条写）。`pow(2,10)=1024.0` 的精确性是 libm 的实践性质，不是标准保证——Linux 回填时实测确认。
  - **不宣称数学库完整**：没有 `f32`、十进制小数、`min`/`max`、`vec[f64]`/`map[string, f64]`、`&f64` 借用、复数或矩阵；这是 v1 的 11 个函数。
  - `-lm` 只在 Linux 链接行出现；不能把它说成「所有平台」的变化。
  - IEEE 域错误行为依赖正确实现的 libm：CRT 或 glibc 的 bug 会直接成为 AE 程序的行为，这记为对外部实现的已知依赖。
- 过程发现：
  1. **fmt 验收的失败是陈旧二进制**：`unknown function 'abs'` 来自 `target/release` 的旧 `ae.exe`（构建于数学库之前），重建后 42 个文件全过。「跑验收前先确认 release 与源码同步」值得写进流程记忆。
  2. **版本测试硬编码**：`cache_and_version_commands_work` 断言 `ae 0.1.0`，版本提升立刻把它打破；已改为跟随 `CARGO_PKG_VERSION`，以后版本提升不再破坏测试。
  3. **emission 风格从既有代码取**：新发射分支最初写了行内 `/* line:column */` 注释，核对既有生成 C（零内联块注释）后删除——保持风格一致比多留信息更好。
- 验证：Windows 35 单元 + 170 集成、`--leak` 32 用例 PASS（基线 2 块）、fmt 验收 42 文件、40 程序 `check`；归档 `bench/results/2026-11-11-windows-math/`。Linux 回填（同一源码树 3916057，`bench/results/2026-11-11-linux-math/`）：35 单元 + 170 集成全通过、`--leak` 32 用例基线 0 块、`--sanitize` 32 用例 0 报告、fmt 验收 42 文件幂等、**math_basics 输出与 Windows 逐字节一致**（含 `pow(2,10)=1024.0` 精确值——「libm 实践性质」在本机得到实测确认）、生成 C 字节数与 Windows 相同。状态：**双平台验证**（2026-11-11）。

## ADR-61：`vec[f64]`——f64 元素的拥有型向量容器

- 背景：`f64` 落地（ADR-37）与数学内建（ADR-60）之后，数据分析领域（§14.1）剩下的最短短板是**容器装不下 `f64`**：统计均值方差要先把样本逐个 `to_f64` 再手工累加，真实数值工作流（特征向量、时间序列）没有数组就没法写。本轮补上容器层，范围与 ADR-60 同等克制：只做向量，`map[string, f64]` 不在本轮。
- 决策：
  1. **第三容器家族，照 `vec` 同构**：`Type::VecF`/`Type::VecFRef` 进入类型系统，运行时 `ae_f64vec_*`（new/push/pop/len/get/release/forfeit）与 `ae_vec_*` 同构——`double` 数据、8 字节/元素、**无状态位无借用标记**（元素是纯值，没有 string 那套 borrowed 视图）。`ae_f64vec_get` 复用 `ae_vec_index` 做受检边界，不复制检查逻辑。
  2. **字面量按元素推断**：`vec[1, 2]`→`vec`，`vec[1.0, 2.0]`→`vec[f64]`，混合直接报错（禁隐式转换在字面量内同样成立）；`vec[]` 空字面量仍是 `vec`（i64），空 `vec[f64]` 用新内建 `f64vec_new()`——对齐 `strvec_new` 的先例（有字面量的类型不需要 new，但累积循环需要空起点）。
  3. **`sort`/`reverse` 对 `vec[f64]` 显式拒绝**：NaN 没有全序，i64 的数值比较器和 string 的字节序都无法照搬到 f64 而不引入平台相关的顺序。拒绝比给一个「看起来能用」的平台相关排序诚实。
  4. **借用与移动照抄 `vec`**：`&vec[f64]` 只读借用、可作参数、可作 `&T` 泛型实参；for-in 按值迭代（`x` 是 `f64` 拷贝），循环期间容器被借用；结构体字段与枚举负载可用 `vec[f64]` 并随所属值恰好释放一次。
  5. **顺手补一个两家族共有的漏洞**：文档（§控制流）一直声称「循环体内移动或原地修改（push/pop/索引写）都在编译期拒绝」，但索引写实际没查借用表——`for x in v { v[0] = …; }` 在 i64 vec 上也放行。本轮统一补上借用检查，让实现追上文档。
- 已排除的做法：
  - **把 `vec` 泛型化**（`vec[T]` 全类型实例化）：当前三个容器各自手写是刻意保留的——泛型容器需要先有真正的泛型策略与代码膨胀预算（§阶段 B 第 3 条），不是本轮能顺带做的。
  - **`sort` 用「NaN 排最后」的约定**：任何约定都是平台相关的语义决定，先拒绝、留待有真实需求时按规范设计。
  - **f64 元素借用（`&f64`）**：只读借用白名单仍是 string/vec/vec[string]/vec[f64] 四种容器；标量借用没有用例支撑。
  - **`map[string, f64]`**：`map_get` 返回 `IntResult`，f64 版需要 `FloatResult` 或 `Option[f64]` 形状决定（`nan` 与「不存在」的区分），独立设计，不塞进本轮。
- 资源成本（归档 `bench/results/2026-11-12-windows-vecoff64/`）：
  - **生成 C**：`print(1)` 13,822 → 13,909（+87：`ae_f64vec` typedef 与 `ae_vec` typedef 同类常驻——结构体布局引用它；f64vec **函数**按可达闭包裁剪，不用的程序一个不保留。第一版把 240 字符注释放 typedef 旁进了常驻前缀，按 ADR-50 纪律移进函数体）。
  - **运行时**：槽 8 字节/元素；`--leak` 33 用例（新增 float_stats）全部等于 UCRT 基线 2 块——字段/负载释放路径恰好一次。
  - **验证**：35 单元 + 174 集成（新增 4 个：存取迭代、移动借用提前返回、11 类拒绝、字段与负载释放）；fmt 验收 43 文件幂等；41 程序 `check`；示例 `float_stats.ae`（统计 + `sqrt` 联动）输出全为精确可表示值。
- 边界（对外表述不得越过）：
  - 不宣称「泛型容器」：`vec[f64]` 是手写第三家族，泛型化是独立决策。
  - 不宣称 map 装得下 f64：`map[string, i64]` 仍是唯一 map 形状。
  - 一个旧测试因此**改变语义**：`vec[1.0]` 从拒绝项变为合法字面量（语言成长），该测试改为断言混合字面量仍被拒绝——语言变化必须连同测试语义一起记录，不是「顺手删个用例」。
  - 循环借用期间索引写从「放行」变「拒绝」是一次收紧（实现追上文档既有声称），理论上可能拒绝本来能跑的程序；现有语料无此写法，若将来撞上，迁移方式是把写操作挪出循环。
- 过程发现：
  1. **Option 解包装的是什么**：字面量推断最初写 `element_ty.unwrap_or(Type::Vec)`，而 `element_ty: Option<Type>` 装的是**元素类型**——`vec[3]` 因此推断成 i64，15 个既有测试当场失败。解包前先问「Option 里装的到底是谁」。
  2. **by_ref 标志的第二处漏改**：for-in 元素构造的 `first_ty == Type::VecRef` 没带 VecFRef，借用参数上迭代生成了值形态 C，gcc 以「v0 is a pointer」抓到。新增类型的每个布尔标志都要问「还有哪些类型共享这条路径」。
- 验证：Windows 35 单元 + 174 集成、`--leak` 33 用例 PASS（基线 2 块）、fmt 验收 43 文件、41 程序 `check`；归档 `bench/results/2026-11-12-windows-vecoff64/`。状态：**单平台验证**，Linux 回填（`2026-11-12-linux-vecoff64/`）前不得升级。
