# 对外宣称负面清单

> 迁自方案 v0.2 §20.4（2026-11-12）。任何对外表述（README、发布说明、报告）不得越过以下条目；条目随能力变化由对应 ADR 修订。总规则：宣称必须同时满足 **双平台验证 + 可重跑报告 + 公平对照**（方案 v0.3 §7.3）。

1. 不宣称「已完成内存安全语言」：当前是受限借用 + 编译期移动集合 + 运行时哨兵。
2. 不宣称达到 Go 的编译速度或 Rust 的性能/安全保证，也不宣称低 CPU、内存、磁盘占用已达标。
3. 不宣称超过 Gojo 或 Python：没有固定版本、等功能、同输入的可发布对比报告。
4. 不宣称生成的 C 在所有输入下无未定义行为：净化器与分配计数只覆盖已列用例。
5. 不宣称现有内容寻址缓存等于包级增量构建，也不宣称缓存命中结果可替代冷构建测量。
6. 不宣称兼容 Python 生态、支持 GPU/网络/线程，或「所有任务都能单语言完成」。
7. 不把单平台通过的新特性写成双平台验证；只有两平台各跑一次全套命令才升级状态。
8. 不宣称 `f64` 与 C 数学库逐位一致（尚未提供数学库），也不把规范文本形式说成「最短十进制」：它取的是能往返的最短有效位数，并在定点与科学计数法间取更短者。
9. 不宣称 W3 已完成包级增量，也不宣称「改一个函数体不重建无关包」：当前只做到运行时按需裁剪与接口摘要诊断，用户模块仍是同一翻译单元，摘要也不参与缓存失效判定。
10. 不把被实测否决的方案写成成果：PCH（69 MB 缓存换约 0.8 s）与分离翻译单元（冷构建回归约 68%、热仅快约 18%）已回退；也不把 Linux 的编译耗时当作 Windows 的编译速度，两者被 `<windows.h>` 拉开一个数量级。
11. 不宣称「已移除 `<windows.h>` 依赖」或「W6 手写最小 Win32 声明已实现」：ADR-39 只让不触及 Win32 层的程序不再引入该头，用到文件/目录/时钟/环境/工作目录/子进程的程序仍会解析它，也没有引入任何 ABI 假设。不把 Windows 侧的头文件收益说成跨平台收益（Linux 本来就不预处理该分支），也不把跨会话的墙钟绝对值当精确加速比。
12. trait/impl 静态分派已实现（ADR-47，双平台），但**不宣称完整的 trait 系统**：无方法调用语法、无 `&T` trait 参数、无泛型 impl、无默认方法、无动态分派、无关联类型/where 子句；trait 方法不能在泛型体外直接调用；也不把 ADR-40 的声明处预检查说成「约束证明了泛型体合法」（漏报允许、误报不允许）。不宣称「零编译时间回归」，不把 `constraint_audit_timings.py` 的上界差值当纯审计成本（含既有 O(N²) token 复制），也不把跨会话的墙钟绝对值相减。
13. 不把「很多泛型声明的文件变快」说成「编译器普遍快 N 倍」：ADR-41 消除的是按声明数呈 O(N²) 的前端复制，单函数程序的差异在测量噪声内。不把旧/新二进制对照的比值当普遍加速比，不拿跨归档的绝对值相减，不宣称峰值内存下降的具体数字（未采样），也不把「生成 C 逐字节相同」的对照环境差异（如 `git archive` 带出的 CRLF）忽略或当成语义变化。
14. 不把 `check --json` 说成语言服务器或完整编辑器协议（ADR-48）：没有增量、没有错误恢复（数组当前至多 1 个元素）、只有起始位置；`message` 是展示文本、不保证逐字稳定，编辑器应以 `file`/`line`/`column` 为契约。也不宣称「检查不需要构建」是普遍事实——它只对 `check`/`check --json` 成立（纯前端），`run`/`build` 仍需 C 工具链。
15. 不把 `split`/`lines` 的 arena 优化说成零拷贝或普遍加速（ADR-49）：元素仍复制字节并自带 NUL，只覆盖这两个内建，`push`/`args`/`keys` 的向量仍逐元素自有；不把 text 负载的 1.84/2.45 倍当通用加速比，也不宣称峰值内存下降（未采样）。使用融合路径的程序可执行文件会变大（`split_arena.ae` +2,341 字节），这笔代价不得隐去。
22. 不把 ADR-57 说成「map 变快了」：时间上的 1.012× / 1.027× 在噪声边缘，表述为「同样的速度、更少的内存」；收益是表本体 −22%、峰值 −15%（3.43 → 2.90 MB，已低于 Rust 的 3.04）；这是内部布局，`keys()` 顺序与哈希不变；内存数字是 VmHWM 峰值、包含键字符串，不是表本体。
21. 不把 ADR-56 的 1.17× 当普遍加速比：收益是负载相关的（探测密集的表明显、几个键的小表几乎无差别），而内存代价对所有表成立（每槽 32 字节 + 0.5 装载率，10000 键的表 512 KB → 1 MB，负载峰值 2.44 → 3.43 MB）；`keys` 按字节序排序，迭代顺序与可观察行为不变；哈希函数未改，也不宣称「map 比 Rust 快」（仍慢 4%、内存多 10%）；`map_get` 未命中时分配理由字符串（1M 次约 6.9 ms）只是量到了，没有修。
20. 不把 ADR-55 说成「所有字符都能显示」：控制台能否显示某字符由它自己决定，conhost 把 emoji 之类非 BMP 字符换成 `U+FFFD`，且与代码页无关（936 与 65001 一样；直接调用 `WriteConsoleW` 的探针同样如此，与运行时无关），而同一段文本写进文件仍是完整 UTF-8；只处理 stdout（运行时错误消息是 ASCII，仍是 `fprintf`）；不改控制台代码页，也不改控制台的其它全局状态；控制台输出不缓冲，每行一次系统调用；代价是生成 C `print(1)` +3,902 字节（+34%）、不打印的程序 +525 字节、构建时间噪声内 +1 ms、控制台吞吐无回归。
19. 不把 ADR-54 说成「编码问题已全部解决」：命令行在进入 `main` 前已被 CRT 转成 ANSI 代码页，代码页表示不了的字符（部分 emoji）已丢失、无法恢复；只修了 `args()`，控制台输出编码与 `AE_CC` 自身路径是各自的话题；代价是调用 `args()` 的程序在 Windows 上保留 `<windows.h>`（不用 `args()` 的程序仍去头）。
18. 不把 `tokenize` 说成通用迭代器或「`split` 变快了」（ADR-53）：它只有「字符串 + 分隔符」一种形态，没有 `len`（计数必须消费整条流），游标不能 `print`/进容器/作返回值，分隔符上限 16 字节；`split` 一行未改，变快的是用另一种写法写的同一个程序；2.59 倍来自「不再物化 45 万 token」，对 token 很少的输入两种写法几乎无差别；也不把 Windows 的 1.22 倍与 Linux 的 2.59 倍混为一谈，更不跨会话比较墙钟数字（本轮起计时与峰值内存分两趟，早期 Windows 数字偏高）。
17. 不把 `slice_view` 的字段视图说成字段级借用或通用借用检查器（ADR-52）：它借用的是**整个变量**，写同结构体的其它字段也会被拒绝；视图仍只读、不能作返回值/字段/枚举负载；嵌套字段、元素上的字段与非字符串字段仍未支持。
23. 不把 ADR-59 说成「编译更快」：改的是**交付产物的优化默认**，构建侧反而更贵（Linux +12.8–87.4 ms fresh-cache）；运行加速数字是负载相关的（Linux 1.34×–4.05×，Windows 含进程启动只报方向）；flag 夹在参数中间仍被拒绝；`-O2` 产物略小是 MinGW 本机观察。
25. 不把 ADR-61 说成「泛型容器」：`vec[f64]` 是手写第三家族（`vec`、`vec[string]`、`vec[f64]`），`map` 仍只装 `i64`；`sort`/`reverse` 对 vec[f64] 显式拒绝是设计决定（NaN 无全序），不是缺陷；「循环借用期间索引写」从放行变拒绝是一次收紧（实现追上文档既有声称），不是修复安全漏洞的夸大宣传；`vec[1.0]` 从拒绝变合法是语言成长，旧测试语义随之更新过。
24. 不把 ADR-60 说成「数学库已完成」：只有 11 个内建（无 `f32`、十进制、`min`/`max`、`vec[f64]`）；`sqrt(-1)`→`nan` 是 IEEE 语义与 `/` 的检查式除零**有意不对称**，不是遗漏；超越函数文本只保证「精确值与 `nan` 拼写两平台一致」，逐字节一致的打印文本只对精确值成立；`pow(2,10)=1024` 的精确性是 libm 实践性质（本机 glibc/UCRT 实测），不是标准保证。
16. 不把 ADR-50 的收益说成「编译器普遍提速 10%+」：它是每程序少编译约 14 KB 文本的**常量**收益，程序越大比例越小；端到端冷构建的 11.4% 大于单文件 gcc 差值，机制未完全归因，只报实测值；也不宣称可执行文件变小（不变）或峰值内存下降。
