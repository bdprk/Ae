# 探索性基准

`python bench/run.py` 测试开发模式，`python bench/run.py --release` 测试优化模式，加 `--cold` 时每个 AE 构建使用全新空缓存目录（测量真实编译）。脚本使用本机 Python、Rust、GCC 和 Go。脚本先编译 AE 编译器，再编译三个求和程序并确认输出一致，记录每次构建/运行的墙钟时间、可执行文件大小，以及（支持 getrusage 的平台上）直接子进程 CPU 时间。重复运行在每轮内跨语言交错。运行过程使用系统临时目录，结果以 JSON 输出。

这只是验证测量流程，并非语言性能排名：输入很小；开发模式下 AE 使用 GCC `-O0`，Rust 使用 `opt-level=0`；优化模式分别使用 `-O2` 和 `opt-level=2`，Go 始终使用默认构建；相同数字的优化等级不代表优化完全等价。AE 的 `build` 复用内容寻址缓存：不带 `--cold` 时重复构建测的是缓存命中路径；冷构建请使用 `--cold`。各构建的外部工具链缓存状态不受控；重复在每轮内跨语言交错但未随机化，未控制温度与电源策略；墙钟包含进程启动开销。Go 手动检查加法溢出，Rust 使用 checked_add，AE 启用内置检查；错误处理方式仍不同。CPU 时间仅在支持 `resource` 的平台上记录，且只覆盖直接子进程（如 gcc 驱动本身；cc1/as/ld 等孙代进程不计）；峰值内存、缓存体积、温度/电源策略仍未测量。Linux 与 Gojo 的数字不在本脚本范围内。

后续必须加入：峰值内存（程序与编译器分别口径）、更长且更多样的真实工作负载、重复次数/随机化策略细化、温度等环境记录；并保持可复现的冷/热缓存定义。记录完整环境与原始结果。运行输出可重定向到项目外部或自行选择的文件，避免把机器环境数据无意提交到仓库。

`python bench/phases.py` 将生成的 C 单独编译为目标文件，再单独链接，各运行五次并验证输出。该实验使用两次 GCC 调用，与正常一次调用的完整构建不完全等价；结果包含进程启动时间和不可控的缓存状态。
