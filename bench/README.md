# 探索性基准

`python bench/run.py` 测试开发模式，`python bench/run.py --release` 测试优化模式，加 `--cold` 时每个 AE 构建使用全新空缓存目录（测量真实编译）。`--workload sum|text|map|all` 选择工作负载（默认三个都跑）。脚本使用本机 Python、Rust、GCC 和 Go，先编译 AE 编译器，再按语言编译/运行并确认所有实现输出一致，记录每次构建与运行的墙钟时间、可执行文件大小、直接子进程 CPU 时间（支持 getrusage 的平台）与峰值内存。重复运行在每轮内跨语言交错。运行过程使用系统临时目录，结果以 JSON 输出。

三个工作负载：

- `sum`：一百万次带溢出检查的加法，覆盖 AE/Go/Rust，是最小的纯计算对照。
- `text`：读取生成的 2.6 MB、5 万行 ASCII 文本，按空格切分，输出字节数、令牌数与令牌内字节和；求和令牌长度保证每个字节都被读到，无法被「只打印文件大小」优化掉。额外加入 Python，因为文本处理正是设计方案 §14.2 要对比的场景——代价是它的运行时间含解释器启动，且没有构建阶段（`build_*` 字段为 null）。
- `map`：固定种子的 LCG 产生一百万次抽取，写入 10000 个字符串键的 `map[string, i64]` 直方图，再用计数加权校验和读完全部桶，`len` 报告触达了多少键。校验和无法从抽取数或键数推出来，因此每次抽取与每次查找都不可省略。额外加入 Python，因为 dict 计数正是容器与分配负载的对照场景；AE 实现的 `Err` 分支不打印任何内容，缺键按 0 贡献处理，与 Go/Python/Rust 三份孪生程序一致。

峰值内存取自操作系统的高水位计数（Windows `GetProcessMemoryInfo` 的 `PeakWorkingSetSize`，Linux `/proc/<pid>/status` 的 `VmHWM`），每毫秒采样一次：只要退出前有一次采样成功，得到的就是真实峰值；运行时间短于采样间隔的进程可能报 null。构建时只采样直接子进程，所以 gcc 派生出的 cc1/as/ld 与 rustc 的 codegen 子进程**不计入**，这一项的语义是「编译器驱动本身的峰值」，不是整个构建树的峰值。

这只是验证测量流程，并非语言性能排名：输入很小；开发模式下 AE 使用 GCC `-O0`，Rust 使用 `opt-level=0`；优化模式分别使用 `-O2` 和 `opt-level=2`，Go 始终使用默认构建；相同数字的优化等级不代表优化完全等价。AE 的 `build` 复用内容寻址缓存：不带 `--cold` 时重复构建测的是缓存命中路径；冷构建请使用 `--cold`。各构建的外部工具链缓存状态不受控；重复在每轮内跨语言交错但未随机化，未控制温度与电源策略；墙钟包含进程启动开销。Go 手动检查加法溢出，Rust 使用 checked_add，AE 启用内置检查；错误处理方式仍不同。CPU 时间仅在支持 `resource` 的平台上记录，且只覆盖直接子进程（如 gcc 驱动本身；cc1/as/ld 等孙代进程不计）。缓存体积、温度/电源策略仍未测量。Linux 与 Gojo 的数字不在本脚本范围内。

最新一轮结果索引在 `bench/results/<日期>-<机器>/PLATFORM.txt`（含环境、原始 JSON 与观察）。当前可量化的事实：热缓存下的 AE 构建时间由缓存命中决定，不能当作编译速度证据；text 负载下 AE 的运行峰值明显高于 Rust，原因是 `split` 为每个令牌单独分配字符串；map 负载的运行时间主因是字符串构造而非 map 操作（热点分解见 `2026-11-11-windows-map-hotspots/`），针对它的三项优化已双平台验证——字面量拼接融合（ADR-44）、to_string 栈缓冲（ADR-45）、`map_inc` 计数内建（ADR-46），同次对照累计 map 变体 -23.4%、计数形状约 -32%（`2026-11-11-{windows,linux}-litcat/`、`-intbuf/`、`-map-inc/`）。

后续必须加入：更长且更多样的真实工作负载（`map` 计数已加入，仍缺文件整理流程）、重复次数/随机化策略细化、温度等环境记录；构建峰值需要覆盖整棵进程树（job object / cgroup）；并保持可复现的冷/热缓存定义。记录完整环境与原始结果。运行输出可重定向到项目外部或自行选择的文件，避免把机器环境数据无意提交到仓库。

`python bench/phases.py` 将生成的 C 单独编译为目标文件，再单独链接，各运行五次并验证输出。该实验使用两次 GCC 调用，与正常一次调用的完整构建不完全等价；结果包含进程启动时间和不可控的缓存状态。
