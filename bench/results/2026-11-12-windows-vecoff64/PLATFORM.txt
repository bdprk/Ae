ADR-61 vec[f64]（f64 元素向量容器）· Windows 归档（2026-11-12）

## 平台
Windows x86-64，8 核 / 16 线程，MinGW-W64 GCC 16.2.0（UCRT）。ae 0.1.1。

## 命令（工作目录 = 仓库根）
- cargo test --locked
- python scripts/verify_generated_c.py --leak（用例表新增 float_stats.ae）
- python scripts/fmt_acceptance.py --json fmt-acceptance.json
- for f in $(find examples -name "*.ae" ! -name "report.ae" ! -name "words.ae"); do ae check "$f"; done
- cargo run -- run examples/float_stats.ae

## 交付内容
- 类型 `vec[f64]`（拥有型，元素是纯值：无所有权、无借用元素、无逐元素释放）
  与只读借用 `&vec[f64]`；`Type::VecF`/`Type::VecFRef` 进入审计类型集与
  `&T` 泛型借用可实例化集合。
- 字面量 `vec[...]` 按元素类型推断：全 i64 → `vec`，全 f64 → `vec[f64]`，
  混合报「does not convert implicitly」；`vec[]` 空字面量仍是 `vec`（i64），
  空的 f64 向量用新内建 `f64vec_new()`（对齐 `strvec_new` 先例）。
- 操作：受检下标读写、`len`、`push`/`pop`（语句内建，函数式写法）、
  for-in 按值迭代、移动与释放（提前返回、`?`、结构体字段、枚举负载）、
  `&vec[f64]` 只读借用与转发（借用变量发射时解引用为值）。
- **不做**：`sort`/`reverse` 对 vec[f64] 显式拒绝（NaN 无全序，报错信息写明）；
  `map[string, f64]`（独立设计：FloatResult 形状问题另立 ADR）；字段上的
  元素索引（与既有 vec 字段限制一致）。
- 运行时家族 `ae_f64vec_*`（new/push/pop/len/get/release/forfeit）与
  `ae_vec_*` 同构；get 复用 `ae_vec_index` 做受检边界检查。

## 说明
- 过程发现（两处真实 bug，测试抓到）：
  1. 字面量推断最初写 `element_ty.unwrap_or(Type::Vec)`——`element_ty` 是
     Option<Type>，unwrap_or 返回的是**元素类型**（Int），不是向量类型；
     `let v = vec[3]` 因此推断成 i64，15 个既有测试当场失败。教训：Option
     解包的语义要盯着装的是什么。
  2. for-in 元素构造的 by_ref 标志只写了 `first_ty == Type::VecRef`，漏了
     VecFRef——借用参数上迭代的元素访问生成了值形态的 C（`v0.data`），gcc
     以「v0 is a pointer」抓到。既有 i64 vec 的写法提醒了正确形状。
- Linux 回填待做：同一提交树在 instabox-node 跑全套（`--sanitize` + `--leak`
  + fmt 验收 + float_stats 输出对照），归档 `2026-11-12-linux-vecoff64/`，
  状态才升级为双平台验证。
