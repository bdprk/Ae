Measured build effect (this machine, wall clock, gcc -std=c11 -O0)
  c_compile_ms (header omitted):        31.396
  header_baseline_c_compile_ms:         31.998
  Difference: 0.6 ms, inside measurement noise.

  Four build scenarios (ms): cold 36.248 | unchanged 4.617 |
    implementation_edit 36.522 | interface_edit 36.129
  generated C (print(1)): 20,352 bytes, byte-identical size to Windows
  -O0 executable: 17,168 bytes

  This is the expected platform asymmetry and is itself evidence: Linux never
  preprocesses the #ifdef _WIN32 branch, so removing its include cannot change
  the compile cost. The ~545-980 ms saving is Windows-only. It is not a
  generated-C size effect and must not be reported as a Linux improvement.

Boundaries (do not overstate)
  - The generated C text is identical on both platforms; the header decision
    depends on which runtime capabilities the program reaches, not on the
    host OS.
  - No Win32 declarations were hand-written; W6 is NOT implemented and no
    ABI assumption was introduced.
  - No new cache kind, no resident process, no safety check was disabled.
  - A missing marker would fail at C compile time (explicit), never silently
    change runtime behaviour; an extra marker only costs one header parse.
