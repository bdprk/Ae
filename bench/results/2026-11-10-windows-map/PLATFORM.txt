## 负载定义
固定种子 LCG（x = x*48271 mod 2147483647，种子 1234567）抽 1,000,000 次，
写入 10000 个 "k<n>" 字符串键的 map[string,i64] 直方图；再以计数 * (i+1)
加权校验和读完全部 10000 桶。校验和无法从抽取数/键数推出，每次抽取与查找
不可省略。四份孪生程序（map.ae / map.go / map.py / map.rs）语义逐点对应，
缺键处理一致（首见计 1 / 校验和贡献 0）。

## 观察（只报方向与量级，不作排名）
1. 运行时间：release 模式 AE 258 ms 慢于 Go / Rust 的 185 ms（约 1.4×）；
   dev 模式 AE 354 ms 与 Rust dev 346 ms 相当、慢于 Go 198 ms。方向：
   AE 的 map 路径（哈希 + 每键字符串拷贝）尚有优化空间，未定位热点。
2. 运行峰值内存：AE 4.7 MB ≈ Rust 4.8 MB < Python 10.7 MB < Go 11.4 MB。
   这是 map 路径内存表现良好的第一个数据点——与 text 负载（AE 峰值
   明显高于 Rust，split 每令牌分配）结论不同；两条负载各说各的，不互相推翻。
3. 热缓存构建 61–65 ms：这是内容寻址缓存命中路径的时间，按 §20.4 第 5 条
   不得当作编译速度证据；本轮未跑 --cold。
4. 产物体积：Go 2.46 MB 远大于 Rust 137 KB / AE 72 KB（release）。

## 已知差异 / 归一化规则
- CPU 时间在 Windows 上为 null（无 getrusage；Linux 归档才会有）。
- 构建峰值只含编译器驱动直接子进程，gcc 的 cc1/as/ld 与 rustc codegen
  孙代进程不计入；该字段语义是「驱动峰值」而非整棵构建树峰值。
- 输出比较先做 CRLF→LF 归一化（AE 在 Windows 上以文本模式写 stdout）。
- AE 构建复用内容寻址缓存（本轮未加 --cold）；外部工具链缓存不受控；
  温度、电源、频率未记录。
